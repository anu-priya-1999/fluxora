# 19. Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Static analysis produces incorrect/incomplete dependency edges (dynamic imports, reflection-like patterns, unusual frameworks) | High | High | Confidence scoring + provenance tagging (P3); explicit coverage reporting; golden-fixture regression suite grown continuously from real-world edge cases; graceful partial-analysis rather than silent gaps |
| LLM hallucinates a claim not supported by evidence | Medium | Critical (trust-destroying for this product category) | Structural mitigation via context scoping + evidence-id manifest; schema + grounding validation with retry/reject; deterministic fallback explanation; continuous AI eval suite tracking hallucination rate as a release-gating metric (`09-ai-architecture.md`, `12-testing-strategy.md §12.5`) |
| Prompt injection via repository content (comments, README, commit messages) manipulates AI output | Medium | High | Structural: model never determines facts from raw file content; delimited/labeled untrusted-content handling for the limited cases where excerpts are shown; grounding validation as a second line of defense; adversarial fixture testing (`11-security-architecture.md §11.9`) |
| Graph traversal performance degrades on very large or highly-connected repositories | Medium | Medium | Depth caps, indexing strategy validated against a deliberately large synthetic fixture, defined triggers for moving to a dedicated graph engine (`06-database-schema.md §6.1`) |
| LLM API cost scales faster than revenue/usage justifies (cost-model risk, real for any AI product) | Medium | High | Response caching, task-appropriate model routing, context minimization, per-org rate limiting, continuous cost tracking alongside quality metrics (`16-cost-model.md`) |
| Cross-tenant data leakage | Low (with defense-in-depth) | Critical | RLS at the database layer + application-layer authz as a second independent check; tenant-scoped object storage and cache keys; specifically tested via cross-tenant-read-attempt integration tests (`11-security-architecture.md §11.4`, `12-testing-strategy.md §12.2`) |
| GitHub API rate limiting or outage blocks ingestion at scale | Medium | Medium | Exponential backoff, job-level retry with idempotency, GitHub App installation-token model (higher rate limits than personal OAuth), status visibility to the user rather than silent stalling |
| Worker crash mid-analysis causes duplicate or corrupted graph writes | Low (mitigated by design) | High | Transactional `AnalysisRun` writes (all-or-nothing commit), idempotency keys on every job, visibility-timeout-based reclaim of crashed jobs (`05-component-responsibilities.md §5.7, §5.16`) |
| Simulation rule table oversimplifies real-world failure dynamics, producing misleading confidence | Medium | Medium | Rules explicitly surface assumptions (not hidden), confidence is first-class output, runtime telemetry (Phase 10) is planned specifically to ground/correct static assumptions over time |
| Malicious or pathological repository content (zip bombs, deeply nested ASTs) crashes or hangs a worker | Low (mitigated by design) | Medium | Hard size/time limits on extraction and parsing, sandboxed execution with no code execution at all, resource-limited containers (`11-security-architecture.md §11.10`) |
| Single-Postgres-instance becomes a bottleneck before sharding work is prioritized | Medium (at scale) | Medium | Read replica as an intermediate step before full sharding; scaling triggers documented in advance (`15-scaling-strategy.md`) so this isn't discovered reactively |
| Evidence-writing discipline erodes over time as new features are added by different contributors | Medium | High (undermines the core trust proposition silently) | CI-enforced lint check requiring every graph/impact/simulation write path to have a corresponding evidence write (`12-testing-strategy.md §12.1`) — makes the principle structurally enforced, not just documented |
| Solo-developer/portfolio-project scope creep prevents ever reaching a demoable MVP | High (the most realistic risk for this specific context) | High | Explicit, written MVP boundary (`02-product-scope.md`) with a hard phase cutoff (Phase 9) before "nice to have" phases (10–12); the roadmap is intentionally sequenced so Phase 9 alone is already a complete, demoable story |
