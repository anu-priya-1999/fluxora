# 1. The entire Fluxora backend in one picture


Your current architecture is:

```text

                         FLUXORA

                            │

             ┌──────────────┼──────────────┐

             ↓              ↓              ↓

            WEB            API          WORKERS

             │              │              │

             │              ├──────────────┤

             │              ↓

             │              ↑
```

```text

   └── @fluxora/shared-types

   └── @fluxora/shared-types

```

The arrows mean **"depends on / uses."**

# 2. First understand the difference between `apps` and `packages`


This is the foundation.

## `apps/`


These are **actual applications/services that run**.

You have:

```text

apps/

├── api

├── web

└── workers

```

### `web`


The thing the user sees in the browser.

### `api`


The backend that receives requests and performs application operations.

### `workers`


Background processing for expensive/long-running jobs.

---

## `packages/`


These are **reusable internal building blocks**.

You have:

```text

packages/

├── shared-types

└── db

```

They aren't the main user-facing applications.

Think:

```text

apps = things that run

packages = things other parts of Fluxora use

```

---

# 3. `shared-types` — the simplest explanation


`shared-types` answers:

> **"What does our data look like?"**

It does **not** answer:

> "Where is the data stored?"

That's the job of `db`.

From your Step 2 implementation, `shared-types` now contains concepts such as:

```text

Organization

User

UserRole

PlanTier

```

and the create-input types for them.

So imagine:

```ts

type User = {

  id: string

  organizationId: string

  role: UserRole

}

```

This means:

> "A User has these fields and these types."

It does **not** mean:

> "Save this User in PostgreSQL."

---

# 4. Why `shared-types` exists


Because many parts of Fluxora need to agree on the same data shape.

For example:

```text

             User

              │

        shared-types

          /        \\

         /          \\

       API          Web

```

The API knows:

> "This is what a User looks like."

The Web knows:

> "This is what a User looks like."

So both use the same contract.

Without that, you could end up with:

```text

API thinks:

User = { id, name, role }

Web thinks:

User = { userId, displayName, permissions }

```

Now they disagree.

`shared-types` gives them a shared language.

---

# 5. What does "type" mean in TypeScript?


A type is basically a **description of allowed data**.

For example:

```ts

type UserRole = "owner" | "admin" | "member" | "viewer"

```

This says a user role can only be one of those values.

Another:

```ts

type PlanTier = "free" | "pro" | "enterprise"

```

This prevents random values from flowing through the system.

So:

```text

shared-types

      ↓

strong contracts between parts of Fluxora

```

# 6. Why `db` is separate


Now the other half:

> **`db` answers how Fluxora talks to PostgreSQL.**

Suppose we have a User.

`shared-types` says:

```text

"What is a User?"

```

`db` says:

```text

"How do I save/find/update that User?"

```

So:

```text

              USER

               │

       ┌───────┴────────┐

       ↓                ↓

 shared-types           db

       ↓                ↓

 data shape          persistence

```

This distinction is extremely important.

---

# 7. What is persistence?


Persistence means:

> **Data that survives after your program stops running.**

For example:

```text

JavaScript variable

      ↓

exists in RAM

      ↓

program closes

      ↓

gone

```

But:

```text

User

 ↓

PostgreSQL

 ↓

stored on disk

 ↓

program restarts

 ↓

User still exists

```

That's persistence.

The `db` package manages that persistence boundary.

---

# 8. What is PostgreSQL?


PostgreSQL is your **database server**.

Think:

```text

Fluxora application

       ↓

      DB

       ↓

PostgreSQL

       ↓

tables / rows / data

```

PostgreSQL actually stores your:

* organizations

* users

* later repositories

* snapshots

* analysis runs

* graph nodes

* evidence

* impact analyses

* etc.

`db` is the bridge between your TypeScript application and PostgreSQL.

# 10. Why does `workers` use both?


Same basic reason.

Workers will eventually do things such as:

```text

create AnalysisRun

create symbols

create graph

write evidence

```

They need:

### `shared-types`


To understand the shapes of those objects.

### `db`


To store the resulting information.

So:

```text

 ├── shared-types

 └── db

       ↓

   PostgreSQL

```

# 11. Why does `web` NOT use `db`?


This is deliberate.

You don't want:

```text

Browser → PostgreSQL

```

because your database should not be exposed directly to the browser.

Instead:

```text

Browser

   ↓

Web

   ↓

API

   ↓

DB

   ↓

PostgreSQL

```

The API is the security/business-logic boundary.

This is a fundamental web architecture concept.


So the project has centralized TypeScript rules but can specialize them per package.

# 16. `db/src/pool.ts`


This handles the **database connection pool**.

This is an important backend concept.

Suppose 20 requests arrive.

You don't want:

```text

Request 1 → create connection → query → destroy

Request 2 → create connection → query → destroy

Request 3 → create connection → query → destroy

...

```

Instead:

```text

                 PostgreSQL

                /    |    \\

               /     |     \\

            connection pool

             /   /   |   \\

           API requests

```

The pool manages reusable DB connections.

That's why `pool.ts` exists.

---

# 17. `db/src/tenant.ts`

This is one of the most important security files.

Fluxora is **multi-tenant**.

That means:

```text

Organization A

  ├── users

  └── repositories

Organization B

  ├── users

  └── repositories

```

Organization A must never see Organization B's data.

`tenant.ts` helps establish:

> **Which organization is this database operation happening for?**

Conceptually:

```text

Request

  ↓

Organization = A

  ↓

tenant context

  ↓

PostgreSQL

  ↓

RLS

  ↓

only A's rows

```

---

# 18. What is a tenant?

A tenant is basically:

> **one customer/organization using the shared application.**

Example:

```text

Fluxora

├── Acme

├── Globex

└── Umbrella

```

Each company is a tenant.

That's why the system is called **multi-tenant**.

---

# 19. What is RLS?

RLS = **Row Level Security**.

This is a PostgreSQL security mechanism.

Suppose the database has:

```text

users

--------------------------------

id | organization_id | name

--------------------------------

1  | A               | Alice

2  | A               | Bob

3  | B               | Carol

```

If you're operating as Organization A, RLS can ensure:

```text

Alice ✅

Bob   ✅

Carol ❌

```

even though Carol exists in the same table.

So there are two layers of protection:

```text

Application

   ↓

tenant-aware query

   ↓

PostgreSQL

   ↓

RLS

   ↓

final security boundary

```

This is much stronger than simply trusting application code.

# 21. Why not just manually create tables?

Because production software needs repeatability.

Imagine your laptop has:

```text

Database v5

```

and production has:

```text

Database v3

```

How do we know how to upgrade?

Migrations.

```text

v3

 ↓ migration 004

v4

 ↓ migration 005

v5

```

That is why migrations exist.

# 26. `db/src/mappers.ts`

A mapper converts one representation into another.


# 31. The most important distinction

Please memorize this table:

| Part             | Main job                                        |

| ---------------- | ----------------------------------------------- |

| **Web**          | UI users interact with                          |

| **API**          | Receives requests and applies application logic |

| **Workers**      | Performs background/long-running work           |

| **shared-types** | Defines shared data contracts                   |

| **db**           | Handles persistence/database access             |

| **PostgreSQL**   | Actually stores the data                        |

This is the architecture in plain English.

# 32. One complete example

Let's imagine Alice joins Acme.

## Step 1 — Type

`shared-types` says:

```text

User

has:

id

organizationId

role

...

```

It tells us what a User **looks like**.

## Step 2 — Request

Browser sends:

```text

POST /users

```

to the API.

## Step 3 — API

API handles the request.

It uses:

```text

@fluxora/shared-types

```

for the data contract.

And:

```text

@fluxora/db

```

to persist the User.

## Step 4 — Repository

The User repository performs the persistence operation.

## Step 5 — Tenant

The database operation runs in the context of:

```text

Acme

```

## Step 6 — PostgreSQL

PostgreSQL stores the user.

## Step 7 — RLS

PostgreSQL ensures another organization's context cannot access Acme's rows.

So the full flow is:

```text

Alice

 ↓

Browser

 ↓

Web

 ↓

API

 ├── shared-types

 │      ↓

 │   User contract

 │

 └── db

       ↓

   User repository

       ↓

   tenant context

       ↓

   PostgreSQL

       ↓

      RLS

```

**That is what we have built in Steps 1–2.**

When you're confused, come back to this:

**`shared-types`**

> "How do we store and retrieve our data?"

> "Where is our persistent data actually stored?"

> "How does the outside world ask Fluxora to do something?"

**`web`**

> "What does the user see and interact with?"

**`workers`**

> "What work happens in the background?"

> "How does PostgreSQL prevent one organization from seeing another organization's rows?"

> "How do we safely evolve the database schema over time?"

**`repositories`**

> "Where do we organize database operations for a particular domain object?"

**`mappers`**

> "How do we translate between database representation and application representation?"
