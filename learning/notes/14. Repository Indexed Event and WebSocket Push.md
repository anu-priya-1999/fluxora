# Fluxora Step 15 — Learning Notes: Repository Indexed Event and WebSocket Push

## 1. What Step 15 Builds

Step 15 connects the asynchronous ingestion pipeline (Step 12-14) with real-time UI notification:

```text
Worker Ingestion Finished
       ↓
Update Connection Status → "active"
       ↓
Emit repository.indexed Event (PostgreSQL Events Outbox)
       ↓
PostgreSQL Trigger (pg_notify('fluxora_events', ...))
       ↓
API PostgreSQL Listener (LISTEN fluxora_events)
       ↓
API WebSocket Hub (organization-partitioned routing)
       ↓
Authenticated WebSocket Connection (/api/v1/ws)
       ↓
Frontend Dashboard Real-time Activity Feed
```

---

## 2. Core Architectural Decisions

### A. The Transactional Outbox Pattern
Instead of broadcasting directly from the worker to WebSockets via an external message broker, we write events to the PostgreSQL `events` table:
- **Durability**: The event is permanently recorded in PostgreSQL.
- **Tenant Isolation**: RLS is enabled on `events`, scoping all rows to `organization_id`.
- **Idempotency**: A database-level unique constraint `(organization_id, idempotency_key)` guarantees that retried worker runs do not emit duplicate events.

### B. PostgreSQL LISTEN/NOTIFY Delivery
- In early stages of an architecture, adding Redis Pub/Sub, Kafka, or RabbitMQ introduces operational complexity and cost.
- PostgreSQL's native `LISTEN`/`NOTIFY` allows pub-sub messaging directly on the existing database instance with near-zero latency.
- Trigger `events_notify_trigger` executes on `INSERT` to publish the serialized event JSON envelope.

### C. Authenticated WebSockets with Clerk
- The standard WebSocket API in web browsers does not permit sending custom HTTP headers during connection establishment.
- Fluxora authenticates `/api/v1/ws` by supporting query parameters (`?token=<token>`), authorization headers, and Sec-WebSocket-Protocol.
- Handshakes are authenticated against Clerk before `handleUpgrade` finishes, returning standard HTTP 401 Unauthorized for invalid sessions.

### D. In-Memory Tenant Hub Routing
- The `WebSocketHub` in `apps/api` maintains active connections categorized by `organizationId`.
- Even though the PostgreSQL trigger notifies the server of all events, the hub strictly routes each event envelope only to clients connected under matching `organization_id`.

## 3. Implementation Verification

Focused tests ensure each boundary is rock-solid:
1. `packages/db/src/repositories/event.test.ts`: Verifies RLS isolation, deduplication via unique constraints, and end-to-end `LISTEN`/`NOTIFY` reception.
2. `apps/workers/src/ingest/ingest.test.ts`: Verifies that the worker emits `repository.indexed` with the right payload and idempotency key on successful completion.
3. `apps/api/src/ws/ws.test.ts`: Verifies unauthenticated/invalid handshake rejection (401), token parsing, ping/pong, and multi-tenant broadcast isolation.
4. `apps/web/src/events/repository-events.test.ts`: Verifies client-side validation of `repository.indexed` event payloads.
