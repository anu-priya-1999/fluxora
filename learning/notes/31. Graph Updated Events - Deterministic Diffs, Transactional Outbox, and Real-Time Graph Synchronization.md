# 31. Graph Updated Events — Deterministic Diffs, Transactional Outbox, and Real-Time Graph Synchronization

## Context & Engineering Objective

Global Step 32 implements `graph.updated` domain event emission and deterministic graph diff summary computation (`docs/architecture/08-events-and-async-architecture.md §8.1`, `docs/architecture/17-implementation-roadmap.md §Phase 4 Step 6`).

When the graph builder projects normalized repository intelligence into `graph_nodes`, `graph_edges`, and `evidence` (Step 28), consumers need to know precisely what changed compared to previous snapshot runs. Step 32 establishes a deterministic graph diff engine and connects it directly to the transactional outbox (`events` table) and the WebSocket broadcast infrastructure.

---

## Core Technical Concepts Explained

### 1. In-Memory Deterministic Graph Diff Engine
Rather than relying on non-deterministic database ordering or complex triggers, `computeGraphDiff(previous, current)` performs pure in-memory set comparison:
- **Canonical Node Identification**: Compares nodes using their deterministic string IDs (`repo:path:symbol`).
- **Canonical Edge Keying**: Uniquely identifies edges via composite keys: `sourceNodeId:targetNodeId:edgeType`.
- **Change Detection**: Nodes are flagged as `changed` if `nodeType`, `name`, `path`, `confidence`, or `metadata` differ between versions. Edges are flagged as `changed` if `confidence`, `provenance`, `canonicalId`, or `metadata` differ.
- **Recursive JSON Key Sorting**: Metadata objects are serialized using `canonicalStringify`, sorting nested keys recursively to avoid false positive diffs caused by non-deterministic object key insertion orders.
- **Deterministic Array Sorting**: Added, removed, and changed nodes are sorted alphabetically by `id`. Added, removed, and changed edges are sorted by `sourceNodeId:targetNodeId:edgeType`.

### 2. Transactional Outbox Pattern & Failure Atomicity
Graph updates must never emit false notifications if the database write fails:
- Graph nodes, edges, evidence, and the `graph.updated` event are persisted inside the **same** `withTenant` PostgreSQL transaction.
- If graph persistence fails or an invariant is violated, the entire transaction rolls back, including the outbox event.
- When the transaction successfully commits, PostgreSQL's `fluxora_notify_event()` trigger fires `NOTIFY fluxora_events`, broadcasting the event payload to listening API gateways.

### 3. Outbox-to-WebSocket Bridge
Fluxora leverages PostgreSQL `LISTEN/NOTIFY` via `createEventListener` in `apps/api/src/ws/server.ts`:
- The API gateway subscribes to the channel.
- Incoming notifications are routed to the WebSocket connection pool.
- Messages are filtered strictly by `organizationId`, ensuring that subscribers only receive events for their own tenant.

### 4. Idempotency & Repeatability
- Event emission uses a deterministic `idempotency_key = graph:updated:<analysisRunId>:<previousAnalysisRunId|initial>`.
- Running the graph builder multiple times on the same analysis run reuses the same key, ensuring database idempotency and preventing duplicate outbox entries.

### 5. Multi-Tenant Isolation
- Ingestion queries (`getGraphStateForAnalysisRunTx`) set `app.current_organization_id` via `withTenant`.
- Defensive SQL clauses (`AND fluxora_analysis_run_in_current_tenant(analysis_run_id)`) verify that the requested analysis run belongs to the active tenant.
- Cross-tenant comparison is physically blocked at the database layer.
