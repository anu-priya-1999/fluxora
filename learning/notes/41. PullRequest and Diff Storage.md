# 42. PullRequest and Diff Storage

## Overview

In Fluxora's architecture, pull request analysis is divided into discrete, verifiable phases:
1. **Step 41 (Ingestion Boundary)**: Webhook reception, HMAC-SHA256 signature verification, and asynchronous queue handoff.
2. **Step 42 (Storage Layer)**: Durable, tenant-scoped storage of pull requests, changed files, and git diffs.
3. **Step 43 (Impact Analysis Engine)**: Diff-to-symbol resolution and deterministic graph traversal for blast-radius calculation.
4. **Step 44–47**: Evidence persistence, REST API exposure, frontend change-mode overlay, and golden fixture verification.

Step 42 acts as the **persisted source of truth** that bridges the asynchronous webhook queue to downstream deterministic graph traversal.

## 1. Relational Modeling for Pull Requests

### The `pull_requests` Table
A pull request represents a proposed set of changes from a head branch/commit to a base branch/commit within a repository.

Key fields:
- `id` (UUID, Primary Key): Stable internal identifier.
- `organization_id` (UUID): Tenant scope for multi-tenant isolation.
- `repository_id` (UUID): Foreign key to the Fluxora `repositories` table.
- `github_pr_id` (TEXT): GitHub's global entity ID.
- `number` (INTEGER): Repository-scoped PR number (e.g. `#42`).
- `title` & `url`: Human-readable identifier and GitHub link.
- `base_ref` & `base_sha`: Target branch and 40-character commit SHA.
- `head_ref` & `head_sha`: Source branch and 40-character commit SHA.
- `status` (`'open' | 'closed' | 'merged'`): State of the PR.
- `author_login` & `author_id`: PR author metadata.
- `last_delivery_id`: GitHub webhook delivery ID for traceability.

**Uniqueness Constraint**:
```sql
CONSTRAINT uq_pull_requests_repo_number UNIQUE (repository_id, number)
```
A pull request number is unique within a repository. Using `(repository_id, number)` allows idempotent upserts (`ON CONFLICT (repository_id, number) DO UPDATE ...`).

### The `pull_request_files` Table
Stores individual file modifications within a pull request snapshot.

Key fields:
- `id` (UUID, Primary Key).
- `pull_request_id` (UUID): Foreign key to `pull_requests` (`ON DELETE CASCADE`).
- `path` (TEXT): File path relative to repository root.
- `previous_path` (TEXT): Original file path if renamed.
- `status` (`'added' | 'modified' | 'removed' | 'renamed'`).
- `additions`, `deletions`, `changes` (INTEGER): Line change counts.
- `patch` (TEXT): Unified diff hunk for this file.
- `patch_truncated` (BOOLEAN): Flag indicating whether the patch exceeded byte limits.
- `base_sha` & `head_sha` (TEXT): Blob SHAs for before/after references.

**Uniqueness Constraint**:
```sql
CONSTRAINT uq_pull_request_files_pr_path UNIQUE (pull_request_id, path)
```
Guarantees that a file cannot appear twice within the same PR record.

## 2. Row-Level Security (RLS) & Multi-Tenant Isolation

Fluxora uses PostgreSQL Row-Level Security (RLS) to enforce strict tenant isolation at the database engine level.

1. **`pull_requests` Policy**:
   `pull_requests` directly carries `organization_id`:
   ```sql
   CREATE POLICY pull_requests_tenant_isolation ON pull_requests
     FOR ALL
     USING (organization_id = fluxora_current_org_id())
     WITH CHECK (organization_id = fluxora_current_org_id());
   ```

2. **`pull_request_files` Policy via Parent Invariant**:
   `pull_request_files` does not redundantly store `organization_id`. Instead, it enforces tenancy via the parent relationship using a `SECURITY DEFINER` helper function:
   ```sql
   CREATE OR REPLACE FUNCTION fluxora_pull_request_in_current_tenant(target_pull_request_id uuid)
   RETURNS boolean
   LANGUAGE sql
   STABLE
   SECURITY DEFINER
   SET search_path = public
   AS $$
     SELECT EXISTS (
       SELECT 1
       FROM pull_requests
       WHERE id = target_pull_request_id
         AND organization_id = fluxora_current_org_id()
     );
   $$;
   ```
   Every operation on `pull_request_files` checks `fluxora_pull_request_in_current_tenant(pull_request_id)`.
   If Tenant A attempts to insert, update, or read files belonging to Tenant B's PR, PostgreSQL silently filters out or rejects the row.

3. **`FORCE ROW LEVEL SECURITY`**:
   Both tables have `FORCE ROW LEVEL SECURITY` enabled to prevent table owners or unintended roles from bypassing tenant boundaries.

## 3. Atomic Replacement & Transaction Boundaries

When a developer pushes new commits to an open PR, GitHub sends a `pull_request.synchronize` webhook event. The head commit changes, and the set of modified files may differ entirely from earlier commits.

### The Problem: Partial Updates & Race Conditions
If files were updated row-by-row outside a transaction:
- Old files no longer changed would remain in the database (ghost files).
- Network failures halfway through would leave the PR with half new files and half old files.
- Downstream impact analysis would run against corrupted diff state.

### The Solution: `savePullRequestWithFiles`
All database modifications occur within a single atomic PostgreSQL transaction:
```typescript
await withTenant(pool, input.pr.organizationId, async (client) => {
  // 1. Upsert PullRequest
  const pullRequest = await upsertPullRequest(client, input.pr);

  // 2. Replace changed files atomically
  const files = await replacePullRequestFiles(client, pullRequest.id, input.files);

  return { pullRequest, files };
});
```

`replacePullRequestFiles` executes:
1. `DELETE FROM pull_request_files WHERE pull_request_id = $1`
2. Batch insert of all current `input.files`.

If any constraint fails (e.g. invalid SHA regex, duplicate path, negative additions), the transaction rolls back completely. The PR state remains strictly consistent.

## 4. GitHub API Fetching & Pagination Best Practices

### Fetch Outside the DB Transaction
Slow external network calls (such as GitHub HTTP requests) must **never** be performed inside a database transaction (`withTenant`). Holding a database connection and table locks open while waiting for external network I/O risks pool exhaustion and connection timeouts.

Order of operations:
1. Authenticate with GitHub App installation token.
2. Fetch PR metadata (`GET /repos/:owner/:repo/pulls/:number`).
3. Fetch changed files (`GET /repos/:owner/:repo/pulls/:number/files`) across multiple pages.
4. Truncate patches and enforce safety limits in memory.
5. Open DB transaction (`savePullRequestWithFiles`) and commit within milliseconds.

### Diff & File Limits
Pull requests can be arbitrarily large (e.g. automated dependency upgrades altering thousands of files or minified bundles). Step 42 enforces strict defensive limits:
- `maxFilesPerPr`: Default 1,000 files. Prevents memory exhaustion and unbounded DB writes.
- `maxPatchBytesPerFile`: Default 512 KB per patch. Larger patches are truncated with `patch_truncated = true`.
- `maxTotalPatchBytesPerPr`: Default 10 MB per PR. If total patch size exceeds this limit, subsequent file patches are omitted.

## 5. Security & Invariant Checklist

| Principle | Implementation |
|---|---|
| **Zero Secret Leakage** | GitHub installation tokens are minted in memory, used immediately, and never logged or stored in PostgreSQL. |
| **Untrusted Repository Content** | File paths, patch diffs, and titles are treated as untrusted text. No code execution occurs. |
| **Deterministic Data Only** | No LLMs or probabilistic guessing are used to infer file diffs or PR metadata. |
| **Strict Scope Enforcement** | No impact analysis, graph traversal, or blast-radius calculation is executed in Step 42. |
