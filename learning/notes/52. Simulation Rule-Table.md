# Engineering Notes — Step 53: Simulation Rule Table

## 1. Architectural Philosophy: Deterministic Core vs. Probabilistic AI

Fluxora's simulation system is built on an uncompromising principle: **system state changes must be 100% deterministic and grounded in code evidence**. An LLM never decides whether an outage cascades or whether a service degrades.

The simulation flow is:
```
Scenario Definition
  → Initialize Nodes (HEALTHY)
  → Propagation Engine (Step 54)
  → Rule Table (Step 53)
  → State Transitions
  → Convergence Check
  → SimulationResult & Evidence
```

In Step 53, the Rule Table is decoupled from traversal algorithms, database connections, and worker queues. It is a pure function:
$$\text{Decision} = f(\text{EdgeType}, \text{SourceState}, \text{TargetState}, \text{Metadata}, \text{FailureType})$$

---

## 2. The Four Normative Propagation Rules

1. **`calls.sync.no_fallback`**:
   - `CALLS + sync + no fallback` → caller `DEGRADED`.
   - If a downstream dependency fails and the caller synchronously waits for it without fallback protection, the caller's thread/connection pool degrades.
2. **`calls.circuit_breaker`**:
   - `CALLS + circuit breaker present` → caller `DEGRADED`, `capped=true`.
   - When a circuit breaker trips, it fails fast. The caller degrades for requests relying on that dependency, but the blast radius is strictly capped: failures do not cascade indefinitely.
3. **`writes.failure`**:
   - `WRITES + failed dependency` → dependent readers `AT_RISK`.
   - If a datastore experiences a write outage, subsequent reads (`QUERIES_DB`) risk reading stale, incomplete, or corrupted state. Dependent writes do not match this rule.
4. **`emits.consumer_only`**:
   - `EMITS + consumer` → consumer `AT_RISK`; producer unaffected.
   - In event-driven systems, an event broker or message queue outage puts consumers at risk of missed or delayed messages. The producer remains unaffected due to decoupled asynchronous emission.

## 3. Critical Semantic Boundaries & Lessons Learned

### A. Fallback & Async are Suppressors, Not Separate Rules
In early drafts, it might be tempting to invent rules like `CALLS + fallback → HEALTHY` or `CALLS + async → HEALTHY`.
However, the architecture specifies that nodes are initialized `HEALTHY` and only transition state when a propagation rule matches.
- A fallback handler suppresses the `calls.sync.no_fallback` degradation.
- An asynchronous call suppresses synchronous blocking.
- Both situations are simply **non-matches** (`matched: false`). The propagation engine preserves the node's existing state without inventing synthetic state transitions.

### B. Narrowing `WRITES+failure` to Dependent Reads
A database write failure affects downstream components that read or query that data (`QUERIES_DB`), causing them to become `AT_RISK` of inconsistent state. Evaluating the rule across a write edge (`WRITES`) is a non-match.

### C. Tri-State Metadata (`true | false | "unknown"`)
Static analysis often cannot definitively prove the absence of a pattern:
- Static analysis may verify a circuit breaker is present (`true`).
- Static analysis may verify code paths lack any protection (`false`).
- Or the pattern may be ambiguous or unanalyzed (`"unknown"`).

Converting `"unknown"` silently to `false` creates false certainty. By preserving `"unknown"`, the Rule Table can apply conservative defaults (assume no protection) while explicitly generating an assumption note:
> *"No circuit breaker detected on OrderService->PaymentService call"*

This transparency is a core feature of Fluxora, not a deficiency to conceal.

### D. Qualitative Latency Modeling
MVP simulation models failure modes qualitatively:
- `unavailable`: dependency is down/failed.
- `latency`: dependency is degraded due to response delays.

Latency propagates through synchronous blocking calls and datastore queries without introducing complex queueing simulations, traffic multipliers, or synthetic milliseconds.
