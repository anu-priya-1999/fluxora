# 45. PR Impact Analysis API

## Overview & System Role

Global Step 45 exposes the deterministic change-impact analysis engine (Step 43) and its durable persistence store (Step 44) through a clean, multi-tenant HTTP REST API and distributed job queue orchestration.

It provides two core capabilities:
1. `POST /api/v1/pull-requests/:id/analyze-impact`: Asynchronously schedules change-impact analysis for a pull request, returning `202 Accepted` with a job ID and idempotency key.
2. `GET /api/v1/impact-analyses/:id`: Retrieves the durable, evidence-backed impact analysis record with direct/downstream findings, taxonomy categories, and metrics.

---

## 1. Why Long-Running Analysis Must Return 202 Accepted

In a production software digital twin:
- Dependency graph traversal and multi-seed blast-radius calculations across large codebases can involve thousands of nodes and hundreds of transitive dependency chains.
- Synchronously blocking an HTTP connection during graph traversal creates risk of client timeouts, HTTP thread pool exhaustion, and poor user experience.
- By adhering to the `202 Accepted` pattern specified in `docs/architecture/07-api-architecture.md`:
  - The HTTP layer validates inputs, verifies tenant permissions, resolves the snapshot analysis run, enqueues a background job in PostgreSQL, and returns immediately.
  - Workers in `apps/workers` pick up the job and execute Step 44's `persistPullRequestImpactAnalysis` within a dedicated transaction.
  - Clients can subsequently query `GET /api/v1/impact-analyses/:id` or poll the pull request's latest analysis.

---

## 2. Strict Tenancy & Security Boundaries

Cross-tenant data leakage is strictly prohibited:
- **Session Identity**: The user's `organizationId` is extracted solely from the verified JWT / Clerk session via `resolveSessionFromRequest`.
- **Client Parameter Rejection**: If a client provides `organization_id` in the request body, query params, or URL, the request is immediately rejected with `400 invalid_request`.
- **Resource Tenancy**: The pull request must belong to the caller's organization. If a user requests analysis on a pull request from another tenant, the system returns `404 pull_request_not_found`, completely hiding whether the foreign resource exists.
- **RLS Enforcement**: Storage queries for both the PR and the completed analysis run are evaluated against PostgreSQL Row-Level Security (`FORCE ROW LEVEL SECURITY`).

---

## 3. Idempotency & Deduplication Design

To prevent redundant computation on repeated requests:
- Clients provide an optional `Idempotency-Key` header.
- The system generates a deterministic idempotency key:
  `pull_request.impact_analysis:${pullRequestId}:${analysisRunId}:${clientKey}`.
- The job payload includes a deterministic `impactAnalysisId`:
  `EvidenceWriter.generateDeterministicUuid(`${organizationId}:${jobIdempotencyKey}`)`.
- If the same request is submitted multiple times:
  - The database job queue rejects duplicate pending jobs or reuses the existing job identifier.
  - Repeated executions in the worker update the same `impact_analyses` row via `ON CONFLICT (id) DO UPDATE` and `writeEvidenceBatchTx`, producing zero duplicate rows or duplicate evidence records.

---

## 4. Read-Only GET Idempotency

When retrieving an impact analysis via `GET /api/v1/impact-analyses/:id`:
- The handler executes `getImpactAnalysisById` within the authenticated tenant scope.
- It performs **zero recomputations**: no Git diff parsing, no symbol resolution, and no recursive graph traversal.
- The returned payload presents a clean, consistent view of direct impacts, downstream impacts, affected APIs, affected events, affected services, workflow summaries, and associated evidence IDs.

---

## Key Takeaways

1. **Deterministic Core Preserved**: HTTP API exposure does not alter or re-implement any algorithmic traversal logic; it orchestrates Step 43 and Step 44.
2. **Separation of Concerns**: HTTP parsing (`apps/api`), job queue orchestration (`apps/workers`), and persistence (`packages/db`) maintain strict modular boundaries.
3. **Fail-Closed Security**: Client cannot forge tenant context, and cross-tenant resources return 404 without information disclosure.
