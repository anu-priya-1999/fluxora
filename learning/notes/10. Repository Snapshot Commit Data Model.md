# Personal Learning — Step 11: Repository, Snapshot, and Commit

Canonical architecture: `docs/architecture/06-database-schema.md`, `docs/architecture/11-security-architecture.md` §11.4 / §11.7, `docs/architecture/17-implementation-roadmap.md` Phase 2 Step 2 (global Step 11).

Implementation: `packages/db/migrations/0011_repositories_snapshots_commits.sql`, `packages/db/src/repositories/repository.ts`, `repository-snapshot.ts`, `commit.ts`.

This step stores **metadata only**. It does not fetch GitHub trees, mint installation tokens, upload bytes, or run workers.

---

## Why Repository is a tenant-owned resource

A Fluxora organization is the tenant boundary. A connected GitHub repository is something that organization chose to analyze. Access to its metadata, snapshots, and later graph/evidence must never leak to another organization.

`repositories.organization_id` is therefore a real foreign key to `organizations`, not an optional tag. Row-Level Security on `repositories` compares that column to `fluxora_current_org_id()` — the same session variable every other tenant table already uses.

The GitHub repo id (`github_repo_id`) identifies the repo **on GitHub**. It does not identify the Fluxora tenant. Two Fluxora organizations may legitimately connect the same public GitHub repository, so uniqueness is `(organization_id, github_repo_id)`, not a global unique `github_repo_id`. That is different from `github_installations.github_installation_id`, which is a single App installation that must belong to only one Fluxora org.

---

## Why Snapshot is immutable

A snapshot is a frozen copy of a repository tree at one commit. Analysis, evidence, and later impact reports hang off that freeze.

If a snapshot could be overwritten:

- a re-fetch from GitHub could change files under an id that evidence already cited
- two workers could disagree about what `snapshot_id` meant
- TOCTOU appears: analysis starts against tree A, GitHub or storage later becomes tree B, results mix both

Immutability is enforced three ways:

1. **No UPDATE RLS policy** on `repository_snapshots` under `FORCE ROW LEVEL SECURITY` — the application role cannot update rows even if SQL says `UPDATE`.
2. **Unique `(repository_id, commit_sha)`** — a second insert of the same commit cannot create a different row. Identical payload is treated as idempotent replay. A different payload is rejected (`RepositorySnapshotImmutableError`).
3. **Application code never issues a successful overwrite.** `tryOverwriteRepositorySnapshot` exists only so tests can prove the database denies it.

File bytes are not in PostgreSQL. `storage_uri` is a pointer. Step 12 will write the object once. Changing bytes behind the same URI would still be a storage-layer bug; the relational row is not allowed to retarget that pointer.

## Repository vs RepositorySnapshot vs Commit

| Thing | What it is | Changes over time? |
|---|---|---|
| **Repository** | Fluxora's connection to a GitHub repo (name, default branch, connection status) | Yes: reconnect, rename, `last_indexed_at`, `needs_reauth` |
| **Commit** | Git object metadata: sha, author, message, parents, timestamp | No as git objects. Rows are insert-only. History accumulates. |
| **RepositorySnapshot** | "We packaged this commit's tree and stored it at `storage_uri`" | No. New commit → new snapshot. Same commit → same snapshot. |

Repository is the live **connection**. Commit is **history metadata**. Snapshot is **the immutable artifact** later workers will unpack.

---

## Why a snapshot is not the same thing as a commit

A commit exists on GitHub whether Fluxora ingested it or not. Fluxora may know many commits (SHAs, messages, parent chain) and only snapshot some of them (for example `main` HEAD after each index).

A snapshot always **names** a commit (`commit_sha`) and also records:

- which **ref** was requested (`refs/heads/main`)
- where the **bytes** went (`storage_uri`)
- **size** metadata (`file_count`, `size_bytes`)

You can list commits without having blobs. You cannot analyze a tree without a snapshot. Mixing them into one table would force either storing storage fields on every git commit row (mostly null) or losing git history that was not ingested.

The unique key is `(repository_id, commit_sha)`: one stored tree per commit. `ref` is provenance ("we took this snapshot because main pointed here"), not a second identity. If `main` and a tag share a SHA, they share one snapshot.

## Why parent-chain tenancy is used for child tables

Architecture §6.5: top-level tables carry `organization_id`. Child tables inherit tenancy through parents.

`repository_snapshots` and `commits` have `repository_id`, not `organization_id`.

Reasons:

- The tenant of a snapshot **is** the tenant of its repository. Duplicating `organization_id` can drift (row says org A, parent repo says org B).
- RLS still works: `fluxora_repository_in_current_tenant(repository_id)` exists against `repositories` for the current org.
- Foreign keys already require a real parent repository.

Duplicating `organization_id` on hot-path tables is an allowed later optimization if join cost shows up. It is not required at Step 11.

---

## How foreign keys protect integrity

- `repositories.organization_id → organizations(id) ON DELETE CASCADE` — deleting an org removes its repos.
- `repository_snapshots.repository_id → repositories(id) ON DELETE CASCADE`
- `commits.repository_id → repositories(id) ON DELETE CASCADE`

You cannot snapshot a UUID that is not a repository. You cannot leave orphan snapshots after a repo is removed.

**Important pitfall:** PostgreSQL foreign-key checks are **not** subject to RLS. A session that knows another tenant's `repository_id` could satisfy the FK while inserting a child row. That is why INSERT policies use `WITH CHECK (fluxora_repository_in_current_tenant(repository_id))`. The FK is integrity. RLS is tenancy. You need both.

Local `TRUNCATE organizations CASCADE` in `db:reset` still clears these tables through the FK.

## How indexes map to expected query paths

| Index / unique | Query path |
|---|---|
| `repositories_organization_github_repo_id_unique` | Connect / look up by GitHub id **inside one org** |
| `repositories_organization_id_idx` | List repos for the current tenant |
| `repositories_organization_connection_status_idx` | Dashboards / workers: which repos are `active` vs `error` |
| `repositories_organization_created_at_idx` | Recency listing |
| `repository_snapshots_repository_commit_sha_unique` | Idempotent ingest: "do we already have this SHA?" |
| `repository_snapshots_repository_created_at_idx` | Latest snapshot for a repo |
| `commits_repository_sha_unique` | Look up / replay a git SHA |
| `commits_repository_committed_at_idx` | History listing |

No GIN on `parent_shas` yet. Walking parent chains in SQL is not a Step 11 query.

## How PostgreSQL RLS evaluates access

1. API/worker starts a transaction and `set_config('app.current_org_id', org_id, true)`.
2. `fluxora_current_org_id()` reads that setting.
3. **Repository** policies: `organization_id = fluxora_current_org_id()` for SELECT/INSERT/UPDATE/DELETE.
4. **Snapshot/commit** policies call `fluxora_repository_in_current_tenant(repository_id)`, which `EXISTS` a `repositories` row with that id **and** current org. Nested RLS on `repositories` applies, so the EXISTS cannot see another tenant's repo.
5. Superusers bypass FORCE RLS. Integration tests `SET LOCAL ROLE` to `fluxora_rls_test` (`NOBYPASSRLS`) via `FLUXORA_DATABASE_ROLE` so policies are actually evaluated on a local superuser connection.
6. Snapshots and commits have **no UPDATE policy**. An `UPDATE` matches zero rows (default deny), so immutability holds at the database, not only in TypeScript.

Application `WHERE repository_id = $1` is not enough. Cross-tenant tests set a different org on the session and must see empty reads.

## How this prepares Step 12 ingestion

Step 12 will: mint an installation token, fetch a ref, write an object, then insert `Commit` + `RepositorySnapshot` and flip `connection_status` / `last_indexed_at`.

This step already provides:

- a place to record the repo as `pending` then `active` or `error`
- immutable snapshot identity keyed by commit SHA (safe retries)
- commit parent metadata for later history UI
- tenant-safe writes the worker can run under `withTenant`
- `storage_uri` as a contract for S3/filesystem keys (`s3://…/{org}/{repo}/{sha}` style) without implementing upload

What Step 12 must **not** do: `UPDATE` snapshot bytes metadata in place; mutate git commit rows; skip `withTenant`.

## Trade-offs and alternatives

**Global unique `github_repo_id`.** Simpler "one Fluxora copy of each GitHub repo." Rejects two tenants analyzing the same public repo. Wrong for a multi-tenant product.

**`organization_id` on every child table.** Faster RLS, denormalized, can drift. Deferred.

**Store file contents in PostgreSQL.** Easy joins, terrible for large trees, backups, and memory. Architecture puts blobs in object storage.

**Snapshot unique on `(repository_id, commit_sha, ref)`.** Would duplicate blob metadata when two refs share a SHA.

**Allow multiple snapshots per SHA.** Useful if storage layout changes; breaks "this SHA is this tree" unless old rows are retained as history. MVP chooses one snapshot per SHA.

**Enum vs text check for `connection_status`.** Enum matches a closed set (`pending | active | needs_reauth | error`). Jobs used text CHECK because status sets evolved with retries. Connection status is a product enum.

## Mistakes and pitfalls

- Treating GitHub repo id as the Fluxora primary key. GitHub ids are external; Fluxora `id` is internal.
- Putting `organization_id` on snapshots "just in case" against architecture §6.5.
- Relying on FK alone for tenant isolation (FK bypasses RLS).
- `UPDATE` snapshots when re-indexing. Re-index = new SHA = new snapshot, or identical SHA = no-op.
- JSON numbers for `github_repo_id` (same lesson as installation ids). Keep decimal strings in TypeScript; `::bigint` in SQL.
- Unique violation aborting the whole transaction. Writes use a **savepoint**, same pattern as GitHub installations.
- Forgetting DELETE policies on children so `ON DELETE CASCADE` fails under FORCE RLS.
- Implementing ingestion, tokens, S3, or connect API in this step.

## Worked example: GitHub repository → commit → snapshot

GitHub repo `octocat/hello-world` has id `1296269`. Default branch `master`. HEAD commit:

- sha `7fd1a60b01f91b314f59955a4e4d4e80d8edf11d`
- parent `553c2077f0edc3d5dc5d17262f6aa498e69d6f8e`
- message `Merge pull request #6…`

Fluxora org `org_A` (after Step 10 installation) inserts:

1. `repositories`: `organization_id = org_A`, `github_repo_id = 1296269`, `name = hello-world`, `default_branch = master`, `connection_status = pending`.
2. Step 12 worker (not this step) fetches that SHA, uploads a tarball to `s3://fluxora-snapshots/{org_A}/{repo_id}/7fd1a60b…`.
3. `commits`: sha `7fd1a60b…`, parent_shas `{553c2077…}`, author/message/date from GitHub.
4. `repository_snapshots`: `commit_sha = 7fd1a60b…`, `ref = refs/heads/master`, `storage_uri` as above, `file_count` / `size_bytes` from the package.
5. `repositories.connection_status = active`, `last_indexed_at = now()`.

If the worker retries the same SHA, unique constraints plus identical-payload replay return the same snapshot and commit ids. If org `org_B` uses the same GitHub id `1296269`, it gets a **different** `repositories.id` and its own snapshots. `org_B` cannot `SELECT` `org_A`'s rows because RLS `organization_id` / parent-chain checks fail.
