# 55. Simulation Studio UI (Global Step 56)

## Overview & System Role

Global Step 56 delivers the **Simulation Studio UI**, bringing interactive failure scenario experimentation and deterministic causal path inspection to the Fluxora digital twin (`docs/architecture/17-implementation-roadmap.md`, Phase 8 Step 5).

Building directly upon the persistence models of Step 52, the pure rule table of Step 53, the deterministic propagation engine of Step 54, and the authenticated HTTP APIs of Step 55, the Simulation Studio enables engineers to:
1. Select an indexed repository and a verified analysis-run graph snapshot.
2. Select a target service, route, datastore, or broker from the real analysis graph.
3. Configure a failure scenario (`unavailable` or `latency`).
4. Execute the simulation against the deterministic engine with duplicate-submission protection.
5. Inspect the resulting blast radius across all 4 canonical states (`healthy`, `at_risk`, `degraded`, `failed`).
6. Trace step-by-step causal paths explaining the exact sequence of rule applications, edge transitions, assumptions, and confidence scores behind every degraded or failed node.

---

## 1. Architectural Philosophy: Deterministic Core in the UI

Fluxora's Core Principle P1 establishes that **the deterministic core and the probabilistic AI edge must never be conflated**:
- The frontend **never** runs its own heuristic failure propagation loop or guesses cascade paths.
- The UI strictly reflects the deterministic results computed by the Step 54 backend engine via the Step 55 API.
- The simulation confidence score is derived from static AST metadata completeness and conservative assumptions—it is **never** presented as an empirical SLA probability, downtime percentage, or statistical likelihood.
- Latency propagation is modeled qualitatively (`at_risk` or `degraded` upstream callers); the UI never fabricates numerical millisecond queueing latency or synthetic MTTR estimates.

## 2. Step 55 API Contract Alignment & Wire Protocol

The Simulation Studio communicates with Fluxora's backend via Node's native `node:http` server (`apps/api/src/http/server.ts`), adhering strictly to the verified Step 55 contracts:

### A. Scenario Creation (`POST /api/v1/scenarios`)
- **Request Body**:
  ```json
  {
    "name": "Payment Gateway Outage",
    "target_node_id": "node-uuid-1234",
    "failure_type": "unavailable",
    "repository_id": "repo-uuid-5678",
    "analysis_run_id": "run-uuid-9012",
    "parameters": {}
  }
  ```
- **Strict Invariants**:
  - `seed_failures` is **not supported** in Step 55 and is explicitly rejected with `400 invalid_request` by the backend parser.
  - `organization_id` must **never** be supplied by the client; tenant identity is established strictly from the verified Clerk session.
  - Supported `failure_type` values are strictly `"unavailable"` and `"latency"`.
- **Response**: Returns a flat `ScenarioResponse` (`id`, `name`, `target_node_id`, `failure_type`, `repository_id`, `parameters`, `created_at`).

### B. Scenario Execution (`POST /api/v1/scenarios/:id/run`)
- Executes the simulation synchronously against the active analysis run snapshot.
- Consumes `SimulationResponse` containing:
  - `id`: Simulation runtime ID.
  - `status`: `"completed"` or `"failed"`.
  - `total_results`: Total count of evaluated nodes.
  - `converged`: Boolean flag indicating if the propagation reached an equilibrium.
  - `iterations`: Number of worklist loops before termination.
  - `results`: Array of individual node simulation results.
  - `assumptions`: Array of rule-level hypotheses recorded during propagation.

### C. Results Retrieval (`GET /api/v1/simulations/:id/results`)
- Consumes `SimulationResultsListResponse`:
  ```json
  {
    "simulation_id": "sim-uuid-3456",
    "results": [
      {
        "node_id": "node-uuid-1234",
        "resulting_state": "failed",
        "state": "failed",
        "propagation_path": [
          {
            "nodeId": "node-uuid-1234",
            "ruleId": "seed_failure",
            "previousState": "healthy",
            "resultingState": "failed",
            "edgeId": null,
            "assumptions": ["Target node injected with unavailable failure"],
            "confidence": 1.0
          }
        ],
        "rule_applied": "seed_failure",
        "assumptions": ["Target node injected with unavailable failure"],
        "confidence": 1.0
      }
    ],
    "total": 1
  }
  ```
- **Contract Precision**:
  - The response uses `total` (not `total_affected`).
  - Causal steps are nested under `propagation_path` (not `causal_steps`).
  - `rule_table_version` is safely extracted from causal step metadata rather than assumed to be present at the top level.

## 3. Canonical Result States vs. Failure Types

A critical source of bugs in failure modeling is conflating **input failure triggers** with **resulting system states**:
- **Input Failure Types**: `"unavailable"` (seed resource completely unreachable) and `"latency"` (seed resource suffering severe degradation/timeout).
- **Canonical Result States**:
  1. `failed` (Severity 3): The node has suffered complete operational failure (e.g. synchronous callee failed with no fallback).
  2. `degraded` (Severity 2): The node is impaired (e.g. latency cascade through synchronous call, or async worker experiencing retry backoff).
  3. `at_risk` (Severity 1): The node is vulnerable or exposed to potential cascade (e.g. upstream broker failure where consumer relies on dead-letter queues).
  4. `healthy` (Severity 0): The node remains fully operational or is insulated by architectural boundaries (e.g. circuit breakers or independent components).

> [!IMPORTANT]
> The UI strictly rejects synthetic or non-canonical states like `delayed`. Latency injection results in `degraded` or `at_risk` states, preserving mathematical monotonicity across the system.

## 4. Impact Summary Metrics

The studio computes impact metrics dynamically from verified result records:
$$\text{Total Affected} = N_{\text{failed}} + N_{\text{degraded}} + N_{\text{at\_risk}}$$
$$\text{Healthy Preserved} = N_{\text{healthy}}$$

- **Severity Sorting**: Results table sorts primarily by canonical state severity (`failed` > `degraded` > `at_risk` > `healthy`), ensuring engineers immediately see the most critical casualties of an outage.
- **Filter Categories**: Engineers can filter by canonical state (`All`, `Failed`, `Degraded`, `At Risk`, `Healthy`) and search by node name or ID.

## 5. Causal Path Inspector: Deconstructing Propagation

Every affected node must explain its state. Selecting any node in the results table activates the **Causal Path Inspector**, which renders the step-by-step causal chain:

1. **Seed Step (Hop 0)**:
   - `edgeId`: `null` (rendered as `"None (Seed target failure)"`).
   - `ruleId`: `"seed_failure"` or direct injection.
   - `previousState`: `"healthy"` $\to$ `resultingState`: `"failed"` or `"degraded"`.
2. **Propagated Steps (Hops 1..N)**:
   - `edgeId`: Exact UUID of the graph edge transmitting the failure.
   - `ruleId`: Exact rule applied (e.g. `calls.sync.no_fallback`, `broker.unavailable.consumer_at_risk`).
   - `ruleVersion`: Rule table version governing the transition.
   - `previousState` $\to$ `resultingState`.
   - `assumptions`: Explicit listing of static analysis limits (e.g. `"No circuit breaker or fallback detected in call AST"`).
   - `confidence`: Confidence score (0.0–1.0) indicating certainty of the structural link.
   - `capped`: Highlighted badge if propagation hit maximum traversal depth or iteration boundaries.

## 6. Dependent State Invalidation Discipline

To guarantee that an engineer never runs or views a simulation with mismatched repository, analysis-run, or node context, the UI enforces strict cascading invalidation:

| Changed Dimension | Invalidated State |
|---|---|
| **Repository Changed** | Analysis run reset, target node cleared, graph nodes cleared, scenario cleared, simulation cleared, results table cleared. |
| **Analysis Run Changed** | Target node cleared, graph nodes cleared, scenario cleared, simulation cleared, results table cleared. |
| **Target Node Changed** | Scenario cleared, simulation cleared, results table cleared. |

### Deep-Linking from Architecture Explorer
When exploring the graph in the Architecture Explorer (`/repositories/[repoId]/explorer`), engineers can click the **Simulation Studio** button in the header. The studio pre-populates `repository_id`, `analysis_run_id`, and `target_node_id` from query parameters, allowing seamless 1-click failure hypothesis testing directly from visual inspection.

## 7. Error Handling & Honesty

In accordance with Fluxora's reliability guidelines, the UI never disguises an infrastructure failure as an empty or successful simulation:
- **401 Unauthorized**: Displays an authentication error banner instructing the user to sign in.
- **404 Not Found**: Surfaces an explicit error if the repository, analysis run, or scenario cannot be found.
- **422 Convergence Failure**: Displays a clear warning explaining that the failure graph did not converge within configured iteration limits.
- **500 Server Error**: Shows an error banner with retry capability without leaking database internals.
- **Empty Graph / No Affected Nodes**: Explicitly distinguishes between an API failure and a genuine zero-impact scenario (e.g. an isolated leaf node with no incoming dependencies).
