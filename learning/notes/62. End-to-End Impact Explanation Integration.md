# 62. End-to-End Impact Explanation Integration

## Architectural Concept

In an enterprise-grade AI system, integrating large language models with a mission-critical deterministic core requires strict architectural discipline. A common failure mode in AI-augmented software is allowing probabilistic model failures (such as token rate limits, context length overflows, network timeouts, or ungrounded hallucinations) to corrupt, delay, or invalidate the underlying deterministic findings.

Fluxora's **Global Step 62** demonstrates how to build an end-to-end production AI pipeline that enhances deterministic software graph analysis while remaining strictly decoupled from the system's core source of truth.

## Key Principles & Invariants

### 1. The Deterministic Invariant (P1 / P10)
The deterministic blast-radius engine is the sole authority for code changes and system impact. The LLM does not perform graph traversal, discover dependencies, or infer relationships from raw code. The LLM only receives verified facts and evidence records to synthesize a natural-language narration.

### 2. Failure Isolation Boundary
AI generation is treated as an optional enhancement. If the model provider times out, hits a rate limit, or fails structured-output validation, the failure is caught and recorded in the `ai_analyses` table with `status = 'failed'` or `status = 'rejected'`. The deterministic impact analysis job completes successfully, the findings are saved to PostgreSQL, and no unnecessary queue retries are triggered.

### 3. Strict Whole-Response Rejection (ADR-014)
When model output contains ungrounded claims or hallucinated evidence IDs, Fluxora rejects the entire response. We never silently strip ungrounded claims, because doing so mutilates the narrative coherence of the explanation. Furthermore, raw ungrounded model completions are never stored in `output_text` or returned via the API, preventing hallucinations from reaching users.

### 4. Explicit Lifecycle vs. Validation Status
A clear distinction is maintained between operational lifecycle states (`pending`, `completed`, `rejected`, `failed`) and validation results (`passed`, `rejected`). A network timeout is a provider failure (`status = 'failed'`), not a validation rejection (`status = 'rejected'`).

### 5. Multi-Tenant Row-Level Security
The `ai_analyses` table enforces PostgreSQL Row-Level Security (`ENABLE & FORCE ROW LEVEL SECURITY`), binding all operations to `current_setting('app.current_org_id')`. Multi-tenancy is enforced at the database engine boundary, preventing cross-tenant leakage even in the event of application bugs.

### 6. Idempotent Upsert
Repeated webhook deliveries or manual re-analysis invocations for the same impact analysis use `UNIQUE (organization_id, subject_type, subject_id)` to update the existing AI record in-place, preventing duplicate records and eliminating redundant third-party LLM calls.
