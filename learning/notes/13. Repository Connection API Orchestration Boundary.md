# Fluxora Step 14 — Learning Notes

## 1. What Step 14 Builds

Step 14 adds the repository connection API/orchestration boundary:

```text
POST /api/v1/repositories/connect
        ↓
Authenticate Clerk session
        ↓
Resolve authenticated GitHub identity
        ↓
Resolve tenant / organization
        ↓
Validate GitHub installation belongs to that organization
        ↓
Call GitHub with installation credentials
        ↓
Fetch repository metadata
        ↓
Resolve branch/ref → exact commit SHA
        ↓
Find/create Repository
        ↓
Set repository to pending
        ↓
Enqueue existing repository.ingest job
        ↓
Return HTTP 202
```

The HTTP request does not perform repository download, extraction, snapshot packaging, or AI analysis. Those remain in the existing worker pipeline.

## 2. The Most Important Concept: HTTP vs Application Logic

Step 14 deliberately separates the HTTP boundary from repository-connection orchestration.

```text
apps/api/src/http/repositories.ts
    = HTTP request/response handling

apps/api/src/http/repository-request.ts
    = pure request/path validation

apps/api/src/repositories/connect.ts
    = repository connection orchestration

apps/api/src/github/repository-client.ts
    = GitHub API interaction
```

This separation matters because each layer has a different responsibility.

### HTTP layer

`repositories.ts` handles:

- request headers
- content type
- Clerk authentication
- request-body reading
- HTTP status codes
- JSON responses
- mapping domain/GitHub errors into stable API errors

### Request-validation layer

`repository-request.ts` contains:

- `REPOSITORY_CONNECT_PATH`
- `isRepositoryConnectPath()`
- `parseConnectBody()`
- `RequestValidationError`

It has no Clerk dependency.

That makes its tests independent of authentication/environment configuration.

### Orchestration layer

`repositories/connect.ts` coordinates:

1. tenant-owned GitHub installation lookup
2. installation-id ownership check
3. GitHub repository/ref resolution
4. repository find-or-create
5. pending-state update
6. `repository.ingest` enqueue
7. commit-based idempotency

## 3. Branch vs Commit SHA

A branch is a moving reference.

```text
main
 ↓
current commit
 ↓
abcdef...40-character SHA
```

Step 14 resolves the requested `ref` to the exact commit SHA before creating the ingestion job.

The external request remains:

```json
{
  "github_installation_id": "12345678",
  "repo_full_name": "acme-corp/checkout-service",
  "branch": "main"
}
```

Internally, the job is pinned to:

```json
{
  "repositoryId": "...",
  "ref": "main",
  "commitSha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

This matters because `main` can move while the commit SHA identifies one immutable repository state.

## 4. Installation Ownership

Step 10 established the GitHub App installation and persisted the tenant-owned installation.

Step 14 does not blindly trust the installation ID sent by the browser.

The orchestration first loads the installation for the authenticated organization:

```text
organizationId
   ↓
stored GithubInstallation
   ↓
compare stored installation ID
   ↓
match → continue
mismatch → 403
```

Failure classes include:

- no installation → `github_installation_required`
- installation belongs to another organization → `github_installation_mismatch`

This is an important tenant-boundary check.

## 5. GitHub Authentication

The API-side GitHub repository client:

1. creates a short-lived GitHub App JWT;
2. exchanges it for a short-lived installation access token;
3. uses that installation token to request repository metadata;
4. uses the same token to resolve the requested ref.

The token is not persisted as application data.

The repository client also validates response structure and classifies failures rather than returning arbitrary GitHub response bodies.

## 6. Large GitHub IDs

GitHub repository IDs are numeric in the REST response, but PostgreSQL stores the value as `bigint`.

JavaScript `number` cannot safely represent every 64-bit integer.

Step 14 therefore preserves integer JSON values as strings before persistence.

The repository client validates:

- positive canonical decimal form
- PostgreSQL `bigint` maximum
- repository full-name format
- full 40-character lowercase hexadecimal commit SHA

This prevents silent numeric precision loss.

## 7. Repository Find-or-Create

When the resolved GitHub repository is found:

```text
organization + githubRepoId
        ↓
existing Repository
```

When it does not exist:

```text
create Repository
        ↓
connectionStatus = pending
```

There is also a race-safe path:

```text
get → not found
        ↓
create
        ↓
unique conflict
        ↓
re-read
```

If another request created the repository first, Step 14 re-reads the tenant-scoped row instead of failing the entire connect operation.

## 8. Idempotent Job Enqueue

Step 14 reuses the existing PostgreSQL-backed job queue.

The job type is:

```text
repository.ingest
```

The idempotency key is:

```text
repository.ingest:{repositoryId}:{commitSha}
```

This gives commit-level idempotency.

Two requests for the same repository at the same commit resolve to the same logical ingestion job instead of creating duplicate work.

## 9. Why the API Returns 202

Step 14 returns:

```text
202 Accepted
```

because repository ingestion is asynchronous.

The API only starts the workflow:

```text
connect
  ↓
enqueue
  ↓
return
```

The worker later performs:

```text
download
  ↓
extract
  ↓
package
  ↓
store snapshot
```

This prevents the HTTP request from becoming a long-running ingestion process.

## 10. Response

The endpoint returns the accepted repository/job information, including:

```json
{
  "repository_id": "...",
  "status": "pending",
  "job_id": "...",
  "ref": "main",
  "commit_sha": "..."
}
```

The exact job and repository state is therefore available to the caller immediately after enqueue.

## 11. Error Mapping

Step 14 maps failures into stable API semantics.

| Condition                   | HTTP | API code                       |
| --------------------------- | ---: | ------------------------------ |
| GitHub App not configured   |  503 | `github_app_not_configured`    |
| invalid session             |  401 | `invalid_session`              |
| no connected GitHub account |  403 | `github_account_required`      |
| installation missing        |  409 | `github_installation_required` |
| installation mismatch       |  403 | `github_installation_mismatch` |
| repository inaccessible     |  404 | `repository_not_accessible`    |
| invalid ref                 |  422 | `invalid_ref`                  |
| GitHub re-auth needed       |  409 | `github_reauth_required`       |
| GitHub rate limited         |  503 | `github_rate_limited`          |
| GitHub unavailable          |  503 | `github_unavailable`           |

The endpoint does not expose arbitrary GitHub response bodies.

## 12. Testing Lesson From Step 14

A pure parsing test should not import an HTTP module that pulls in Clerk, DB, and GitHub dependencies.

That is why the request helpers were separated into:

```text
http/repository-request.ts
```

The test can then exercise:

```text
path recognition
request parsing
numeric installation-id rejection
repository-name validation
branch/ref validation
```

without loading Clerk.

The repository-client tests use dependency injection for:

```text
config
fetchImpl
now
```

which keeps GitHub API tests deterministic and avoids real network calls.

## 13. What Step 14 Does Not Do

Step 14 does not implement:

- repository download
- archive extraction
- snapshot packaging
- object-storage persistence
- AST analysis
- symbol indexing
- dependency graph construction
- WebSocket progress
- AI reasoning

Those remain separate roadmap steps.

## 14. Mental Model

Remember Step 14 as:

> **Validate → resolve → persist → enqueue → return.**

The API validates the user's request and tenant context, resolves the repository to an exact commit, persists repository metadata, enqueues existing ingestion work, and returns without performing heavy ingestion itself.
