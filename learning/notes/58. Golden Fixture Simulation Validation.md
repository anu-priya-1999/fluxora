# 57. Golden Fixture Simulation Validation

## 1. Executive Summary & Objective

In **Global Step 58**, Fluxora reaches the culmination of **Phase 8 (Simulation)**: validating the Step 53 Simulation Rule Table and the Step 54 Deterministic Simulation Engine against Fluxora's real, immutable Taxonomy golden repository fixture (`shadcn-ui/taxonomy`).

Synthetic tests verify code paths in isolation, but only a real, production-scale repository fixture tests the true end-to-end reality of static analysis, graph projection, and simulation propagation. This note articulates the core engineering principles, semantic boundaries, causal evidence mechanics, and testing architectures established during Step 58.

---

## 2. Core Architectural Principles

### 2.1 Principle P1: The Deterministic Core
Fluxora is founded on the thesis that architecture understanding, blast-radius calculation, and failure simulation must be **100% deterministic, queryable, and verifiable**. Probabilistic models (LLMs) exist solely at the outer boundary to narrate, explain, and synthesize already-computed deterministic facts. If failure simulation were non-deterministic or probabilistic, customer trust in change-impact reports would collapse.

### 2.2 Principle P2: Immutable Evidence Provenance
Every structural assertion and state transition in Fluxora must trace to concrete source code provenance. For simulation:
- Every non-seed failure transition must identify the exact graph edge traversed (`edgeId`).
- The transition must cite the canonical rule ID and rule version (`ruleId`, `ruleVersion`).
- The transition must record explicit assumptions made when inspecting edge metadata.
- A complete, structured causal trail must link the node back to the root failure seed.

## 3. Golden Fixtures vs. Synthetic Testing

While synthetic unit tests (such as constructing 2-node or 3-node mock graphs) are essential for exercising boundary conditions (e.g., cycle termination, state severity monotonicity), they suffer from blind spots:
1. **Simplified Topologies**: Synthetic graphs tend to be clean trees or DAGs. Real codebases have dense fan-outs, barrel files, and hundreds of module imports.
2. **Artificial Metadata**: Synthetic tests typically populate perfect metadata. Real static analysis produces missing, partial, or unverified metadata.
3. **Scale and Convergence**: Synthetic graphs rarely stress worklist queues at hundreds of nodes.

Fluxora anchors its quality strategy in a pinned, real-world Next.js open-source repository fixture:
- **Repository**: `shadcn-ui/taxonomy`
- **Fixture ID**: `golden-taxonomy-v1`
- **Pinned Commit**: `298a8857c7128a0d121e7f699dfd729f23b3966d`
- **File Count**: 177 files
- **Baseline Graph**: 490 nodes (367 symbols, 118 modules, 5 API routes), 888 edges (511 `IMPORTS`, 5 `EXPOSES_ROUTE`, 372 `RESOLVES_TO`).

All tests run completely **offline** without network access to GitHub, reading passive snapshot bytes verified against SHA-256 hashes recorded in `fixtures/golden/manifest.json`.

## 4. The Critical Semantic Boundary: `IMPORTS` is Not `CALLS`

A foundational architectural invariant verified in Step 58 is the strict distinction between module imports and runtime function invocations:

```text
┌────────────────────────┐                   ┌───────────────────────┐
│       Module A         │ ─── IMPORTS ───>  │       Module B        │
│ (Static Dependency)    │                   │   (Export Provider)   │
└────────────────────────┘                   └───────────────────────┘
           │                                             ▲
           │                                             │
           └──────────── CALLS (Runtime Invoc.) ─────────┘
```

### 4.1 The False-Positive Trap of Conflating Imports with Calls
In TypeScript / Next.js applications, files import modules for diverse reasons:
- Importing TypeScript type definitions or interfaces.
- Importing utility constants or icon maps.
- Importing helper functions that are never executed on specific code paths.

If a failure simulation engine treated every `IMPORTS` edge as a `CALLS` edge, injecting a failure into a common utility (e.g. `lib/utils.ts` or `lib/subscription.ts`) would immediately cascade degradation to dozens or hundreds of files across the codebase. This creates enormous false-positive blast radii, rendering the simulation engine useless for real architectural risk assessment.

### 4.2 The Rule Table Contract
The Step 53 Simulation Rule Table implements rules for actual operational interactions:
- `CALLS`: Synchronous or asynchronous invocation of a dependency.
- `QUERIES_DB` / `WRITES`: Database reads and mutations.
- `CONSUMES_EVENT` / `EMITS_EVENT`: Asynchronous event pub/sub.

It **does not match on `IMPORTS`**.

In Step 58, **Test B (IMPORTS Negative Control)** explicitly proves this:
- Target `mod:lib/subscription.ts` is seeded with `unavailable` failure (`failed`).
- The pure Taxonomy graph has an `IMPORTS` edge from `mod:app/api/users/stripe/route.ts` to `mod:lib/subscription.ts`.
- When evaluated by `runSimulationEngine`, the caller remains `healthy`! Zero downstream degradation occurs across `IMPORTS`.

## 5. Fixture-Backed Test Relationship Provenance (ADR-012)

While the Taxonomy repository contains `IMPORTS` edges, current static analysis in Phase 3 does not yet emit first-class `CALLS` edges. However, inspecting the actual pinned source code reveals a genuine, hand-verified functional dependency:

```typescript
// File: fixtures/golden/taxonomy/app/api/users/stripe/route.ts
// Line 20:
const subscriptionPlan = await getUserSubscriptionPlan(session.user.id)
```

And in `lib/subscription.ts`:
```typescript
// File: fixtures/golden/taxonomy/lib/subscription.ts
// Line 7:
export async function getUserSubscriptionPlan(userId: string): Promise<UserSubscriptionPlan>
```

### 5.1 Architecture of Separation
Rather than fabricating a `CALLS` edge in the production graph builder (which would violate Step 33 graph contracts) or relabeling `IMPORTS` (which would violate simulation semantics), Step 58 establishes ADR-012:

1. **Manifest Ground Truth**: The call site is documented with exact source coordinates in `fixtures/golden/simulation-manifest.json`:
   ```json
   {
     "edgeId": "test-edge:mod:app/api/users/stripe/route.ts->mod:lib/subscription.ts:CALLS",
     "callerCanonicalId": "mod:app/api/users/stripe/route.ts",
     "calleeCanonicalId": "mod:lib/subscription.ts",
     "edgeType": "CALLS",
     "invokedSymbol": "getUserSubscriptionPlan",
     "sourceFile": "app/api/users/stripe/route.ts",
     "sourceLine": 20,
     "sourceSnippet": "const subscriptionPlan = await getUserSubscriptionPlan(session.user.id)",
     "metadata": {
       "sync": true,
       "hasFallback": "unknown",
       "hasCircuitBreaker": "unknown"
     },
     "isTestOnly": true,
     "provenance": "test-fixture-manual-verification"
   }
   ```
2. **In-Memory Snapshot Augmentation**: In `golden-simulation.test.ts`, this test relationship is added to the in-memory `SimulationGraphSnapshot.edges` without modifying or persisting it into the production `GraphProjectionResult`.
3. **Integrity Verification**: `golden.test.ts` validates that the source file exists in the golden fixture, line 20 matches `sourceSnippet` character-for-character, and `lib/subscription.ts` actually exports `getUserSubscriptionPlan`.

## 6. Deterministic Worklist Propagation & Verification

When `runSimulationEngine` executes the scenario against the augmented snapshot:

### 6.1 Step-by-Step State Evolution
1. **Target Failure Seeding**:
   - `targetNode`: `mod:lib/subscription.ts`
   - State transition: `healthy → failed`
   - Seed causal step: `edgeId: null`, `ruleId: target_failure`, `confidence: 1.0`
   - Assumption: `"Scenario target node directly seeded as failed (unavailable)"`
   - Work queue: `[targetNode.id]`

2. **Worklist Iteration 1**:
   - Dequeues `targetNode.id`. Inspects incident edges.
   - Evaluates test edge: `mod:app/api/users/stripe/route.ts` `--CALLS-->` `mod:lib/subscription.ts`.
   - `edge.metadata`: `{ sync: true, hasFallback: "unknown", hasCircuitBreaker: "unknown" }`.
   - Rule evaluated: `CALLS+sync+no_fallback`.
   - Decision:
     - `matched`: `true`
     - `affectedNode`: `"source"` (`mod:app/api/users/stripe/route.ts`)
     - `resultingState`: `"degraded"`
     - `confidence`: `0.9` (lowered from 1.0 due to unverified fallback and circuit-breaker metadata)
     - `assumptions`:
       - `"No circuit breaker detected on app/api/users/stripe/route.ts->lib/subscription.ts call"`
       - `"No fallback handler detected on app/api/users/stripe/route.ts->lib/subscription.ts call"`
   - Monotonic update: Caller transitions `healthy → degraded`.
   - Work queue: `[callerNode.id]`.

3. **Worklist Iteration 2**:
   - Dequeues `callerNode.id`.
   - Incident edges are evaluated, but no connected dependency is impaired.
   - Work queue empties.
   - Algorithm converges in 2 iterations!

### 6.2 Causal Trail Verification
The resulting propagation path on the degraded caller is verified:
- **Hop 0**: `mod:lib/subscription.ts` (`healthy → failed`, `edgeId: null`, rule `target_failure`, confidence `1.0`).
- **Hop 1**: `mod:app/api/users/stripe/route.ts` (`healthy → degraded`, `edgeId: test-edge:...`, rule `CALLS+sync+no_fallback`, confidence `0.9`).

### 6.3 Negative Control Verification
`mod:components/site-footer.tsx` (an unrelated UI component) is asserted:
- Remains `healthy` in `nodeStates`.
- Is absent from `results` array.

### 6.4 Determinism Across Runs
Three consecutive executions of the identical scenario produce bit-for-bit identical node states, rule applications, confidence values, causal paths, and iteration counts.

## 7. Trade-offs and Future Evolution

| Architectural Choice | Trade-off / Benefit | Future Upgrade Trigger |
|---|---|---|
| **Test-only `CALLS` edge injection** | Enables realistic simulation validation without destabilizing production graph extraction. | When static extraction introduces first-class AST call-graph indexing (Phase 11 or dedicated AST expansion). |
| **Conservative metadata defaults** | When metadata is `unknown`, engine assumes synchronous without fallback (generating explicit assumptions). | When static AST analysis can verify try/catch blocks or circuit breaker libraries, upgrading confidence to 1.0. |
| **Pure in-memory engine validation** | Fast (<10s), deterministic, runs in CI without PostgreSQL requirement. | Covered in tandem with Step 54's full PostgreSQL persistence integration test suite. |

---

## 8. Summary
Step 58 proves that Fluxora's simulation engine is sound, deterministic, and rigorously distinguishes structural code imports from operational call invocations against a real, production-scale codebase.
