# 40. Architecture Explorer UI Polish

## What This Step Does

Step 40 is the final polish step for the Architecture Explorer. It makes the explorer feel complete and production-ready by adding proper feedback for every state the user can encounter:

- **Loading** — when you first open the explorer, you see a clear spinner and message instead of a blank screen
- **Ready** — the graph is loaded and fully interactive (this already existed)
- **Empty** — the query worked but returned zero nodes ("No Graph Nodes Found")
- **Analysis Not Ready** — the server hasn't finished analyzing the repository yet ("Analysis Not Ready")
- **Error** — something went wrong loading the graph, with a retry button
- **Background Refreshing** — the graph is updating in the background (thin progress bar, graph stays visible)
- **WebSocket Connected/Reconnecting/Disconnected** — small status badge in the header

## Loading vs Background Refreshing

These are fundamentally different:

- **Loading** happens when there's NO graph data yet (first visit, or after an error). The user sees a loading spinner.
- **Background Refreshing** happens when the graph is ALREADY visible and a new fetch is triggered (by a live update, filter change, or retry). The existing graph stays on screen with a subtle progress bar at the top.

The key principle: **never blank the screen when you already have useful data to show**.

## Empty vs Error

- **Empty**: The server responded successfully with `{ nodes: [], edges: [] }`. The query worked, but there's nothing to display. The user should try adjusting filters or waiting for analysis.
- **Error**: The server couldn't respond (network error, 500, auth issue). Something is broken. The user should retry.

These get different visual treatments (inbox icon vs warning icon) and different actionable guidance.

## Stale-Data Preservation

This is a crucial UX pattern: **if you already have valid graph data, don't throw it away just because a refresh failed**.

Example flow:
1. User loads graph successfully → sees 15 nodes
2. Live update triggers a refetch → progress bar appears
3. Refetch fails (network blip) → error banner appears above graph
4. User can still interact with the 15 nodes, click to inspect, pan/zoom
5. User clicks "Retry" on the banner → successful refresh → banner disappears, graph updates

## Retry

Retry is simple: it increments a counter (`liveUpdateTrigger`) that's in the dependency array of the fetch `useEffect`. This triggers the exact same fetch pipeline with the exact same context, filters, and parameters. No new endpoints, no separate code path.

## WebSocket Status

The WebSocket connection badge is informational. It tells the user whether live updates are flowing:
- "Live" (green dot) — WebSocket connected, updates will arrive in real-time
- "Reconnecting" (amber dot) — WebSocket is trying to reconnect
- "Offline" (gray dot) — WebSocket is down, but the graph is still fully usable

Critically: a WebSocket outage NEVER disables the graph. The graph was loaded via HTTP and remains interactive regardless of WebSocket state.

## Why Graph Truth Remains Backend-Authoritative

The WebSocket is an **invalidation signal**, not a data channel. When a `graph.updated` event arrives, the client doesn't try to apply the diff directly. Instead, it triggers a fresh `POST /api/v1/graph/query` to get the complete, authoritative graph from the server's recursive CTE.

This is safer because:
- The server applies RLS tenant isolation
- The server applies depth limits and confidence thresholds
- The server handles the complete traversal logic
- The client doesn't need to implement graph algorithms

## Why Refresh Failures Should Not Destroy Usable Data

Imagine you're presenting a graph in a meeting and a network blip causes a background refresh to fail. The worst possible UX would be to blank the screen and show an error. Instead:

- The graph stays visible
- A small error banner appears
- You can dismiss it or retry
- Your work continues uninterrupted

## How UI State Is Separated from Domain Graph State

The `ExplorerState` union type represents what the explorer should *render*:
- `loading` / `empty` / `not_ready` / `error` — no graph to show, render a status screen
- `ready` — graph available, render the full explorer

Separately, `isRefreshing` and `refreshError` are presentational concerns:
- `isRefreshing` controls whether the progress bar is visible
- `refreshError` controls whether the error banner is visible

And `connectionStatus` is purely informational:
- It controls what the connection badge says
- It never affects whether the graph is displayed

This separation means domain logic (graph traversal, filtering, LOD) is completely decoupled from presentation concerns (spinners, banners, badges).
