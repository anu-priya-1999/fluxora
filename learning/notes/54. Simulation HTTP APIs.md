# 54. Simulation HTTP APIs (Global Step 55)

## Overview

Global Step 55 connects Fluxora's deterministic simulation capabilities to the API layer, exposing:
- `POST /scenarios`
- `POST /scenarios/:id/run`
- `GET /simulations/:id`
- `GET /simulations/:id/results`

## Key Design Decisions & Invariants

1. **Synchronous Execution Model**:
   - `executeSimulation` in Step 54 runs synchronously and atomically.
   - The API reflects this reality by returning `200 OK` with full results rather than falsely returning `202 Accepted` with a non-existent job queue.
   - Future background job delegation can be introduced when asynchronous workers are actually provisioned.

2. **No Duplication of Propagation Logic**:
   - The route handler orchestrates authentication, request body parsing, snapshot resolution, and error mapping.
   - All propagation semantics remain in the pure Step 54 `runSimulationEngine` and transaction orchestration in `executeSimulation`.

3. **Strict Tenant & Snapshot Scoping**:
   - Tenant identity is derived strictly from verified Clerk Bearer tokens and confirmed GitHub accounts.
   - Explicit client attempts to supply `organization_id` in the request body are rejected (`400 invalid_request`).
   - Cross-tenant lookups return `404 Not Found` to prevent resource enumeration.
   - Target nodes must belong to the specified analysis run snapshot; cross-run boundary mismatches are rejected.

4. **Preserved Causal Provenance & Evidence Invariants**:
   - The results endpoint returns complete `propagation_path` arrays with structured `SimulationCausalStep` items.
   - Applied rules, explicit assumptions (e.g. unknown circuit breaker), and confidence scores are serialized intact.
   - `EvidenceWriter` writes `simulation_state` evidence records atomically in the database transaction.

5. **MVP Failure Types Only**:
   - The API layer strictly restricts `failure_type` to `"unavailable"` and `"latency"`.
   - Unsupported types such as `"capacity"` or `"removal"` are explicitly rejected with `400 unsupported_failure_type`.

6. **Idempotency & Tenant-Scoped Resolvers**:
   - Each accepted HTTP run request initializes a distinct `Simulation` record. Within each simulation execution, result persistence is idempotent via `ON CONFLICT (simulation_id, node_id) DO UPDATE`.
   - Default resource resolvers execute queries within `withTenant` transactional boundaries ensuring RLS policy compliance.
   - Scenario creation returns pure, flat `ScenarioResponse` directly without redundant wrapper properties.
