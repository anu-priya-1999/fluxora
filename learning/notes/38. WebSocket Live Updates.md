# 39. WebSocket Live Updates

Personal engineering notes on Global Step 39: Live updates, WebSockets, invalidation patterns, and real-time state synchronization.

---

## 1. WebSocket vs HTTP: When to Use Which?

When building modern web apps that show live data, there are two primary communication patterns:

1. **HTTP (Request-Response)**:
   - Client asks, server answers.
   - Ideal for queries with parameterized filters (e.g., "Give me the graph starting from Node X up to depth 3 with confidence > 0.8").
   - Stateless, cacheable, and deterministic.
   - Drawback for live updates: To know when something changed, the client has to poll repeatedly (e.g. asking every 2 seconds "Did it change? Did it change?"). This creates wasteful CPU overhead on both the database and API.

2. **WebSocket (Persistent Bidirectional Channel)**:
   - After a quick HTTP handshake, the TCP connection remains open.
   - The server can push data to the client at any time with minimal overhead (just small frame headers).
   - Ideal for real-time notifications, typing indicators, and change events.

In Fluxora, we combine both: **WebSocket for the notification signal, HTTP for the authoritative data query.**

## 2. Why Fluxora Uses WebSocket as an Invalidation Channel

A tempting but flawed architecture is trying to stream the entire updated graph—or every individual added/deleted node—over the WebSocket connection:

```
❌ Bad Idea: Stream Graph Mutations over WebSocket
Server: "Delete Edge #49" ─> Client mutates internal state
Server: "Add Node #82"   ─> Client inserts node
Problem: What if a message drops during a reconnect?
Problem: What if user had filters active?
Result:  Client graph state drifts from database reality!
```

Instead, Fluxora uses the **Invalidation Channel pattern**:
```
✅ Clean Pattern: WebSocket as Invalidation Signal
1. PostgreSQL updates the graph in a transaction.
2. An event "graph.updated" is sent over WebSocket (just a tiny signal with runId & repoId).
3. The Explorer client receives the signal: "Aha! My graph is outdated."
4. The client issues a fresh POST /api/v1/graph/query with the user's exact active filters.
5. The backend executes the authoritative recursive CTE and returns the exact truth.
```

### Why this is superior:
1. **Zero State Drift**: The client never tries to reinvent graph algorithms in JavaScript. The database recursive CTE is the single source of truth.
2. **Filter Awareness**: The backend query engine already knows how to filter by node types, edge types, depth, and confidence. An invalidation signal doesn't need to know or calculate any of that.
3. **Resilience to Dropped Messages**: If a WebSocket message is missed while a laptop lid was closed, the first query on reconnect fetches the fresh authoritative state anyway.

## 3. How Reconnects Work Without Causing a Storm

When a server reboots or WiFi blips, 10,000 connected browsers might all try to reconnect at the exact same millisecond. If they all retry in a tight loop (`while (!connected) connect()`), they DDoS the server (a "thundering herd" or "reconnect storm").

To prevent this:
1. **Exponential Backoff**: Each failed attempt doubles the wait time:
   - Attempt 1: 1 second
   - Attempt 2: 2 seconds
   - Attempt 3: 4 seconds
   - Attempt 4: 8 seconds
   - Attempt 5: 10 seconds (capped)
2. **Bounded Attempts**: Stop after 5 retries. Don't run an infinite timer.
3. **Reset on Success**: When the socket successfully opens, reset the counter to zero.

## 4. Race Conditions and Stale Responses

Imagine this scenario:
- **T = 0ms**: Run 1 finishes → WebSocket sends `graph.updated`. Refetch A starts (slow network, takes 300ms).
- **T = 50ms**: Run 2 finishes → WebSocket sends `graph.updated`. Refetch B starts (fast network, takes 50ms).
- **T = 100ms**: Refetch B finishes and renders the newest graph.
- **T = 300ms**: Refetch A finally finishes!

If you're not careful, Refetch A will overwrite Refetch B, displaying an older graph even though a newer one was already on screen!

### How we solve it:
We track the request generation with cancellation. If a new request is started before the old one finishes, the old request's callback is marked cancelled (`isCancelled = true` / generation check) and its result is safely ignored.

## 5. React Lifecycle & Cleanup Discipline

React 18 introduced Strict Mode in development, which intentionally mounts, unmounts, and remounts components to test for memory leaks and missing cleanup.

If your WebSocket effect doesn't properly clean up:
- Mount 1 opens Socket 1.
- Strict Mode unmounts Mount 1. Socket 1 stays open!
- Mount 2 opens Socket 2.
- Now every event is processed twice!

### In Step 39:
Our `createExplorerWebSocketClient` returns an explicit `close()` method:
- Clears any pending `setTimeout` reconnect timer.
- Removes all event handlers (`onopen`, `onmessage`, `onclose`, `onerror = null`).
- Calls `ws.close()`.
On component unmount, the cleanup function runs `client.close()`. No leaks, no duplicate connections.

## 6. Tenant Isolation: Why the Browser Cannot Pick Its Organization

In a multi-tenant B2B SaaS application like Fluxora, Customer A must never receive events from Customer B.

Some architectures make the mistake of having the browser send:
`ws.send(JSON.stringify({ subscribe: "org_customer_b" }))`
This is completely insecure because a malicious user could modify their browser JavaScript to subscribe to another company's updates.

In Fluxora:
1. The WebSocket connection requires a Clerk session JWT passed securely via the `Sec-WebSocket-Protocol: bearer.<jwt>` header.
2. The server cryptographically validates the JWT.
3. The server extracts the authenticated `user_id` and looks up their verified `organization_id` in PostgreSQL.
4. The server registers the socket in `WebSocketHub` under that verified `organization_id`.
5. When an event is broadcast, `WebSocketHub` only delivers it to sockets in that exact organization's bucket.

Tenant boundaries are 100% enforced server-side.
