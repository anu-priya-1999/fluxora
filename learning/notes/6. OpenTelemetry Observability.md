# Fluxora — Personal Learning Notes — Part 6 OpenTelemetry Observability

## 1. The 30-second explanation

Fluxora needs observability because API requests and asynchronous workers are long-running, distributed pieces of a system. I used OpenTelemetry as the instrumentation layer so Fluxora can produce three kinds of telemetry:

- traces — what happened and in what order
- metrics — how much/how often/how long
- logs — detailed event information

The application sends telemetry through OTLP/HTTP to an OpenTelemetry Collector. The Collector is the transport/processing boundary between the application and the eventual observability backend.

For the MVP I verified this locally without Docker:

```text
Fluxora API
    ↓
OpenTelemetry SDK
    ↓
OTLP/HTTP :4318
    ↓
OpenTelemetry Collector
    ↓
debug exporter
    ↓
traces / metrics / logs
```

The dummy endpoint generated telemetry and I verified the Collector received it.

---

## 2. Why did Fluxora need OpenTelemetry?

Without observability, I can know that an API returned 200, but I cannot easily answer:

- How long did it take?
- Where did the time go?
- How many requests are failing?
- Which worker/job is slow?
- What happened before a failure?
- Can I correlate a log with a request?

Fluxora will later have:

```text
API
workers
repository ingestion
static analysis
graph construction
impact analysis
simulation
AI reasoning
```

So observability is foundational, not an afterthought.

---

## 3. The three signals

### Traces

A trace represents one operation/request as a sequence of spans.

Example:

```text
HTTP request
   ↓
fluxora.telemetry.dummy
```

Later a real Fluxora operation could become:

```text
POST /repositories/connect
        ↓
enqueue repository.ingest
        ↓
worker
        ↓
download snapshot
        ↓
analyze repository
        ↓
persist graph
```

A trace helps me understand the complete path.

### Metrics

Metrics are numerical measurements collected over time.

Examples relevant to Fluxora:

```text
API latency
queue backlog
job failure rate
analysis duration
graph size
AI token/cost usage
```

Our HTTP instrumentation generated:

```text
http.server.request.duration
```

for the dummy endpoint.

### Logs

Logs carry detailed event information.

Our dummy endpoint emitted:

```text
fluxora.telemetry.dummy.request
```

The Collector output showed the event body, endpoint attribute, and trace/span IDs.

That correlation is important because it connects a detailed log event to the trace that caused it.

---

## 4. Why OpenTelemetry instead of vendor-specific instrumentation?

OpenTelemetry gives Fluxora a vendor-neutral instrumentation layer.

The application should not have to know whether the eventual backend is:

```text
Tempo
Jaeger-compatible backend
Prometheus-compatible metrics backend
cloud observability vendor
```

The app produces standard telemetry; the Collector/backend handles the destination.

Interview sentence:

> "I wanted instrumentation to be vendor-neutral, so I put OpenTelemetry between the application and the observability backend."

---

## 5. Why use an OpenTelemetry Collector?

The application sends telemetry to the Collector instead of coupling the application directly to one final backend.

```text
App
 ↓
OTLP
 ↓
Collector
 ↓
processing/routing
 ↓
backend(s)
```

Benefits:

- central telemetry boundary
- easier backend changes
- centralized processing
- centralized routing
- less vendor coupling
- application configuration stays simpler

For my local verification the Collector used the `debug` exporter so I could visibly prove the signals arrived.

---

## 6. Why OTLP?

OTLP is the transport we use between Fluxora and the Collector.

For this local setup:

```text
OTLP/HTTP
localhost:4318
```

The important mental model is:

```text
OpenTelemetry SDK = creates telemetry
OTLP = transports telemetry
Collector = receives/processes/routes telemetry
Backend = stores/visualizes telemetry
```

Do not confuse these four layers in an interview.

---

## 7. Why `@fluxora/observability`?

I deliberately created a shared package:

```text
packages/observability/
```

instead of putting OpenTelemetry configuration independently into API and worker code.

The dependency direction is:

```text
apps/api ───────┐
                ├──> @fluxora/observability
apps/workers ───┘
```

This gives Fluxora one place for:

- configuration
- SDK creation
- exporters
- tracing helpers
- telemetry signal helpers

It also prevents OpenTelemetry-specific implementation details from spreading throughout the application.

## 8. Service identity

The SDK resource includes:

```text
service.name
service.version
deployment.environment.name
```

For the API we verified:

```text
service.name = @fluxora/api
service.version = 0.0.0
deployment.environment.name = development
```

Why this matters:

If I have many services later:

```text
@fluxora/api
@fluxora/workers
@fluxora/ingestion
@fluxora/analysis
```

I need telemetry to be attributable to the service that produced it.

Interview sentence:

> "Service identity is attached as resource metadata rather than manually repeated on every signal."

## 9. Why initialize OpenTelemetry before the application?

This was an important implementation detail.

Instrumentation has to be initialized before the modules being instrumented are loaded.

Our Node startup became:

```text
Node process starts
    ↓
telemetry.ts is imported
    ↓
OTel initialization / instrumentation registration
    ↓
application module loads
    ↓
HTTP server starts
```

The API start command is:

```text
node --experimental-strip-types --import ./src/telemetry.ts src/server.ts
```

The `--import` preload ensures the telemetry initialization happens before the main API module graph is evaluated.

---

## 10. Why was this initially tricky?

The API imports Node's HTTP module through:

```text
apps/api/src/http/server.ts
```

so automatic HTTP instrumentation must be active before the HTTP module is evaluated.

We initially tried the older loader-hook approach and hit:

```text
ERR_MODULE_NOT_FOUND
Cannot find package '@opentelemetry/instrumentation'
```

The API also runs on Node 24.18.0.

We corrected the startup design to use Node's preload/import mechanism and explicitly installed the instrumentation package.

Learning:

> "In Node ESM, instrumentation timing matters. It is not enough to initialize telemetry after the application modules have already loaded."

---

## 11. Why automatic HTTP instrumentation?

I used:

```text
@opentelemetry/instrumentation-http
```

instead of manually creating a span around every HTTP request.

That gives automatic HTTP-level telemetry.

The Collector verified:

```text
http.server.request.duration
```

for the dummy request.

This means the instrumentation can cover ordinary HTTP behavior without every route having to reinvent the same instrumentation.

---

## 12. Manual instrumentation vs automatic instrumentation

### Automatic instrumentation

Good for common libraries/frameworks:

```text
Node HTTP
database clients
HTTP clients
```

### Manual instrumentation

Good for Fluxora-specific business operations:

```text
fluxora.telemetry.dummy
repository.ingestion
analysis
simulation
AI reasoning
```

The dummy endpoint intentionally demonstrates manual instrumentation with a Fluxora-specific span.

Interview sentence:

> "I use automatic instrumentation for infrastructure-level behavior and manual spans for business-level operations where the generic library instrumentation doesn't express the actual workflow."

The log records from the dummy endpoint included:

```text

```

That means I can conceptually move from:

```text

```

## 16. The worker observability design

The worker does not currently have a standalone process entrypoint. It has the reusable:

```text
JobWorker
```

class.

I instrumented job execution so a job can have a span:

```text
fluxora.worker.job.process
```

with attributes such as:

```text
fluxora.worker.id
fluxora.job.id
fluxora.job.type
fluxora.job.organization_id
fluxora.job.attempt
```

This is important because Fluxora's Step 6 queue is retryable and idempotent.

Later I want to be able to answer:

- Which job was slow?
- Which attempt failed?
- Which worker processed it?
- Which tenant did it belong to?
- Was it retried?

---

## 17. Why tenant information needs care

Fluxora is multi-tenant.

Telemetry can accidentally become a data-leak surface if sensitive tenant information is emitted indiscriminately.

Therefore:

```text
tenant-aware application security
        +
careful telemetry attributes
```

I should avoid putting secrets, tokens, repository contents, or sensitive payloads into telemetry.

Interview sentence:

> "Observability is part of the security boundary; I don't treat logs and traces as a safe place to dump arbitrary request or tenant data."

---

## 18. Important mistake I made during Step 7

The first version of `signals.ts` created telemetry instruments at module-load time:

```text
getTracer()
getMeter()
getLogger()
```

before the SDK provider was fully registered.

That can result in no-op/global-provider behavior.

The correction was to resolve the tracer/meter/logger lazily when the signal is actually emitted.

Learning:

> "Telemetry provider initialization order matters just as much as application initialization order."

This is an interview-worthy debugging story.

---

## 19. Another debugging lesson: self-instrumentation

HTTP auto-instrumentation also sees HTTP requests made by the telemetry exporters themselves.

So the application can observe its own:

```text
POST localhost:4318
```

export calls.

That creates noisy telemetry such as:

```text
http.client.request.duration
```

and can make debugging harder.

This is an observability design consideration:

> "Instrumentation should not create an infinite or noisy telemetry feedback loop."

# Interview Questions & Answers

## Q1. What is OpenTelemetry?

> "OpenTelemetry is a vendor-neutral observability framework. In Fluxora I use it to instrument the API and workers and produce traces, metrics, and logs, which are exported through OTLP to an OpenTelemetry Collector."

## Q2. Why not just use logs?

> "Logs are useful for detailed events, but they don't naturally show the complete causal path of a request. Traces give me the workflow, metrics show aggregate behavior, and logs provide detailed context. Together they give a much more complete picture."

## Q3. What is a span?

> "A span represents one timed operation inside a trace. For example, my dummy endpoint creates the `fluxora.telemetry.dummy` span."

## Q4. What is a trace?

> "A trace represents the end-to-end operation and contains one or more spans."

## Q5. What is OTLP?

> "OTLP is the OpenTelemetry protocol used to transport telemetry from the application SDK to the Collector or another compatible endpoint."

## Q6. Why use a Collector?

> "It decouples the application from the final backend and gives me one place for routing, processing, and exporting telemetry."

## Q7. Why is service.name important?

> "Because observability systems need to know which logical service emitted the telemetry. In Fluxora the API identifies itself as `@fluxora/api`."

## Q8. Why initialize OTel before the application?

> "Automatic instrumentation needs to patch/register the target modules before they are loaded. With Node ESM, startup ordering is especially important."

## Q9. Why did you create a shared observability package?

> "To keep telemetry configuration centralized and prevent vendor-specific OpenTelemetry code from being scattered through the API and worker implementations."

## Q10. How did you test it?

> "I ran the API, started a local OpenTelemetry Collector, called a dummy endpoint, and verified that the Collector received ResourceLogs, ResourceSpans, and ResourceMetrics for `@fluxora/api`."

## Q11. How would you instrument a real repository analysis job?

> "I would create a root job span and child spans for ingestion, parsing, graph extraction, persistence, and AI reasoning. Metrics would capture durations, failure rates, queue depth, and AI usage. Logs would capture detailed failure context while avoiding secrets and raw repository content."

## Q12. What would you monitor in production?

```text
API:
latency
error rate
request volume

Workers:
queue depth
job duration
retry count
dead-letter count
worker failures

Analysis:
ingestion duration
analysis duration
graph size

AI:
request count
latency
errors
token/cost usage
```
