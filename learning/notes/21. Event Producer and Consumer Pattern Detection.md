# Fluxora Step 22 — Learning Notes: Event Producer and Consumer Pattern Detection

## 1. Role in Code Intelligence Pipeline

Event producer and consumer detection (`docs/architecture/05-component-responsibilities.md §5.5`, `docs/architecture/17-implementation-roadmap.md §Phase 3 Step 5`) is the fifth milestone of Phase 3 (Code Intelligence).

While prior steps answered:
- **Step 18**: *"What programming languages and frameworks are present?"*
- **Step 19**: *"What symbols exist in source files?"*
- **Step 20**: *"How are modules connected through imports and exports?"*
- **Step 21**: *"What HTTP API routes and Express routers are defined?"*

Step 22 answers:
> *"Where are event-driven asynchronous message producers and consumers invoked, and what event names, topics, channels, or queues do they target?"*

This connects static code analysis to asynchronous, decoupled message architectures (event-driven microservices, background job dispatchers, Pub/Sub channels).

---

## 2. Invariant: Deterministic Static Analysis vs. Runtime Execution

Customer repository code is untrusted:
- **Never Run Code**: Emitters, brokers, queues, and listeners are never instantiated or executed.
- **AST Pattern & Provenance Matching**: Calls like `emit()`, `publish()`, `send()`, and `consume()` are only recognized when their receivers are proven to originate from known event libraries (`events`, `redis`, `kafkajs`, `amqplib`).
- **Dynamic Expression Safety**: If an event topic is computed dynamically (e.g. `client.publish(getTopicName(), data)`), it is recorded as `null` with `status: "unresolved"`. Code is never evaluated.
- **Reproducible Findings**: Given identical snapshot inputs, detected producers, consumers, source locations, and IDs are 100% deterministic.

## 3. Ecosystem Call Shapes

### 1. Node.js EventEmitter
- Producer: `emitter.emit("event", ...)` or `this.emit("event", ...)` in an EventEmitter subclass.
- Consumer: `emitter.on("event", fn)`, `emitter.once("event", fn)`, `emitter.addListener("event", fn)`.

### 2. Redis Pub/Sub
- Producer: `client.publish("channel", ...)`
- Consumer: `client.subscribe("channel", fn)`, `client.pSubscribe("pattern", fn)`.

### 3. KafkaJS
- Producer: `producer.send({ topic: "...", messages: [...] })`
- Consumer: `consumer.subscribe({ topic: "..." })`, `consumer.run({ eachMessage: ... })`, `consumer.run({ eachBatch: ... })`.

### 4. RabbitMQ / amqplib
- Producer: `channel.publish(exchange, routingKey, ...)`, `channel.sendToQueue(queue, ...)`.
- Consumer: `channel.consume(queue, fn)`.

---

## 4. False-Positive Strategy

Generic names like `emit`, `publish`, and `consume` are common across non-pubsub domains (e.g. WebSocket clients, reactive streams, CMS publishing tools, stream iterators).

Fluxora prevents false positives by requiring:
1. An explicit import or `require()` of the respective library (`events`, `node:events`, `redis`, `ioredis`, `kafkajs`, `amqplib`).
2. An AST binding showing the variable was instantiated from the library constructor or factory method (`new EventEmitter()`, `createClient()`, `kafka.producer()`, `conn.createChannel()`).
3. Class heritage analysis confirming subclassing of `EventEmitter`.
4. Without this provenance, any invocation of `.emit()`, `.publish()`, etc., is rejected.
