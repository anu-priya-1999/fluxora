# Fluxora — Personal Learning Notes — Part 7 CI/CD and Production Deployment

## 1. The 30-second explanation

Fluxora now has a real CI/CD foundation.

The important idea is:

```text
A commit is not trusted just because it exists.

It must pass automated quality gates,
then be delivered to a runtime,
then be verified as healthy.
```

My current Fluxora path is:

```text
GitHub
  ↓
GitHub Actions
  ↓
lint + typecheck + test + build
  ↓
main
  ├── Vercel → Next.js web
  └── Render → API
                   ↓
                PostgreSQL
```

The API and frontend are independently hosted because they are different application responsibilities.

---

# 2. What is CI?

Continuous Integration means integrating changes frequently while automatically checking whether those changes remain healthy.

In Fluxora, CI currently checks:

```text
lint
 ↓
typecheck
 ↓
test
 ↓
build
```

The CI workflow is in:

```text
.github/workflows/ci.yml
```

It runs for:

```text
pull_request
push to main
```

### My interview answer

> "Fluxora's CI pipeline runs on pull requests and main-branch pushes. It installs dependencies from the frozen pnpm lockfile, then runs linting, TypeScript type checking, tests, and the production build. The goal is to stop broken code from being treated as an approved integration point."

---

# 3. What is CD?

Continuous Delivery/Deployment is the process of getting validated code into an environment where it runs.

Current Fluxora delivery:

```text
main
 ├── Vercel → web
 └── Render → API
```

Render is configured for automatic deployment on commit.

Vercel is connected to the web application deployment.

### Important interview nuance

I should **not** say:

> "Fluxora has a complete enterprise CI/CD promotion system."

The accurate statement is:

> "I implemented a working CI/CD foundation and hosted frontend/API deployment. A fuller staging-promotion-rollback pipeline is future hardening."

---

# 4. Why does Fluxora need CI/CD?

Without CI/CD, every deployment becomes manual:

```text
change code
 ↓
remember tests
 ↓
remember build
 ↓
remember environment variables
 ↓
manually deploy
 ↓
manually check health
```

That creates human error and inconsistent releases.

With CI/CD:

```text
commit
 ↓
automated verification
 ↓
repeatable delivery
 ↓
health verification
```

This makes the deployment process reproducible.

---

# 5. Why did I choose GitHub Actions for CI?

Fluxora already lives in GitHub.

Advantages for this project:

- the workflow lives with the source code
- pull requests can trigger quality gates
- main-branch pushes can trigger verification
- no separate CI vendor is required for the MVP
- workflow configuration is version controlled

The key architecture idea is:

```text
source of truth = GitHub
CI definition   = repository code
```

---

# 6. Why `pnpm/action-setup` and Node setup?

Fluxora uses pnpm as the workspace package manager.

The CI runner must use the same package manager version as the project.

We use:

```text
pnpm 10.34.5
Node 24
```

The workflow uses the official GitHub Actions setup actions for pnpm and Node.

Interview point:

> "I pinned the package-manager version because changing package-manager versions can change lockfile interpretation and dependency installation behavior."

---

# 7. Why use a frozen lockfile?

The lockfile represents the exact dependency graph we committed.

```text
package.json
      +
pnpm-lock.yaml
      ↓
reproducible dependency install
```

With:

```text
pnpm install --frozen-lockfile
```

CI fails rather than silently modifying the lockfile.

This protects against dependency drift between developer machines and CI.

---

# 8. Why lint?

Linting catches classes of problems that TypeScript does not necessarily catch.

Examples:

- unused variables
- problematic patterns
- framework-specific mistakes
- consistency issues
- unsafe or suspicious constructs depending on configured rules

It is cheap compared with debugging the same issues after deployment.

---

# 9. Why typecheck?

TypeScript type checking validates the program's declared type relationships.

Important distinction:

```text
lint
≠
typecheck
```

Lint is rule/pattern oriented.

Typecheck asks whether the TypeScript program satisfies its type constraints.

Fluxora runs both.

---

# 10. Why tests?

Tests protect behavior, not just syntax.

Current Step 8 CI runs the repository test command.

The existing infrastructure test suite reported:

```text
7 passed
0 failed
```

This is particularly important because Fluxora already contains distributed-system-style logic such as:

- job ownership
- retry behavior
- idempotency
- tenant isolation
- object-storage behavior

A deployment pipeline should not reduce validation to compilation only.

---

# 11. Why build if typecheck already passed?

Because typechecking does not prove that the production bundler/build pipeline works.

For the Next.js app, the production build can catch:

- bundling failures
- invalid imports
- framework build errors
- production-only compilation problems
- asset/build configuration issues

So:

```text
typecheck = program type correctness
build     = production artifact generation
```

They answer different questions.

# 12. The API build-script lesson

I initially considered a Render build command containing:

```text
pnpm --filter @fluxora/api build
```

Then I inspected `apps/api/package.json` and found that there is **no `build` script**.

The actual API scripts are:

```json
"start": "node --experimental-strip-types --import ./src/telemetry.ts src/server.ts",
"typecheck": "tsc --noEmit -p tsconfig.json"
```

That mattered.

Instead of inventing a fake build pipeline, we use:

```text
pnpm install --frozen-lockfile
  ↓
pnpm db:migrate
  ↓
pnpm --filter @fluxora/api typecheck
```

and then start the API directly.

### Interview lesson

> "I aligned deployment commands with the package's actual runtime model instead of forcing every service into a compiled-artifact pattern."

# 13. Why Vercel for the frontend?

Fluxora's web application is Next.js.

Vercel is optimized for deploying Next.js applications and provides a clean Git-connected workflow for the frontend.

The architecture becomes:

```text
browser
  ↓
Vercel
  ↓
Next.js
```

This lets frontend delivery evolve independently from the API runtime.

---

# 14. Why Render for the API?

The API is a Node service with responsibilities that are distinct from the frontend:

- authentication verification
- authorization
- tenant checks
- database operations
- job orchestration
- graph reads
- analysis-result reads

Keeping it as a separately deployed service gives it an independent runtime boundary.

The architecture is:

```text
Next.js web
    ↓
Fluxora API
    ↓
PostgreSQL
```

Later the API can interact with:

```text
Redis
object storage
workers
```

without requiring the browser-facing application to own those responsibilities.

---

# 15. Why not run the API in Vercel too?

The architecture intentionally keeps frontend and backend responsibilities separate.

The API is expected to grow into a service that orchestrates jobs and reads heavy analysis results.

Workers also need a separate execution model later.

Separating the API now gives us:

- independent scaling
- independent deployment
- clearer security boundaries
- clearer operational boundaries
- a natural place for asynchronous job orchestration

It is an architectural choice, not just a hosting preference.

# 16. Why is the Render Root Directory blank?

Because Fluxora is a monorepo.

The API imports:

```text
@fluxora/db
@fluxora/observability
@fluxora/shared-types
```

Those packages live outside:

```text
apps/api
```

So Render needs access to the repository root and the workspace lockfile.

We use:

```text
root directory = repository root
```

and then target the API with:

```text
pnpm --filter @fluxora/api ...
```

---

# 17. Why does the API use `0.0.0.0`?

This was an important networking concept.

`127.0.0.1` means the local loopback interface.

`0.0.0.0` means bind to all available interfaces.

For a public hosted service:

```text
server
  ↓
bind 0.0.0.0
  ↓
Render can route traffic to it
```

A server bound only to `127.0.0.1` could be unreachable from the platform's routing layer.

Render documents the requirement for web services to bind to `0.0.0.0`.

---

# 18. Why does the API read `PORT`?

A hosting platform owns the externally allocated port.

So the API should not assume:

```text
4000 forever
```

Instead Fluxora now uses the runtime-provided `PORT` first:

```text
PORT
 ↓
API_PORT fallback
 ↓
4000 default
```

This preserves local development while satisfying the hosted environment.

---

# 19. Why is `NODE_ENV` development locally but production on Render?

Because environment is runtime configuration.

Local:

```text
NODE_ENV=development
```

Render:

```text
NODE_ENV=production
```

The code is the same.

The environment is different.

Mental model:

```text
same source code
       │
       ├── local environment
       │      development
       │
       └── hosted environment
              production
```

This is normal deployment practice.

---

# 20. Why should secrets live in Render instead of Git?

Secrets should not become part of repository history.

Fluxora uses runtime environment configuration for values such as:

```text
DATABASE_URL
CLERK_SECRET_KEY
CLERK_AUTHORIZED_PARTIES
```

The repository contains configuration contracts/examples, not actual production secrets.

This also allows the same source code to run against different environments.

# 23. Why can't Render use my local PostgreSQL?

My local database is:

```text
localhost:5432/fluxora_dev
```

That address only works from the local machine.

From Render, `localhost` means the Render runtime itself.

So:

```text
Render API
   X
localhost:5432 on my PC
```

The correct architecture is:

```text
Render API
   ↓
Hosted PostgreSQL
```

The connection is supplied through:

```text
DATABASE_URL
```

---

# 24. Why did we need a hosted Postgres database?

Because the API's production health check intentionally depends on database connectivity.

The check does:

```sql
SELECT 1
```

So the hosted API needs a hosted database endpoint.

This gives a real runtime architecture:

```text
API
 ↓
Database
```

rather than a fake deployment with no persistent backend.

---

# 25. Why is `/healthz` unauthenticated?

Render needs to determine whether the service is healthy before normal user traffic is considered ready.

If the health endpoint required a user login, the infrastructure would need application credentials just to know whether the server is alive.

So `/healthz` is a small infrastructure-facing endpoint.

It intentionally does not expose business data.

It checks:

```text
HTTP process
   +
critical DB connectivity
```

---

# 26. Why does `/healthz` execute `SELECT 1`?

A process can be alive while its database dependency is broken.

For example:

```text
Node process = running
Database = unavailable
```

A pure process-level check would report healthy even though the API cannot perform meaningful work.

By running:

```sql
SELECT 1
```

we test a critical dependency.

This is an application-level readiness check.

Render's health-check documentation explicitly gives this type of dependency check as an example of useful health behavior.

# 29. Does every commit create a GitHub Actions run?

No.

A Git commit is version history.

A workflow run happens when a commit causes an event matching the workflow's trigger rules.

Current workflow:

```text
pull_request
push to main
```

Therefore:

```text
arbitrary local commit
        ≠
action run
```

until the corresponding GitHub event matches the workflow trigger.

# 31. Why did the commit hash change during cherry-pick?

The hosted-runtime change originally existed as:

```text
84... / a541366
```

on the temporary branch.

After cherry-picking onto `main`, Git created a new commit object:

```text
83b6602
```

This is normal because a commit hash includes parent/history metadata.

The content can be the same while the commit identity changes when the parent changes.

Interview answer:

> "Cherry-pick replays a change onto a different parent, so the resulting commit gets a new SHA."

# 33. Why did Render use a Free instance?

The current goal was to validate the hosted architecture without immediately adding a server bill.

Render's current documentation says Free services are intended for testing, hobby projects, and previewing the platform rather than production workloads.

Important current limitations include:

- spin-down after 15 minutes of inactivity
- about one minute to wake
- 750 included Free instance-hours per workspace per calendar month
- one instance only
- no persistent disk
- no SSH access
- Free Postgres expiration after 30 days

Source: https://render.com/docs/free

Therefore:

```text
Free
= current deployment validation

Production paid tier
= future always-on workload
```

# 36. Interview question: "Why separate frontend and backend deployments?"

Answer:

> "The frontend and backend have different responsibilities and scaling characteristics. The Next.js application is optimized for frontend delivery, while the API owns authentication verification, authorization, tenancy, persistence, and job orchestration.
