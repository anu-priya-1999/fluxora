# 41. GitHub Pull Request Webhook Handling

## What Is a Webhook?

A webhook is an HTTP-based push notification mechanism where an external service (the event producer, here GitHub) sends an HTTP POST request to a pre-configured URL on your server (the event consumer) when an event occurs.

Instead of your server polling GitHub every few seconds asking "did anyone open a pull request?", GitHub pushes the event to Fluxora the moment it happens. This provides:
- **Instant reactivity**: PR impact analysis can begin within milliseconds of a PR being opened.
- **Resource efficiency**: Zero polling traffic or unnecessary API calls when repositories are idle.

## GitHub Webhook Delivery

When a user opens or synchronizes a pull request on a connected GitHub repository, GitHub's webhook engine (`GitHub-Hookshot`) packages the event and sends an HTTP POST request to Fluxora's webhook endpoint (`/api/v1/webhooks/github`).

The request includes specific HTTP headers:
- `X-GitHub-Event`: The name of the event (e.g. `pull_request`, `push`, `issues`).
- `X-Hub-Signature-256`: An HMAC-SHA256 signature generated by GitHub using your shared webhook secret (`sha256=<hex-digest>`).
- `X-GitHub-Delivery`: A unique GUID identifying this specific delivery attempt (e.g. `72d3162e-cc78-11e3-81ab-4c9367dc0958`).
- `Content-Type`: `application/json`.

## HMAC Signature Verification & Why Raw Bodies Matter

### What Is HMAC?
HMAC (Hash-based Message Authentication Code) combines a cryptographic hash function (SHA-256) with a secret key known only to GitHub and Fluxora. GitHub computes:
$$\text{HMAC} = \text{HMAC-SHA256}(\text{rawBody}, \text{secret})$$

When Fluxora receives the request, it recomputes the HMAC-SHA256 over the exact same raw payload and compares it to GitHub's `X-Hub-Signature-256` header.

### Why Raw Request Bodies Matter
HMAC operates at the **byte level**.
If you parse the JSON body into an in-memory JavaScript object first and then try to re-serialize it with `JSON.stringify(parsed)` to verify the signature:
- Key order might change (`{"a":1,"b":2}` vs `{"b":2,"a":1}`).
- Whitespace or indentation differs.
- Unicode character escaping or float representations may differ.

Any difference—even a single whitespace byte—completely changes the SHA-256 digest!
Therefore, you must capture the **raw, unparsed bytes (`Buffer`) directly from the HTTP incoming stream** before any JSON parsing.

### Timing-Safe Equality
When comparing the computed digest with the provided signature, standard string comparison (`a === b`) is vulnerable to **timing attacks**:
- `===` compares character-by-character and returns `false` on the first mismatch.
- An attacker can measure request duration down to microseconds to guess characters one by one.

Using `crypto.timingSafeEqual(sigBuffer, digestBuffer)` ensures comparison time is constant regardless of where or whether bytes differ, closing timing side channels completely.

## Why Webhook Handlers Must Be Fast

GitHub expects webhook endpoints to return an HTTP 2xx response within **10 seconds** (recommended under 1–2 seconds).
If your webhook endpoint performs expensive work synchronously (such as cloning a repository, extracting ASTs, computing graph diffs, or traversing dependencies):
1. **GitHub Timeout**: GitHub terminates the HTTP connection after 10 seconds and logs a delivery failure.
2. **Delivery Retries**: GitHub retries failed webhooks, potentially spawning duplicate heavy analyses that overwhelm server CPU and memory.
3. **HTTP Thread Starvation**: Long-running synchronous webhook handlers block API server worker threads and degrade API responsiveness.

## Asynchronous Job Handoff

The proper architecture for webhook processing is:
```
Webhook Arrives → Verify Signature → Validate Schema → Enqueue Job → Respond 200 OK
                                                          ↓
                                           Worker Fleet Picks Up Job Later
```
The HTTP handler acknowledges receipt quickly, ensuring GitHub is satisfied and freeing HTTP connections. The actual analysis work is processed by the background worker fleet.

## Retries & Idempotency

GitHub webhooks are delivered with **at-least-once delivery guarantees**. GitHub will retry a delivery if:
- The network drops before receiving the response;
- The server returns a 5xx error;
- The response takes longer than 10 seconds.

If GitHub delivers the same webhook twice:
- Both deliveries carry the **identical `X-GitHub-Delivery` GUID**.
- Fluxora uses `pull_request.webhook:${deliveryId}` as the `idempotency_key` on the PostgreSQL `jobs` table.
- PostgreSQL's `ON CONFLICT (organization_id, idempotency_key) DO UPDATE SET id = jobs.id` ensures only one job is ever created in the queue.
- The second delivery receives the existing job ID and returns 200 OK, preventing redundant downstream work.

## Installation-to-Tenant Association & Trust Boundaries

A GitHub webhook is an **unauthenticated server-to-server request**. It does not carry a Clerk user JWT or a session cookie.

### Trust Boundary Rule
**Never trust client-supplied tenant identifiers in a webhook.**
- An attacker or malformed payload could include `organization_id: "victim-org-uuid"`.
- If the server used this property, one tenant could trigger actions in another tenant's account.

### Authoritative Tenant Mapping
Fluxora resolves tenancy using the cryptographic trust chain:
1. GitHub proves authenticity via HMAC using the GitHub App's secret.
2. The payload contains GitHub's authoritative `installation.id`.
3. Fluxora queries its internal `github_installations` table where installations were previously connected by authenticated tenant owners.
4. The tenant (`organization_id`) is retrieved from PostgreSQL.
5. If the installation ID is unknown or not connected to any Fluxora organization, the webhook is rejected (`404 Not Found`) and **no tenant-scoped job is created**.
