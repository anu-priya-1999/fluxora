# 36. Node Inspector Panel and Evidence Trail

## 1. Purpose and Role of Step 36

Global Step 36 brings verified provenance directly to the engineer's fingertips in the Architecture Explorer.

In a software digital twin, visual nodes on a graph are meaningless unless engineers can instantly verify *why* a node exists and inspect the exact lines of source code that produced it. The `NodeInspectorPanel` and `EvidenceTrail` provide this transparency by projecting server-verified attributes and AST coordinates alongside the graph canvas.

---

## 2. Selection Architecture: Minimal Shared State

Rather than introducing an external state library (like Zustand or Redux), selection state is owned at the minimal common parent: `ArchitectureExplorerClient`.

```
ArchitectureExplorerClient
  ├── selectedNodeId: string | null
  │
  ├── GraphCanvas (receives selectedNodeId, onNodeClick, onPaneClick)
  └── NodeInspectorPanel (receives selectedNode, evidence, onClose)
        └── EvidenceTrail (receives evidence, selectedNodeId)
```

- **Select**: Clicking a node sets `selectedNodeId = node.id`.
- **Replace**: Clicking another node sets `selectedNodeId = otherNode.id`.
- **Clear**: Clicking the canvas background pane or clicking "Clear" in the inspector header resets `selectedNodeId = null`.
- **Derived Node**: The inspector receives `selectedNode = graph.nodes.find(n => n.id === selectedNodeId) ?? null` deterministically.

---

## 3. Explicit Evidence Association Rule

The browser never guesses or infers evidence relationships. Evidence is associated strictly using:

$$\text{match} = (\text{evidence.subject\_type} = \text{"graph\_node"}) \land (\text{evidence.subject\_id} = \text{selectedNode.id})$$

Under this invariant:
- Edge evidence (`subject_type = "graph_edge"`) is strictly ignored.
- Evidence belonging to other nodes or other subject types (`impact_finding`, `simulation_state`) is strictly ignored.
- No secondary HTTP request or database query is performed; evidence is sliced directly from the existing `GraphQueryResponse.evidence` collection.

---

## 4. Deterministic Evidence Ordering

To ensure reproducible UI rendering across renders and browser engines, evidence is sorted deterministically using a multi-key comparator:

1. **`file_path`**: Lexicographical ascending (`a.file_path.localeCompare(b.file_path)`).
2. **`line_start`**: Numerical ascending (`(a.line_start ?? -1) - (b.line_start ?? -1)`).
3. **`line_end`**: Numerical ascending (`(a.line_end ?? -1) - (b.line_end ?? -1)`).
4. **`id`**: Lexicographical ascending tie-breaker (`a.id.localeCompare(b.id)`).

Timestamps and arbitrary rankings are never used.

---

## 5. Resilient Coordinate and Metadata Formatting

- **Coordinate Formatting (`formatCoordinates`)**:
  - Full range: `Lines 10–25, Col 1–50`
  - Single line with column range: `Line 42, Col 5–15`
  - Line only range: `Lines 15–20`
  - Single line: `Line 42`
  - Missing coordinates: safely returns `null` without throwing or rendering invalid placeholders.
- **Metadata Protection (`safeFormatMetadataValue`)**:
  - Primitives and booleans render as clean strings.
  - JSON objects and arrays render cleanly up to 200 characters; oversized payloads are safely truncated with `...` to prevent UI overflow.

---

## 6. Security and System Boundaries

- `apps/web` does **not** import `@fluxora/db`.
- No new API endpoints or database connections were added.
- Customer code is never executed in the browser; metadata and evidence paths are treated as presentational strings.
- Tenancy is preserved entirely through the backend's verified Clerk token and PostgreSQL Row-Level Security (RLS).
