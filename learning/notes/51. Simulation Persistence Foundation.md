# 52. Simulation Persistence Foundation

## Overview & System Role

Global Step 52 establishes the **Simulation Persistence Foundation**, marking the beginning of **Phase 8: Simulation** in the Fluxora Engineering Roadmap (`docs/architecture/17-implementation-roadmap.md`).

Fluxora is an AI-powered software digital twin. While Phase 4 built the structural code dependency graph, Phase 6 established pull request blast-radius impact analysis, and Phase 7 hardened the evidence engine, Phase 8 enables engineers to perform deterministic what-if scenario simulations:
> *"What happens if the Payment Gateway becomes unavailable?"*
> *"What happens if Redis latency degrades by 800ms?"*

Step 52 builds the persistence layer and domain contracts that store simulation hypotheses, execution runs, and node-level outcomes without prematurely entangling rule evaluation or graph traversal logic.

## 1. The Core Triad: Scenario, Simulation, and SimulationResult

```
┌──────────────────────────────────────────────────────────────┐
│                           Scenario                           │
│  "What hypothesis are we testing and what is the target?"   │
│  - target_node_id, failure_type, parameters, name            │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               │ 1 : N (executed across graph runs)
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                          Simulation                          │
│     "When did we run this scenario against which graph?"     │
│  - scenario_id, analysis_run_id, status                      │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               │ 1 : N (node-level outcomes)
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                       SimulationResult                       │
│    "What was the resulting state of each affected node?"     │
│  - node_id, resulting_state, propagation_path, rule_applied, │
│    assumptions, confidence                                   │
└──────────────────────────────────────────────────────────────┘
```

### Why Three Separate Entities?
1. **Hypothesis Reuse (`Scenario`)**:
   In production architectures, resilience scenarios are standing questions (e.g., *"Third-party KYC API fails"*, *"Order database read-replica lags"*). Engineers do not want to redefine the hypothesis every time they push a commit. A `Scenario` persists independently of any specific graph snapshot.
2. **Snapshot-Isolated Execution (`Simulation`)**:
   Software graphs change with every commit. Running Scenario S against Commit A produces Simulation 1. After a developer adds a fallback cache or circuit breaker, running Scenario S against Commit B produces Simulation 2. Comparing Simulation 1 and Simulation 2 proves architectural hardening deterministically.
3. **Discrete Structural Evidence (`SimulationResult`)**:
   Complex distributed failures affect multiple downstream services in different ways. Some degrade (`degraded`), some become completely unreachable (`failed`), while others remain vulnerable to cascade collapse (`at_risk`). Modeling results per-node enables fine-grained visual overlays and precise evidence auditing.

## 2. Key Architectural Invariants

### A. The Analysis-Run Snapshot Boundary
A simulation must never mix a target node from graph version $V_1$ with propagation results evaluated against graph version $V_2$.
- The repository strictly validates that `Scenario.target_node_id` exists in the graph snapshot of `Simulation.analysis_run_id`.
- Every node in `SimulationResult` is verified to belong to that same `analysis_run_id`.
- Mismatched runs are rejected with `SimulationPersistenceValidationError`.

### B. Tenancy & Row-Level Security (RLS)
- Multi-tenant isolation is enforced at the database hardware layer with PostgreSQL `FORCE ROW LEVEL SECURITY`.
- `scenarios` directly checks `organization_id = fluxora_current_org_id()`.
- `simulations` joins through `scenarios` via `fluxora_scenario_in_current_tenant()`.
- `simulation_results` joins through `simulations` via `fluxora_simulation_in_current_tenant()`.
- Cross-tenant queries return empty results or throw typed not-found errors; cross-tenant writes fail RLS security checks.

### C. Domain Enum Bounding vs. Rule Scope
- The database schema supports all 4 domain failure types: `unavailable`, `latency`, `capacity`, and `removal`.
- Per `02-product-scope.md`, the MVP simulation rule table (Step 53) strictly implements `infra-unavailable` and `latency-degradation`.
- Supporting the full domain vocabulary in the database now prevents unnecessary breaking migrations in future steps.

### D. Idempotency & Batch Persistence
- `simulation_results` contains a composite uniqueness constraint: `UNIQUE (simulation_id, node_id)`.
- Batch saves use `ON CONFLICT (simulation_id, node_id) DO UPDATE`, allowing background workers to safely retry simulation writes without duplicating records.
