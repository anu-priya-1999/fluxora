# 58. Model Gateway Foundation: Architecture, Resilience, and Observability

## 1. Introduction & Context

In a production AI platform like Fluxora, the model gateway is the single controlled boundary between application code and external Large Language Model (LLM) APIs.

A common pitfall in AI applications is scattering direct SDK calls (e.g., `anthropic.messages.create`) across controllers, workers, and background jobs. This leads to:
- Fragmented retry and rate-limiting logic.
- Leaked credentials in stack traces and logs.
- Unmonitored token spend and uncontrolled costs.
- Tight coupling to a specific provider's API types.
- Broken local development workflows requiring paid API keys for trivial tests.

Global Step 59 introduces a **production-quality Model Gateway** that abstracts providers, handles transient failures, enforces per-task budgets, tracks token costs, redacts credentials, and enables offline deterministic development.

## 2. Core Concepts

### 2.1 Provider Abstraction & Adapter Pattern
The application interacts exclusively with a narrow contract:
```ts
interface ModelGateway {
  generate(request: ModelGatewayRequest): Promise<ModelGatewayResponse>;
}
```
The caller provides structured messages, task type, prompt version, and optional budget limits. The low-level provider adapter (e.g., `AnthropicProviderAdapter` or `MockModelProvider`) is responsible for translating this request into provider-specific payloads, invoking the API, extracting content and usage metadata, and mapping provider errors to a unified typed error hierarchy (`ModelGatewayError`).

This guarantees that:
- Provider swaps or secondary provider routing require zero changes to application code.
- Provider SDK response types never leak into product workflows.

### 2.2 Task-Aware Routing & Model Tiers
Different tasks have vastly different latency requirements, token volumes, and reasoning complexity:
- **Impact Explanation**: Requires high reasoning capability to explain subtle architectural dependencies. Budget: 20 seconds. Primary model: `claude-sonnet-5-5`.
- **Simulation Narration**: Explains multi-step failure cascades. Bounded default budget: 30 seconds. Primary model: `claude-sonnet-5-5`.
- **Free-Form Chat**: Interactive Q&A. Budget: 45 seconds. Primary model: `claude-sonnet-5-5`.

By parameterizing requests by `ModelTaskType`, the gateway selects task-appropriate models, enforces safety limits on client overrides, and avoids a one-size-fits-all cost and latency profile.

### 2.3 Transient Failures vs. Fatal Errors
Not all errors should be retried:
| Error Category | HTTP / Root Cause | Classification | Action |
|---|---|---|---|
| Rate Limit | 429 Too Many Requests | Retryable | Exponential backoff or `Retry-After` delay |
| Server Error | 500, 502, 503, 504 | Retryable | Exponential backoff |
| Network Timeout | ETIMEDOUT, 408 | Retryable | Exponential backoff |
| Authentication | 401 Unauthorized, 403 Forbidden | Fatal | Fail fast; do not retry or fallback |
| Invalid Request | 400 Bad Request, unparseable payload | Fatal | Fail fast; do not retry or fallback |
| Aborted | Caller cancelled `AbortSignal` | Fatal | Cancel immediately; clean up timers |

### 2.4 Model Fallback vs. Deterministic Product Fallback
It is critical to distinguish two different levels of fallback in Fluxora:
1. **Model Fallback (Infrastructure Level)**:
   - Within the Model Gateway, if the primary model (`claude-sonnet-5-5`) exhausts its retry budget due to transient provider rate limits or outages, the gateway attempts a secondary model (`claude-haiku-5-5`).
   - This occurs inside the infrastructure layer. If the fallback succeeds, the product still receives an AI-generated explanation (with `usedFallback: true` recorded).
2. **Deterministic Product Fallback (Orchestration Level — Step 66 / Phase 9 Step 8)**:
   - If the Model Gateway completely fails (e.g., all models down, timeout exceeded, or retries exhausted) OR if the generated output fails structured schema / evidence-grounding validation, the product falls back to a **deterministic, non-AI explanation** generated directly from the graph evidence (ADR-010).
   - This ensures the user is never left without an explanation and the core product experience is never blocked.

## 3. Resilience Engineering

### 3.1 Bounded Exponential Backoff
For retryable errors, the retry delay is calculated as:
$$\text{delay} = \min\left(\text{baseDelay} \times 2^{\text{attempt} - 1}, \text{maxDelay}\right)$$
If the provider supplies a `Retry-After` header, the gateway respects that delay up to a safety ceiling (`maxRetryAfterMs`), preventing rogue providers or bad headers from hanging worker execution for hours.

### 3.2 Cancellation Propagation
When a background worker shuts down or a client aborts an HTTP request, the gateway's `AbortSignal` listener:
1. Immediately aborts in-flight fetch/socket requests via the official SDK's abort mechanism.
2. Aborts any pending retry sleep timer via `clearTimeout`.
3. Rejects the promise with `ModelGatewayError.aborted()`, preventing wasted API calls and orphaned background promises.

## 4. Cost Accounting & Pricing Registry

Because LLM API calls are metered on tokens, cost accounting must be:
1. **Model-Aware**: Rates differ dramatically (Sonnet: \$3/\$15 per MTok; Haiku: \$0.80/\$4.00 per MTok).
2. **Honest & Non-Fabricating**: If pricing for a model is unknown or token usage was not reported, cost must be `null`—never assumed to be zero.
3. **Multi-Attempt Aggregate**: If attempt 1 failed after consuming tokens and attempt 2 succeeded on fallback, the billed cost of the entire request is the sum of both billable attempts.

$$\text{cost\_usd} = \sum_{\text{attempts}} \left[\left(\frac{\text{input\_tokens}_i}{1{,}000{,}000} \times \text{rate}_{\text{in}, i}\right) + \left(\frac{\text{output\_tokens}_i}{1{,}000{,}000} \times \text{rate}_{\text{out}, i}\right)\right]$$

## 5. Security & Secret Safety

1. **Secrets Client Integration**: API keys are retrieved from `SecretsClient` with in-memory caching. No keys are written to disk or committed to Git.
2. **Automated Redaction**: All error messages pass through `sanitizeErrorMessage()`, which matches regex patterns for Anthropic keys (`sk-ant-...`) and Bearer tokens, replacing them with `[REDACTED_API_KEY]`.
3. **Log Sanitization**: OpenTelemetry log events and span attributes never include full prompt text, customer repository contents, or private parameters.

## 6. Mock-First Local Development

By defaulting `USE_REAL_LLM=false`, developers can:
- Run all unit, integration, and golden fixture tests without network access or paid API keys.
- Develop front-end components and worker handlers offline.
- Reliably test error paths (timeouts, rate limits, aborts) by injecting deterministic mock behaviors.

When testing prompts or evaluating model quality, setting `USE_REAL_LLM=true` enables the real Anthropic provider and enforces fail-closed configuration validation.
