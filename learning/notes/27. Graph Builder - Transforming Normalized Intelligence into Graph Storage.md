# 27. Graph Builder — Transforming Normalized Intelligence into Graph Storage

## What is a Graph Builder?

The **Graph Builder** is the translation bridge between static code-intelligence extraction (Phase 3) and relational graph persistence (Phase 4).

While Phase 3 parses source files into AST symbols, module dependencies, API routes, event patterns, and database operations, Phase 4 stores those findings as a queryable, typed property graph with evidence in PostgreSQL (`GraphNode`, `GraphEdge`, `Evidence`).

---

## Key Engineering Concepts

### 1. Graph Projection

**Graph Projection** is a pure functional transformation:

$$\text{Phase 3 Normalized Result} \xrightarrow{\text{Projection}} \text{Graph Nodes + Graph Edges + Evidence Records}$$

Why separate Graph Projection from database writes?
- **In-Memory Testing**: The projection layer is 100% pure and deterministic. It can be tested instantly in unit tests without starting PostgreSQL or creating test databases.
- **Decoupled Architecture**: Conversion rules and relationship semantics are cleanly separated from SQL queries, connection pools, and database migrations.

### 2. Graph Node vs. Graph Edge

- **Graph Node**: Represents a distinct entity in the codebase.
  - Examples: a TypeScript function (`symbol`), a source file (`module`), an HTTP API route (`api`), a pub/sub event (`event`), or a database table (`database`).
  - Identifiers: `canonicalId` (e.g. `sym:src/auth.ts#function:login:100` or `mod:src/index.ts`).
- **Graph Edge**: Represents a directed relationship connecting a source node to a target node.
  - Examples: `IMPORTS` (`mod:A` $\rightarrow$ `mod:B`), `EXPOSES_ROUTE` (`mod:api/route.ts` $\rightarrow$ `route:/api/posts`), `EMITS_EVENT` (`mod:producer.ts` $\rightarrow$ `event:user.created`), `QUERIES_DB` (`mod:repo.ts` $\rightarrow$ `db:user_table`).

### 3. Canonical Identity

A **Canonical ID** is a globally unique, deterministic string identifier representing a single entity across the system.
- **Example**: `sym:src/auth.ts#function:login:100`
- **Why it matters**: Multiple import statements or export aliases referring to `login` in `src/auth.ts` will resolve to the exact same canonical ID. This prevents duplicate nodes for the same underlying code declaration.

### 4. Deterministic Graph Construction

Given the exact same input repository snapshot and normalized analysis result:
- The graph builder MUST produce the exact same set of nodes.
- The graph builder MUST produce the exact same set of edges.
- The graph builder MUST produce the exact same set of evidence records.
- Ordering MUST be sorted lexicographically ASC.

**Why determinism is critical**: If two identical runs produced different node IDs or different edge orders, diffing graphs across commits would generate false noise and invalidate caching layers.

### 5. Idempotency

**Idempotency** means that executing the Graph Builder twice on the same snapshot produces the exact same outcome without creating duplicate database records or throwing constraint errors.
- **Implementation**: Database tables enforce `UNIQUE (analysis_run_id, canonical_id)` for nodes and `UNIQUE (analysis_run_id, source_node_id, target_node_id, edge_type)` for edges, combined with `ON CONFLICT (...) DO UPDATE`.

### 6. Referential Integrity & Endpoint Validation

Before any edge is inserted into PostgreSQL:
- The Graph Builder verifies that **both the source node and target node exist** in the node set.
- If an edge points to an external package or missing symbol (e.g. an unresolved import), the edge is safely rejected and counted in statistics rather than fabricating fake nodes or creating dangling foreign key errors.

### 7. Provenance & Evidence

**Provenance** answers: *"Why does this graph node or edge exist?"*
- Every node and edge created by the builder generates a corresponding `EvidenceRecord`.
- Evidence records store the source file path, line numbers (`lineStart`, `lineEnd`), column ranges, symbol IDs, and a plain-English relationship description (e.g. `Declared symbol "login" of kind "function"`).
- Evidence ensures every claim in Fluxora is traceable back to verified source code.

### 8. Transactional Graph Writes

Graph construction must be **atomic**:
- Nodes, edges, and evidence records for an analysis run are persisted inside a single PostgreSQL transaction (`withTenant`).
- If any database query fails or a constraint is violated, PostgreSQL issues a `ROLLBACK`. This guarantees that an analysis run never leaves a corrupt or partial graph state in the database.

### 9. Tenant & Analysis Scope Isolation

- Every persisted row is bound to `organization_id` and `analysis_run_id`.
- Database access is protected by Row-Level Security (RLS) policies (`fluxora_analysis_run_in_current_tenant`). Cross-tenant reads or writes are rejected at the database engine level.

## Concrete Mapping Example

Consider two files:

`src/auth.ts`:
```ts
export function login() { ... }
```

`src/index.ts`:
```ts
import { login } from "./auth";
```

### Graph Projection Output:

1. **Graph Nodes**:
   - `mod:src/auth.ts` (`nodeType = "module"`)
   - `mod:src/index.ts` (`nodeType = "module"`)
   - `sym:src/auth.ts#function:login:10` (`nodeType = "symbol"`)

2. **Graph Edges**:
   - `mod:src/index.ts` $\xrightarrow{\text{IMPORTS}}$ `mod:src/auth.ts`
   - `mod:src/auth.ts` $\xrightarrow{\text{RESOLVES\_TO}}$ `sym:src/auth.ts#function:login:10`

3. **Evidence Records**:
   - Evidence for `mod:src/auth.ts`: `Module declaration for file src/auth.ts`
   - Evidence for `sym:...`: `Declared symbol "login" of kind "function"` (lines 10–12)
   - Evidence for `IMPORTS` edge: `Import reference from src/index.ts to src/utils.ts`
