# Personal Learning — Step 12: Repository Ingestion Worker

Step 12 pulls GitHub repository bytes into an isolated working directory. It does not analyze code, persist snapshots, or talk to the browser.

## Why ingestion is asynchronous

Fetching and unpacking a repository can take seconds to minutes, hit GitHub rate limits, and use disk and memory. The API must stay tenant-scoped and fast: enqueue a job and return. A request-thread clone would couple HTTP timeouts to GitHub and let one large repo stall the API.

## Worker vs API

- **API (later connect route):** authenticate the user, authorize the org, insert/load `Repository`, enqueue `repository.ingest` with `organization_id` and an idempotency key.
- **Worker:** claim the job, re-check tenant ownership, mint a GitHub App installation token, fetch, extract, classify failures, complete/fail the job.

The worker does not use the Clerk session. GitHub calls use a short-lived installation token. The API never holds repository bytes in this step.

## Job leasing

`claimNextJob` leases a `pending` row (`running`, `locked_by`, `lease_expires_at`) and increments `attempt_count`. If the process dies, the lease expires and another worker can claim it. Completion and failure require the same `workerId` and a live lease. That is how two workers avoid completing the same attempt.

## At-least-once delivery

A crash after GitHub fetch but before `completeJob` means the job is claimed again. Handlers must tolerate a second run. Step 12 creates no snapshot rows, so a retry only creates a new temp directory and may set `connection_status` to the same value again.

## Idempotency

Do not add a second idempotency table. `jobs` is unique on `(organization_id, idempotency_key)`. The agreed key is `repository.ingest:{repositoryId}:{commitSha}`. Enqueue (Step 13+) uses it; the worker consumes it. `commitSha` is optional on the payload so a future connect API can enqueue after resolving the SHA, or the worker can resolve `ref` itself.

## GitHub App installation token lifecycle

1. Load the org’s Step 10 `github_installations` row (installation id, not a token).
2. Sign a short GitHub App JWT with the App private key (minutes, not hours).
3. `POST /app/installations/{id}/access_tokens` → token (~1 hour).
4. Use it for this job only. Do not persist it. Do not log it.
5. Follow tarball `302` to `codeload.github.com` **without** the `Authorization` header so the installation token is not sent to a different host.

Clerk tokens never touch GitHub. There is no token table.

## Rate limits and retry classification

GitHub `429`, `x-ratelimit-remaining: 0`, or `403` + `Retry-After` are **retryable**. `JobWorker` already `failJob`s then `retryFailedJob` until `max_attempts`, then `dead_letter`. Do not invent a second backoff queue.

Permanent errors set `retryable: false` so `retryFailedJob` is skipped. The job stays `failed` (or `dead_letter` if attempts are exhausted).

## `needs_reauth`

`401`/`403` that are not rate limits, a 404 on the repository id, or a missing installation mean Fluxora cannot speak for that GitHub account. Set `connection_status = needs_reauth` and fail permanently. Retrying until dead-letter would hide a user-action problem (reinstall the App / grant repo access).

## Temporary working directories

Each attempt uses `mkdtemp(os.tmpdir()/fluxora-ingest-*)`. Success returns `workDir` for Step 13; the handler `rm`s it in `finally`. Failure also deletes it. Delete is restricted to paths under that prefix.

## Path traversal

Tar members are relative POSIX paths. After stripping GitHub’s `{repo}-{sha}/` prefix, any `..`, absolute path, drive letter, or NUL is a permanent `unsafe_archive` failure. The resolved path must stay under `path.resolve(workDir)`.

## Archive / decompression attacks

- Cap compressed bytes while downloading (and `Content-Length` when present).
- Cap uncompressed bytes and file count while extracting.
- Cap wall-clock time.
- Reject symlinks, hard links, and device files.
- Stream gzip+tar so a tiny compressed bomb cannot expand fully in RAM.
- Malformed tar is caught and becomes `unsafe_archive`, not an unhandled crash.

## Untrusted repository content and no execution

Customer trees are data: comments, READMEs, and `package.json` scripts are not instructions to Fluxora. The worker writes files. It does not `eval`, `import()`, `require`, or run `npm install` / git hooks. Analysis that compiles TypeScript is a later sandboxed worker, still without executing the product.

## How Step 12 feeds Step 13

The result is `{ workDir, commitSha, ref, fileCount, sizeBytes, repositoryId, organizationId }`. Step 13 should upload that tree, insert the immutable `RepositorySnapshot` (and `Commit` if needed), then delete `workDir`. Step 12 already marked `active` on successful materialization; snapshot identity remains `(repository_id, commit_sha)` uniqueness from Step 11.
