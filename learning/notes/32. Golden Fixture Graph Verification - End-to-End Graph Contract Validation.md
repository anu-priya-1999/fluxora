# 33. Golden Fixture Graph Verification - End-to-End Graph Contract Validation

## 1. What Step 33 Verifies

Global Step 33 establishes the end-to-end integration and verification gate between the normalized code-intelligence output (Phase 3) and PostgreSQL graph persistence (Phase 4).

Instead of testing functions in isolation with synthetic mocks, Step 33 executes the full production pipeline:
1. Ingests source files from a real multi-file TypeScript repository fixture (`packages/db/src/fixtures/taxonomy`).
2. Extracts symbols, module dependencies, and API routes via Phase 3 extractors.
3. Normalizes imports, exports, and re-export barrels (`runNormalizedAnalysisPipeline`).
4. Projects normalized entities into `GraphNode` and `GraphEdge` structures and persists them via `buildAndPersistGraph`.
5. Stores nodes, edges, and provenance in PostgreSQL (`graph_nodes`, `graph_edges`, `evidence`) inside a tenant-isolated transaction (`withTenant`).
6. Reads the persisted state back using standard read repositories (`listGraphNodes`, `listGraphEdges`, `getGraphNodeById`, `listEvidenceForSubject`, `getEvidenceById`).
7. Asserts the canonical graph contract: counts, types, canonical IDs, directionality, evidence coordinates, determinism, idempotency, RLS isolation, and negative boundary conditions.

---

## 2. Why Golden Fixtures are Essential

In complex compilers, static analysis pipelines, and digital-twin systems:
- Unit tests only prove that individual functions satisfy their localized specifications.
- They do **not** detect subtle mismatches between layers: e.g., an extractor producing 1-based coordinates while a database constraint expects a certain column order, or an event notification payload overflowing a database trigger limit.
- A **Golden Fixture** serves as an immutable, deterministic benchmark. If any upstream extractor, AST visitor, or schema migration alters the graph structure, the golden fixture immediately flags the regression before it affects downstream consumers (UI canvas, change-impact analysis, or query APIs).

## 3. The 7 Canonical Graph Verification Contracts

The Step 33 test suite (`apps/workers/src/pipeline/golden-graph.test.ts`) organizes assertions into 7 distinct contract tests:

### Contract 1: Canonical GraphNodes Contract
- **Counts and Distribution**: Asserts exactly 490 nodes (367 `symbol`, 118 `module`, 5 `api`).
- **Canonical Identifier Format**:
  - Modules: `mod:<filepath>` (e.g. `mod:lib/db.ts`).
  - Symbols: `sym:<filepath>#<name>:<line>` (e.g. `sym:lib/db.ts#db:5`).
  - Routes: `route:<filepath>#<handler>:<method>:<path>:<line>` (e.g. `route:app/api/posts/route.ts#app-router-handler:GET:/api/posts:360`).
- **Uniqueness**: Canonical IDs within an analysis run must be strictly distinct (zero duplicate nodes).

### Contract 2: Canonical GraphEdges Contract
- **Counts and Types**: Asserts exactly 888 edges (511 `IMPORTS`, 372 `RESOLVES_TO`, 5 `EXPOSES_ROUTE`).
- **Directionality & Endpoints**:
  - For `IMPORTS`: Source is an importing module, target is an imported module.
  - For `EXPOSES_ROUTE`: Source is a module handler, target is an API route node.
- **Referential Integrity**: Every `sourceNodeId` and `targetNodeId` must exist in the database and belong to the same analysis run.

### Contract 3: Evidence Provenance Contract
- **100% Coverage**: Every graph node (490) and edge (888) is accompanied by an evidence record (1378 total).
- **Physical Coordinates**: Asserts non-null file paths, confidence scores of 1.0, and positive 1-based start lines.

### Contract 4: Determinism & Idempotency
- **Exact Parity**: Re-running graph persistence on the same repository snapshot produces the exact same node and edge sets.
- **Zero Duplicate Creation**: Re-running persistence does not inflate table row counts.

### Contract 5: Tenant and Analysis-Run Isolation
- **Row-Level Security (RLS)**: Setting `app.current_organization_id` to Organization B prevents any read of Organization A's graph.
- **Run Isolation**: An analysis run within Organization A cannot observe or query nodes belonging to another analysis run.

### Contract 6: Meaningful Negative Assertions
- Confirms the absence of non-existent files (e.g. `services/billing.ts`), phantom symbols (`calculateTaxes`), synthetic routes (`DELETE /api/unknown`), and dangling edges.

### Contract 7: Bounded-Depth CTE Traversal Smoke Test
- Executes Step 30 recursive-CTE graph traversal on the persisted golden graph to confirm that upstream module dependencies and API routes resolve correctly across multiple hops.

## 4. What This Test Proves vs. What It Does NOT Prove

| What It Proves | What It Does NOT Prove |
| :--- | :--- |
| End-to-end AST extraction and normalization accurately project into relational graph tables. | Does not simulate live GitHub webhooks or queue concurrency delays. |
| Deterministic graph generation produces identical output across executions. | Does not test visual canvas rendering or React Flow layout (Phase 5). |
| All graph nodes and edges have verified source code evidence attached via `EvidenceWriter`. | Does not test dynamic runtime behavior or microservice network calls. |
| RLS guarantees zero cross-tenant data leakage. | Does not test LLM summary generation or prompt accuracy (Phase 9). |
