# Engineering Notes: Step 54 — Simulation Engine

These notes explain the design decisions, mathematical properties, and implementation details of the Fluxora Simulation Engine in plain English.

---

## 1. Why a Worklist Algorithm Instead of Recursion?

When propagating failures through a software architecture graph, naive recursive DFS (depth-first search) introduces several severe operational risks:
1. **Stack Overflow**: In large codebases or deep dependency chains, call stack depth can exceed engine limits.
2. **Infinite Recursion on Cycles**: If Service A calls Service B and Service B calls Service A, recursive DFS will loop indefinitely unless guarded by complex, mutable visited sets.
3. **Uncontrolled Evaluation Order**: In recursion, the order of state exploration depends on stack frame unwind order, making tie-breaking and determinism fragile.

A **worklist algorithm** (queue-based BFS/FIFO) replaces call stack recursion with an explicit, inspectable data structure. Nodes that undergo a state change are placed into a work queue. Each iteration pops the next changed node, inspects its incident edges, evaluates rules, applies state changes, and enqueues newly degraded nodes.

---

## 2. Why Monotonic State Transitions Guarantee Termination

In Fluxora, node simulation states are ordered strictly by severity:
```
healthy (0) < at_risk (1) < degraded (2) < failed (3)
```

The fundamental invariant of the simulation engine is **monotonicity**:
> **A node's state can only ever move to a strictly more severe state.**
> A node can never heal during a failure simulation.

Because:
1. There are only 4 possible states.
2. Any individual node can transition at most 3 times (`healthy -> at_risk -> degraded -> failed`).
3. For a finite graph of $N$ nodes, the total number of state transitions across the entire graph cannot exceed $3N$.
4. Nodes are only enqueued when their state strictly worsens.

Therefore, the maximum number of items ever enqueued across the entire simulation run is bounded by $3N$. This provides a mathematical proof of termination without needing arbitrary depth limits.

## 3. How Convergence Works in Cyclic Graphs

Consider a circular dependency:
```
PaymentService  <--->  CheckoutService
```
1. We seed `PaymentService` as `failed`.
2. `PaymentService` is placed in the queue.
3. The engine pops `PaymentService`. It evaluates the `CheckoutService --CALLS--> PaymentService` edge.
4. `CheckoutService` transitions from `healthy` to `degraded`.
5. `CheckoutService` is enqueued.
6. The engine pops `CheckoutService`. It evaluates `PaymentService --CALLS--> CheckoutService`.
7. `PaymentService` is already `failed` (severity 3). The rule proposes `degraded` (severity 2).
8. `isStateMoreSevere("degraded", "failed")` is `false`. No transition occurs.
9. No nodes are enqueued.
10. The queue becomes empty. The graph has reached a stable equilibrium (**converged**).

## 4. Why Graph Direction Cannot Be Hard-Coded

In traditional impact analysis (e.g. Git blast radius), traversal often flows in one static direction (e.g. callee to caller). In failure simulation, different relationship types have opposite propagation directions:
- **`CALLS` (Source = Caller, Target = Callee)**: If the callee (target) fails, the caller (source) degrades. Propagation flows **backwards** from target to source.
- **`CONSUMES_EVENT` (Source = Broker/Topic, Target = Consumer)**: If the broker (source) fails, the consumer (target) is placed at risk. Propagation flows **forwards** from source to target.
- **`QUERIES_DB` (Source = Reader, Target = Datastore)**: If the datastore (target) fails, the reader (source) is at risk.

The Step 53 Rule Table's `SimulationRuleDecision.affectedNode` explicitly designates which side (`source` or `target`) is affected. The engine inspects incident edges symmetrically and applies the rule's declared affected side.

## 5. How Causal Propagation Paths Are Built

Every affected node must answer the engineer's question: *"Why did my service fail?"*

Each time an affected node undergoes a state transition, the engine creates a `SimulationCausalStep`:
- `nodeId`: who transitioned.
- `edgeId`: the graph edge that transmitted the failure.
- `ruleId`: the specific rule applied (e.g. `CALLS+sync+no_fallback`).
- `ruleVersion`: version of the rule table.
- `previousState` & `resultingState`: what changed.
- `assumptions`: what was assumed about unknown metadata.
- `confidence`: confidence score of the decision.

When failure propagates across multiple hops ($A \to B \to C$), node $C$ inherits the causal history leading to $B$ plus its own transition step:
`[Step(A=failed, seed), Step(B=degraded, edge=A->B), Step(C=degraded, edge=B->C)]`.

---

## 6. Why Simulation Output Must Be Evidence-Backed

Fluxora's Core Principle P2 states: **No unverified assertions.**

A simulation result could easily be dismissed as a speculative guess unless it is rooted in concrete code evidence. When a node degrades because of a synchronous call without fallback, the resulting `simulation_state` evidence record links directly to:
- The graph edge connecting the two services.
- The base evidence and source code coordinates (file path, line start, line end) where that call was identified in the repository.
- The exact rule that triggered the transition.

Engineers can click from the simulation failure directly to the exact lines of code where the unhandled synchronous call was made.

---

## 7. Why Deterministic Ordering Matters

If an engine processes edges or queues based on hash map iteration, database retrieval order, or arbitrary UUIDs, two runs of the same scenario on the same commit could produce slightly different propagation orders or tie-breaking decisions.

To guarantee bit-for-bit repeatability:
1. Edges are sorted deterministically (`sourceNodeId ASC`, `targetNodeId ASC`, `edgeType ASC`, `id ASC`).
2. Queue order is deterministic FIFO.
3. Competing explanations of equal severity respect the first deterministic explanation (tie-breaking).
4. Output arrays are sorted by `nodeId ASC`.

Two engineers running the same simulation on identical code get identical results, identical causal paths, and identical evidence IDs.

---

## 8. Why Latency Remains Qualitative in MVP

Step 54 supports `"latency"` scenarios, but models them **qualitatively** rather than numerically:
- Latency injection seeds the target node as `degraded` (not "500ms" or "p99 = 2.4s").
- A synchronous call to a degraded dependency degrades the caller.
- An asynchronous call or circuit breaker isolates the latency.

Why? Numerical latency modeling requires queueing theory, concurrency limits, traffic multipliers, and runtime telemetry. Doing that in static analysis produces false precision and hallucinated numbers. Qualitative simulation models real structural failure modes truthfully.

---

## 9. Separation of Pure Engine and Database Persistence

- **Pure Domain Engine (`runSimulationEngine`)**: Free of PostgreSQL, SQL queries, network calls, or mutations. It takes a pure data snapshot and returns a pure result. This makes it instantly testable with in-memory fixtures.
- **Database Orchestration (`executeSimulation`)**: Handles database connections, transaction boundaries (`withTenant`), RLS enforcement, simulation status updates (`pending -> running -> completed`), and atomic writes via `EvidenceWriter`.
