# 63. AI Simulation Narration

## Architectural Concept

Deterministic failure simulation allows engineers to inject synthetic faults (service unavailability, packet latency, disk corruption, dependency degradation) into a software digital twin and trace how failures propagate across deep dependency cascades.

While the deterministic simulation engine computes exact propagation paths, hop distances, circuit breaker caps, and component states, the results can be complex and overwhelming for human operators inspecting hundreds of affected nodes.

**Global Step 63** introduces evidence-grounded AI simulation narration. It translates multi-hop failure cascades into clear, structured architectural explanations while enforcing non-negotiable boundaries:
1. **The deterministic simulation remains the sole source of truth.**
2. **AI narration is strictly an optional enhancement.** If the LLM times out, errors, or fails validation, the simulation run remains 100% successful and fully interactive.
3. **Strict evidence grounding.** Every claim made by the model must cite verified simulation evidence IDs from the trusted manifest.
4. **Explicit distinction between simulation and reality.** Simulated failure propagation must never be presented as an observed production incident.

## Key Principles & Engineering Invariants

### 1. Deterministic Engine Authority
The LLM is strictly a narrator, never a simulator. The deterministic simulation engine alone determines:
- Which component was targeted.
- Which dependencies propagated the failure.
- Hop distances and traversal ordering.
- State transitions (`failed`, `degraded`, `at_risk`, `healthy`) and circuit-breaker `capped` flags.
- Deterministic context prioritization (`confidence DESC → severity DESC → hopDistance ASC → nodeId ASC`): higher-confidence outcomes take priority even when a lower-confidence outcome has greater severity; severity resolves equal-confidence outcomes; shorter hop distances resolve equal-confidence, equal-severity outcomes; and lexicographical `nodeId` provides the final deterministic tie-breaker to decide which results survive the maximum-result and character budgets. (`capped` is a separate boolean flag, not a severity level; unknown states default to severity `0`.)
- Convergence and iteration metrics.

### 2. Simulation vs. Production Incident Distinction
A critical safety requirement of simulation narration is preventing operator panic. The model prompt explicitly commands:
- "Explain only the deterministic simulation results supplied in context."
- "Do not suggest that a simulated failure actually happened in production."
- "Clearly distinguish the simulated scenario from real production observations."
The UI reinforces this with an amber warning disclaimer on every AI simulation panel.

### 3. Strict Evidence Grounding
Every claim returned by the LLM in `output_structured.claims` must cite evidence IDs strictly contained in `allowedEvidenceIds`. If the model invents an ID or cites an evidence record trimmed during context budgeting, the output is rejected atomically.

### 4. Bounded Discovery & Polling Race Resolution
When the client receives a simulation response before the worker has committed the initial pending record, the frontend uses a bounded discovery poller:
- Polls up to `MAX_AI_DISCOVERY_ATTEMPTS = 5` at `AI_DISCOVERY_INTERVAL_MS = 2000ms`.
- Halts immediately upon discovering `ai_analysis_id`.
- If discovery exhausts without finding a record, gracefully transitions to unavailable with an interactive "Check again" retry button.
- Strictly cancels all timers upon component unmount.
