# 26. Graph Storage — GraphNode, GraphEdge, and Evidence Persistence

## Concept 1: Modeling Directed Graphs in Relational PostgreSQL

While graph databases (like Neo4j) use native pointer-chasing structures, relational databases (PostgreSQL) represent directed graphs using normalized tables for **Nodes** and **Edges**.

In Fluxora, graph persistence is designed around four key entities:
- **`analysis_runs`**: Execution context scoping the graph to a specific repository snapshot.
- **`graph_nodes`**: Primary entities (modules, symbols, functions, routes, databases).
- **`graph_edges`**: Directed relationships between nodes (`IMPORTS`, `CALLS`, `EXPOSES_ROUTE`, `READS_TABLE`).
- **`evidence`**: Code provenance tracking line numbers, file paths, and symbol IDs explaining edge/node existence.

---

## Concept 2: Scope Enforcement via Composite Foreign Keys

A critical bug in multi-tenant graph storage is allowing an edge to connect Node A in Tenant 1 with Node B in Tenant 2, or connecting nodes across different analysis runs.

Fluxora prevents cross-run and cross-tenant edge linking at the schema layer using **Composite Foreign Keys**:

```sql
CONSTRAINT graph_edges_source_node_fk
  FOREIGN KEY (source_node_id, analysis_run_id)
  REFERENCES graph_nodes (id, analysis_run_id)
  ON DELETE CASCADE,

CONSTRAINT graph_edges_target_node_fk
  FOREIGN KEY (target_node_id, analysis_run_id)
  REFERENCES graph_nodes (id, analysis_run_id)
  ON DELETE CASCADE
```

Because `(id, analysis_run_id)` must match on both source and target nodes, PostgreSQL guarantees at database level that an edge can ONLY connect two nodes that belong to the **exact same analysis run** (and thus the exact same tenant).

## Concept 3: Row-Level Security (RLS) & Recursion Avoidance

Multi-tenant RLS policies evaluate `fluxora_current_org_id()` on every operation.

When writing RLS policies on child tables:
1. Helper functions MUST be defined with `SECURITY DEFINER SET search_path = pg_catalog, public` so tenant lookups can query parent tables without running into nested RLS policy loops.
2. Parent table policies (like `analysis_runs`) should reference direct parent columns (`snapshot_id`) rather than querying `analysis_runs` inside its own RLS policy function, eliminating RLS recursion.

---

## Concept 4: Deterministic Graph Ingestion with `ON CONFLICT`

Graph construction engines (Step 28) generate nodes and edges from AST analysis. To support idempotent and parallel graph writes, the database enforces unique constraints:

- `UNIQUE (analysis_run_id, canonical_id)` on `graph_nodes`
- `UNIQUE (analysis_run_id, source_node_id, target_node_id, edge_type)` on `graph_edges`

This enables bulk ingestion queries to use `ON CONFLICT (...) DO UPDATE` safely without creating duplicate graph entities or failing on repeated runs.
