# 44. Impact Analysis Persistence & Evidence Linking

## Overview & System Role

Global Step 44 bridges the gap between pure in-memory blast-radius computation (Step 43) and durable multi-tenant persistence. It takes the output of the Impact Analysis Engine and guarantees that:
1. Every impact calculation is stored durably in PostgreSQL with full relational and JSONB fidelity.
2. Every affected node finding is backed by an immutable, deterministic `impact_finding` **Evidence** record.
3. All writes are enforced by PostgreSQL Row-Level Security (RLS) under tenant isolation.
4. Repeated executions are 100% idempotent and produce stable primary keys.

---

## 1. Why Persisting Impact Findings Requires EvidenceWriter

In Fluxora, an architectural claim (such as "this pull request impacts `/api/checkout`") is not treated as authoritative unless it is supported by first-class provenance:
- **Graph Nodes & Edges** represent static code structures backed by parser evidence.
- **Impact Findings** represent analytical conclusions derived from diff hunks and graph traversal.

By routing impact findings through `EvidenceWriter`:
- Every finding gets an entry in the `evidence` table with `subject_type = 'impact_finding'`.
- The finding points back to the affected symbol's file path, coordinates, and canonical identity.
- The evidence metadata preserves the exact BFS path (`['nodeA', 'nodeB', 'nodeC']`), the hop depth, and citations of intermediate edge evidence.
- Downstream UI components (like the Architecture Explorer and Node Inspector) can display an unbroken audit trail:
  $$\text{PR Diff} \to \text{Changed Symbol} \to \text{Dependency Edges} \to \text{Affected API}$$

---

## 2. Deterministic Identifiers & Idempotency

Step 44 adheres to Fluxora's strict idempotency model:
- Evidence IDs are generated using a deterministic SHA-256 hash:
  $$\text{id} = \text{SHA256}(\text{analysisRunId} + \text{":evidence:impact\_finding:"} + \text{nodeId} + \text{":"} + \text{filePath} + \text{":"} + \text{description})$$
- When a job worker or analysis run re-executes for the same PR snapshot:
  - The generated evidence IDs are identical.
  - The database write utilizes `ON CONFLICT (id) DO UPDATE`.
  - No orphaned or duplicate evidence rows accumulate in PostgreSQL.

---

## 3. Multi-Tenant Row-Level Security Architecture

All database queries run inside `withTenant(pool, organizationId, ...)`:
- Sets session variable `app.current_org_id`.
- Evaluates against `FORCE ROW LEVEL SECURITY`.
- `impact_analyses` relies on parent PR security:
  ```sql
  CREATE POLICY impact_analyses_tenant_select ON impact_analyses
    FOR SELECT
    USING (fluxora_pull_request_in_current_tenant(pull_request_id));
  ```
- Cross-tenant queries are blocked at the database engine level, returning `null` or empty arrays rather than leaking existence.

---

## 4. Key Engineering Takeaways

- **Atomic Transactions**: An impact analysis and its evidence records commit together or fail together. An unevidenced impact finding never leaks into the database.
- **JSONB Fidelity**: Direct impacts, downstream impacts, and taxonomy lists are stored as structured JSONB arrays with embedded evidence IDs, enabling rapid indexing and instant retrieval for API consumers.
- **Decoupled Engine & Persistence**: The Step 43 engine remains a pure, testable function, while Step 44 handles PostgreSQL persistence, transactions, and evidence derivation.
