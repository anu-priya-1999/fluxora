# 43. Impact Analysis Engine

## Overview & System Role

In Fluxora's architecture, pull request impact analysis is divided into sequential, decoupled steps:
1. **Step 41**: GitHub Webhook Ingestion & HMAC Verification
2. **Step 42**: Pull Request & Diff Storage (PostgreSQL persistence & limits)
3. **Step 43 (Current Step)**: **Impact Analysis Engine** (in-memory, deterministic blast-radius computation)
4. **Step 44**: Impact Analysis Persistence & Evidence Linking
5. **Step 45**: Impact Analysis API Endpoints
6. **Step 46**: Frontend Architecture Explorer Change Mode Overlay
7. **Step 47**: Golden Fixture Validation & End-to-End Test Suite

Step 43 is the **deterministic core** of change intelligence. It consumes the stored diffs from Step 42 and the repository dependency graph to compute exactly what code symbols, API endpoints, message events, and services are impacted by a PR.

---

## 1. Architectural Core Invariant: Determinism vs. LLM Probabilism

A foundational rule of Fluxora (Core Invariant 4.1) is:
> Dependency graph construction, relationship discovery, blast-radius calculation, and change-impact propagation must **never** depend on an LLM.

### Why Determinism Matters in Impact Analysis
If an AI model were asked to "guess" the impact of a PR:
- Results would vary across runs (non-reproducible CI checks).
- Hallucinations would invent phantom dependencies or miss mission-critical database interactions.
- Traversal depth and blast radius could not be audited or formally verified.

Instead, Fluxora uses **deterministic AST static analysis and graph traversal**. The output of Step 43 is mathematical and repeatable: given the same repository snapshot, the same graph, and the same changed files, the blast radius is 100% identical every time.

---

## 2. The Impact Analysis Pipeline

```
PullRequest Changed Files (path, status, patch)
                       │
                       ▼
    Step 1: Unified Diff Hunk Parsing
            - Parse @@ -old,count +new,count @@ headers
            - Extract modified line ranges (oldLines, newLines)
                       │
                       ▼
    Step 2: Changed-Symbol Resolution
            - Match file paths to graph symbol nodes
            - Match line ranges to AST symbol declarations (lineStart .. lineEnd)
            - Fall back to file/module symbols if diff is unaligned
            - Record unresolvable files (e.g. docs, configs) in unresolvedFiles
                       │
                       ▼
    Step 3: Multi-Seed BFS Graph Traversal
            - Seed nodes assigned depth = 0, confidence = 1.0
            - Queue seeds and traverse downstream (source -> target)
            - Track visited set to terminate on graph cycles
            - Deduplicate to the shallowest path if multiple seeds reach the same node
            - Enforce maximum depth ceiling (default 5, hard cap 20)
                       │
                       ▼
    Step 4: Classification & Confidence Decay
            - Direct impact (depth = 1) vs Downstream impact (depth >= 2)
            - Categorize API routes, events, services
            - Decay confidence: C = 1.0 * (0.9 ^ depth)
            - Detect and report truncation if depth ceiling reached with outgoing edges
                       │
                       ▼
    Step 5: Deterministic Output Sorting
            - Findings sorted by depth ASC, confidence DESC, nodeId ASC
```

## 3. Deep Dive: Changed-File to Changed-Symbol Resolution

Pull requests modify *files*, but architectural graphs model *symbols* (functions, classes, endpoints, types). The engine bridges this gap:

### 1. Unified Diff Parsing
Standard unified diff hunks provide line-number offsets:
```diff
@@ -45,6 +45,8 @@ export class PaymentService {
+  async processRefund(transactionId: string): Promise<RefundResult> {
+    return this.gateway.refund(transactionId);
+  }
```
`parsePatchModifiedLines` extracts the affected line numbers (`45..47`).

### 2. AST Line Intersect
Each symbol node in Fluxora's graph contains metadata:
```json
{
  "lineStart": 44,
  "lineEnd": 52
}
```
If any modified line intersects `[symbol.lineStart, symbol.lineEnd]`, the symbol is selected as an exact seed.

### 3. Graceful Fallbacks & Unresolved Tracking
- If a file diff has no hunks (e.g. newly created file or whole-file modification), all symbols declared in the file are selected.
- If a changed file contains no graph symbols (e.g. `README.md`, `.github/workflows/ci.yml`), it is tracked in `unresolvedFiles` with a specific reason:
  - `no_symbols_found`: Non-code file or file with no exported symbols.
  - `deleted_file_no_longer_in_snapshot`: Deleted file whose symbols no longer exist in the snapshot.

## 4. Graph Traversal: BFS vs. DFS

Why Breadth-First Search (BFS) is chosen over Depth-First Search (DFS):

1. **Shortest Distance Guarantee**: In an unweighted directed graph, BFS visits nodes in order of shortest distance from seeds. When multiple paths lead to node $X$, BFS discovers $X$ via its shallowest path first.
2. **Confidence Maximization**: Because confidence decays with depth ($0.9^d$), the shallowest path represents the highest-confidence impact.
3. **Natural Stratification**: BFS directly partitions nodes into `depth = 1` (direct impacts) and `depth >= 2` (downstream impacts).

### Cycle Prevention
Software graphs frequently have cycles (e.g. recursive calls, circular imports, mutual service dependencies).
The engine maintains a `visited` set of node IDs. Any edge leading to an already-visited node is skipped, preventing infinite loops.

---

## 5. Confidence Decay Model

Confidence represents how directly and reliably an upstream code change influences a downstream component.
$$\text{Confidence}(d) = \text{InitialConfidence} \times \lambda^d$$
- $\text{InitialConfidence} = 1.0$ (direct seed change)
- $\lambda = 0.9$ (default decay per hop)
- $d = \text{hop distance}$

| Hop Depth | Confidence Score | Semantic Meaning |
|---|---|---|
| 0 | 1.000 | Changed Seed Symbol |
| 1 | 0.900 | Direct Downstream Caller / Consumer |
| 2 | 0.810 | Secondary Dependency |
| 3 | 0.729 | Tertiary Transitive Impact |
| 4 | 0.656 | Quaternary Transitive Impact |
| 5 | 0.590 | 5-Hop Horizon Impact |

Confidence is strictly monotonic non-increasing with depth.

## 6. Defensive Bounds & Truncation Semantics

Unbounded graph traversal in a large monorepo (100k+ nodes) risks:
- Out-of-memory errors
- Query timeouts
- Diluted signal-to-noise ratio

Fluxora enforces:
- `DEFAULT_IMPACT_MAX_DEPTH = 5` hops
- `HARD_MAX_IMPACT_DEPTH = 20` hops

### Truncation Flag
If traversal stops at `depth === maxDepth`, and any node at that depth has outgoing downstream edges, the engine marks:
- `ImpactFinding.truncated = true` for those frontier nodes.
- `ImpactAnalysisResult.truncated = true` at the top level.

This guarantees that downstream users and UI components are explicitly notified that additional impacts exist beyond the search horizon.

---

## 7. Multi-Tenant Row-Level Security (RLS) Safety

All database operations run within `withTenant(pool, organizationId, ...)`:
- Sets `SET LOCAL app.current_organization_id = $organizationId`.
- PostgreSQL evaluates `FORCE ROW LEVEL SECURITY` on `repositories`, `repository_snapshots`, `graph_nodes`, `graph_edges`, and `pull_requests`.
- Tenancy mismatch between the pull request and the repository results in an immediate `PullRequestNotFoundError`.

---

## 8. Explicit Boundary: Why Step 43 Does NOT Persist Results

In accordance with sequential roadmap discipline:
- **Step 43 owns the *computation***: In-memory AST resolution, graph traversal, and taxonomy classification.
- **Step 44 owns the *persistence***: `impact_analyses` database table, migration, RLS policies, and `EvidenceWriter` provenance linking.

Keeping calculation pure and decoupled from persistence allows:
- Lightning-fast unit testing without database locks.
- Flexible re-runs and dry-runs without generating database bloat.
- Clean separation of concerns between algorithms and storage.
