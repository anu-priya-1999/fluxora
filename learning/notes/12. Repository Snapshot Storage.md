# Personal Learning Notes — Step 13: Repository Snapshot Storage

**Covers:** Global Step 13 — deterministic snapshot packaging, SHA-256 integrity, object-storage persistence, immutable PostgreSQL metadata, and failure cleanup.

---

## 1. What problem did Step 13 solve?

Step 12 downloaded a repository and extracted it into a temporary worker directory.

That directory is intentionally short-lived.

Step 13 converts that temporary materialization into a **durable, immutable repository snapshot** that later analysis workers can consume without downloading the repository again.

```text
Step 12
GitHub → download → validate → extract → temporary workDir

Step 13
workDir → deterministic archive → SHA-256 → object storage
       → RepositorySnapshot metadata in PostgreSQL
```

The important boundary is:

> **Step 12 gets the repository. Step 13 freezes and persists the repository.**

---

## 2. What is the snapshot?

The current implementation stores the repository tree as one compressed archive:

```text
snapshot.tar.gz
```

It is **not** one object per source file.

Example:

```text
snapshot.tar.gz
├── README.md
├── package.json
└── src/
    ├── index.ts
    └── utils.ts
```

Object storage contains the archive bytes.

PostgreSQL contains metadata about those bytes.

---

## 3. Why deterministic packaging?

The same repository contents should produce the same logical snapshot.

Fluxora therefore removes accidental machine-specific differences:

```text
stable file ordering
        +
portable archive metadata
        +
normalized timestamps
        ↓
deterministic archive bytes
```

The goal is:

```text
same repository tree
      ↓
same snapshot bytes
      ↓
same SHA-256
```

This matters because later analysis must be reproducible and traceable to an exact input artifact.

---

## 4. Packaging flow

The worker:

1. walks the extracted work directory;
2. keeps regular files and skips symbolic links;
3. sorts normalized relative paths;
4. enforces the file-count limit;
5. writes a portable tar stream;
6. gzip-compresses it;
7. normalizes the gzip header;
8. enforces the compressed archive limit;
9. writes `snapshot.tar.gz`;
10. hashes the exact final archive bytes with SHA-256.

The implementation does **not** execute, import, or evaluate repository content.

---

## 5. Why SHA-256?

SHA-256 is the content fingerprint of the final archive.

```text
snapshot.tar.gz
      ↓
   SHA-256
      ↓
64 lowercase hexadecimal characters
```

If the archive bytes change, the checksum changes.

The critical distinction is:

```text
commitSha
  = identity of the Git revision

sha256
  = fingerprint of the exact packaged bytes
```

Both are useful, but they answer different questions.

---

## 6. Object storage vs PostgreSQL

This is one of the most important Step 13 concepts.

### Object storage

Stores the large binary artifact:

```text
snapshot.tar.gz
```

### PostgreSQL

Stores the relational metadata:

```text
RepositorySnapshot
├── id
├── repositoryId
├── commitSha
├── ref
├── storageUri
├── sha256
├── fileCount
├── sizeBytes
└── createdAt
```

So:

```text
Object storage = repository bytes
PostgreSQL     = snapshot identity + metadata
```

PostgreSQL is not used as a blob store for the entire repository archive.

---

## 7. Why reuse the existing object-storage abstraction?

Fluxora already has an object-storage boundary from Step 5.

Step 13 reuses that contract rather than embedding filesystem/S3 implementation details inside ingestion.

Current adapters:

```text
Local
  ↓
FilesystemObjectStorage

Production
  ↓
S3ObjectStorage
```

This keeps domain code independent from a particular storage provider.

---

## 8. Tenant-safe object key

Snapshot objects are scoped by:

```text
organizationId/
repositoryId/
snapshotId/
snapshot.tar.gz
```

Conceptually:

```text
org-A/repo-1/snapshot-1/snapshot.tar.gz
org-B/repo-1/snapshot-2/snapshot.tar.gz
```

This aligns object storage with Fluxora's tenant-isolation model.

The existing path helper also rejects unsafe traversal/path patterns.

---

## 9. Snapshot immutability

A snapshot represents a frozen repository tree for a commit.

We do not mutate that artifact later.

```text
commit A → snapshot A

commit B → snapshot B
```

rather than:

```text
commit A ─┐
          ├→ one mutable snapshot
commit B ─┘
```

Why?

Because later evidence and analysis must be able to point to a stable input.

---

## 10. Repository vs Commit vs Snapshot

These concepts are easy to confuse.

### Repository

Fluxora's tenant-owned connection to a GitHub repository.

### Commit

Git history metadata:

```text
SHA
author
message
parents
```

### Snapshot

The actual frozen source tree packaged for a commit:

```text
commitSha
ref
storageUri
sha256
fileCount
sizeBytes
```

Interview sound bite:

> **Repository = connection. Commit = Git history fact. Snapshot = frozen source artifact.**

---

## 11. Why commit SHA is stored on the snapshot

The snapshot must answer:

> Which exact Git revision produced these bytes?

For example:

```text
repository = repo-123
commitSha  = aaaaaaaaa...
snapshotId = 555555...
sha256     = <64-char checksum>
```

Later analysis can therefore be tied to both the repository revision and the exact stored artifact.

---

## 12. Partial-failure handling

Step 13 crosses two persistence systems:

```text
Object storage
       +
PostgreSQL
```

That creates a partial-failure risk.

Example:

```text
upload object ✅
DB insert     ❌
```

Without cleanup, the object becomes orphaned.

The implementation therefore deletes the uploaded object when snapshot metadata persistence fails.

Likewise, a failed packaging attempt removes the partial archive.

This is a distributed-systems invariant:

> Do not intentionally leave a successful side effect behind when the related metadata operation fails.

---

## 13. Idempotency

Step 13 preserves the snapshot identity rule established by Step 11:

```text
(repository_id, commit_sha)
```

is the logical uniqueness boundary.

Re-running the same successful ingestion must not replace the existing immutable snapshot object.

A different commit gets a different snapshot.

The tests verify that repeated successful ingestion is idempotent and does not replace the snapshot object.

---

## 14. Failure and size limits

Packaging is bounded by the existing ingestion limits:

```text
max file count
max total repository bytes
max compressed snapshot bytes
timeout
```

There are two important size stages:

```text
GitHub archive
   ↓
uncompressed repository limits
   ↓
temporary workDir
   ↓
compressed snapshot limit
   ↓
object storage
```

This prevents an oversized repository from silently becoming an oversized durable artifact.

---

## 15. Temporary directory lifecycle

The worker owns the temporary extraction directory.

Lifecycle:

```text
download
  ↓
extract
  ↓
package
  ↓
upload
  ↓
persist metadata
  ↓
cleanup workDir
```

The temporary directory is not the durable source of truth.

After Step 13:

```text
object storage + PostgreSQL metadata
```

become the durable representation.

---

## 16. Why not store the archive in PostgreSQL?

Large repository blobs are not a good fit for the relational system of record.

PostgreSQL is better suited for:

- tenant metadata
- repository relationships
- jobs
- graph data
- evidence
- analysis records

Object storage is better suited for:

- repository snapshots
- large artifacts
- binary files

This keeps relational queries, WAL, and database backups from being dominated by large source archives.

---

## 17. What Step 13 does NOT do

Step 13 does not yet:

- parse TypeScript/JavaScript;
- extract symbols;
- build the dependency graph;
- calculate blast radius;
- expose the repository connect API;
- push WebSocket progress;
- invoke an LLM.

Its responsibility ends at:

```text
durable, verified repository snapshot
```

## 20. Important Node 24 lesson

During verification, Node 24's strip-only TypeScript runtime exposed two concrete compatibility problems:

1. TypeScript parameter-property syntax in a runtime-tested class.
2. Passing `undefined` as an extra `pipeline()` argument.

The final implementation uses explicit class fields and conditional pipeline options.

Useful rule:

> With `node --experimental-strip-types`, keep runtime-tested TypeScript syntax erasable, and don't pass `undefined` where Node expects another stream or options object.

## 21. Senior interview summary

> "Step 13 turns the temporary repository materialized by the ingestion worker into a durable immutable artifact. Fluxora deterministically packages the extracted tree as a gzip-compressed tar archive, calculates SHA-256 over the final archive bytes, uploads that archive through the existing object-storage abstraction, and persists a tenant-scoped RepositorySnapshot row containing the commit SHA, storage URI, checksum, file count and size. PostgreSQL stores metadata while object storage stores the bytes. The implementation also cleans up partial archives and deletes uploaded objects if metadata persistence fails."

## 22. Memory anchor

Remember:

```text
FREEZE → FINGERPRINT → STORE → DESCRIBE → CLEAN
```

- **FREEZE** = deterministic `snapshot.tar.gz`
- **FINGERPRINT** = SHA-256
- **STORE** = object storage
- **DESCRIBE** = RepositorySnapshot in PostgreSQL
- **CLEAN** = remove temporary/partial artifacts

---

## 23. Connection to later phases

After Step 13, Fluxora finally has a stable input artifact for code intelligence:

```text
RepositorySnapshot
      ↓
future analysis worker
      ↓
language/framework detection
      ↓
symbols
      ↓
imports / relationships
      ↓
graph
```

This is why Step 13 is an important boundary: later analysis can operate on a **frozen snapshot** rather than the moving GitHub repository.
