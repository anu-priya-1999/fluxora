# 1. `config.ts` → `DATABASE_URL`


First: **what is `DATABASE_URL`?**

Your PostgreSQL database is running separately from your TypeScript code.

Your application needs to know:

> "Which database should I connect to, and with which credentials?"

That information is represented by:

```env

DATABASE_URL=postgresql://postgres:password@localhost:5432/fluxora_dev

```

The general structure is:

```text

postgresql://USER:PASSWORD@HOST:PORT/DATABASE

```

For you:

```text

USER       = postgres

PASSWORD   = your PostgreSQL password

HOST       = localhost

PORT       = 5432

DATABASE   = fluxora_dev

```

## What does `config.ts` do?


Instead of letting every file directly read:

```ts

process.env.DATABASE_URL

```

we centralize that logic.

Conceptually:

```text

.env

  ↓

DATABASE_URL

  ↓

config.ts

  ↓

getDatabaseUrl()

  ↓

database connection code

```

So `config.ts` answers:

> **"What database configuration are we using?"**

It is configuration, **not the database connection itself**.

The Fluxora notes describe `config.ts` as the place handling `DATABASE_URL` and `getDatabaseUrl()`.

# 2. `pool.ts` → connection pool


Now we know **which database** we want.

Next question:

> **"How do we actually connect to PostgreSQL efficiently?"**

That's `pool.ts`.

## What's a database connection?


A connection is basically a communication channel between:

```text

Fluxora

   ↕

PostgreSQL

```

You could theoretically do:

```text

Request 1 → open connection → query → close

Request 2 → open connection → query → close

Request 3 → open connection → query → close

```

But repeatedly opening and closing connections is inefficient.

## Connection pool


Instead, we maintain a pool of reusable connections:

```text

              PostgreSQL

            /     |     \\

           /      |      \\

        Conn1   Conn2   Conn3

                 |      /

                 |     /

             Connection

                Pool

                 ↑

             Fluxora

```

When Fluxora needs to query PostgreSQL:

```text

API request

   ↓

pool

   ↓

borrow connection

   ↓

query PostgreSQL

   ↓

release connection

```

So:

> **`pool.ts` manages reusable database connections.**

It doesn't decide **what** a user is or **which query** to run. It manages the connection infrastructure. The learning notes identify connection pooling as a key backend concept here.

# 3. Repositories → persistence operations


Now we have:

```text

config.ts

= where is the DB?

pool.ts

= how do we connect to it?

```

Next:

> **"What do we actually do with the data?"**

That's where **repositories** come in.

You have:

```text

repositories/

├── organization.ts

└── user.ts

```

A repository organizes database operations for a specific domain object.

For example, conceptually:

```text

UserRepository

├── createUser()

├── findUser()

├── updateUser()

└── ...

```

and:

```text

OrganizationRepository

├── createOrganization()

├── findOrganization()

└── ...

```

So:

```text

API

 ↓

UserRepository

 ↓

PostgreSQL

```

The repository is a **persistence layer**.

### What does persistence mean?


Persistence means:

> **saving data so it survives after the application stops.**

For example:

```text

let user = {...}

```

exists in memory.

Restart the program:

```text

user → gone

```

But:

```text

user

 ↓

PostgreSQL

```

survives a restart.

The notes describe repositories as the layer that centralizes database access for Organization/User instead of scattering SQL across API handlers.

# 4. Tenant + RLS


This is **very important for Fluxora**.

## What is a tenant?


A **tenant** is a customer/organization using the same application.

For example:

```text

Fluxora

├── Acme

├── Globex

└── Umbrella

```

Here:

```text

Acme     = tenant

Globex   = tenant

Umbrella = tenant

```

Each organization has its own users and eventually its own repositories, analysis results, graph data, etc.

The architecture is explicitly designed as a multi-tenant system.

---

# 5. Why do we need tenant context?


Imagine PostgreSQL contains:

```text

users

id | organization_id | name

---+------------------+------

1  | A                | Alice

2  | A                | Bob

3  | B                | Carol

```

Alice belongs to Acme.

Carol belongs to Globex.

When Alice makes a request, Fluxora needs to know:

```text

current organization = Acme

```

Otherwise, how would the database know which organization's data she's allowed to see?

That's what **tenant context** is about.

Conceptually:

```text

User request

    ↓

Who is this user?

    ↓

Which organization?

    ↓

tenant context = Acme

```

Your `tenant.ts` is part of this mechanism.

---

# 6. What is RLS?


RLS = **Row Level Security**.

It is a PostgreSQL security feature.

Let's say the database contains:

```text

users

id | organization_id | name

---+------------------+------

1  | A                | Alice

2  | A                | Bob

3  | B                | Carol

```

If the current tenant is:

```text

A

```

RLS can make PostgreSQL enforce:

```text

Alice ✅

Bob   ✅

Carol ❌

```

Even though Carol is in the same table.

This is very important:

> The database itself participates in enforcing tenant isolation.

So the security chain becomes:

```text

Request

   ↓

tenant context

   ↓

PostgreSQL

   ↓

RLS

   ↓

only allowed rows

```

The architecture notes explicitly describe RLS as the database-level tenant security boundary.

---

# 7. Why not trust only the application?


Suppose the API is supposed to do:

```sql

SELECT *

FROM users

WHERE organization_id = 'A';

```

What if a developer accidentally writes:

```sql

SELECT *

FROM users;

```

Without a database-level safeguard, potentially all users are returned.

With RLS:

```text

Application makes mistake

        ↓

PostgreSQL

        ↓

RLS still applies

        ↓

unauthorized tenant rows blocked

```

That's called **defense in depth**.

# 9. What is a migration?


A migration is a controlled database change.

For example:

```text

Database version 0

        ↓

migration 0001

        ↓

Organization + User + RLS

```

Later:

```text

migration 0002

        ↓

Repository tables

```

Later:

```text

migration 0003

        ↓

Snapshots

```

Later:

```text

migration 0004

        ↓

Analysis tables

```

So migrations are basically **version history for your database schema**.

The Fluxora notes describe `0001` as the first migration and explain the later evolution model.

# 11. `migrate/runner.ts`


This is the **actual migration engine**.

Its job is roughly:

```text

1. Find migration files

2. Find which migrations are already applied

3. Determine what's missing

4. Execute missing SQL

5. Record them as applied

```

So:

```text

runner

  ↓

find migration files

  ↓

compare with migration history

  ↓

execute missing migrations

  ↓

record success

```

The notes describe exactly this role for `runner.ts`.

```text
plan_tier

```

So:

```text

0001_organization_user_rls.sql

```

> **"Database change #1: create the initial tenant/user/security foundation."**

# 13. `schema_migrations`


This is the piece people often miss.

We have migration files on the computer:

```text

packages/db/migrations/

0001_organization_user_rls.sql

0002_...

0003_...

```

But PostgreSQL also needs to remember:

> **"Which ones have already been executed?"**

That's what:

```text

schema_migrations

```

is for.

Conceptually:

```text

schema_migrations

name

-----------------------------

0001_organization_user_rls.sql

0002_repository.sql

0003_snapshot.sql

```

So next time you run:

```powershell

pnpm db:migrate

```

the runner can say:

```text

0001 → already done ✅

0002 → already done ✅

0003 → NOT done ❌

```

and execute only the missing migration.

```text

User

PlanTier

```

```text

 ↓

shared-types

```

> "The API uses the shared definitions of what these objects look like."

# 17. API → DB


The API needs actual data.

So:

```text

API

 ↓

 ↓

PostgreSQL

```

The DB package handles:

```text

repositories

queries

mappers

```

The Web does **not** directly use PostgreSQL.

That's an important security boundary.
