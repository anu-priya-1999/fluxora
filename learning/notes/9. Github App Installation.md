# GitHub App Installation

Step 10 connects a GitHub App installation to the Fluxora organization that belongs to the signed-in user. It stops there. No repository list, clone, snapshot, worker, or webhook is part of this step.

The current hosted split is: **web on Vercel, API on Render**. After GitHub redirects back to `/github/setup`, the **browser** obtains a Clerk session token and POSTs to the Render API. That is why CORS exists on this one API path.

---

## GitHub App vs Clerk

These are different credentials for different jobs.

Clerk is the login provider. After sign-in, Clerk gives Fluxora a session and the linked GitHub account: `externalAccounts[].provider === "github"` and `providerUserId`. That id is the GitHub user. Clerk does not grant Fluxora permission to read repositories, and Fluxora does not ask Clerk for a GitHub access token in this step.

The GitHub App is Fluxora's own integration. GitHub issues an App ID and a private key when the App is registered. Those prove "this process is the Fluxora App." They say nothing about which person is logged in.

Both are required at completion time:

1. Clerk session proves which Fluxora user is calling.
2. App JWT proves Fluxora may ask GitHub about an installation.
3. The installation's `account.id` must equal the Clerk GitHub user id.

Signing in with GitHub through Clerk does not install the App. Installing the App does not create a Fluxora session. The setup page is the join.

**Why Clerk is still needed if GitHub authenticates the installer:** GitHub's install UI proves the person can install the App on a GitHub account. It does not tell Fluxora which tenant row to write, and it does not create a Fluxora session. Fluxora's tenant is the Clerk user provisioned into `organizations` / `users`. Without Clerk, an installation id in a URL would have no trusted Fluxora identity.

## App ID vs installation ID

| Value | What it is | Where it lives |
| --- | --- | --- |
| App ID | One id for the Fluxora GitHub App | `GITHUB_APP_ID` on the API host (Render) |
| App private key | Signs the App JWT | `GITHUB_APP_PRIVATE_KEY` or `GITHUB_APP_PRIVATE_KEY_FILE` on the API host |
| App slug | Public name in `https://github.com/apps/{slug}` | `GITHUB_APP_SLUG` or `NEXT_PUBLIC_GITHUB_APP_SLUG` on the web host (Vercel) |
| Installation id | One install of that App on one GitHub account | Query string, then `github_installations.github_installation_id` |

The installation id is dynamic. GitHub creates it when someone installs or requests an update, then redirects the browser to the Setup URL with `installation_id` and `setup_action`. Nothing in the repo hard-codes an installation id, and `.env.example` does not have one.

A reinstall can produce a new installation id for the same GitHub account. The same completion call for the same id is a no-op.

**Why the id is dynamic:** an env var would freeze one person's install into every environment and would be wrong the moment they reinstall. GitHub is the source of the id; Fluxora only stores what GitHub just created, after verification.

---

## Why the id is a string

The HTTP body field is `github_installation_id` and it must be a JSON string of decimal digits. A JSON number is rejected.

`JSON.parse` turns numbers into IEEE-754 values. Integers above `Number.MAX_SAFE_INTEGER` (`9007199254740991`) round silently. GitHub ids are sent to PostgreSQL `bigint`, which can hold up to `9223372036854775807`. The API therefore:

- rejects non-strings
- rejects leading zeros, signs, decimals, and values that do not fit in `bigint`
- keeps the digits as a string in TypeScript
- writes `$n::bigint` and reads `column::text`

The parser also quotes integers in GitHub's JSON before `JSON.parse`, so a large `id` in the installation payload stays a string. Decimal numbers are left alone. An earlier version of that scanner quoted only the digits before a dot, which would have turned `1.5` into `"1".5` and broken the payload. The scanner now consumes a full JSON number and quotes it only when the whole token is an integer.

The existing user row still stores `users.github_user_id` through the Step 3 provision function, which takes a JavaScript number. Completion therefore also requires the Clerk GitHub user id to be a safe integer. An unsafe id is rejected instead of rounded. Installation ids themselves never pass through `Number`.

## GitHub App JWT

GitHub has no SDK call in this step. `node:crypto` `createSign("RSA-SHA256")` builds a JWT:

- header `alg=RS256`, `typ=JWT`
- `iss` is the App ID string
- `iat` is 60 seconds in the past, so a small clock skew does not make the token "issued in the future"
- `exp` is 9 minutes after `iat` (60s skew + 8 minute lifetime), under GitHub's 10-minute maximum
- the private key signs the token and is not placed inside it

The API then calls:

```text
GET https://api.github.com/app/installations/{installation_id}
Authorization: Bearer <app jwt>
Accept: application/vnd.github+json
User-Agent: fluxora
X-GitHub-Api-Version: 2022-11-28
```

Redirects are errors. The timeout is 10 seconds. A 404 is "installation not found." A 401 means the App credentials were rejected. Other failures are "GitHub unavailable." Response bodies are not logged.

This JWT is not an installation access token. Installation tokens last about an hour and are what later ingestion will use to read repositories. Step 10 does not mint or store them. The only persisted GitHub identifier is the installation id, plus the account id, login, and type needed to show what was verified.

**Why a short App JWT instead of an installation token here:** Step 10 only needs to *read the installation resource* as the App. An installation token would grant repository access that this step does not use and would be another secret to handle.

## Installation verification

The installation id in the query string is untrusted. Anyone can open `/github/setup?installation_id=123`.

The API loads that installation with the App JWT and accepts it only when:

- `account.type` is `User`
- `account.id` equals the Clerk `providerUserId`
- the id GitHub returned equals the id that was submitted

An Organization installation is rejected even if some other field looks familiar. Its `account.id` is the org id, not the person. The App JWT does not prove that the signed-in user is an owner of that org. Treating org installs as "belongs to this user" would attach the wrong tenant. Org support needs a later, explicit membership check.

Only Fluxora roles `owner` and `admin` may complete the call. The signed-in user is provisioned with the same Clerk → `fluxora_provision_github_user` path as `GET /api/v1/auth/me`, so the first completion still creates the organization if `/me` has not run yet.

**How another GitHub account is stopped from claiming an installation:** the attacker would need a Clerk session whose linked GitHub `providerUserId` equals GitHub's `account.id` for that installation. A victim's Clerk session cannot store an attacker's install, and an attacker's session cannot store the victim's install. If the installation id is already stored for another organization, the global unique index yields 409 `installation_conflict` without naming that organization.

## Clerk browser token flow

The first Setup URL implementation completed installation from the **Next.js server component**: `auth()` plus server-side `getToken()`, then a server-side `fetch` to the API.

That broke in production after the GitHub redirect:

- GitHub redirected successfully to `/github/setup?installation_id=...`
- the Vercel page rendered
- Clerk `auth()` reported the user as authenticated
- server-side `session.getToken()` returned `null`
- the page showed "Authentication required."

The shipped flow splits the work:

1. The **server** page (`page.tsx`) still uses `auth()` to decide signed-in vs `redirectToSignIn`, and still validates `installation_id` / `setup_action`. It reads `FLUXORA_API_URL` on the server and passes that origin into a client component. It does **not** read a Clerk JWT.
2. The **client** component (`github-setup-completion.tsx`) waits for Clerk `useAuth().isLoaded`, then calls `getToken()` in the browser.
3. `completeGithubInstallationFromBrowser` POSTs `{ github_installation_id }` to `{apiUrl}/api/v1/github/installations` with `Authorization: Bearer <token>`.

If `getToken()` is still null, the client shows "Authentication required." and does not call the API.

`FLUXORA_API_URL` is not a `NEXT_PUBLIC_*` variable. The server passes `apiUrl` as a React prop so the browser knows the Render origin without putting the private key (or any GitHub App secret) on the web host.

Root layout wraps the app in `ClerkProvider`. `apps/web/src/proxy.ts` runs `clerkMiddleware()` so Clerk cookies exist for `/github/setup`.

## Vercel → Render cross-origin request and CORS

A server-side POST from Next.js to Render is **not** a browser CORS request. A `fetch` from JavaScript running on `https://<vercel-app>` to `https://<render-api>` **is**.

Browsers will:

1. Send `OPTIONS /api/v1/github/installations` (preflight) because the POST has `Authorization` and `Content-Type: application/json`.
2. Only send the POST if the preflight response allows that origin, method, and those headers.

The native `node:http` API had no CORS handling until this path moved to the browser. CORS is implemented only for the GitHub installation path, not for `/healthz` or `/api/v1/auth/me`.

Allowed origins come from `CLERK_AUTHORIZED_PARTIES` (same list Clerk already uses for token `authorizedParties`). Default if unset: `http://localhost:3000`. Origins are compared exactly. `*` is never used.

Allowed methods in the header: `GET, POST, OPTIONS`. Allowed request headers: `Authorization, Content-Type`. Echoed origin plus `vary: Origin`.

**Why CORS is required:** the token now lives in the browser, so the completion POST is a cross-origin XHR/fetch. Without CORS, the browser blocks the call even if Render would have accepted it.

## How the GitHub setup redirect works

```text
Dashboard "Connect GitHub"
  → https://github.com/apps/{slug}/installations/new
  → user installs on their personal GitHub account
  → GitHub redirects GET to {web origin}/github/setup?installation_id=...&setup_action=install|update
  → Next.js server component: Clerk session check + query validation + read FLUXORA_API_URL
  → Client component: useAuth().getToken()
  → (browser) OPTIONS {FLUXORA_API_URL}/api/v1/github/installations   [if cross-origin]
  → (browser) POST {FLUXORA_API_URL}/api/v1/github/installations
     body: { "github_installation_id": "<digits>" }
     Authorization: Bearer <Clerk session token>
     Origin: <Vercel origin>
```

The dashboard change is only that link. The rest of the dashboard is unchanged. If the slug is missing or contains characters that are not a slug, the page says Connect GitHub is not configured instead of building a broken URL.

GitHub's redirect is a GET. Repeating the GET is safe because completion is idempotent. The ownership check is what stops a forged `installation_id` from being stored for the victim: the attacker's installation account will not match the victim's Clerk GitHub user, and the victim's installation will not match the attacker's session.

`FLUXORA_API_URL` must be `https`, or `http` on localhost / `127.0.0.1`, with no username or password in the URL. The helper stores only the origin (path is stripped).

If the user is signed out, `auth().redirectToSignIn` uses `returnBackUrl` built from `NEXT_PUBLIC_APP_URL` or `VERCEL_URL` so Clerk can send them back to the same setup query string.

## Tenant mapping and RLS

The row lives in `github_installations` (migration `0008_github_installations.sql`):

- `organization_id` → `organizations(id)` `ON DELETE CASCADE`
- `github_installation_id bigint` unique across all tenants
- unique `organization_id` (one current installation per organization)
- `github_account_type` must be `User`
- RLS select/insert/update/delete using `organization_id = fluxora_current_org_id()`
- `ENABLE` and `FORCE ROW LEVEL SECURITY`, same pattern as `users` and `jobs`

Writes go through `withTenant`, so the session variable is set inside the transaction. The insert also sends `organization_id` as a parameter. RLS is defense in depth, not the only filter.

RLS hides another organization's row, so a `SELECT` cannot tell you who already owns an installation id. The global unique index can. That is intentional: the database, not the application, stops a second tenant from claiming the same install.

Local reset already runs `TRUNCATE organizations CASCADE`. The new foreign key means installation rows disappear with the organization. Seed does not insert an installation. Connecting GitHub stays a real user action.

## Idempotency

`planGithubInstallationWrite` decides:

- no row → insert, `created: true`
- same installation id, account id, login, and type → return the row, `created: false`
- same account, new installation id or login → update (reinstall)
- different account id → reject

A concurrent duplicate insert can hit the unique index. See the PostgreSQL lesson below.

Replaying GitHub's setup redirect (same `installation_id`, same Clerk user) is the "unchanged" case: HTTP 200, `created: false`. That is why a GET Setup URL is acceptable.

---

## Least privilege

Configured on the GitHub App, not in code:

- Repository contents: Read
- Pull requests: Read
- Metadata: Read

No write permissions, no administration, no webhook subscription in this step. The code never asks GitHub for a broader token.

The web process is allowed to know `GITHUB_APP_SLUG` / `NEXT_PUBLIC_GITHUB_APP_SLUG`, `FLUXORA_API_URL`, and `NEXT_PUBLIC_APP_URL`. It never loads `GITHUB_APP_PRIVATE_KEY`. The browser only receives the public install URL (from the dashboard) and the API origin (as a prop on the setup page).

Logs go through `redactForLog`, which strips PEM blocks, `Bearer` tokens, and JWTs. Error responses use fixed codes and messages. GitHub response bodies and key material are not returned to the client.

Missing App configuration returns 503 `github_app_not_configured` and still lets `/healthz` start. A half-set App id or a non-PEM key fails when the API server is constructed, with a message that does not include the key.

## Secret handling

| Secret / setting | Who has it | Why |
| --- | --- | --- |
| `CLERK_SECRET_KEY` | API | Verify Clerk JWTs and load the Clerk user |
| Clerk publishable key / ClerkProvider | Web | Browser and Next.js session |
| `GITHUB_APP_ID` + private key | API only | Sign App JWTs |
| `GITHUB_APP_SLUG` | Web | Public install URL |
| `FLUXORA_API_URL` | Web server (passed to client as origin) | Where to POST |
| `CLERK_AUTHORIZED_PARTIES` | API | Clerk `azp` check **and** CORS allowlist |
| Installation id | Query string, then DB | Not a secret; still untrusted until GitHub verifies it |

**Why the private key must not be in Vercel:** Vercel is the Next.js frontend. Signing App JWTs is an API job. Putting the PEM on Vercel would expand who can mint App credentials, mix frontend env with GitHub App identity, and fight least privilege. Architecture's long-term store is a secrets manager; Step 10 follows the same env pattern the API already uses for `CLERK_SECRET_KEY`.

## Production vs local environment variables

**API (local):** `apps/api/src/env.ts` `loadRootEnv()` reads repo-root `.env` for keys that are not already set. Used by `apps/api/src/server.ts` and telemetry. GitHub App config is loaded later in `createApiServer()`, not at import time.

**API (Render):** hosted environment variables. Same names: `DATABASE_URL`, `CLERK_SECRET_KEY`, `CLERK_AUTHORIZED_PARTIES` (must include the exact Vercel origin, e.g. `https://fluxora-rho-cyan.vercel.app`, and `http://localhost:3000` if you still complete setup locally), `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` (or `_FILE` only if a file exists on that host), optional `GITHUB_API_BASE_URL`.

**Web (local):** Next.js / Vercel load env themselves. `apps/web/src/github/env.ts` used to copy selected keys from the repo-root `.env` with `node:fs`. That was emptied: `loadWebRootEnv()` is intentionally a no-op. The comment in that file says local web-specific variables should live in `apps/web/.env.local`. The leftover `ROOT_ENV_KEYS` list is only referenced with `void ROOT_ENV_KEYS` so it is not used.

**Web (Vercel):** set `GITHUB_APP_SLUG` (and/or `NEXT_PUBLIC_GITHUB_APP_SLUG`), `FLUXORA_API_URL` (https Render origin), `NEXT_PUBLIC_APP_URL` (https Vercel origin). Do not set the GitHub App private key.

`.env.example` still lists the GitHub App and web keys at the repo root for humans. Installation ids are explicitly not env vars.

PEM in `.env`: a real multiline PEM is not one env line. Use escaped `\n` (normalized by `normalizePrivateKeyPem`) or `GITHUB_APP_PRIVATE_KEY_FILE`.

## Security trade-offs

- Personal installations only. Faster and stricter. Org installs that a user administers are rejected until there is a real membership check.
- Setup completion starts from GitHub's GET. Required by GitHub's redirect. Safe only because the write is idempotent and the account is checked against Clerk.
- Token acquisition in the browser. Required after server `getToken()` returned null on Vercel. Cost: the completion POST is cross-origin, so the API must speak CORS.
- CORS allowlist reused from `CLERK_AUTHORIZED_PARTIES` instead of a second origin env var. Same trusted web origins Clerk already accepts as `azp`.
- CORS applied only on `/api/v1/github/installations`. Other API routes stay same-origin-or-server-called.
- App private key in the API environment or a file path. The architecture's long-term place is the secrets manager. Step 5 already has that abstraction; this step follows the same env pattern the API already uses for `CLERK_SECRET_KEY`, and it does not commit the key.
- `FORCE ROW LEVEL SECURITY` still does not apply to a PostgreSQL superuser. That is the existing local-dev behavior, not a new hole. The unique installation id still applies to superusers.
- Clerk user ids still cross a JavaScript number at the old provision function. Installation ids do not.

## Bugs and lessons from this implementation

These were found while writing and deploying the step. Typecheck, lint, test, build, and migrate were not executed as part of the documentation update.

1. PostgreSQL aborts the whole transaction on `unique_violation` (`23505`). Catching that error and then `SELECT`ing again fails with "current transaction is aborted." The installation write opens savepoint `fluxora_github_installation_write`, rolls back to it after a unique violation, and only then re-reads the caller's row. RLS is why the code cannot just look up the other tenant first: that row is invisible, so the unique index is the backstop.

2. Quoting JSON integers naively corrupts decimals. The installation parser must quote large integers so `JSON.parse` cannot round them, but it has to consume a full number token first.

3. A PEM pasted into `.env` with real line breaks is not one env value. The loader reads one line at a time. Use a single line with escaped `\n`, which `normalizePrivateKeyPem` turns back into newlines, or set `GITHUB_APP_PRIVATE_KEY_FILE` to a pem file that is not committed. The signing code accepts that normalized PEM. A GitHub "invalid JWT" or an OpenSSL decoder error is the usual symptom of a key that is still one line of literal `\n` or is not a PEM at all.

4. Importing the HTTP route module from a unit test also imports `apps/api/src/auth/clerk.ts`, which throws at import time when `CLERK_SECRET_KEY` is missing. The status-code mapper lives in `apps/api/src/github/http-error.ts` so the Step 10 tests can run without booting Clerk. Same family of bug as the Step 9 seed CLI: module evaluation runs top-level code. GitHub App config is loaded inside `createApiServer`, after `loadRootEnv()`, not at import time, so an unconfigured App does not prevent the module from loading.

5. GitHub rejects App JWTs whose `iat` is in the future or whose lifetime is over 10 minutes. The token is backdated 60 seconds and expires 9 minutes after `iat`.

6. **Server-side Clerk `getToken()` returned null after the GitHub redirect.** `auth()` still said the user was signed in. The Setup URL therefore could not POST a Bearer token from the Next.js server. Token acquisition moved to `useAuth().getToken()` in a client component. Verification, RLS, and GitHub App JWT signing stayed on the API.

7. **Cross-origin Vercel → Render required CORS.** Once the browser POSTed to Render, the native `node:http` server had to answer `OPTIONS` and attach CORS headers on `POST /api/v1/github/installations`. Allowlist is `CLERK_AUTHORIZED_PARTIES`, never `*`.

8. **Vercel / Turbopack failed when the web code manually loaded the repo-root `.env`.** The original `loadWebRootEnv()` used `node:fs` / `fileURLToPath` to copy `GITHUB_APP_SLUG`, `NEXT_PUBLIC_GITHUB_APP_SLUG`, `FLUXORA_API_URL`, and `NEXT_PUBLIC_APP_URL` from the monorepo `.env`. That does not belong in a Next/Vercel bundle. The function is now empty; Next and Vercel inject env. Local web values belong in `apps/web/.env.local`. The API still loads repo-root `.env` via `apps/api/src/env.ts`.

9. **React ref / lint in the client setup component.** Completing in `useEffect` needs to avoid double-POST and avoid `setState` after unmount. A ref-based "keep the latest `getToken`" pattern fights `react-hooks` lint. The shipped component lists `[apiUrl, installationId, isLoaded, getToken]` and uses a `cancelled` boolean in the effect cleanup instead of a ref.

10. **OPTIONS `writeHead` still calls `responseHeaders({})`.** In `apps/api/src/http/server.ts`, preflight first `applyCorsHeaders(res, preflight.headers)` via `res.setHeader`, then `res.writeHead(preflight.status, responseHeaders({}))`. The empty object does not pass CORS headers into `responseHeaders`. CORS therefore depends on Node merging headers already set with `setHeader`. POST responses go through `sendJson` → `responseHeaders({ content-type, ... })` after the same `applyCorsHeaders` call. The empty `responseHeaders({})` argument is leftover/incorrect wiring relative to passing `preflight.headers` into `writeHead`.
