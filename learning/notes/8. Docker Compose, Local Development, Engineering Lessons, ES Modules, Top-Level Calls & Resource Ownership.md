# 3. Docker Compose is a recipe

Compose defines the intended local infrastructure:

```text
PostgreSQL
Redis
MinIO
MinIO initialization
```

It does not mean Docker must run on every development machine.

Current hardware is only:

```text
Windows
4 GB RAM
```

so the practical local mode is:

```text
PostgreSQL → native PostgreSQL 18.6
Redis → in-memory adapter
Object storage → filesystem adapter
API/workers/web → native Node
```

The important architectural idea is the **contract**, not the container runtime.

# 4. Local vs production

Local:

```text
Postgres
InMemoryRedis
FilesystemObjectStorage
EnvSecretsProvider
```

Production:

```text
managed PostgreSQL
real/managed Redis
S3-compatible object storage
managed secrets
```

The application should not need business-logic rewrites when infrastructure changes.

# 5. Why port 5433 in Compose?

Native PostgreSQL already listens on:

```text
localhost:5432
```

Therefore Compose maps:

```text
host 5433 → container 5432
```

Otherwise there would be a host port collision.

# 6. Why MinIO?

MinIO gives local S3-compatible semantics.

That lets the code exercise an object-storage contract locally without using real AWS storage.

The conceptual mapping is:

```text
local → MinIO
production → S3
```

# 7. Migration vs seed

This distinction is fundamental.

## Migration

Changes **database structure**:

```text

column
index
constraint
function

```

## Seed

Creates **known development data**:

```text
local organization
local user
fixture records later
```

So:

```text
migration ≠ seed
```

Step 9 therefore does not need a new SQL migration.

# 9. Seed idempotency

A developer will run the seed command repeatedly.

A bad seed does:

```text
seed 1 → Org A
seed 2 → Org B
seed 3 → Org C
```

A good seed converges:

```text
seed 1 → Org A / User A
seed 2 → Org A / User A
seed 3 → Org A / User A
```

Fluxora was verified this way.

The same organization and user IDs were returned on repeated seed executions.

---

# 10. Why idempotency matters beyond seed

Distributed systems naturally retry.

Examples:

```text
worker crash
network timeout
lost acknowledgement
process restart
duplicate delivery
```

Therefore important operations should be safe to repeat.

A useful senior phrase:

> At-least-once execution becomes practical when handlers are idempotent.

# 11. Reset is destructive

Reset returns local development to a known state.

Conceptually:

```text
dirty local DB
     ↓
reset
     ↓
clean local DB
     ↓
seed
     ↓
known development state
```

But reset can delete a lot of data.

Therefore it must be guarded.

---

# 12. Fail-closed reset safety

The reset command validates that the target looks like local development:

```text
NODE_ENV = development
host = loopback
database = fluxora_dev
```

If those conditions are not satisfied:

```text
stop
```

rather than:

```text
truncate anyway
```

This protects against:

```text
wrong .env
wrong DATABASE_URL
wrong shell variable
wrong terminal
```

---

# 13. Why `TRUNCATE organizations CASCADE`

The organization is the tenant root.

Dependent rows can be cleared using the database's foreign-key relationships.

```sql
TRUNCATE TABLE organizations CASCADE;
```

This is powerful and destructive, which is exactly why the local-target guard matters.

# 14. The most important debugging lesson

The Step 9 reset verification found a runtime/module-lifecycle bug.

The initial seed module effectively looked like:

```ts
export async function seedLocalData() {
  // seed
}

async function main() {
  await seedLocalData();
  await closePool();
}

main();
```

The problem is the last line:

```ts
main();
```

---

# 15. What is a top-level call?

A **top-level call** is a function call written directly at module scope.

Example:

```ts
function main() {
  console.log("hello");
}

main();
```

This:

```ts
main();
```

is top-level because it is directly in the module.

Compare:

```ts
function start() {
  main();
}
```

Here `main()` is not top-level. It only runs when `start()` runs.

---

# 16. The critical ES module rule

Remember:

> Importing a module evaluates the module's top-level code.

But:

> Importing a function does not execute that function's body.

Example:

```ts
// seed.ts
export function seed() {
  console.log("seed");
}

function main() {
  console.log("main");
}

main();
```

Then:

```ts
// reset.ts
import { seed } from "./seed.ts";
```

The effective behavior is:

```text
seed function → defined
main function → defined
main()         → executed because it is top-level
seed()         → NOT executed automatically
```

This distinction is extremely important.

---

# 17. Why our reset bug happened

`reset.ts` needed:

```ts
import { seedLocalData } from "./seed.ts";
```

We only wanted the reusable seed function.

But importing `seed.ts` caused the module to be evaluated.

Because `seed.ts` contained:

```ts
main();
```

its CLI entrypoint also ran.

So the module had an unintended side effect when imported.

---

# 18. Why that caused a pool error

The seed CLI also participated in database-pool cleanup:

```ts
closePool();
```

The reset flow also needed to own cleanup.

That meant the same shared PostgreSQL pool could be closed more than once.

Observed error:

```text
Error: Called end on pool more than once
```

This was not a PostgreSQL schema problem.

It was a **module side-effect + resource ownership problem**.

---

# 19. Correct module/CLI design

Reusable logic:

```ts
export async function seedLocalData() {
  ...
}
```

CLI logic:

```ts
async function main() {
  await seedLocalData();
  await closePool();
}
```

Then:

```ts
if (isDirectExecution) {
  main();
}
```

Now:

```text
pnpm db:seed
    ↓
seed.ts directly executed
    ↓
main() runs
```

But:

```text
reset.ts imports seed.ts
    ↓
seedLocalData available
    ↓
seed.ts CLI main does NOT run
```

---

# 20. General lesson: resource ownership

A component that owns a resource should control its lifecycle.

Good:

```text
main
  ↓
acquire
  ↓
use
  ↓
release
```

Bad:

```text
module A acquires
module B secretly closes
module C closes again
```

Hidden ownership creates nondeterministic lifecycle behavior.

---

# 21. Why typecheck didn't catch the bug

The code was type-correct.

There was nothing syntactically/type-wise invalid about:

```ts
main();
```

The bug was behavioral:

```text
valid code
+
unexpected runtime side effect
```

Static typing generally cannot prove:

> "This module must never execute this function when imported."

That requires runtime/integration testing and architectural discipline.

---

# 22. Why verification mattered

The first broad quality gate passed:

```text
typecheck
lint
tests
build
```

But the explicit reset acceptance test exposed the lifecycle bug.

This is an important engineering lesson:

> Passing unit/type/build checks does not prove every integration lifecycle behavior is correct.

So we fixed the bug and reran the full quality gate.
