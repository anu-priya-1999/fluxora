# Fluxora — Personal Learning Notes — Part 4: Infrastructure Foundation

**Covers:** Phase 1, Step 5

---

## 1. The core idea

Step 5 introduces infrastructure boundaries for:

```text
Redis
Object storage
Secrets
```

The most important architectural lesson is:

```text
application
    ↓
stable interface
    ↓
local implementation OR production implementation
```

We therefore write both local and production adapters, but do not require production infrastructure to run on the 4 GB development machine.

---

## 2. Local vs production

```text
                    Fluxora application
                           │
                    stable interface
                           │
              ┌────────────┴────────────┐
              │                         │
           LOCAL                    PRODUCTION
              │                         │
     InMemoryRedisAdapter        RedisAdapter
                                  → real Redis

     FilesystemObjectStorage      S3ObjectStorage
                                  → AWS S3

     EnvSecretsProvider           SecretsManagerProvider
                                  → AWS Secrets Manager
```

This is a real production architecture with lightweight local implementations.

# Redis

## 4. Redis contract

`RedisClient` defines:

```text
get
set
delete
setIfAbsent
increment
expire
ping
close
```

The application depends on this interface.

---

## 5. Local Redis implementation

```text
InMemoryRedisAdapter
```

This is for local execution and tests.

It provides the same application-facing behavior without requiring a Redis server.

The important idea is:

> Local infrastructure can be lightweight while the application contract stays production-oriented.

---

## 6. Production Redis implementation

```text
RedisAdapter
```

uses the real Node Redis client.

Flow:

```text
application
    ↓
RedisClient
    ↓
RedisAdapter
    ↓
Node Redis
    ↓
Redis
```

The adapter translates the external Redis API into Fluxora's contract.

For example, the Redis `expire` operation returns a numeric result, while Fluxora's contract returns `boolean`. The adapter converts that result to `result > 0`.

---

## 7. Tenant-safe Redis keys

Helpers:

```text
organizationRedisKey()
cacheKey()
lockKey()
rateLimitKey()
```

Example:

```text
org:org-123:cache:repository:456
```

The organization is part of the namespace.

That makes tenant scoping an explicit infrastructure convention rather than letting every caller invent its own key format.

# Object storage

## 8. Why object storage?

PostgreSQL is the system of record for relational application data.

Repository snapshots and large artifacts belong in object storage.

Conceptually:

```text
PostgreSQL
    → relational metadata

Object storage
    → repository snapshots / large artifacts
```

---

## 9. Object storage contract

`ObjectStorageClient` provides:

```text
put
get
exists
delete
close
```

Implementations:

```text
ObjectStorageClient
        │
        ├── FilesystemObjectStorage
        └── S3ObjectStorage
```

---

## 10. Local filesystem adapter

```text
FilesystemObjectStorage
```

is used for local development and tests.

It lets us exercise real write/read/delete behavior without running MinIO or connecting to AWS.

---

## 11. Production S3 adapter

```text
S3ObjectStorage
```

uses the AWS S3 SDK.

Mapping:

```text
put    → PutObject
get    → GetObject
exists → HeadObject
delete → DeleteObject
```

The adapter accepts an injectable S3 client, which keeps it testable without requiring a real AWS bucket.

---

## 12. Tenant-safe snapshot paths

Fluxora uses:

```text
{organizationId}/{repositoryId}/{snapshotId}/{objectName}
```

Example:

```text
org-123/repo-456/snapshot-789/source/index.ts
```

The path helper rejects invalid segments and traversal patterns such as:

```text
../../secret.txt
```

The lesson:

> Storage keys are part of the security boundary, not just filenames.

# Secrets

## 13. Secrets contract

```text
SecretsClient
      │
      ├── EnvSecretsProvider
      └── SecretsManagerProvider
```

The application asks for a secret without knowing where it comes from.

---

## 14. Local secrets provider

```text
EnvSecretsProvider
```

reads from:

```text
process.env
```

This is the local implementation.

It does not mean environment variables are the production secret-management architecture.

---

## 15. Production secrets provider

```text
SecretsManagerProvider
```

uses AWS Secrets Manager.

Flow:

```text
application
    ↓
SecretsClient
    ↓
SecretsManagerProvider
    ↓
AWS Secrets Manager
```

---

## 16. Secret caching

```text
CachedSecretsClient
```

wraps another `SecretsClient`.

```text
application
    ↓
CachedSecretsClient
    ↓
SecretsClient
    ├── EnvSecretsProvider
    └── SecretsManagerProvider
```

The cache is:

```text
in-memory
short-lived
TTL-based
```

It is not written to disk.

This separates caching from the secret provider itself.

# Node 24 native TypeScript execution

## 17. `tsc` vs Node runtime

Fluxora currently has two different jobs:

```text
tsc --noEmit
    ↓
typechecking

node --experimental-strip-types --test
    ↓
direct TypeScript test execution
```

Node's strip-only runtime does not support TypeScript parameter properties.

For example, this failed:

```ts
constructor(
  private readonly source: SecretsClient,
) {}
```

So it was changed to:

```ts
private readonly source: SecretsClient;

constructor(source: SecretsClient) {
  this.source = source;
}
```

This was a runtime compatibility issue, not an architecture change.

# Testing

## 18. Runtime tests

The local test suite verifies:

```text
Redis key generation
Redis set-if-absent
Redis increment
Redis delete
Redis ping

filesystem object storage
write/read
```

Typechecking and runtime testing are different guarantees:

```text
Typecheck
→ type consistency

```

## 19. What we did not run locally

We did not require:

```text

Redis server
MinIO
AWS S3
AWS Secrets Manager
```

The production code exists, but production infrastructure is deferred to deployment.

# 20. Final mental model

```text
                 Fluxora application
                         │
              infrastructure interfaces
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
      Redis           Storage          Secrets
        │                │                │
    interface        interface        interface
        │                │                │
    ┌───┴───┐        ┌───┴───┐        ┌───┴──────┐
    ↓       ↓        ↓       ↓        ↓          ↓
  local    prod    local    prod    local       prod
    │       │        │       │        │          │

                                                Manager
```

The sentence to remember:

> **Stable interfaces allow Fluxora to use lightweight local infrastructure and real production infrastructure without rewriting application code.**
