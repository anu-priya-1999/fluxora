# 46. Change Mode Overlay

## Overview & System Role

Global Step 46 introduces **Change Mode** to the Fluxora Architecture Explorer (`apps/web`). It visualizes pull request blast radius and change-impact analysis results directly on top of the canonical architecture dependency graph, enabling developers and reviewers to see the ripple effects of code changes without navigating away from the system model.

Rather than generating an isolated sub-graph or disconnected report table, Change Mode is an **interactive visual overlay** over the existing React Flow graph topology returned by `/graph/query`.

---

## 1. What Change Mode Is

Change Mode is a specialized exploration overlay within the Architecture Explorer. When activated for a given pull request and impact analysis record:
- The base dependency graph topology remains completely intact.
- Nodes directly altered by the PR diff are highlighted with high-contrast visual accents.
- Downstream nodes reached via dependency traversal are styled with chromatic indicators corresponding to propagation hop distance.
- Impacted API endpoints and asynchronous event producers/consumers are marked with dedicated semantic badges.
- Unaffected nodes are softened into the background, providing immediate clarity on the blast radius.

---

## 2. Why It Is an Overlay Instead of a Second Graph

Fluxora is built on the core invariant that the architecture graph is the authoritative digital twin of the software system.
- **Spatial Memory**: Engineers understand system architecture through spatial continuity—where services, modules, database tables, and queues sit relative to one another.
- **Context Preservation**: A separate "impact-only" graph strips out structural context. Reviewers cannot determine whether an impacted utility is isolated or part of a core ingestion pipeline without seeing unaffected neighbors.
- **Single Source of Truth**: The graph topology is fetched from `POST /graph/query`. Change Mode simply projects impact findings onto the existing nodes, ensuring zero divergence between architecture exploration and change-impact analysis.

---

## 3. How Persisted ImpactAnalysis Data Reaches the Frontend

The client never parses diffs or runs graph traversal algorithms. The data flow is strictly read-only and server-authoritative:

```
Pull Request Event / Manual Trigger
               │
               ▼
   PostgreSQL `impact_analyses` (Step 44 Persistence)
               │
               ▼
   GET /api/v1/impact-analyses/:id (Step 45 REST API)
               │  [Bearer JWT + Tenant RLS]
               ▼
   Frontend Normalization (`normalizeImpactAnalysisResponse`)
               │
               ▼
   NormalizedChangeModeState ($O(1)$ Sets & Maps)
               │
               ▼
   GraphCanvas + NodeRenderer + NodeInspectorPanel
```

1. The user enables Change Mode or navigates to `/explorer?impact_id=<uuid>`.
2. The client invokes `fetchImpactAnalysis(analysisId, sessionToken)` targeting `GET /api/v1/impact-analyses/:id`.
3. The server authenticates the session, verifies multi-tenant isolation via PostgreSQL Row-Level Security, and returns the durable record.
4. The frontend normalizes the response into a compact, lookup-efficient state.

---

## 4. Representation of Direct vs. Downstream Impact

Visual hierarchy distinguishes the source of change from transitive fallout:

| Impact Category | Visual Treatment | Badge / Label | Rationale |
| --- | --- | --- | --- |
| **Direct Change** (depth = 0) | Crimson border (`#dc2626`), 3px glowing ring, bright background | `Direct Change` (red badge) | Highest visual weight; immediately draws reviewer focus to edited code. |
| **Downstream Impact** (depth >= 1) | Chromatic amber border fading with hop distance, warm background | `Downstream (hop N)` (amber badge) | Distinct from direct changes; communicates progressive downstream risk. |
| **Unaffected Nodes** | Reduced opacity (`0.45`), subtle desaturation (`grayscale(30%)`) | None | Recedes into background while remaining interactive and clickable. |

---

## 5. Hop Distance and Confidence Semantics

- **Chromatic Hop Decay**: Downstream nodes use a graduated color scale:
  - Hop 1: `#d97706` (saturated amber)
  - Hop 2: `#f59e0b` (medium amber)
  - Hop 3+: `#fbbf24` (light amber)
- **Low-Confidence Findings**: Findings with confidence scores below 70% ($< 0.70$) are rendered with dashed borders (`2px dashed <color>`) and marked with an explicit `(low)` tag in both the node header and the inspector panel. Uncertainty is never obscured.

---

## 6. Identification of Affected APIs and Events

Architectural boundaries require special attention during code reviews:
- **Affected APIs**: Nodes categorized under `affected_apis` (HTTP endpoints, RPC methods) receive an emerald `API` badge (`#d1fae5` / `#047857`).
- **Affected Events**: Nodes categorized under `affected_events` (message schemas, event producers, Kafka consumers) receive a purple `Event` badge (`#ede9fe` / `#6d28d9`).

---

## 7. Evidence ID Preservation

Every impact finding generated by Step 43 and persisted by Step 44 links directly to deterministic evidence records via `EvidenceWriter`:
- The frontend normalization extracts, deduplicates, and lexicographically sorts all evidence IDs per node.
- When an impacted node is selected, `NodeInspectorPanel` displays the linked evidence IDs under "Linked Evidence IDs".
- Reviewers can trace any visual impact finding directly to AST provenance, source code coordinates, and git commits.

---

## 8. Unresolved Files and Truncated State Handling

- **Unresolved Files**: Non-code files (e.g., markdown documentation, images, configuration files without symbol nodes) cannot be mapped to dependency graph nodes. Rather than omitting them, the `ChangeModeBar` renders a warning banner with an expandable drawer listing each unresolved file path and reason.
- **Truncated Traversal**: If blast-radius traversal exceeded the configured `maxDepth` ceiling, the backend marks `truncated: true`. The frontend displays a prominent amber warning indicator detailing the truncation reason and the maximum depth reached.

---

## 9. Filter and Level-of-Detail (LOD) Interaction

Change Mode coexists deterministically with existing graph navigation features:
- **GraphFilters**: Node type, edge type, confidence threshold, and depth filters remain fully operational. Filtering nodes does not purge them from the normalized impact state.
- **Level-of-Detail (LOD)**: Zoom tiers (System, Module, Detail) continue to aggregate and de-aggregate nodes smoothly.
- **Slice Metrics**: If impacted nodes are hidden because of active filters or LOD clustering, the canvas LOD badge displays an active count (e.g. `• 3/5 impacted visible`), preventing false assumptions of safety.

---

## 10. Selection Priority & Inspector Integration

- **Selection Priority**: Selection state (`isSelected`) takes strict precedence over Change Mode styling. Selecting an impacted node applies the primary blue border (`#2563eb`) and focus ring, ensuring visual consistency across all exploration modes.
- **NodeInspectorPanel**: Selecting any node when Change Mode is active renders a dedicated "PR Impact Analysis" card showing:
  - Role (`Direct Change`, `Downstream`, or `Unaffected`)
  - Hop distance and confidence percentage
  - Contract flags (`API`, `Event`)
  - Direct links to durable evidence records

---

## 11. Security & Architecture Boundaries

1. **Zero Client Traversal**: The browser never executes graph traversal, AST parsing, or diff calculations.
2. **Zero Direct DB/GitHub Access**: The frontend communicates exclusively with `apps/api` via Bearer JWT. It never connects to PostgreSQL, Redis, MinIO, or GitHub directly.
3. **Multi-Tenant Isolation**: The backend enforces PostgreSQL Row-Level Security (`FORCE ROW LEVEL SECURITY`). Any attempt to fetch an impact analysis belonging to another organization returns `404 Not Found`.

---

## 12. State Management & Lifecycle

Change Mode supports six well-defined states:
1. **OFF**: Default explorer behavior; zero overlay styling.
2. **LOADING**: Fetching impact analysis from REST API; non-blocking spinner.
3. **PENDING / RUNNING**: Analysis scheduled or running on backend; automatic polling every 4 seconds.
4. **READY**: Impact findings successfully loaded, normalized, and visualized.
5. **EMPTY**: Analysis succeeded with 0 affected nodes; informative notice.
6. **ERROR**: Network or server failure; actionable error alert with "Retry" action that preserves the base graph.
