# 48. Evidence Completeness Audit & Hardening

## Overview & System Role

Global Step 48 inaugurates **Phase 7: Evidence Engine (Hardening Pass)** of the Fluxora Engineering Roadmap (`docs/architecture/17-implementation-roadmap.md`, Phase 7, Step 1).

In Fluxora's architecture, the digital twin is not merely a model of code relationships; it is an **evidence-backed deterministic truth engine**. Every single structural node, dependency edge, and change-impact finding is an engineering conclusion. If any conclusion can be created, persisted, or displayed without immutable provenance linking it to real source code lines, the system fails its core product thesis.

Global Step 48 audits every conclusion-producing write path across the monorepo, guarantees **100% Evidence Completeness**, closes identified edge-case gaps, hardens the static AST linter (`pnpm lint:evidence`), and proves atomic transaction rollbacks and tenant isolation across the database.

---

## 1. The Core Invariant: No Conclusion Without Evidence

```
             ┌─────────────────────────┐
             │ AST / Traversal Engine  │
             └────────────┬────────────┘
                          │ Discovered Conclusion
                          ▼
             ┌─────────────────────────┐
             │     EvidenceWriter      │
             └────────────┬────────────┘
                          │ Deterministic Evidence Input
                          ▼
             ┌─────────────────────────┐
             │   Atomic Transaction    │
             │                         │
             │  ┌───────────────────┐  │
             │  │ Conclusion Record │  │ (GraphEdge / ImpactAnalysis)
             │  └───────────────────┘  │
             │            ▲            │
             │            │ 1:1 Link   │
             │  ┌─────────┴─────────┐  │
             │  │   Evidence Record │  │ (Exact File, Symbol, Lines, Conf)
             │  └───────────────────┘  │
             └─────────────────────────┘
```

The system invariant states:
> **Every conclusion-producing graph write or impact result MUST have corresponding immutable evidence created via `EvidenceWriter` in the same atomic database transaction.**

If an evidence write fails, the conclusion write **must roll back**. If an evidence record is queried, it must reflect the real source coordinates without fabrication.

## 2. Gaps Discovered During Audit & Applied Remediations

1. **Impact Finding Evidence in Specialized Categories**:
   - *Issue*: In `saveImpactAnalysisTx`, while `directImpact` and `downstreamImpact` generated evidence inputs and received updated `evidenceIds`, the filtered categorized arrays (`affectedApis`, `affectedEvents`, `affectedServices`) were persisted using raw findings without populating `evidenceIds`.
   - *Fix*: Unified finding processing across all 5 categories using `processFinding(finding)`. When a node appears in multiple lists (e.g. an API route handler in both `downstreamImpact` and `affectedApis`), a single deterministic evidence input is generated, and the evidence ID is populated across all relevant lists.
2. **Static AST Linter Blind Spots**:
   - *Issue*: `verifyGraphWritePaths` only looked for graph edge writes (`INSERT INTO graph_edges`, `batchCreateGraphEdges`) in a restricted file list. It did not monitor graph node writes or impact analysis persistence methods (`saveImpactAnalysis`, `saveImpactAnalysisTx`, `persistPullRequestImpactAnalysis`).
   - *Fix*: Expanded regex and AST matcher in `packages/db/src/repositories/evidence-lint.ts` to detect both graph node/edge writes and impact analysis writes across `graph.ts`, `impact-analysis.ts`, `graph-builder.ts`, and `impact-handler.ts`.
3. **Workspace Path Resolution in CI**:
   - *Issue*: Running the linter from subdirectories or in tests caused relative path resolution failures.
   - *Fix*: Added `findWorkspaceRoot` to dynamically discover `pnpm-workspace.yaml`.
4. **Graph Build Multi-Tenant & Run Validation**:
   - *Issue*: `persistGraphBuild` did not explicitly validate that all incoming nodes, edges, and evidence belonged to the same `analysisRunId` and `organizationId`.
   - *Fix*: Added strict pre-flight validation preventing cross-run or cross-tenant contamination.

## 3. Graph Edge Evidence Across All Supported Types

Every graph edge in Fluxora represents a discovered relationship between two nodes. During Step 48, all 8 supported relationship types were validated end-to-end:

| Edge Type | Discovered Semantics | Source Node | Target Node | Evidence File / Symbol |
| --- | --- | --- | --- | --- |
| `IMPORTS` | Static module import | Module A | Module B | File containing `import ... from ...` |
| `CALLS` | Function/method invocation | Function A | Function B | Line range containing invocation |
| `EXTENDS` | Class/interface inheritance | Class A | Class B | Class declaration line range |
| `EXPOSES_ROUTE` | HTTP route registration | Route Node | Handler Symbol | Router file / handler definition |
| `EMITS_EVENT` | Event producer publish | Service / Symbol | Event Topic | Publish call site |
| `CONSUMES_EVENT` | Event subscriber handler | Event Topic | Consumer Symbol | Subscribe call site |
| `QUERIES_DB` | Database read reference | Symbol / Function | DB Table / Model | Query call site (e.g. Prisma find) |
| `WRITES` | Database write mutation | Symbol / Function | DB Table / Model | Mutation call site (e.g. Prisma create) |

## 4. Confidence Decay Preservation

During graph traversal, confidence decays exponentially with distance from the modified seed node:
$$\text{confidence} = \text{base\_confidence} \times (0.9)^{\text{depth}}$$

- Depth 1 (Direct Impact): $0.90$
- Depth 2 (Downstream Hop 1): $0.81$
- Depth 3 (Downstream Hop 2): $0.729$

**Evidence Invariant**: The evidence row created for an impact finding preserves the **exact decayed confidence** of the finding. It is NEVER artificially reset to `1.0` or rounded. Monotonic decay is verified across traversal hops.

---

## 5. Atomicity & Rollback Guarantees

Graph writes and evidence writes execute within a single client transaction:
```sql
BEGIN;
-- Write conclusion
-- Write evidence
COMMIT;
```
If an error occurs during evidence creation (e.g. invalid foreign key, malformed type, or constraint violation), the database transaction triggers `ROLLBACK`. Integration tests prove that:
1. No partial graph nodes or edges persist.
2. No partial impact analysis records persist.
3. Zero orphan conclusions can ever exist in the system.

---

## 6. Deterministic Evidence Identity & Idempotency

Evidence IDs are generated deterministically using SHA-256 (UUID v5):
- For Graph Edges: `uuid(analysisRunId + ":edge:" + sourceCanonicalId + "->" + targetCanonicalId + ":" + edgeType)`
- For Impact Findings: `uuid(analysisRunId + ":impact_finding:" + nodeId + ":" + filePath + ":" + path.join("->"))`

This guarantees:
1. Re-running the pipeline on identical code produces the exact same evidence IDs.
2. Upsert operations execute `ON CONFLICT (id) DO UPDATE` or `DO NOTHING`, creating **zero duplicate evidence rows**.
3. Different analysis runs on the same repository produce isolated, distinct evidence rows.
4. Non-member tenants are strictly isolated by Row-Level Security (RLS).
