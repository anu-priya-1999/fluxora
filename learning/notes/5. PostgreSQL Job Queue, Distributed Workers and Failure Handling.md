# 1. The 30-second mental model

Fluxora separates fast API work from expensive asynchronous work:

```text
Browser
   ↓
API
   ↓
enqueue job
   ↓
PostgreSQL jobs table
   ↓
Worker claims job
   ↓
Handler executes
   ↓
complete / fail
   ↓
retry / dead-letter
```

The sentence to remember:

> **Fluxora uses a PostgreSQL-backed, at-least-once job system. Jobs are tenant-scoped and idempotent; workers claim them with `FOR UPDATE SKIP LOCKED`, hold a lease, and either complete, retry, or dead-letter them.**

---

# 2. Why does Fluxora need workers?

Repository ingestion, analysis, graph construction, impact analysis, simulation, and AI reasoning can take much longer than a normal HTTP request should.

So:

```text
API
=
request/response work

Worker
=
background work
```

The API should not do:

```text
POST /analyze
   ↓
analyze entire repository
   ↓
wait 30 seconds
   ↓
respond
```

Instead:

```text
POST /analyze
   ↓
create durable job
   ↓
return job id
```

Then:

```text
worker
   ↓
claim job
   ↓
execute work
   ↓
persist result
```

This keeps the API responsive.

Fluxora already uses PostgreSQL as its system of record.

The MVP therefore avoids adding another infrastructure dependency just to implement a basic queue.

Instead:

```text
PostgreSQL
+

+
row locking
+

```

is enough to provide the queue semantics we need.

The scaling story is:

```text
MVP

        ↓

```

Important interview phrase:

> **I optimized the MVP for correctness and fewer moving parts, not premature infrastructure complexity.**

# 4. What exactly is a job?

A job is durable work waiting to be executed.

The important fields are:

```text
id
organization_id
type
payload
status
idempotency_key
attempt_count
max_attempts
available_at
locked_at
locked_by
lease_expires_at
last_error
created_at
started_at
completed_at
failed_at
```

### `organization_id`

The tenant that owns the job.

### `type`

The kind of work:

```text
repository.ingest
analysis.run
impact.analyze
simulation.run
ai.explain
```

Future Fluxora handlers will use types like these.

### `payload`

The structured input for the job.

### `status`

```text
pending
running
completed
failed
dead_letter
```

### `idempotency_key`

The logical identity of a submission.

### `attempt_count`

How many execution attempts have occurred.

### `max_attempts`

How many attempts are allowed.

### `available_at`

When the job is eligible to execute.

### `locked_by`

Which worker currently owns the job.

### `lease_expires_at`

When that temporary ownership expires.

### `last_error`

The latest execution failure.

# 5. What is at-least-once delivery?

Very important:

> **At-least-once means the system will not intentionally lose accepted work, but the same job may execute more than once.**

Example:

```text
Worker A claims job
      ↓
starts processing
      ↓
Worker A crashes
      ↓
lease expires
      ↓
Worker B reclaims job
```

The same logical job has now been attempted twice.

So Fluxora does NOT claim exactly-once execution.

Instead:

```text
durable work
+
safe re-execution
```

That is why idempotency matters.

---

# 6. What is idempotency?

Idempotency means:

> Repeating the same logical request should not create duplicate logical effects.

Fluxora uses:

```text
UNIQUE (organization_id, idempotency_key)
```

Therefore:

```text
Tenant A + key X
   ↓
Job A

Tenant A + key X again
   ↓
same Job A
```

but:

```text
Tenant B + key X
   ↓
Job B
```

So the idempotency scope is per tenant.

This was actually runtime-tested.

---

# 7. Why a database constraint instead of only application code?

A fragile approach is:

```text
SELECT existing job
       ↓
if none
       ↓
INSERT
```

Two concurrent requests could both see “none”.

Then both insert.

That is a race condition.

Fluxora instead lets PostgreSQL enforce the invariant:

```sql
UNIQUE (organization_id, idempotency_key)
```

and uses:

```sql
ON CONFLICT (organization_id, idempotency_key)
```

So the database arbitrates the race.

Interview phrase:

> **Idempotency is a database invariant, not merely an application convention.**

---

# 8. How does a worker safely claim a job?

This is one of my main interview concepts.

Two workers can ask for work at the same time:

```text
Worker A ──┐
           ├── PostgreSQL
Worker B ──┘
```

Fluxora uses:

```sql
FOR UPDATE SKIP LOCKED
```

Meaning:

```text
Worker A
   ↓
locks Job 1
   ↓
claims Job 1

Worker B
   ↓
sees Job 1 is already locked
   ↓
skips it
   ↓
can claim Job 2
```

This avoids double-claiming the same available row.

---

# 9. Why is `SKIP LOCKED` useful?

Without it, a worker may block behind another worker's row lock.

With:

```sql
SKIP LOCKED
```

the worker says, conceptually:

> "Give me an eligible job that is not currently locked; don't make me wait for somebody else's job."

That makes it suitable for a queue where many workers are polling concurrently.

---

# 10. Why do jobs need a lease?

A lock alone doesn't define long-lived worker ownership safely.

Suppose:

```text
Worker A claims Job 1
Worker A crashes
```

If ownership never expired, Job 1 could remain stuck forever.

Fluxora therefore stores:

```text
locked_by
lease_expires_at
```

The worker gets temporary ownership:

```text
claim
 ↓
running
 ↓
lease = 60 seconds
```

If the worker disappears:

```text
worker crashes
      ↓
lease expires
      ↓
job becomes claimable
```

This is similar conceptually to a queue visibility timeout.

---

# 11. Crash recovery

The failure sequence:

```text
Job 1
status = pending

      ↓

Worker A claims

      ↓

status = running
attempt = 1
locked_by = A
lease_expires_at = T

      ↓

Worker A crashes

      ↓

T passes

      ↓

Worker B claims same job

      ↓

attempt = 2
locked_by = B
```

I verified this against real PostgreSQL.

The observed behavior was:

```text
Worker 1 → attemptCount = 1

lease expires

Worker 2 → attemptCount = 2
```

This is an important interview proof point.

---

# 12. How do I stop a stale worker?

Consider:

```text
Worker A claims Job 1

A stalls

lease expires

Worker B reclaims Job 1

A wakes up
```

Worker A must not be able to say:

```text
complete Job 1
```

after Worker B owns it.

So completion requires:

```text
status = running
AND
locked_by = current worker
AND
lease_expires_at > now()
```

Therefore:

```text
stale Worker A
→ completion rejected

current Worker B
→ completion accepted
```

I runtime-tested this.

# 13. Job lifecycle

The core state machine is:

```text
             ┌────────────┐
             │   pending  │
             └─────┬──────┘
                   │
                 claim
                   │
                   ▼
             ┌────────────┐
             │   running  │
             └──┬─────┬───┘
                │     │
             success failure
                │     │
                ▼     ▼
          completed   failed
                       │
                     retry
                       │
                       ▼
                    pending
```

If attempts are exhausted:

```text
failed
  ↓
dead_letter
```

If a running job is abandoned:

```text
running
  ↓
lease expires
  ↓
eligible for reclaim
```

# 14. Completion

When the handler succeeds:

```text
running
   ↓
completeJob()
   ↓
completed
```

Completion clears execution ownership:

```text
locked_at = null
locked_by = null
lease_expires_at = null
```

and records:

```text
completed_at
```

# 15. Failure and retry

If the handler throws:

```text
running
   ↓
failJob()
```

Then:

```text
attempts remain
   ↓
failed
   ↓
retry
   ↓
pending
```

If the maximum is reached:

```text
failed
   ↓
dead_letter
```

The latest failure is stored in:

```text
last_error
```

---

# 16. Why dead-lettering?

Without dead-lettering:

```text
fail
retry
fail
retry
fail
retry
...
forever
```

That can consume worker capacity indefinitely.

So Fluxora uses:

```text
max_attempts
```

and eventually:

```text
dead_letter
```

The queue therefore has a finite failure boundary.

# 17. Worker architecture

The worker is deliberately generic:

```text
JobWorker
   ↓
claimNextJob()
   ↓
find handler by job.type
   ↓
execute handler
   ↓
complete OR fail
```

The worker itself does not contain product-specific repository analysis logic.

Instead it uses a handler registry:

```text
{
  "test.echo": testEchoHandler,
  "repository.ingest": repositoryIngestHandler,
  ...
}
```

This keeps the queue engine independent from the future Fluxora workloads.

# 20. Tenant-aware jobs

A job contains:

```text
organization_id
```

Normal application DB operations are wrapped in tenant context.

PostgreSQL RLS remains enabled.

Therefore tenant isolation exists at multiple levels:

```text
application authorization
        +
PostgreSQL RLS
        +
tenant-scoped jobs
        +
tenant-scoped storage
        +
tenant-scoped cache keys
```

This is defense in depth.

# 21. The worker security subtlety

A normal API operation is naturally tenant-scoped:

```text
request
 ↓
organization context
 ↓
RLS
```

A worker must claim across organizations, so it needs a controlled privileged path.

Fluxora uses PostgreSQL `SECURITY DEFINER` functions for the queue primitives rather than casually disabling RLS.

Important interview distinction:

```text
local verification
=
PostgreSQL superuser

production
=
narrowly scoped worker privileges
```

The local role was:

```text
current_user = postgres
rolsuper = true
rolbypassrls = true
```

That was useful for validating queue mechanics. It is not the production credential model.

# 24. Interview answer: "How did you prevent duplicate jobs?"

> "I made idempotency a database invariant. Every job carries an organization ID and idempotency key, and PostgreSQL enforces a unique constraint on that pair. Enqueue uses conflict handling, so concurrent duplicate submissions resolve to the same logical job. I also verified that the same key is deduplicated inside one tenant while another tenant can independently use the same key."

---

# 25. Interview answer: "How did you handle worker crashes?"

> "A worker atomically claims a job with `FOR UPDATE SKIP LOCKED`, marks it running, stores its worker ID, and sets a lease expiry. If the worker crashes before completion, the lease expires and another worker can reclaim the job. I verified this by having a second worker reclaim the same job and observing the attempt count go from 1 to 2."

---

# 26. Interview answer: "Why PostgreSQL instead of SQS/Kafka?"

> "For the MVP, PostgreSQL was already the durable system of record, so a database-backed queue gave us durability and concurrency control without introducing another service prematurely. The worker contract is independent of the queue implementation, so at larger scale the queue can move to SQS or Kafka."

---

# 27. Interview answer: "Is this exactly-once?"

> **No.**

Better answer:

> "The queue provides at-least-once delivery. A worker crash can cause a job to execute again after lease expiry. Therefore handlers must be idempotent. I would not claim exactly-once end-to-end execution."

---

# 28. Interview answer: "Why `SKIP LOCKED`?"

> "`SKIP LOCKED` lets multiple workers claim different eligible rows concurrently without waiting on rows already claimed by another worker."

---

# 29. Interview answer: "How do you stop infinite retries?"

> "Each job tracks `attempt_count` and `max_attempts`. Failed work is retried while attempts remain; once the maximum is reached, the job moves to `dead_letter` so the system does not retry forever."

---

# 30. Interview answer: "How do you stop a stale worker?"

> "Completion requires the job to still be running, the caller's worker ID to match `locked_by`, and the lease to still be valid. A worker whose lease has expired cannot complete a job that another worker may have reclaimed."
