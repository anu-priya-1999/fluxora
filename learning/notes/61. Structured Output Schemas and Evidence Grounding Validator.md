# 61. Structured Output Schemas and Evidence Grounding Validator

## 1. Executive Summary & Problem Space

When integrating Large Language Models (LLMs) into high-assurance systems, the greatest operational risk is **uncontrolled probabilistic edge failure**:
1. **Schema Non-Compliance**: LLMs return Markdown fences (````json ... ````), conversational filler ("Sure, here is your JSON:"), missing keys, extra keys, or coerced types.
2. **Hallucinated Citations**: LLMs fabricate citations, invent identifiers, or reuse IDs from unrelated context to appear authoritative.
3. **Silent Degradation**: Permissive parser architectures that attempt to regex-extract JSON, strip unknown fields, or salvage partially valid responses mask underlying model failure and produce subtly corrupt domain data.

In Fluxora Global Step 61, we establish a **strict, deterministic admission-control boundary** between raw LLM text completions and Fluxora's verified product data structures.

This note explores the engineering architecture of strict schema validation, evidence-manifest grounding, bounded corrective retries, and the critical distinction between citation provenance and semantic entailment.

---

## 2. Architecture & Design Principles

### 2.1 Deterministic Admission Control
The AI layer never defines system truth (Principle P1/P10). The model's sole job is to explain already-computed deterministic impact analyses.

The Structured Output Validator acts as an **admission controller**:
- If the model's output conforms strictly to the task schema and cites only verified evidence IDs from the trusted manifest, it is admitted into the application layer.
- If the output violates schema constraints or cites a single ungrounded ID, it is rejected in its entirety (ADR-014).

```text
       ┌────────────────────────┐
       │   Raw LLM Completion   │
       └───────────┬────────────┘
                   │
                   ▼
       ┌────────────────────────┐
       │   Strict JSON Parser   │ ──(Fences, Prose, Malformed)──► Reject ($)
       └───────────┬────────────┘
                   │ Parsed Record<string, unknown>
                   ▼
       ┌────────────────────────┐
       │    Schema Validator    │ ──(Extra keys, Bad types)─────► Reject (Path)
       └───────────┬────────────┘
                   │
                   ▼
       ┌────────────────────────┐
       │   Grounding Validator  │ ──(Unknown ID, Duplicate ID)──► Reject (ID)
       └───────────┬────────────┘
                   │
         [All Checks Pass?]
         ├── Yes ──► Validated ImpactExplanationOutput
         └── No  ──► Bounded Corrective Retry (Max 1) ──► Fail Closed
```

## 3. Strict JSON Parsing vs. Permissive Extraction

### The Danger of Permissive Parsing
Many AI libraries employ "forgiving" regex parsers that search for the first `{` and last `}` in a response. This introduces critical vulnerabilities:
- **Prompt Injection Echo**: If a repository file contained a JSON snippet like `{"summary": "Attacker payload"}`, a regex extractor might latch onto the injected snippet rather than the model's actual answer.
- **Ambiguous Syntax**: Markdown fences often signal that the model misunderstood the formatting instructions or began generating conversational prose before or after the code block.

### Strict Parsing Rules
Under `apps/workers/src/ai/structured-output/parser.ts`:
1. **No Code Fences**: Any text beginning or ending with ```` ``` ```` is rejected immediately with `MARKDOWN_CODE_FENCE_DETECTED`.
2. **No Surrounding Prose**: The entire trimmed text must parse as JSON via `JSON.parse()`. Trailing commentary like `"...} Hope this helps!"` triggers `JSON_PARSE_ERROR`.
3. **Object Root Only**: Arrays (`[...]`), primitives (`42`, `"text"`, `true`), and `null` are rejected with `INVALID_ROOT_TYPE`.
4. **No Auto-Repair**: Syntax errors are never patched or guessed.

## 4. The Canonical 4-Field Impact-Explanation Contract

Following `docs/architecture/09-ai-architecture.md §9.6`, the schema for `impact_explanation` contains exactly four properties:

```typescript
export interface ImpactExplanationOutput {
  readonly summary: string;
  readonly claims: readonly ImpactExplanationClaim[];
  readonly confidence: ImpactExplanationConfidence; // 'high' | 'medium' | 'low'
  readonly caveats: readonly string[];
}

export interface ImpactExplanationClaim {
  readonly text: string;
  readonly evidence_ids: readonly string[];
}
```

### Constraint Enforcement Matrix
1. **Forbidden Properties**: Any extra property at the root (e.g. `suggestions`, `model_manifest`) or inside a claim object (e.g. `severity`, `confidence`) is rejected with `UNRECOGNIZED_PROPERTY`.
2. **Non-Empty String Validation**: Required strings (`summary`, `claim.text`, `caveat`, `evidence_id`) must not be empty or whitespace-only (`EMPTY_STRING`).
3. **Hard Bounds**:
   - `summary`: $\le 2,000$ characters.
   - `claims`: $\le 50$ items.
   - `claim.text`: $\le 1,200$ characters.
   - `claim.evidence_ids`: 1 to 20 IDs per claim.
   - `evidence_id`: $\le 128$ characters.
   - `caveats`: $\le 20$ items ($\le 500$ characters each).
   - Returned validation issues: $\le 20$ issues (`MAX_VALIDATION_ISSUES = 20`, enforced in `validator.ts`).
   - Corrective retry feedback issues: $\le 10$ issues (`MAX_CORRECTIVE_FEEDBACK_ISSUES = 10`, enforced in `retry.ts`).
4. **Zero Coercion**: Numbers are not parsed from strings, uppercase enums (`"HIGH"`) are not lowercased, and missing fields are not substituted with defaults.

## 5. Evidence Grounding & The Three-Level Guarantee Model

A critical contribution of Step 61 is formalizing the **Three Levels of Grounding Guarantees**:

```text
Level 1: Structural Evidence Association (Step 60 — Context Assembler)
  - Subject Type === "impact_finding"
  - Matching analysisRunId and impactAnalysisId
  - Exact subject node matching (subjectId === finding.node.id)
  - Result: Allowed Evidence Manifest (allowedEvidenceIds)

Level 2: Evidence Manifest Membership (Step 61 — Output Validator)
  - Every claim must cite >= 1 evidence ID
  - Every cited ID must exist in allowedEvidenceIds
  - Result: Citation Provenance and Allowlist Compliance

Level 3: Semantic Evidence Support (Step 65 / Human Review)
  - Does the evidence text substantively support the claim?
  - Acknowledged Limitation: Manifest membership does NOT guarantee semantic support.
```

### Why Manifest Membership Does Not Equal Semantic Truth
Consider a model that generates:
```json
{
  "claims": [
    {
      "text": "The payment service database schema was completely dropped.",
      "evidence_ids": ["ev-payment-route-1"]
    }
  ]
}
```
If `ev-payment-route-1` is in the allowed manifest (because the PR touched a route in `PaymentService`), the Level 2 validator confirms:
- Provenance: Valid.
- Allowlist: Compliant.

However, the evidence record actually describes an HTTP route modification, NOT a database drop. **Manifest membership alone cannot detect semantic distortion.**

Failing to document this distinction creates a false sense of security. Fluxora explicitly documents that Level 2 validation guarantees citation provenance, while semantic support is an acknowledged limitation evaluated in Step 65.

## 6. Strict Whole-Response Rejection vs. Partial Stripping (ADR-014)

When a model response contains an ungrounded citation (e.g. 4 valid claims and 1 citing a fabricated ID), there are two approaches:
1. **Partial Stripping**: Delete the invalid claim or strip the bad ID.
2. **Whole-Response Rejection (Fluxora's Decision)**: Reject the entire completion.

### Why Whole-Response Rejection is Superior
- **Semantic Integrity**: If the model wrote: *"The PR modifies Auth. Consequently, Billing is broken"*, and the validator strips the Auth claim because of an invalid ID, the remaining Billing claim loses its logical antecedent.
- **Audit Transparency**: Silent stripping hides prompt degradation and model hallucinations from operators and evaluation harnesses.
- **Fail-Closed Safety**: In mission-critical infrastructure software, showing a deterministic fallback explanation (Step 66) is far safer than showing a mutilated, partially stripped AI response.

## 7. Bounded Corrective Retries

When validation fails, Step 61 provides a bounded corrective retry helper (`validateImpactExplanationWithRetry`):

### The Two-Attempt Invariant
- **Total Attempts**: At most 2 (1 initial generation + 1 corrective retry).
- Validation retries are completely separate from Step 59's provider-level network/rate-limit retries.

### Deterministic Feedback Construction
The corrective system instruction:
1. Formats up to 10 validation issues (`MAX_CORRECTIVE_FEEDBACK_ISSUES = 10`) by error code and path (`- [UNKNOWN_EVIDENCE_ID] at 'claims[0].evidence_ids[0]': ...`), preventing prompt bloat while the caller result retains up to 20 issues (`MAX_VALIDATION_ISSUES = 20`) for downstream diagnostics.
2. Instructs the model to return ONLY raw JSON matching the 4 fields.
3. Re-iterates that only IDs from the original allowed manifest are permitted.
4. **Safety Rule**: Never includes raw prior model output in the prompt or error list, preventing feedback reflection attacks.

### Exception Transparency
If the model provider fails during retry (e.g., Anthropic returns 429 or network timeout), the retry helper does NOT convert that error into a validation failure. The exception propagates cleanly so calling orchestrators can distinguish provider downtime from model formatting failure.
