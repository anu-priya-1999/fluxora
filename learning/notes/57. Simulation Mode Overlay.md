# 56. Simulation Mode Overlay in Architecture Explorer (Global Step 57)

## Overview & System Role

Global Step 57 implements the **Simulation Mode Overlay in the Architecture Explorer** (`/repositories/[repoId]/explorer`), bridging the gap between persisted failure scenario computations and interactive spatial architecture graphs (`docs/architecture/17-implementation-roadmap.md`, Phase 8 Step 6).

### The Phase 8 Architectural Arc (Steps 53–57)

To understand Step 57's system role, one must trace the end-to-end progression of Phase 8:
1. **Step 52 (Persistence Foundation):** Designed the relational schema for `Scenario`, `Simulation`, and `SimulationResult` entities with PostgreSQL Row-Level Security (RLS) policies.
2. **Step 53 (Rule Table):** Codified pure, deterministic failure propagation rules (e.g. `RPC_UNAVAILABLE_FALLBACK`, `EVENT_PRODUCER_OFFLINE`, `RPC_LATENCY_TIMEOUT`) mapping topological connections and AST metadata to resulting component states without relying on an LLM.
3. **Step 54 (Deterministic Simulation Engine):** Implemented an iterative worklist breadth-first search (BFS) propagation engine enforcing monotonic state transitions (`healthy` $\to$ `at_risk` $\to$ `degraded` $\to$ `failed`) and recording discrete provenance with `EvidenceWriter`.
4. **Step 55 (Authenticated Simulation APIs):** Exposed Node.js HTTP endpoints (`POST /api/v1/scenarios`, `POST /api/v1/scenarios/:id/run`, `GET /api/v1/simulations/:id`, `GET /api/v1/simulations/:id/results`) guarded by Clerk bearer token authentication and strict tenant boundaries.
5. **Step 56 (Simulation Studio UI):** Provided a dedicated experiment workbench at `/simulations` where engineers formulate failure hypotheses, configure scenarios, trigger synchronous runs, and inspect tabular casualties and causal timelines.
6. **Step 57 (Simulation Mode Overlay):** Projects these persisted simulation results onto the living architectural canvas of the Architecture Explorer.

### Why Persisted Simulations Need Graph Visualization

Tabular casualty lists (such as those in Simulation Studio) answer *what* failed: they list node IDs, resulting states, and applied rules in an indexable table. However, software architectures are complex directed networks. When an outage occurs, an engineer's mental model requires answering spatial and topological questions:
- *Where* is the failure concentrated within the workspace or service boundary?
- *Which* exact network edge or RPC dependency transmitted the fault across services?
- *Where* did the blast radius terminate, and was that termination stopped by a resilient boundary (like a circuit breaker) or because the component had no incoming dependents?
- *How* does the failure cascade relate to the surrounding, unaffected components in the system?

Step 57 provides this spatial comprehension by projecting verified simulation outcomes onto the React Flow architectural graph, highlighting exact causal edges, distinguishing evaluated health from unreached components, and surfacing causal step timelines in the Node Inspector—all while preserving the deterministic core invariants of Fluxora.

## 2. Analysis-Run Snapshot Consistency

### The Threat of Topological Contradiction

In Fluxora, an `AnalysisRun` represents an immutable, point-in-time snapshot of an indexed codebase. A dependency graph generated by `GraphBuilder` belongs to exactly one `AnalysisRun`. Similarly, a `Simulation` executed by the Step 54 engine is bound to the `analysis_run_id` of the graph against which its rules were evaluated.

If the Architecture Explorer allowed rendering a simulation from Snapshot A over the graph canvas of Snapshot B, catastrophic semantic contradictions would occur:
1. **Dangling or Absent Entities:** Nodes or edges referenced in Snapshot A's simulation results might have been deleted, renamed, or refactored away in Snapshot B.
2. **False Causal Paths:** A causal propagation step asserting that `orders-service` failed because edge $E_{42}$ transmitted a synchronous RPC failure to `payment-gateway` could point to an entirely different edge or unrelated service in Snapshot B.
3. **Deceptive Safety Guarantees:** An engineer inspecting Snapshot B (which may contain a newly introduced circuit breaker) might observe an old simulation from Snapshot A (where no circuit breaker existed) and assume the architecture is vulnerable, or vice versa.

### The Context Mismatch Guard

In `apps/web/src/app/repositories/[repoId]/explorer/explorer-client.tsx`, when simulation metadata is retrieved from `GET /api/v1/simulations/:id`, the client performs strict context verification before applying the overlay:

```ts
// apps/web/src/app/repositories/[repoId]/explorer/explorer-client.tsx
if (simRes.data.analysis_run_id !== context.analysisRunId) {
  setSimulationModeState((prev) => {
    if (!prev.enabled || prev.simulationId !== targetSimulationId) return prev;
    return {
      ...prev,
      status: "error",
      errorMessage: `Analysis run mismatch: Simulation belongs to run ${simRes.data.analysis_run_id}, but current explorer is displaying run ${context.analysisRunId}.`,
    };
  });
  return;
}
```

If a mismatch is detected:
- The overlay transitions to an explicit error state (`status: "error"`).
- The existing graph topology is left completely untouched.
- No partial results or foreign node badges are overlaid on the React Flow canvas.

## 3. Semantic Truth for Absent Nodes ("No Result" vs "Healthy")

### The Open-World Assumption in Static Failure Modeling

A fundamental principle of deterministic software digital twins is **honest representation of evidence**:
$$\text{Evaluated Result} \neq \text{Default State}$$

In deterministic failure simulation, traversal begins at an injected seed node and propagates outward strictly across connected dependency edges where deterministic rules match. Graph nodes that are never reached during traversal fall into an open-world category: the engine did not evaluate them.

Consider the four distinct categories of nodes in the system during an active simulation:

| Node Classification | Engine Status | Simulation Result Set | UI Appearance | Inspector Representation |
|---|---|---|---|---|
| **Failed** | Evaluated | Present (`resulting_state: "failed"`) | Red border (`#dc2626`), red tint (`#fef2f2`), `FAILED` badge | Resulting state, rule applied, confidence, causal path |
| **Degraded** | Evaluated | Present (`resulting_state: "degraded"`) | Amber border (`#d97706`), amber tint (`#fffbeb`), `DEGRADED` badge | Resulting state, rule applied, confidence, causal path |
| **At Risk** | Evaluated | Present (`resulting_state: "at_risk"`) | Yellow border (`#eab308`), yellow tint (`#fefce8`), `AT RISK` badge | Resulting state, rule applied, confidence, causal path |
| **Healthy** | Evaluated | Present (`resulting_state: "healthy"`) | Emerald border (`#059669`), emerald tint (`#ecfdf5`), `HEALTHY` badge | Resulting state, rule applied, fallback/boundary evidence |
| **Unreached / Unaffected** | **Not Evaluated** | **Absent** | **Normal Explorer Appearance** (opacity 1.0, base type border/bg, no simulation badge) | *"No simulation result for this node. This node was not reached by the simulation propagation path."* |
| **Invalid / Unrecognized** | Malformed | Present, non-canonical state | **Normal Explorer Appearance** (retained in `invalidResultsByNodeId` for diagnostics) | Unrecognized State error banner explaining exclusion from canonical metrics |

### Why Fabricating "Healthy" Badges Destroys Trust

If unreached nodes were painted green or given a `HEALTHY` badge:
1. **Fabricated Invariant:** The system would be asserting that an unreached service (e.g. an isolated microservice, an upstream caller, or a service three hops removed past an uncapped path) was formally proven to be operational under the outage scenario.
2. **Masked Blind Spots:** If a missing dependency edge in the static extraction phase prevented the simulation engine from traversing into a downstream dependency, painting that unreached dependency green would falsely assure engineers that it is safe from cascade failures.

Therefore, `node-styles.ts` and `NodeRenderer.tsx` enforce:
- Only nodes with explicit entries in `resultsByNodeId` receive simulation styling and badges.
- Absent nodes retain full opacity (`1.0`) and their standard component border colors.
- The Node Inspector explicitly clarifies the lack of simulation evaluation.

## 4. Normalized Simulation View Model & Rendering Performance

### The High-Frequency Render Problem

React Flow operates at 60 frames per second during user pan, zoom, drag, and Level-of-Detail (LOD) transitions. On large architectural graphs ($N \approx 500$ nodes, $E \approx 1200$ edges), any linear search ($O(M)$ where $M$ is simulation results) executed inside node or edge render loops yields unacceptable computational complexity:
$$\text{Per-frame cost} = O(N \cdot M + E \cdot M)$$

For $N=500$ and $M=200$, a single render cycle would execute over $100,000$ operations, causing noticeable frame stutter and UI jank.

### $O(1)$ Indexed View Model (`simulation-mode-data.ts`)

To eliminate this bottleneck, `normalizeSimulationResponse` processes raw API responses **once** upon arrival, compiling them into an immutable `NormalizedSimulationModeState` structure backed by ES6 `Map` and `Set` lookups:

```ts
export interface NormalizedSimulationModeState {
  readonly enabled: boolean;
  readonly simulationId: string | null;
  readonly analysisRunId: string | null;
  readonly executionStatus: SimulationStatus | null;
  readonly status: SimulationModeStatus;
  readonly errorMessage: string | null;

  // Indexed results for O(1) node rendering
  readonly resultsByNodeId: ReadonlyMap<string, SimulationResultResponse>;
  readonly resultingStateByNodeId: ReadonlyMap<string, SimulationResultState>;
  readonly invalidResultsByNodeId: ReadonlyMap<string, SimulationResultResponse>;
  readonly ruleByNodeId: ReadonlyMap<string, string>;
  readonly confidenceByNodeId: ReadonlyMap<string, number>;
  readonly assumptionsByNodeId: ReadonlyMap<string, readonly string[]>;
  readonly causalStepsByNodeId: ReadonlyMap<string, readonly SimulationCausalStep[]>;
  readonly hasCappedByNodeId: ReadonlyMap<string, boolean>;

  // Verified causal edge IDs from structured propagation steps
  readonly causalEdgeIds: ReadonlySet<string>;

  // Aggregate metrics precalculated once
  readonly totalResultsCount: number;
  readonly failedCount: number;
  readonly degradedCount: number;
  readonly atRiskCount: number;
  readonly healthyCount: number;
  readonly cappedCount: number;

  readonly converged?: boolean | undefined;
  readonly iterations?: number | undefined;
  readonly ruleTableVersion?: string | undefined;
}
```

With this view model:
- `NodeRenderer.tsx` checks `resultingStateByNodeId.get(node.id)` in $O(1)$ time.
- `GraphCanvas.tsx` checks `causalEdgeIds.has(edge.id)` in $O(1)$ time.
- Total per-frame overhead drops to $O(N + E)$, maintaining smooth 60 FPS interactions.

### Deterministic Duplicate Resolution & Causal Edge Derivation

During multi-path graph propagation, multiple propagation paths may converge on the same node (e.g. Path A evaluates Node X as `at_risk`, while a subsequent Path B evaluates Node X as `failed`).

```text
       [Seed Failure]
          /      \
         v        v
     [Node A]   [Node B]
         \        /
       (Path 1) (Path 2)
      at_risk    failed
          \      /
           v    v
          [Node X]
```

`normalizeSimulationResponse` resolves duplicates deterministically by **state severity**:
$$\text{failed (4)} > \text{degraded (3)} > \text{at\_risk (2)} > \text{healthy (1)}$$

```ts
// apps/web/src/components/graph/simulation-mode-data.ts
const existingState = resultingStateByNodeId.get(r.node_id);
if (existingState !== undefined) {
  const existingSeverity = SIMULATION_STATE_SEVERITY[existingState] ?? 0;
  const newSeverity = SIMULATION_STATE_SEVERITY[rawState] ?? 0;
  if (newSeverity <= existingSeverity) {
    continue; // Reject lower or equal severity duplicate
  }
  // Decrement prior count if replacing with higher severity
  if (existingState === "failed") failedCount--;
  else if (existingState === "degraded") degradedCount--;
  else if (existingState === "at_risk") atRiskCount--;
  else if (existingState === "healthy") healthyCount--;

  const prevHadCapped = hasCappedByNodeId.get(r.node_id);
  if (prevHadCapped) cappedCount--;
}
```

#### The Stale Causal Edge Leakage Trap
A subtle architectural trap occurs if causal edge IDs are accumulated into `causalEdgeIds` *during* the initial linear scan over raw results. If an intermediate `at_risk` result references Edge $E_1$, and is subsequently superseded by a `failed` result referencing Edge $E_2$, accumulating edges greedily would leave $E_1$ highlighted on the graph canvas.

To prevent this stale leakage, `normalizeSimulationResponse` derives `causalEdgeIds` and `ruleTableVersion` **exclusively** from the final accepted entries in `causalStepsByNodeId.values()` *after* duplicate resolution has completed:

```ts
// Derive causal edge IDs strictly from accepted results
const causalEdgeIds = new Set<string>();
let derivedRuleTableVersion: string | undefined = undefined;

for (const steps of causalStepsByNodeId.values()) {
  for (const step of steps) {
    if (step.edgeId && typeof step.edgeId === "string" && step.edgeId.trim().length > 0) {
      causalEdgeIds.add(step.edgeId.trim());
    }
    if (!derivedRuleTableVersion && step.ruleVersion && step.ruleVersion.trim().length > 0) {
      derivedRuleTableVersion = step.ruleVersion.trim();
    }
  }
}
```

## 5. Structured Causal Evidence & Step Parsing

### The `SimulationCausalStep` Contract

Every simulated state transition must be backed by causal evidence. In `@fluxora/shared-types`, a causal step is defined as:

```ts
export interface SimulationCausalStep {
  readonly nodeId: string;
  readonly edgeId?: string | null | undefined;
  readonly ruleId: string;
  readonly ruleVersion: string;
  readonly previousState: SimulationResultState;
  readonly resultingState: SimulationResultState;
  readonly assumptions: readonly string[];
  readonly confidence: number;
  readonly capped?: boolean | undefined;
}
```

### Robust Parsing Invariants (`extractSimulationCausalSteps`)

In `simulation-mode-data.ts`, `extractSimulationCausalSteps` parses the raw `propagation_path` array. It enforces strict semantic boundaries:

1. **Explicit Node Identity:** A structured causal step missing a `nodeId` is rejected. It is **never** filled in with `result.node_id`, which would falsely attribute another node's step in multi-hop chains.
2. **Canonical State Transitions:** `previousState` and `resultingState` must be canonical simulation states. If missing or malformed, the step is rejected. The normalizer never invents a synthetic `"healthy" \to \text{resultingState}` transition.
3. **Seed Step Handling:** Step 1 (the injected seed failure) represents a synthetic fault injection with no incoming edge. Its `edgeId` is `null` (rendered as `"None (Seed target failure)"` in the UI). The normalizer never creates phantom edge IDs.
4. **Circuit-Breaker Caps:** When a propagation rule detects an architectural boundary (e.g. a circuit breaker or fallback handler), `capped: true` is captured, triggering the `CAPPED` badge in the UI.
5. **Legacy String Entries:** If legacy string entries exist in `propagation_path` (e.g. `"target_failure"`), they are treated as diagnostic strings; they are never converted into invented state transitions or causal edges.

Edges on the React Flow canvas are styled based on set membership in `normalizedState.causalEdgeIds`:

- **Non-Causal Edges:** When Simulation Mode is active, non-causal edges receive muted opacity (`0.35`). This dims unrelated graph noise and allows the engineer to trace the exact cascade path across the topology.

## 7. Multiple Overlay Modes & Precedence

The Architecture Explorer supports two major analytical lenses:
1. **Change Mode (Step 46):** Visualizes pull request blast radius (`direct`, `downstream`, `unaffected`).
2. **Simulation Mode (Step 57):** Visualizes simulated failure propagation (`failed`, `degraded`, `at_risk`, `healthy`).

### Visual Precedence Hierarchy

Allowing both modes to apply border and badge styling simultaneously would cause visual incoherence (e.g. a node displaying conflicting colors or stacked badges).

Fluxora enforces a clear precedence hierarchy:

```text
Selected Node Styling (#2563eb, z-index 1000)
                    │
                    ▼  (if not selected)
Simulation Mode Overlay (when enabled and ready)
                    │
                    ▼  (if simulation mode disabled/idle)
Change Mode Overlay (when enabled and ready)
                    │
                    ▼  (if change mode disabled/idle)
Default Base Graph Styling (by component type)
```

### State Preservation & Seamless Restoration

When Simulation Mode is enabled:
- The active `changeMode` state is **preserved** in React state.
- `GraphCanvas` suppresses Change Mode styling while `simulationMode.status === "ready"`.
- When the user disables Simulation Mode or clicks "Clear", the canvas immediately reverts to displaying the active Change Mode overlay without requiring a re-fetch of PR impact data.
- User selection (`isSelected`) always overrides all overlays, ensuring consistent interactive keyboard and click navigation.

## 8. Polling Lifecycle & Asynchronous State Safety

Failure simulations that take longer to converge transition through `pending` and `running` states on the server.

### Bounded Polling Architecture (`explorer-data.ts`)

To track execution progress without infinite loops or memory leaks, Fluxora implements a bounded polling lifecycle governed by `createSimulationPollController` and `shouldScheduleSimulationPoll`:

1. **Bounded Budget:** Maximum **15 attempts** at **4,000 ms** intervals (a strict 60-second polling ceiling).
2. **Eligibility Predicate (`shouldScheduleSimulationPoll`):**
   ```ts
   export function shouldScheduleSimulationPoll(state: SimulationPollingState): boolean {
     return (
       state.enabled &&
       Boolean(state.simulationId) &&
       (state.executionStatus === "pending" || state.executionStatus === "running") &&
       (state.status === "pending" || state.status === "running")
     );
   }
   ```
3. **Suppression on Active Loading or Error:** If UI status is `"loading"` (an in-flight GET request is active) or `"error"`, polling is strictly suppressed. This prevents overlapping network requests and prevents infinite retry loops on 401, 404, or 500 errors.
4. **Per-Simulation ID Budget Isolation:** The controller tracks the attempt budget relative to a specific `simulationId`. Switching simulation IDs resets the budget counter to 0, ensuring that a previous simulation's exhausted budget does not starve a subsequent simulation.
5. **Deterministic Cleanup:** Timer handles are cancelled on React component unmount, mode disable, simulation clearing, or upon reaching a terminal status (`completed` or `failed`).
6. **Stale Response Protection:** In `explorer-client.tsx`, async fetch completions compare the target simulation ID against current state (`prev.simulationId !== targetSimulationId`). Any slow or out-of-order response from a previously requested simulation is safely discarded.
7. **Manual Refresh:** The UI provides an explicit "Refresh" button triggering a GET-based fetch at any time.

## 9. Honest Uncertainty & Confidence Communication

### The Trap of SLA Misinterpretation

Engineers and executives frequently misinterpret an algorithmic confidence score (e.g. `0.85`) as an empirical SLA probability (e.g. *"There is an 85% probability that this database will crash"*).

Fluxora strictly rejects this misrepresentation. The system enforces:

1. **Prominent Honest Notice:** Displayed in both `SimulationModeBar` and `NodeInspectorPanel`:
   > *"Simulation confidence reflects deterministic rule confidence and static metadata assumptions. It is not a real-world failure probability."*
2. **Transparent Metadata Assumptions:** The Node Inspector explicitly surfaces any static analysis limitation that influenced the decision (e.g. `"No circuit breaker detected on call"`, `"Target node injected with unavailable failure"`).
3. **Qualitative Latency Semantics:** The system explains that latency degradation models topological risk propagation under the `RPC_LATENCY_TIMEOUT` rule, rather than synthesizing fake millisecond histograms or queueing simulations.
4. **Fail-Closed Reporting:** Missing metadata or non-converged runs produce explicit warnings rather than optimistic assumptions.

## 12. Staff Engineering Trade-offs & Takeaways

| Architectural Decision | Chosen Strategy | Alternative Rejected | Rationale & Trade-off |
|---|---|---|---|
| **Data Normalization** | Pure normalization module (`simulation-mode-data.ts`) producing `Map` and `Set` | Ad-hoc array searches inside React Flow render loops | Avoided $O(N \cdot M)$ frame drops during 60 FPS panning/zooming; trade-off is small initial normalization overhead upon fetch completion. |
| **Absent Nodes** | Neutral representation (normal appearance, no badges) | Painting absent nodes green or labeling them `healthy` | Preserved truth in advertising; unreached $\neq$ evaluated and healthy. Prevents dangerous false senses of security. |
