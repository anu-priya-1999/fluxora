# Fluxora Step 7 — OpenTelemetry Observability Interview CheatSheet

## 1. What this step established

Fluxora adds OpenTelemetry-based observability so requests, background jobs, and important operations can be traced and measured across service boundaries.

## 2. 30-second interview answer

> “Fluxora treats observability as part of the architecture rather than an afterthought. OpenTelemetry gives a vendor-neutral way to produce traces and metrics around request and worker execution. The goal is correlation: when an ingestion job fails, I want enough context to follow the operation from API enqueue through worker execution and storage.”

## 3. Core questions

### Q1. What are the three common telemetry signals?

Traces, metrics, and logs. Traces show execution flow, metrics show aggregate behavior, and logs provide detailed event context.

### Q2. What is a trace?

A trace represents one end-to-end operation and contains spans describing meaningful work within that operation.

### Q3. What is a span?

A timed unit of work such as an HTTP request, database call, queue operation, GitHub API request, or snapshot upload.

### Q4. Why is context propagation important?

Without propagated context, an API request and the worker it triggers appear as unrelated operations. Correlation is what makes distributed debugging useful.

### Q5. What should be measured for a worker?

Execution duration, success/failure, retry count, queue wait time, external API latency, and storage time are strong candidates.

### Q6. Why avoid putting secrets into telemetry?

Telemetry systems often have wider access and longer retention than application secrets. Sensitive tokens and private keys should never be emitted into spans or logs.

## 4. Senior-level questions

### Q7. What makes a good span boundary?

A meaningful operation with useful timing and outcome information. Too many tiny spans create overhead and noise; too few make diagnosis difficult.

### Q8. How would you correlate queue jobs?

Include stable non-secret identifiers such as job ID, repository ID, or snapshot ID as attributes, while avoiding personal or secret data unless explicitly required.

### Q9. What is the cardinality problem?

Labels/attributes with an extremely large number of unique values can make metrics expensive or hard to aggregate. High-cardinality data may belong in traces/logs instead.

### Q10. How would you investigate a slow ingestion job?

Start with overall duration, then break the trace into queue wait, GitHub authentication/fetch, extraction, packaging, hashing, object upload, and DB persistence spans if instrumented.

### Q11. How does observability affect retries?

Retry storms can become visible through repeated failure counts, queue age, and latency. Telemetry should help distinguish a single bad request from systemic dependency failure.

### Q12. What is vendor neutrality useful for?

The application can emit standard telemetry without hard-coding business logic to one vendor. The backend/exporter can change later with less application impact.

## 5. Scenario questions

### Scenario: API succeeds but the worker fails later

Use a shared correlation identifier or trace context where supported and inspect the job record plus worker telemetry. The original HTTP 200 does not mean the asynchronous operation succeeded.

### Scenario: metrics look healthy but users report failures

Check whether the metric dimensions aggregate away the affected tenant/resource. Then inspect traces and logs for specific failures.

## 6. Common traps

- Logs are not a substitute for structured traces.
- More telemetry is not automatically better; noisy telemetry increases cost and reduces signal.
- Never put credentials into logs/spans just because they make debugging easier.

## 7. Strong closing statement

> “Step 7 makes the asynchronous architecture diagnosable. The queue can tell me that a job exists; observability helps me explain where time and failures actually occur.”
