# Step 50: Confidence-Based Visual Weighting Interview CheatSheet

## Core Narrative & Architectural Philosophy

**Q: What problem does Step 50 solve in Fluxora?**
- **The "Binary Dependency" Anti-Pattern**: Traditional dependency graph visualization tools treat all relationships as binary: an edge exists or it does not. In real software architectures, dependencies have varying degrees of certainty and strength:
  - An explicit TypeScript static `import` has 100% certainty.
  - A dynamically resolved import has 70%–89% certainty.
  - A naming-convention or heuristic link has < 70% certainty.
  - In a blast-radius analysis, a 4-hop downstream service is subject to traversal decay (`0.9 ** hop`) and has far less immediate impact risk than a direct 0-hop caller.
- **Fluxora's Uncertainty Presentation (Principle P3)**: Step 50 uses authoritative backend confidence values to visually weight edges, findings, and evidence citations so engineers can immediately distinguish verified facts from probabilistic inferences without hiding uncertainty or altering graph topology.

## Technical Highlights & Staff-Level Q&A

### 1. Where Does Confidence Originate, and Who Computes It?
- **Q**: "Why didn't you compute confidence decay in the frontend using the node's depth in the graph?"
- **Answer**:
  - Computing confidence in the browser violates the **Single Source of Truth** invariant.
  - Traversal depth decay (`0.9 ** hop`) is part of the deterministic impact analysis engine (`@fluxora/workers`) and is persisted in PostgreSQL (`@fluxora/db`).
  - If the frontend calculated `confidence = 0.9 ** depth`, the frontend would diverge from CLI exports, API responses, and automated CI reports whenever traversal rules change (e.g. corroborating signals or multi-path decay).
  - The backend is authoritative; the frontend only performs **presentation normalization**.

### 2. Low-Confidence Filtering vs. Visual Weighting
- **Q**: "Why didn't you just filter out or hide edges with low confidence (e.g. < 50%) to keep the graph clean?"
- **Answer**:
  - Hiding uncertain data directly violates **Principle P3 ("Uncertainty is presented, never smoothed over")**.
  - In architecture analysis, hidden dependencies cause the worst production outages (e.g., an unverified runtime event consumer that breaks unexpectedly).
  - Low-confidence edges must remain visible, distinct (dashed, muted opacity), and selectable so engineers can investigate them and inspect their underlying evidence.
  - Edge filtering is only permitted via explicit user controls (`GraphFilters`), never as an automatic visual side effect.

### 3. Non-Fabrication of Confidence
- **Q**: "What happens if a graph edge or node doesn't have a confidence value in the API response?"
- **Answer**:
  - The normalization function `normalizeConfidence` returns `null` for missing or invalid values.
  - The UI applies a neutral default stroke without displaying a fake percentage or assigning an arbitrary tier.
  - In Fluxora, an unstated confidence is an honest absence, not a synthetic `100%` or `0%`.

### 4. Accessibility & Multi-Channel Visual Design
- **Q**: "How do you ensure confidence visual weighting is accessible to colorblind users or screen readers?"
- **Answer**:
  - We strictly adhere to WCAG 2.1 AA (Guideline 1.4.1 Use of Color):
    1. **Stroke Width**: High confidence uses thicker lines (2.0px), medium uses 1.5px, low uses 1.25px.
    2. **Stroke Dash Pattern**: Low-confidence edges use a distinct SVG `strokeDasharray: "4 4"` pattern, instantly recognizable in monochrome.
    3. **ARIA Labels**: Edges and chips provide explicit text: `"CALLS edge from auth to db, High confidence, 95 percent"`.
    4. **Textual Badges**: The inspector and finding cards render explicit numeric percentages and tier text (`High`, `Medium`, `Low`).

### 5. Architectural Boundaries: Step 50 vs. Step 51
- **Q**: "How do you distinguish Step 50 (visual weighting) from Step 51 (evidence coverage)?"
- **Answer**:
  - **Step 50** communicates the *relative strength* of existing relationships and findings currently rendered in the UI.
  - **Step 51** introduces *coverage analytics* across the whole repository: what fraction of files were successfully parsed, what languages were skipped, and where gaps exist in the analysis run (`AnalysisRun.coverage_summary`).
  - Step 50 does not touch coverage analytics or repository-wide health metrics.
