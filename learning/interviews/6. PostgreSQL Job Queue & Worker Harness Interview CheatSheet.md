# Fluxora Step 6 — PostgreSQL Job Queue & Worker Harness Interview CheatSheet

## 1. What this step established

Fluxora introduces a PostgreSQL-backed job queue and a worker harness for background work. This creates a reliable separation between HTTP/request handling and long-running asynchronous processing.

## 2. 30-second interview answer

> “Fluxora uses a PostgreSQL-backed job queue so requests can create durable asynchronous work instead of performing long-running processing inside an HTTP handler. Workers claim jobs, process them, and record success or failure. This makes retries, observability, and recovery explicit and gives repository ingestion a place to run safely outside the request lifecycle.”

## 3. Core questions

### Q1. Why do we need a job queue?

Repository ingestion can take longer than a normal HTTP request and may need retries. A queue provides durable handoff from the request path to a worker.

### Q2. Why use PostgreSQL for the queue?

Fluxora already relies on PostgreSQL and the early queue volume is modest. Using Postgres avoids introducing another queue system before its operational complexity is justified.

### Q3. What is the difference between enqueuing and processing?

Enqueuing records durable intent to perform work. Processing executes the work later in a worker context.

### Q4. What should a worker do when a job fails?

Classify the failure. Retry transient failures; mark permanent/invalid failures as terminal so they are not retried forever.

### Q5. Why is idempotency important?

A worker may process the same logical job more than once because of crashes, retries, or delivery semantics. Repeating work must not corrupt state.

### Q6. What does a worker harness provide?

It standardizes job polling/claiming, execution boundaries, error handling, logging, and shutdown behavior so individual handlers can focus on business logic.

### Q7. Why should HTTP handlers avoid heavy ingestion work?

The request lifecycle is shorter, more failure-prone, and more resource constrained than a dedicated worker. Background processing also makes progress/retry semantics easier to reason about.

## 4. Senior-level questions

### Q8. How do you prevent two workers from processing one job simultaneously?

Use transactional claiming/locking semantics so one worker owns a job while it is in progress. Exact SQL strategy depends on the queue design.

### Q9. What happens if a worker crashes after claiming a job?

The job needs a lease/timeout or equivalent recovery mechanism so an abandoned job can become claimable again.

### Q10. What is at-least-once processing?

A job may run more than once, but should not be silently lost. This is why handlers need idempotent behavior.

### Q11. What metrics matter?

Queue depth, age of oldest job, success/failure counts, retry counts, processing duration, and dead-letter/permanent-failure rates are useful starting metrics.

### Q12. How would you scale workers?

Run more worker processes and ensure the claim operation remains safe under concurrency. Scale based on queue lag and processing time, not simply CPU usage.

## 5. Scenario questions

### Scenario: ingestion request times out

The request should ideally have only enqueued the job. The user can poll a job/resource state rather than depending on the original HTTP request remaining open.

### Scenario: same job executes twice

Verify idempotency first. Then inspect job claim, retry, and lease behavior rather than assuming duplicate execution is impossible.

### Scenario: a GitHub 401 occurs once

Classify whether the error is transient, needs re-authentication, or is permanently invalid. Do not automatically retry every HTTP error.

## 6. Common traps

- A queue does not make work idempotent.
- Retries without classification can create infinite retry storms.
- “Exactly once” execution is usually not a realistic assumption; design for safe repetition.

## 7. Strong closing statement

> “The queue is not just an implementation detail. It is the boundary that turns long-running repository processing into durable, retryable background work.”
