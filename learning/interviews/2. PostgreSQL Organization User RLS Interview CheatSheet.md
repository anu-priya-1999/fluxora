# Fluxora Step 2 — PostgreSQL, Organization/User & RLS Interview CheatSheet

## 1. What this step established

Fluxora establishes PostgreSQL as the relational system of record, organization/user tenancy, migrations, foreign keys, indexes, and PostgreSQL Row-Level Security (RLS). The key rule is that tenant isolation should be enforced by the database rather than relying only on application code.

## 2. 30-second interview answer

> “Fluxora is multi-tenant, so I treat tenant isolation as a database security property. Organizations represent tenants, users are mapped to organizations, and tenant-owned rows are protected by PostgreSQL RLS. Application code still validates authorization, but the database is a second enforcement boundary. Migrations are the canonical way to evolve this schema.”

## 3. Core questions

### Q1. Why PostgreSQL?

Fluxora needs relational integrity, transactions, indexes, foreign keys, and strong consistency around tenant-owned metadata. PostgreSQL also gives a mature RLS model.

### Q2. What is multi-tenancy?

Multiple logical customers share the same service and database while each customer must be isolated from the others. Fluxora uses organization identity as the tenant boundary.

### Q3. What does RLS do?

Row-Level Security lets PostgreSQL decide which rows a role may read or mutate based on policies. It provides a database-enforced filter rather than trusting every query builder call.

### Q4. Why not rely only on `WHERE organization_id = ...`?

A missed predicate becomes a data leak. RLS provides defense in depth and protects even when an application path accidentally forgets a tenant filter.

### Q5. What are foreign keys for?

They prevent invalid references and make relationship ownership explicit. In Fluxora, organization and child-resource relationships must remain structurally valid.

### Q6. Why use migrations?

A migration is a repeatable description of schema evolution. It can be applied in a new environment and reviewed in source control.

### Q7. Why are indexes important in a multi-tenant system?

Tenant-scoped queries often filter by organization plus another key such as repository or created time. Proper indexes reduce scans and make those access patterns predictable.

### Q8. What is the difference between authentication and authorization?

Authentication proves who the caller is. Authorization decides what that identity may access. RLS is one authorization enforcement layer.

### Q9. What happens if RLS is enabled but policies are wrong?

Valid queries can return zero rows or fail writes unexpectedly. Policy behavior must therefore be tested explicitly, not assumed.

### Q10. What does FORCE RLS accomplish?

It makes RLS apply more broadly, including where the table owner would otherwise bypass normal RLS behavior. This helps avoid accidental privileged paths.

## 4. Senior-level questions

### Q11. Why might child tables omit `organization_id`?

If the ownership can be derived safely through a parent relationship, the schema avoids duplicate tenant columns. Fluxora can enforce `Repository → Organization` ownership and let child tables inherit the tenant boundary through that relationship.

### Q12. What are the downsides of RLS?

Policies become part of application behavior and can be difficult to reason about if overly complex. Testing, indexing, role design, and policy documentation are essential.

### Q13. How would you test tenant isolation?

Create data for two organizations, execute reads and writes under a non-bypass tenant-aware role, and assert that cross-tenant rows are inaccessible. Include negative cases, not just happy paths.

### Q14. Why not put all authorization in middleware?

Middleware is easy to bypass accidentally through another execution path. Database enforcement is closer to the data and therefore provides stronger defense in depth.

### Q15. What is the role of a transaction here?

A transaction groups logically related changes so the database does not end up half-updated. Tenant creation, membership changes, or resource initialization may need atomic behavior.

## 5. Failure scenarios

### Scenario: one tenant can query another tenant's repository

Check identity-to-organization mapping, session/role context, the RLS policy, and whether the query uses the intended database role. Do not patch only the UI.

### Scenario: an RLS test passes in a superuser connection

That is weak evidence. Privileged roles may bypass RLS semantics, so security tests should use a restricted non-bypass role.

### Scenario: migration works locally but not in CI

Check ordering, role privileges, environment variables, transaction boundaries, and whether the migration assumes objects that are created only manually.

## 6. Common traps

- RLS is not a replacement for authentication.
- `organization_id` in application memory does not prove tenant isolation.
- A superuser test is not a realistic RLS test.

## 7. Strong closing statement

> “The important design choice in Step 2 is that tenant isolation is not merely a coding convention. PostgreSQL itself participates in enforcing the boundary.”
