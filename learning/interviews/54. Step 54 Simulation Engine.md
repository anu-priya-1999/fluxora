# Staff Engineering Interview Guide: Step 54 — Simulation Engine

This interview guide focuses on systems design, graph algorithms, and formal verification questions centered on building a deterministic scenario propagation engine.

---

### Q1: How would you design a deterministic failure-propagation engine for a distributed software graph?

**Answer:**
A production failure-propagation engine must balance architectural truth, computational efficiency, and determinism.
The design should separate:
1. **The Policy/Rule Layer**: Pure, stateless rule evaluators that take local edge metadata and endpoint states and return a decision (`SimulationRuleDecision`).
2. **The Traversal/Convergence Core**: A worklist algorithm that propagates state changes through the graph without recursion, enforcing monotonic state transitions so cyclic dependencies always converge.
3. **The Provenance & Evidence Layer**: An atomic persistence layer linking every state transition to the underlying source code evidence that justifies it.

The system must never depend on non-deterministic sources (such as LLM generation, thread scheduling, or non-deterministic object iteration order) for structural propagation truth.

---

### Q2: Why use a work queue instead of recursive DFS for graph propagation?

**Answer:**
Recursive DFS suffers from three fatal weaknesses in graph propagation:
1. **Call Stack Exhaustion**: Deep architectural chains or large monorepos can easily cause a stack overflow.
2. **Cycle Vulnerability**: Software architectures routinely contain circular dependencies ($A \to B \to C \to A$). Guarding against cycles with recursion often requires complex or error-prone recursion unwinding.
3. **Non-Deterministic Exploration Order**: Recursion explores subtrees in arbitrary branch order, making deterministic tie-breaking hard to maintain.

A FIFO worklist operates on the heap, consumes $O(N)$ memory, naturally flattens traversal across BFS levels, and makes the iteration count explicitly bounded and observable.

### Q3: How do you mathematically guarantee convergence in cyclic graphs?

**Answer:**
Convergence is guaranteed by **bounded monotonic lattice transitions**:
1. We define a discrete, finite state hierarchy of size $K=4$:
   `healthy (0) < at_risk (1) < degraded (2) < failed (3)`
2. State updates are strictly monotonic: a node at state $S_{current}$ only transitions to proposed state $S_{new}$ if $S_{new} > S_{current}$.
3. For a graph with $N$ vertices, an individual vertex can transition at most $K - 1 = 3$ times.
4. Vertices are only enqueued when a state transition occurs.
5. Therefore, the total number of enqueuing operations across the entire simulation cannot exceed $3N$.
6. Since each iteration dequeues exactly one vertex, the queue must inevitably empty within at most $3N$ transition cycles, proving termination without arbitrary hop truncations.

### Q4: Why can't graph propagation direction be hard-coded as source-to-target or target-to-source?

**Answer:**
Different architectural edge semantics propagate impairment in opposite physical directions:
- In `CALLS(A, B)` ($A$ calls $B$), $A$ is the source and $B$ is the target. If $B$ fails, $A$ degrades. Impairment propagates **backwards** (target $\to$ source).
- In `CONSUMES_EVENT(Broker, Consumer)`, Broker is the source and Consumer is the target. If Broker fails, Consumer is placed at risk. Impairment propagates **forwards** (source $\to$ target).
- In `QUERIES_DB(Reader, Datastore)`, Datastore is the target and Reader is the source. Impairment propagates **backwards** (target $\to$ source).

Hard-coding a single traversal direction either corrupts call-graph logic or breaks event-driven architectures. By delegating the affected side to the rule decision (`affectedNode: "source" | "target"`), the engine evaluates incident edges symmetrically and applies state changes to the declared side.

---

### Q5: How do you represent and explain causal paths for multi-hop failures?

**Answer:**
Every state transition must answer: *"Why is this node degraded?"*
We model the causal explanation as an append-only path of structured `SimulationCausalStep` records:
- Each step captures the affected `nodeId`, the incident `edgeId`, the `ruleId`, the transition (`previousState -> resultingState`), rule assumptions, and confidence.
- When an affected node triggers a downstream node, the downstream node inherits the upstream node's causal history and appends its own step.
- This creates an unbroken causal chain back to the seeded failure root, suitable for rendering in UI timeline overlays or feeding structured grounding context into AI explainers.

---

### Q6: How do you handle competing propagation causes with equal severity?

**Answer:**
If Service C depends on both Service A and Service B, and both A and B fail:
- Both paths propose `degraded` for Service C.
- When the first path arrives, C transitions `healthy -> degraded`.
- When the second path arrives, `isStateMoreSevere("degraded", "degraded")` evaluates to `false`.
- The engine preserves the first deterministic causal explanation and does not overwrite it with the second.
- Deterministic edge sorting (`sourceNodeId ASC`, `targetNodeId ASC`, `edgeType ASC`, `id ASC`) ensures that regardless of machine or environment, the identical first causal path is chosen every time.

### Q7: How does simulation evidence differ from static graph evidence?

**Answer:**
- **Static Graph Evidence** links a concrete code entity (e.g. an AST import declaration or function call) directly to source file coordinates (lines 14–18 in `checkout.ts`).
- **Simulation Evidence** represents a dynamic behavioral *conclusion* derived from an experiment. It links the state change to:
  1. The simulation result ID.
  2. The graph edge that transmitted the failure.
  3. The versioned rule applied (`calls.sync.no_fallback`).
  4. The underlying static evidence of the participating graph edge.

This satisfies Principle P2: even hypothetical "what-if" conclusions must be backed by verifiable evidence rather than speculative hallucination.

---

### Q8: How would runtime telemetry eventually complement this deterministic engine?

**Answer:**
In Phase 10 (post-MVP), real OpenTelemetry trace and metric data can refine static assumptions without compromising determinism:
- If code analysis cannot detect whether a call has a circuit breaker (`hasCircuitBreaker: "unknown"`), runtime metrics can confirm: *"Circuit breaker observed active 42 times in production"*.
- This upgrades the edge metadata from `"unknown"` to `true`, switching the rule evaluation from `calls.sync.no_fallback` to `calls.circuit_breaker`, accurately predicting capped blast radius.
- Telemetry enriches edge metadata and confidence scores; it does not introduce non-deterministic ad-hoc code paths into the propagation core.
