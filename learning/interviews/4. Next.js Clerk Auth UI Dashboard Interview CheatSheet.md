# Fluxora Step 4 — Next.js, Clerk Auth UI & Dashboard Interview CheatSheet

## 1. What this step established

Fluxora adds the Next.js application shell, protected routes, Clerk-backed auth UI, and the initial dashboard experience. The key design concern is keeping browser UX separate from server-side authorization.

## 2. 30-second interview answer

> “The web app is a Next.js frontend that integrates Clerk for the user-facing authentication flow. Protected UI improves the user experience, but security decisions are still made server-side. The dashboard is therefore treated as a client of the authenticated API, not as the ultimate authorization layer.”

## 3. Core questions

### Q1. Why Next.js?

It provides a structured React application model with routing, server/client boundaries, and a mature deployment ecosystem. Fluxora benefits from explicit server/client separation as the application grows.

### Q2. Why should protected UI not be considered security?

Users can bypass browser code. A hidden dashboard button does not prevent a direct HTTP request to the API.

### Q3. What is the server/client boundary in Next.js?

Some code executes on the server and some in the browser. Authentication secrets and privileged operations belong on the server; browser code gets only data necessary for the UI.

### Q4. Why avoid exposing secrets to the client?

Anything shipped to the browser should be treated as public. Server-only credentials such as private keys and database secrets must remain server-side.

### Q5. How should the dashboard load tenant-scoped data?

Use the authenticated API/server boundary and let the backend derive the authorized organization context.

### Q6. What happens when the auth session expires?

The UI should handle an authentication failure predictably: refresh through the provider mechanism where supported or send the user back through the sign-in flow.

### Q7. Why separate API and web applications?

It creates a clean boundary between presentation and backend responsibilities and allows each side to evolve/deploy independently.

## 4. Senior-level questions

### Q8. How do you avoid duplicated auth logic in every page?

Centralize authentication helpers and protected route conventions while keeping authorization decisions close to the backend/resource boundary.

### Q9. What causes hydration problems in auth-aware UIs?

The server and browser may initially have different assumptions about session state or user-specific rendering. Stable server-driven state and provider-supported auth hooks help avoid inconsistent markup.

### Q10. Where would you put optimistic UI?

Only around mutations where the client can safely predict the result. Security-sensitive state such as membership should not be treated as authoritative until the server confirms it.

### Q11. How would you handle loading/error/empty states?

Treat them as explicit product states, especially for async operations like repository connection and ingestion. Avoid showing a generic spinner for every failure.

### Q12. How would you test authenticated UI?

Unit-test rendering and auth-state branches, then use integration/E2E tests for the real redirect/session flow and API boundaries.

## 5. Scenario questions

### Scenario: button hidden, but API endpoint is still callable

That is expected unless the backend blocks the operation. UI gating is UX; backend authorization is security.

### Scenario: user switches organizations

Invalidate or refresh tenant-scoped data, ensure the API resolves the current organization correctly, and avoid keeping stale cross-tenant data in client state.

## 6. Common traps

- Client-side route protection is not sufficient security.
- Never ship Clerk/private server credentials to the browser.
- Avoid duplicating backend authorization rules in React and assuming both will stay synchronized.

## 7. Strong closing statement

> “Step 4 establishes the frontend boundary: Next.js provides the user experience, while authenticated backend calls remain the authority for tenant-scoped operations.”
