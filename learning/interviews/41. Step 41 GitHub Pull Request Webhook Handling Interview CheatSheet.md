# 41. Step 41 GitHub Pull Request Webhook Handling Interview CheatSheet

## Core Concepts & Quick Answers

### Q1: What is a webhook and why do we use it instead of polling GitHub?
**Answer:**
A webhook is an event-driven HTTP push callback. Instead of the client constantly querying GitHub's REST API ("polling") to check for new PRs, GitHub sends an HTTP POST request to our server immediately when an event occurs. Webhooks eliminate polling latency, avoid rate-limiting ceilings, and conserve compute resources by only executing when real work exists.

### Q2: How does GitHub webhook signature verification work?
**Answer:**
GitHub computes an HMAC-SHA256 hash of the exact raw request payload using a shared webhook secret and sends it in the `X-Hub-Signature-256` header (formatted as `sha256=<hex_digest>`). Our server recomputes the HMAC-SHA256 of the raw body buffer and compares it against the header using constant-time comparison (`crypto.timingSafeEqual`). If the header is missing, malformed, or doesn't match, we reject the request with `401 Unauthorized`.

### Q3: Why is it crucial to verify HMAC using the raw request body rather than parsed JSON?
**Answer:**
HMAC is computed over exact byte sequences. When JSON is parsed and re-stringified, serialization variations (key ordering, whitespace, Unicode escaping, number formatting) alter the byte stream. Even a single whitespace difference produces a completely different SHA-256 digest, causing legitimate signatures to fail verification. You must preserve and verify against the raw byte buffer received over the socket.

### Q4: What is a timing attack and how do you protect against it during webhook verification?
**Answer:**
In standard string comparison (`a === b`), evaluation terminates early at the first non-matching byte. An attacker can measure minor response time discrepancies (sub-millisecond or microsecond variations) to deduce correct characters byte-by-byte. Using `crypto.timingSafeEqual` evaluates every byte across equal-length buffers in constant time regardless of where mismatches occur, eliminating side-channel leakage.

### Q5: How do you handle webhook delivery retries and ensure idempotency?
**Answer:**
GitHub delivers webhooks with at-least-once delivery semantics and retries on network blips or timeouts. Every webhook delivery includes an `X-GitHub-Delivery` GUID header. Fluxora derives an idempotency key from this delivery ID (`pull_request.webhook:${deliveryId}`) and writes to the PostgreSQL `jobs` table using:
`ON CONFLICT (organization_id, idempotency_key) DO UPDATE SET id = jobs.id`
If a retry arrives, PostgreSQL returns the existing job without creating a duplicate, ensuring downstream workers execute the work exactly once.

### Q6: How do you enforce multi-tenant isolation on unauthenticated webhooks?
**Answer:**
Webhooks do not carry user auth tokens. We must never trust tenant identifiers provided in the incoming request payload. Instead, we extract GitHub's authoritative `installation.id` and resolve it against our internal `github_installations` table. If the installation exists, we derive the tenant's `organization_id` strictly server-side. If the installation is unknown or unmapped, we reject the request with `404 Not Found` and refuse to create tenant-scoped jobs.

### Q7: Why shouldn't a webhook handler perform impact analysis synchronously?
**Answer:**
GitHub enforces a strict 10-second timeout on webhook deliveries. Complex AST parsing, graph diffing, and blast-radius traversals can take hundreds of milliseconds to several seconds on large codebases. Performing this work synchronously blocks HTTP worker threads, risks timing out GitHub's connection, triggers unintended delivery retries, and makes the API vulnerable to DoS. Acknowledging receipt immediately after enqueuing an asynchronous background job is the canonical architectural pattern.

### Q8: How are unsupported webhook events and PR actions handled?
**Answer:**
Events other than `pull_request` (such as `push` or `issues`) and actions other than `opened` or `synchronize` (such as `closed` or `labeled`) are filtered and safely ignored. The endpoint returns `200 OK` with `{ ok: true, status: "ignored" }`. Returning `200 OK` prevents GitHub from treating ignored events as delivery failures and retrying them unnecessarily.

### Q9: What security boundaries must be maintained in webhook handling?
**Answer:**
1. **Never execute code**: Repository source code referenced in webhooks is untrusted customer input and must never be evaluated.
2. **Never leak secrets**: The webhook secret must never appear in response bodies, error messages, or logs.
3. **Payload size limits**: Webhook bodies must have strict upper bounds (e.g. 1MB cap) to prevent memory-exhaustion DoS attacks.
4. **Tenant isolation**: Cross-tenant fallback is strictly forbidden; unmapped installations cannot enqueue work.

### Q10: What is the boundary between Global Step 41 and future Steps 42–47?
**Answer:**
- **Step 41 (Current)**: Webhook reception, HMAC verification, event/action filtering, validation, normalization, tenant mapping, and job queue handoff.
- **Step 42**: `PullRequest` database table, diff fetching, changed file storage.
- **Step 43**: Impact Analysis Engine (changed files → symbol mapping → graph traversal).
- **Step 44**: `ImpactAnalysis` record persistence + evidence provenance.
- **Step 45**: Public REST API for impact analysis.
- **Step 46**: Frontend change-mode overlay on GraphCanvas.
- **Step 47**: Golden-fixture PR acceptance test suite.
