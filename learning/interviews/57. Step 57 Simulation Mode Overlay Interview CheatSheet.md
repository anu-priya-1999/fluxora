# Staff Engineering Interview Guide: Step 57 — Simulation Mode Overlay in Architecture Explorer

This interview guide focuses on graph visualization architecture, multi-mode visual overlay management, snapshot-scoped referential consistency, semantic integrity of graph traversal results, and honest uncertainty communication for deterministic software digital twins.

---

### Q1: What is the architectural role of Step 57, and how does it relate to Step 56?

**Answer:**
Step 56 introduced the dedicated **Simulation Studio** (`/simulations`), an experiment workbench where engineers formulate failure hypotheses, select failure types, run simulations, and inspect tabular results and causal timelines.

Step 57 connects those persisted simulation results to Fluxora's **Architecture Explorer** (`/repositories/[repoId]/explorer`).
- Instead of inspecting simulation results in isolation in a table, engineers can visualize the failure propagation directly on the real React Flow architectural topology.
- It overlays canonical simulation states (`failed`, `degraded`, `at_risk`, `healthy`) on nodes, highlights the exact causal propagation edges between components, and displays the step-by-step causal evidence in the Node Inspector.
- It bridges the gap between tabular analysis and spatial architectural comprehension without replacing the Simulation Studio or re-running simulations in the browser.

---

### Q2: Why is the analysis-run snapshot consistency check (`simulation.analysis_run_id === context.analysisRunId`) a critical architectural invariant?

**Answer:**
In Fluxora, an `AnalysisRun` represents an immutable point-in-time snapshot of a repository's architecture. Both the dependency graph and any simulations executed against that graph are strictly snapshot-scoped.

If the Architecture Explorer allowed rendering a simulation run from Snapshot A over the graph topology of Snapshot B:
1. **Topological Contradiction**: Graph nodes or edges present in Snapshot A might not exist in Snapshot B, or may have different IDs, relationships, or package boundaries.
2. **False Causal Paths**: A causal step citing edge $E_1$ between Service X and Database Y could point to non-existent edges or unrelated nodes in Snapshot B.
3. **Misleading Risk Assessments**: An engineer reviewing a pull request or refactor in Snapshot B might believe a circuit breaker failed to stop propagation when in reality the simulation was evaluated against legacy code before the fix was committed.

Therefore, `explorer-client.tsx` strictly validates `simulation.analysis_run_id === context.analysisRunId`. If a mismatch is detected, the overlay is rejected with a visible context-mismatch error, and the existing graph is preserved.

### Q3: Why is it a fatal semantic error to label nodes absent from simulation results as "healthy"?

**Answer:**
Deterministic failure simulation operates via directed graph traversal from a failure seed. It visits only the transitive dependents and propagatees governed by deterministic propagation rules (e.g. `RPC_UNAVAILABLE_FALLBACK`, `EVENT_PRODUCER_OFFLINE`).

1. **Unreached $\neq$ Evaluated & Healthy**: A node that does not appear in `simulation.results` was never visited by the engine. It could be completely isolated, upstream of the failure, or beyond a capped propagation boundary. Calling it `healthy` would fabricate an unverified health guarantee.
2. **Honesty & Trust**: Fluxora's thesis is that every structural conclusion must be backed by deterministic evidence. Fabricating a synthetic `healthy` result for unreached nodes violates this core invariant.
3. **UX Solution**: Absent nodes retain their normal Architecture Explorer appearance (opacity 1.0, standard border/background, no simulation badge). The Node Inspector explicitly clarifies: *"No simulation result for this node. This node was not reached by the simulation propagation path."* Only nodes with explicit simulation records returned by the engine receive simulation styling and badges.

### Q4: How are Simulation Mode and Change Mode visual overlays kept mutually exclusive on React Flow?

**Answer:**
Architecture Explorer supports two distinct analytical overlays:
- **Change Mode (Step 46)**: PR blast radius (`changed`, `impacted`, `not_impacted`).
- **Simulation Mode (Step 57)**: Failure scenario propagation (`failed`, `degraded`, `at_risk`, `healthy`).

Allowing both modes to apply border and badge styling simultaneously would result in visual chaos (e.g. a node that is simultaneously orange for PR impact and red for failure, or green for healthy simulation and amber for PR impact).

**Solution**:
1. **Visual Priority**: When Simulation Mode is active and ready (`state.enabled && state.status === "ready"`), it takes visual precedence on the canvas and node renderers.
2. **State Preservation**: The underlying Change Mode state is not cleared or mutated.
3. **Clean Restoration**: When the user toggles Simulation Mode off or clicks "Clear", the canvas immediately reverts to displaying the active Change Mode overlay without re-fetching PR impact data.
4. **Selected Node Precedence**: Selected node highlighting (`#3b82f6`, high z-index) takes priority over both overlay modes to ensure consistent keyboard/click navigation.

### Q5: How are causal edges highlighted without fabricating phantom edges for seed targets?

**Answer:**
A simulation's propagation path consists of discrete steps:
```ts
export interface SimulationCausalStep {
  readonly nodeId: string;
  readonly edgeId?: string | null | undefined;
  readonly ruleId: string;
  readonly ruleVersion: string;
  readonly previousState: SimulationResultState;
  readonly resultingState: SimulationResultState;
  readonly assumptions: readonly string[];
  readonly confidence: number;
  readonly capped?: boolean | undefined;
}
```
1. **Edge Extraction**: In `simulation-mode-data.ts`, `extractSimulationCausalSteps` parses each step. If `step.edgeId` is a non-null, non-empty string, it is collected into `normalizedState.causalEdgeIds: Set<string>`.
2. **Seed Step Handling**: Step 1 (the initial seed target failure) does not originate from an incoming graph edge; its `edgeId` is `null`. The normalizer explicitly handles `edgeId === null` and does not attempt to invent an edge.
3. **Canvas Styling**: In `GraphCanvas.tsx`, edges are mapped. If `causalEdgeIds.has(edge.id)`, the edge receives high-visibility failure stroke styling (`#dc2626`, 3px width, `opacity: 1.0`); non-causal edges receive muted opacity (`0.35`), visually tracing the exact failure path through the architecture.

### Q6: How does the normalized simulation view model (`simulation-mode-data.ts`) optimize rendering performance and prevent state desynchronization?

**Answer:**
React Flow renders dozens or hundreds of nodes and edges at 60 FPS during zooming, panning, and LOD clustering.

If each `NodeRenderer` or `GraphCanvas` edge mapping repeatedly scanned an unindexed `SimulationResultResponse[]` array:
- Per-frame complexity would be $O(N \cdot M)$ where $N$ is graph nodes and $M$ is simulation results.
- During interactive pan/zoom, this causes noticeable frame drops.

**Solution**:
1. **Normalized View Model**:
   - `resultsByNodeId: Map<string, SimulationResultResponse>`: Provides $O(1)$ node lookup in `NodeRenderer` and `node-styles.ts`.
   - `causalEdgeIds: Set<string>`: Provides $O(1)$ edge membership checks in `GraphCanvas`.
2. **Precomputed Aggregates**:
   - Aggregate counts (`failedCount`, `degradedCount`, `atRiskCount`, `healthyCount`, `cappedCount`, `totalAffected`) are computed once upon normalization, not recalculated on every re-render.
3. **Pure Function Discipline**: All normalization logic is pure, immutable, and decoupled from React hooks or DOM state, making it trivially unit-testable and cacheable.

### Q7: How does the UI communicate honest simulation confidence and qualitative latency without misleading users?

**Answer:**
In failure simulation, users can easily misinterpret a confidence score (e.g. `0.90`) as an SLA probability (e.g. "90% chance this service will crash in production").

Fluxora enforces strict truthfulness:
1. **Explicit Notice Banner**: Prominently displayed in both `SimulationModeBar` and `NodeInspectorPanel`:
   > *"Simulation confidence reflects deterministic rule confidence and static metadata assumptions. It is not a real-world failure probability."*
2. **Transparent Assumptions**: The Node Inspector explicitly surfaces any metadata gap that influenced the decision (e.g. `"No circuit breaker detected on call"`).
3. **Qualitative Latency**: Latency degradation models topological risk propagation under the `RPC_LATENCY_TIMEOUT` rule, rather than synthesizing fake millisecond histograms or queueing numbers.
4. **Fail-Fast Error Handling**: Network errors, 401s, 404s, and 422 convergence timeouts are rendered as explicit red error banners with actionable messages, never disguised as "zero affected components".

### Q8: How does duplicate-result resolution prevent stale causal edge and rule-version leakage?

**Answer:**
When multiple simulation results target the same component (e.g. an intermediate propagation state evaluated as `at_risk` followed by an escalating path evaluated as `failed`), the view model resolves duplicates by deterministic state severity (`failed` > `degraded` > `at_risk` > `healthy`).

1. **The Leakage Hazard**: If causal edge IDs (`step.edgeId`) and rule-table versions are accumulated into global sets during linear iteration across raw results, edges belonging to the superseded result (`at_risk`) remain in `causalEdgeIds`. As a result, the canvas would highlight failure edges that were part of a discarded hypothesis rather than the final accepted state.
2. **The Corrected Derivation**:
   - `normalizeSimulationResponse` first completes duplicate resolution to determine the final accepted `causalStepsByNodeId: Map<string, SimulationCausalStep[]>`.
   - `causalEdgeIds` and `ruleTableVersion` are then derived exclusively by iterating over the final accepted entries in `causalStepsByNodeId.values()`.
   - Edges and metadata belonging exclusively to discarded results are completely excluded.
3. **Step-Level Semantic Integrity**: `extractSimulationCausalSteps` strictly validates each step, rejecting steps missing an explicit `nodeId` or canonical `resultingState` rather than dangerously falling back to enclosing result fields which could misattribute state transitions in multi-node propagation paths.

### Q9: How is the simulation polling lifecycle bounded and protected against overlapping fetches, cross-simulation budget leaks, and stale async responses?

**Answer:**
Long-running failure simulations transition through `pending` and `running` before reaching `completed` or `failed`. To track progress in the Architecture Explorer without infinite loops or resource exhaustion, Fluxora implements a bounded polling lifecycle:

1. **Bounded Budget**: Maximum 15 automatic polling attempts per simulation run at 4000ms intervals (60 seconds maximum polling window).
2. **No Overlapping Fetches**: Polling timers are only scheduled when:
   - Simulation Mode is enabled.
   - A simulation ID is present.
   - Server execution status is `pending` or `running`.
   - UI status is also `pending` or `running`.
   If UI status is `loading` (an in-flight GET is active) or `error`, timer scheduling is suppressed. This prevents request stampedes and automatic retry loops on network/API failure.
3. **Per-Simulation Attempt Tracking**: The polling controller scopes attempt counts to a specific simulation ID. Switching from Simulation A to Simulation B resets B's budget to 0 attempts, preventing an exhausted run on A from starving B.
4. **Deterministic Cancellation**: Active timer handles are cancelled on React component unmount, mode disable, simulation clearing/changing, or upon receiving terminal `completed`/`failed` execution statuses.
5. **Stale Response Protection**: All async fetch completions in `explorer-client.tsx` compare the response's target simulation ID against the currently active simulation ID (`prev.simulationId !== targetSimulationId`). Stale responses from slow or prior requests are discarded before mutating state.
6. **GET-Based Manual Refresh**: User-triggered "Refresh" actions invoke a fresh GET request against the existing simulation ID without creating new simulation runs or mutating backend state.
