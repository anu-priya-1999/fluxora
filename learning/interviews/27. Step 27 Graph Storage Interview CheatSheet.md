# Step 27: Graph Storage Interview CheatSheet

## Q1: Why store a graph in relational PostgreSQL instead of a graph database like Neo4j?

**Answer:**
For Fluxora's scale and operational requirements:
1. PostgreSQL provides strict ACID transactions, Row-Level Security (RLS), and proven multi-tenant isolation out of the box.
2. Relational tables simplify joining code graph metadata with organizations, repositories, snapshots, and background jobs without introducing secondary database clusters or complex cross-database synchronization.
3. Recursive Common Table Expressions (CTEs) in PostgreSQL efficiently handle multi-hop dependency traversal and blast-radius queries required for Phase 4 & 5 features.

---

## Q2: Why separate nodes, edges, and evidence into separate tables?

**Answer:**
- **`graph_nodes`** represents canonical code identities (modules, symbols, functions, routes).
- **`graph_edges`** represents normalized directed relationships between nodes (`IMPORTS`, `CALLS`, `EXPOSES_ROUTE`).
- **`evidence`** represents the physical code provenance (file paths, line/column ranges, AST snippets).

Separating evidence from nodes/edges avoids duplicating verbose source location data across multiple edges, enables multiple evidence records per edge, and allows graph traversal queries to fetch thin node/edge records without pulling large text metadata.

---

## Q3: How do composite foreign keys enforce scope isolation in a graph schema?

**Answer:**
By enforcing composite foreign keys on `graph_edges`:
```sql
FOREIGN KEY (source_node_id, analysis_run_id) REFERENCES graph_nodes (id, analysis_run_id)
```
The database verifies at insert time that `source_node_id` and `target_node_id` share the **exact same `analysis_run_id`**. This prevents bugs where an edge connects nodes across different repository snapshots or different tenant organizations.

---

## Q4: How does RLS protect graph data from cross-tenant access?

**Answer:**
1. All queries run inside transactions with session variable `app.current_org_id` set via `withTenant`.
2. `analysis_runs` uses policy `fluxora_snapshot_in_current_tenant(snapshot_id)` which joins `repository_snapshots -> repositories` to verify `organization_id = fluxora_current_org_id()`.
3. `graph_nodes`, `graph_edges`, and `evidence` use policy `fluxora_analysis_run_in_current_tenant(analysis_run_id)`.
4. RLS policies operate at the PostgreSQL kernel level, automatically filtering out cross-tenant rows even if an application bug omits tenant checks.

---

## Q5: What is the difference between a canonical node identity and a database primary key?

**Answer:**
- **Database Primary Key (`id`)**: A random UUID generated per table row for relational primary identity and fast indexed joins.
- **Canonical ID (`canonical_id`)**: A deterministic domain string (e.g. `mod:src/index.ts` or `sym:src/utils.ts#formatDate`) that uniquely identifies the code element within a given analysis run.
- `UNIQUE (analysis_run_id, canonical_id)` ensures that repeating graph extraction on the same repository snapshot updates existing canonical nodes cleanly.

---

## Q6: Why are uniqueness constraints critical for graph ingestion?

**Answer:**
Graph builders process files concurrently or in multiple passes. Uniqueness constraints on `(analysis_run_id, canonical_id)` for nodes and `(analysis_run_id, source_node_id, target_node_id, edge_type)` for edges ensure that ingestion uses `ON CONFLICT (...) DO UPDATE` idempotently without inserting duplicate edges or failing on retry.

---

## Q7: Why is Step 27 storage-only instead of building the graph now?

**Answer:**
Following strict monorepo architecture and incremental phase discipline:
- Step 27 verifies schema design, database migrations, types, CRUD repositories, RLS policies, and index efficiency independently.
- Decoupling storage from graph construction (Step 28) guarantees that database invariants are proven correct before building complex AST extraction and graph propagation engines on top of them.
