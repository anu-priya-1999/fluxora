# Step 52: Simulation Persistence Foundation Interview CheatSheet

## Core Narrative & Problem Statement

**Q: Why separate the simulation domain into three distinct entities (`Scenario`, `Simulation`, `SimulationResult`) instead of one flat table?**
- **Hypothesis vs Execution vs Outcome**: A `Scenario` defines the *what-if hypothesis* (e.g., target node + failure type) and can be evaluated repeatedly. A `Simulation` represents a *single execution* against a specific version of the code graph (`AnalysisRun`). A `SimulationResult` captures the *fine-grained, per-node end state* with its propagation path, rule applied, and assumptions.
- **Snapshot Immutability**: Code graphs change on every commit. By separating `Scenario` from `Simulation`, engineers can run the exact same scenario before and after adding a fallback circuit breaker to verify resilience improvements across commits.

## Technical Highlights & Staff-Level Discussion

### 1. The Analysis-Run Snapshot Boundary
- **Question**: *"How do you prevent a simulation from evaluating a node that no longer exists or combining data across two different git commits?"*
- **Answer**: *"Every `Simulation` explicitly references an immutable `analysis_run_id`. During simulation creation, the repository verifies that the scenario's `target_node_id` exists inside that specific `analysis_run_id`. Furthermore, during result persistence, every affected `node_id` is asserted to belong to that same analysis run. Cross-snapshot contamination is strictly rejected at the persistence boundary."*

### 2. Multi-Tenancy & Row-Level Security (RLS)
- **Question**: *"How is tenant isolation maintained when `simulations` and `simulation_results` don't have an `organization_id` column?"*
- **Answer**: *"We use PostgreSQL Row-Level Security (`FORCE ROW LEVEL SECURITY`) with transitive policy chaining. `scenarios` directly enforces `organization_id = fluxora_current_org_id()`. `simulations` verifies access via `fluxora_scenario_in_current_tenant(scenario_id)`, and `simulation_results` verifies access via `fluxora_simulation_in_current_tenant(simulation_id)`. Cross-tenant queries return zero rows, and cross-tenant foreign key injections are blocked by the database engine."*

### 3. Failure Type Schema Support vs. Rule Table Scope
- **Question**: *"The schema allows 4 failure types ('unavailable', 'latency', 'capacity', 'removal'), but MVP only supports 2. Why not restrict the database check constraint to just 2?"*
- **Answer**: *"The database model defines the canonical product domain contract (`docs/architecture/06-database-schema.md §6.3`). Restricting the database constraint to only the MVP rules would require unnecessary schema migrations when future rules are implemented. Instead, we constrain the schema to valid domain failure types, while the simulation rule engine in Step 53 governs which scenario types have active propagation rules."*

### 4. Why Exclude Rule Logic and Execution in Step 52?
- **Question**: *"Why not implement the propagation engine or at least one rule in this step?"*
- **Answer**: *"Sequential engineering discipline. Step 52 establishes the data model, indexes, RLS policies, and repository contracts. Entangling rule logic into persistence introduces premature coupling, makes unit testing slower, and violates single-responsibility principles. Step 53 will focus exclusively on the deterministic rule table, and Step 54 on the propagation traversal loop."*

## Interview Cheat Sheet Summary Table

| Concern | Implementation | Architectural Invariant |
| --- | --- | --- |
| **System of Record** | PostgreSQL `scenarios`, `simulations`, `simulation_results` | Relational tables with JSONB parameter payloads |
| **Snapshot Isolation** | `analysis_run_id` FK + target node validation | No cross-run graph contamination |
| **Multi-Tenancy** | PostgreSQL `FORCE ROW LEVEL SECURITY` + `withTenant` | Hardware-enforced tenant boundaries |
| **Idempotency** | `UNIQUE (simulation_id, node_id)` + `ON CONFLICT DO UPDATE` | Replay-safe worker execution |
| **Domain Bounding** | Enum CHECK constraints for failure types and resulting states | Bounded state spaces, no arbitrary strings |
| **Evidence Boundary** | `EvidenceSubjectType = 'simulation_state'` reserved | Evidence generation deferred to engine execution |
