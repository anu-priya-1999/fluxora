# Step 48: Evidence Completeness Audit & Hardening Interview CheatSheet

## Core Narrative & Architectural Philosophy

**Q: What is the core problem that Step 48 solves in Fluxora?**
- **The "Unverified Conclusion" Anti-Pattern**: In many AI or developer tools, relationship discovery or blast-radius predictions are generated as transient JSON or detached records without hard links to physical code files. When engineers or security teams challenge a finding, the tool cannot prove *why* the conclusion was reached.
- **Fluxora's Evidence Thesis**: Every graph node, graph edge, and impact finding in Fluxora is an auditable engineering conclusion. Step 48 enforces the invariant that **no conclusion can exist without immutable, traceable evidence**. We audit every conclusion write path, harden both static AST linting and database transactions, and guarantee that evidence can never be decoupled, fabricated, or lost during retries.

## Technical Highlights & Staff-Level Q&A

### 1. Static AST Linting vs. Runtime Verification
- **Q**: "Why do you use TypeScript AST linting (`pnpm lint:evidence`) in CI if you already have integration tests?"
- **Answer**:
  - Runtime tests can verify *existing* code paths, but they cannot prevent a developer from adding a new function tomorrow that executes `client.query("INSERT INTO graph_edges ...")` or `saveImpactAnalysis(...)` without calling `EvidenceWriter`.
  - The static AST linter (`packages/db/src/repositories/evidence-lint.ts`) acts as an architectural guardrail in the CI build pipeline. It parses source files into ASTs using TypeScript Compiler APIs, identifies all conclusion-producing write calls, and verifies that the file imports and calls `EvidenceWriter`. If a conclusion write is introduced without `EvidenceWriter`, `pnpm lint:evidence` fails the build before code can be merged.

### 2. Evidence Completeness Across All Impact Finding Classifications
- **Q**: "What subtle evidence gap did the audit discover in the impact analysis pipeline, and how was it remediated?"
- **Answer**:
  - In `saveImpactAnalysisTx`, while `directImpact` and `downstreamImpact` generated evidence inputs and received updated `evidenceIds`, the filtered categorized arrays (`affectedApis`, `affectedEvents`, and `affectedServices`) were persisted using raw findings without updating their `evidenceIds`.
  - We remediated this by unifying finding processing under `processFinding(finding)`. A single deduplicated evidence input is created for each distinct node across all 5 categories, and its deterministic evidence ID is populated across all relevant lists. Thus, when an API route handler appears in both `downstreamImpact` and `affectedApis`, it points to the same verified evidence record.

### 3. Non-Fabrication Rule & Traversal Evidence
- **Q**: "How do you generate evidence for downstream nodes that were reached via 3 hops of traversal without fabricating file or line numbers?"
- **Answer**:
  - We strictly adhere to the **Non-Fabrication Invariant**: we never invent synthetic line numbers or fake AST coordinates to satisfy a database schema.
  - Direct findings preserve the exact source file and symbol coordinates from AST extraction.
  - For downstream nodes reached via multi-hop traversal, the evidence captures the node's declared location (if known) or its structural identifier, while the traversal path (`finding.path`) is stored in `evidence.metadata.traversalPath`. The evidence explains the causal chain without fabricating source coordinates.

### 4. Confidence Decay Invariant
- **Q**: "Why must confidence decay be mirrored in evidence rows, and what bug does this prevent?"
- **Answer**:
  - Traversal confidence decays exponentially with distance from the seed ($1.0 \times 0.9^{\text{depth}}$).
  - A common bug in impact tools is resetting confidence to `1.0` when writing evidence, or treating evidence confidence as a static schema default.
  - In Fluxora, `EvidenceWriter.createImpactFindingEvidence` explicitly extracts `finding.confidence` and persists it directly into `evidence.confidence`. Our integration tests assert monotonic decay ($\text{conf}(d_1) > \text{conf}(d_2) > \text{conf}(d_3)$), ensuring that downstream findings with decayed confidence (e.g. `0.81` or `0.729`) are never misrepresented as certain truth.

### 5. Atomicity & Rollback Guarantees
- **Q**: "What happens if a database write succeeds for an impact analysis but fails for its evidence records?"
- **Answer**:
  - Both writes occur within the same PostgreSQL transaction (`BEGIN ... COMMIT`).
  - If any evidence write fails (e.g. due to constraint violations, connection drops, or malformed payloads), the entire transaction executes `ROLLBACK`.
  - Integration test `B4` simulates an evidence insertion failure and proves that zero rows remain in `impact_analyses` and zero rows remain in `evidence`. No orphan conclusions can exist.

### 6. Deterministic Evidence Identity & Idempotency
- **Q**: "How do you handle worker retries and duplicate webhooks without creating duplicate evidence records?"
- **Answer**:
  - Evidence IDs are NOT generated using random UUID v4.
  - They are derived deterministically using SHA-256 (UUID v5) from the stable conclusion tuple:
    - Graph Edges: `(analysisRunId, "edge", sourceCanonicalId, targetCanonicalId, edgeType)`
    - Impact Findings: `(analysisRunId, "impact_finding", nodeId, filePath, path.join("->"))`
  - Re-running an analysis with identical inputs derives the exact same UUIDs. PostgreSQL executes `ON CONFLICT (id) DO UPDATE` or `DO NOTHING`, guaranteeing 100% idempotency and zero duplicate evidence rows.
