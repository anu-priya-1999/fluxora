# Step 28 Graph Builder — Senior Engineering Interview CheatSheet

## High-Frequency Senior Architecture & System Design Questions

### 1. Why separate graph storage from graph construction?
**Answer:**
Separating Graph Storage (Step 27) from Graph Construction (Step 28) enforces a clean **Separation of Concerns**:
- **Graph Storage** owns database schema, migration SQL, composite foreign key constraints, index tuning, and PostgreSQL Row-Level Security (RLS) policies.
- **Graph Builder** owns the pure domain logic of projecting Phase 3 normalized AST results into structured graph nodes, directed edges, and evidence records.
- **Testability**: Pure projection logic can be executed and unit tested in memory in milliseconds without requiring database infrastructure or test suites.

---

### 2. Why is deterministic graph construction important?
**Answer:**
In a software digital twin system like Fluxora, code analysis MUST be **100% deterministic**:
- **Reproducibility**: Given the exact same source code snapshot, the system must generate identical node IDs, edge IDs, and evidence trails across any machine or environment.
- **Diff & Delta Computation**: Comparing code architecture across git commits relies on node/edge canonical identity. Non-deterministic IDs or random node ordering would produce false visual diff noise.
- **Caching & Verification**: Golden fixture testing and performance caches require predictable output arrays.

---

### 3. How do you make a graph builder idempotent?
**Answer:**
Idempotency guarantees that executing the Graph Builder multiple times on the same analysis run produces identical data without creating duplicate rows or throwing constraint errors:
1. **Deterministic Primary Keys**: Node, edge, and evidence IDs are derived deterministically using SHA-256 hashes of `(analysisRunId + canonicalId / subjectKey)`.
2. **Database Schema Constraints**: Unique indexes `UNIQUE (analysis_run_id, canonical_id)` on `graph_nodes` and `UNIQUE (analysis_run_id, source_node_id, target_node_id, edge_type)` on `graph_edges`.
3. **`ON CONFLICT DO UPDATE`**: SQL insertion queries update existing records in place rather than inserting duplicate rows.

---

### 4. How do canonical IDs prevent duplicate nodes?
**Answer:**
In complex codebases, a symbol can be imported, re-exported, or aliased through multiple barrel files (e.g. `import { login } from "@/auth"` vs `import { login } from "./auth"`).
Phase 25 Normalization resolves barrel file chains back to the original declaration and assigns a single **Canonical ID** (e.g. `sym:src/auth.ts#function:login:100`).
The Graph Builder maps symbols by canonical ID into a `Map<canonicalId, GraphNodeInput>`. Any re-export or alias encountering the same canonical ID maps to the exact same single `GraphNode`.

---

### 5. How do you handle unresolved imports?
**Answer:**
If an import specifier cannot be resolved to an internal file (e.g., external packages like `react` or `fs`, or unresolvable relative paths), `NormalizedModuleEdge.targetFile` remains `undefined` or unresolved.
The Graph Builder verifies referential integrity before edge creation. If an edge endpoint is unresolvable, the edge is safely rejected and counted in `statistics.rejectedEdgesCount`.
**Crucial Rule**: The builder NEVER fabricates fake nodes or fake edges merely to force an edge to insert.

---

### 6. Why should a graph builder avoid inventing relationships?
**Answer:**
Fluxora operates on the core invariant: **Deterministic Core, Probabilistic AI Edge**.
The dependency graph is the ground truth. If the graph builder fabricated unsupported semantic relationships (e.g. assuming two symbols interact without AST proof), downstream impact analysis and blast-radius traversal would produce false positives, destroying developer trust.
AI models explain deterministic graph evidence; they never invent the underlying graph topology.

---

### 7. How do you preserve evidence/provenance?
**Answer:**
For every `GraphNode` and `GraphEdge` created, the Graph Builder generates an `EvidenceRecord`:
- **Traceable Location**: `filePath`, `lineStart`, `lineEnd`, `columnStart`, `columnEnd`.
- **Subject Linkage**: `subjectType = "graph_node"` or `"graph_edge"` with `subjectId` pointing to the node/edge's deterministic UUID.
- **Human Explanation**: Plain-English description explaining why the node or edge exists (e.g. `Declared symbol "login" of kind "function"`).

---

### 8. What transaction guarantees should graph construction provide?
**Answer:**
Graph construction must be **atomic (All-or-Nothing)**:
- Persisting nodes, edges, and evidence for an analysis run happens within a single database transaction (`withTenant`).
- If an invalid node fails schema validation or a database constraint fails, PostgreSQL issues a `ROLLBACK`.
- An analysis run will never be left in a partially written or corrupt graph state.

---

### 9. How do you prevent cross-tenant graph contamination?
**Answer:**
1. **Scope Association**: Every graph node, edge, and evidence record is explicitly tagged with `analysis_run_id`.
2. **PostgreSQL Row-Level Security (RLS)**: Tables enforce RLS policies (`fluxora_analysis_run_in_current_tenant`) checking that the parent `repository.organization_id = fluxora_current_org_id()`.
3. **Database-Level Protection**: Even if application logic misconfigures IDs, cross-tenant reads or writes fail at the database engine level.

---

### 10. What happens if an edge points to a missing node?
**Answer:**
Before building an edge, the Graph Builder looks up both `sourceCanonicalId` and `targetCanonicalId` in the generated node map.
If either node is missing, the edge creation is aborted, the rejection counter is incremented, and no dangling edge or invalid foreign key error reaches the database.

---

### 11. How would you scale graph construction for a very large repository?
**Answer:**
For massive repositories with millions of symbols:
- **Chunked Batch Processing**: Insert nodes and edges in chunked batches (e.g. 1,000 items per `INSERT ... VALUES` query) within the transaction to minimize memory overhead.
- **Copy Protocol / Staging Tables**: For extreme scale, use PostgreSQL `COPY` into staging tables followed by set-based `INSERT INTO graph_nodes SELECT ... ON CONFLICT DO UPDATE`.
- **Parallel Workers**: Process independent file subgraphs in parallel worker threads before merging into the main transaction.

---

### 12. What are the trade-offs between rebuilding and incremental graph updates?
**Answer:**
- **Rebuilding Per Snapshot (MVP Pattern)**:
  - *Pros*: Simple, completely deterministic, zero risk of stale state or orphaned edges.
  - *Cons*: Higher CPU and database insert overhead on large codebases.
- **Incremental Graph Updates (Production Hardening)**:
  - *Pros*: Fast PR analysis by updating only changed files and their immediate dependencies.
  - *Cons*: Complex invalidation logic; risk of subtle graph drift or orphaned nodes if dependency cascading fails.
