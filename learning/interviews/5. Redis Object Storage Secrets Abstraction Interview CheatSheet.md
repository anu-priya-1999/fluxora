# Fluxora Step 5 — Redis, Object Storage & Secrets Abstraction Interview CheatSheet

## 1. What this step established

Fluxora introduces infrastructure abstractions for Redis, object storage, and secrets. The application depends on interfaces/contracts rather than embedding provider-specific details everywhere.

## 2. 30-second interview answer

> “I separated infrastructure concerns behind small abstractions so the product code does not depend directly on one provider. Redis is suited to ephemeral/cache/coordination workloads, object storage holds durable blobs, and secrets are resolved through a dedicated configuration boundary. This also makes local development and later cloud migration less invasive.”

## 3. Core questions

### Q1. Why abstract object storage?

The application should not need to know whether a blob is stored locally, in S3, or in another provider. It should ask for a storage capability through a stable interface.

### Q2. What belongs in Redis?

Short-lived data, caching, rate-limiting state, coordination, and other workloads where key/value access and TTL semantics are useful. It should not automatically become the source of truth for durable application records.

### Q3. What belongs in PostgreSQL versus object storage?

PostgreSQL is for structured metadata, relationships, constraints, and transactional records. Object storage is for large immutable or blob-like data such as repository archives.

### Q4. Why a secrets abstraction?

It prevents direct environment/secret-manager assumptions from leaking through every package and gives a single boundary for retrieving sensitive configuration.

### Q5. What is the difference between a cache and a source of truth?

A cache can be discarded and rebuilt. A source of truth is authoritative durable state. Confusing them can create correctness bugs.

### Q6. What does an object-storage key represent?

A stable namespace for locating a blob. It should avoid collisions and should encode enough context to support tenant isolation and lifecycle management.

## 4. Senior-level questions

### Q7. Why not store repository archives in PostgreSQL?

Large binary blobs can increase database storage and backup costs and compete with transactional workloads. Object storage is optimized for that use case.

### Q8. How do you avoid cross-tenant object access?

Use tenant-scoped object keys, server-side authorization, and provider-side access controls where applicable. Do not treat a predictable object key as an authorization mechanism by itself.

### Q9. What should happen when object storage upload succeeds but DB persistence fails?

The system needs compensating cleanup or a reconciliation mechanism. Fluxora Step 13 explicitly deletes the uploaded object if final metadata persistence fails.

### Q10. Why keep provider adapters small?

A smaller adapter surface makes testing and migration easier. It also prevents cloud SDK concepts from spreading through business logic.

### Q11. What happens during a provider outage?

The application should distinguish transient infrastructure failure from permanent validation failure and expose appropriate retry behavior at the job/request boundary.

## 5. Scenario questions

### Scenario: a developer stores a cache result as authoritative state

Reject the design unless the data is truly reconstructable. Durable business state belongs in the system of record.

### Scenario: changing S3 to filesystem storage requires editing 30 files

The abstraction boundary is leaking. Move provider-specific code behind one adapter rather than rewriting consumers.

## 6. Common traps

- Redis is not automatically a database replacement.
- Object storage should not own relational metadata.
- An abstraction is useful only if it remains smaller and more stable than the provider API it hides.

## 7. Strong closing statement

> “Step 5 establishes infrastructure boundaries early so later ingestion code can store large artifacts without coupling the entire product to one storage provider.”
