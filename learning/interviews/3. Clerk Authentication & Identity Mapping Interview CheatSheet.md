# Fluxora Step 3 — Clerk Authentication & Identity Mapping Interview CheatSheet

## 1. What this step established

Fluxora uses Clerk for managed authentication while keeping its own organization/user mapping in PostgreSQL. External identity and application identity are deliberately separated.

## 2. 30-second interview answer

> “I use Clerk as the authentication provider, but Fluxora still owns its application-level organization and user records. After verifying the Clerk identity, the API maps that external identity to a Fluxora user and organization. That keeps authentication concerns with the identity provider while keeping tenant relationships and product authorization in our database.”

## 3. Core questions

### Q1. Why use a managed identity provider?

It reduces the amount of security-sensitive authentication code the application must maintain, including sessions, credential flows, and identity lifecycle behavior.

### Q2. Why keep a local user table if Clerk already has users?

The application needs internal relationships and metadata: organization membership, ownership, product settings, audit context, and tenant-specific authorization.

### Q3. What is identity mapping?

It is the mapping from an external subject identifier, such as a Clerk user ID, to a local application user record.

### Q4. What should the API trust from the request?

Only validated authentication claims/token context. Client-supplied user IDs or organization IDs should not be treated as authoritative.

### Q5. How should organization context be determined?

From a trusted authenticated mapping or server-side membership relation, not from an arbitrary browser field.

### Q6. What is the difference between a session and a user record?

A session represents an authenticated interaction context. The user record represents the application's durable identity and relationships.

### Q7. What happens when a Clerk user is removed?

The application needs a lifecycle policy for the local mapping, membership, and any owned data. External identity deletion and internal data deletion are separate decisions.

### Q8. How do you protect API routes?

Require server-side authentication, verify the token/claims with the provider's supported mechanism, map to the internal user/organization, then apply authorization and RLS.

## 4. Senior-level questions

### Q9. Why not copy the entire Clerk user object into PostgreSQL?

Keep only the data the application owns and needs. Duplication increases synchronization problems and may create unnecessary privacy/data-retention risk.

### Q10. What happens if Clerk is temporarily unavailable?

The application should fail closed for operations that require fresh authentication validation rather than inventing a local fallback identity.

### Q11. How would you support multiple auth providers later?

Create an internal identity abstraction keyed by provider + subject, and keep organization/application relationships independent of the provider-specific representation.

### Q12. What is a common authorization mistake?

Validating that a user is logged in and assuming they can access the requested tenant/resource. Authentication and resource authorization are separate checks.

### Q13. Where should authorization ultimately be enforced?

At multiple layers: request authentication, service-level authorization, and database isolation where practical. Fluxora uses RLS as the database boundary.

## 5. Debugging scenarios

### Scenario: user is authenticated but sees no repositories

Check external identity mapping, selected organization membership, tenant context, RLS policies, and whether the UI is connected to the expected database.

### Scenario: a malicious client sends another organization ID

The server must ignore untrusted tenant identifiers and derive tenant context from authenticated membership. RLS provides another isolation layer.

## 6. Common traps

- “Clerk is the database of record for Fluxora users.” — Not necessarily.
- “A valid JWT means the user may access every resource.” — False.
- “The browser can choose the tenant and the server just trusts it.” — Unsafe.

## 7. Strong closing statement

> “The separation is deliberate: Clerk answers ‘who are you?’ while Fluxora answers ‘which tenant are you part of, and what are you allowed to do here?’”
