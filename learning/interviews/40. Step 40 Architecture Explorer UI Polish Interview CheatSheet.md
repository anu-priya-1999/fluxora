# 40. Step 40 Architecture Explorer UI Polish Interview Cheat Sheet

## Likely Interview Questions & Answers

### Q: How do you handle loading states in a data-driven graph visualization?

**A:** We distinguish between initial loading (no data yet → full loading screen with spinner and accessible status role) and background refresh (data already displayed → non-blocking progress bar). The key principle is never blanking useful content when a refetch is in progress. The loading state uses `role="status"` with `aria-live="polite"` so screen readers announce it without being disruptive.

### Q: How do you handle the difference between "empty result" and "error"?

**A:** These are semantically different states with distinct presentations:
- **Empty**: The server responded 200 OK with zero nodes. We show an informative state with guidance (adjust filters, wait for analysis). Uses an inbox icon (📭) and polite status role.
- **Error**: The server failed to respond (network error, auth error, 500). We show an alert state with a retry button. Uses a warning icon (⚠️) and `role="alert"` with `aria-live="assertive"` for screen reader urgency.

Both are distinct from "analysis not ready" (⏳ hourglass), which indicates the backend hasn't finished processing rather than an empty or failed result.

### Q: How do you implement retry/recovery without creating a second data-fetch path?

**A:** Retry simply increments a counter (`liveUpdateTrigger`) that is in the dependency array of the React `useEffect` that triggers the fetch. This re-runs the exact same `buildGraphQueryRequest` → `fetchGraphQuery` pipeline with all current context, filters, and parameters preserved. There is strictly one data-fetch path in the entire component.

### Q: What happens when a background refresh fails?

**A:** The existing graph remains fully visible and interactive. A non-blocking error banner appears above the graph with the error message, a retry button, and a dismiss button. The user can continue working with the current data. This follows the "stale-while-revalidate" resilience UX pattern.

### Q: How do you model the UI state?

**A:** Two orthogonal state dimensions:

1. **Query lifecycle**: `ExplorerState` union type (`loading` | `ready` | `empty` | `not_ready` | `error`)
2. **Connection status**: `ExplorerConnectionStatus` (`connected` | `reconnecting` | `disconnected`)

Plus two supplementary flags:
- `isRefreshing: boolean` — whether a background fetch is in progress while graph is displayed
- `refreshError: string | null` — non-blocking error from a failed background refresh

These dimensions are independent. A `ready` graph with a `disconnected` WebSocket is valid and fully functional.

### Q: Why not use a single combined state machine?

**A:** A single combined state machine would create a combinatorial explosion of states (ready+connected, ready+reconnecting, ready+disconnected, ready+refreshing+connected, etc.). Since graph data and connection status are genuinely independent concerns (a WebSocket outage does not invalidate loaded graph data), keeping them separate makes the code simpler, more testable, and easier to reason about.

### Q: How do you handle WebSocket disconnection?

**A:** A WebSocket disconnection never makes the graph unusable. The graph was loaded via HTTP POST and remains fully interactive. We show a subtle badge in the header ("Offline" with a gray dot) to inform the user that live updates are paused. When the WebSocket reconnects, the badge updates to "Live" (green dot). No polling fallback is introduced.

### Q: What accessibility considerations did you make?

**A:**
- Loading/status messages use `role="status"` with `aria-live="polite"`
- Errors use `role="alert"` with `aria-live="assertive"` for immediate announcement
- All buttons have descriptive `aria-label` attributes
- Status indicators use text labels alongside colors (not color-only)
- Retry buttons are keyboard accessible (standard `<button>` elements)
- The connection badge has an `aria-label` describing the full status

### Q: How do you prevent layout shifts during state transitions?

**A:**
- Loading state has a fixed `minHeight: 400px` matching the graph area
- The updating indicator is `position: absolute` at the top — zero layout displacement
- The refresh error banner is a flex row within the normal flow
- All states maintain the same outer container structure

### Q: How do you ensure selection is preserved across refreshes?

**A:** After each successful fetch, we check if the currently selected node ID still exists in the new data. If it does, selection is preserved and the inspector panel stays open. If the node was removed (e.g., by a filter change or graph update), selection is safely cleared to `null`. This uses a functional state update: `setSelectedNodeId((current) => newNodes.some(n => n.id === current) ? current : null)`.

### Q: What's the performance impact of these changes?

**A:** Minimal:
- No new network requests or endpoints
- No polling
- Status components are lightweight (small DOM elements with inline styles)
- CSS animations use `opacity` and `transform` (GPU-composited)
- `isRefreshing` and `refreshError` are primitive values, not complex objects
- The `mapWsStatusToConnectionStatus` function is a simple switch statement

### Q: What tradeoffs did you make?

**A:**
1. **Manual retry vs auto-retry**: We chose manual retry (button click) for initial errors. The WebSocket has its own automatic reconnection with exponential backoff, but HTTP query errors are user-triggered. This avoids hammering a potentially down server.
2. **Inline banner vs toast**: We chose an inline error banner over a toast system. Toasts can be missed and add unnecessary UI dependencies. The banner stays visible until dismissed or resolved.
3. **Inline styles vs CSS modules**: We used inline styles to match the existing codebase pattern and avoid adding new build dependencies.
4. **Simple boolean tracking vs state machine**: We used `isRefreshing` boolean + `refreshError` string instead of a formal state machine library. The state space is small enough that this is clearer.
