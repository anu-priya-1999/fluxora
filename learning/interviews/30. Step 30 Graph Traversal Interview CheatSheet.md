# Step 30 Graph Traversal Interview CheatSheet

## Executive Summary

Global Step 30 implements **Bounded-Depth Recursive-CTE Graph Traversal** (`traverseGraph`) in `@fluxora/db`. It allows Fluxora to perform deterministic, tenant-isolated graph reachability queries over PostgreSQL using `WITH RECURSIVE` CTE queries with cycle prevention and depth caps.

---

## Key Interview Questions & Concise Answers

### Q1: What is a graph traversal and why does Fluxora need it?
**Answer:** Graph traversal is the process of visiting adjacent nodes in a dependency graph starting from a target node. Fluxora uses graph traversal to perform change-impact analysis (blast-radius calculation) and scenario simulation. Traversal finds all direct and downstream dependent services, modules, APIs, and events within a configured depth limit.

### Q2: What is a PostgreSQL Recursive CTE and how does it work?
**Answer:** A recursive Common Table Expression (`WITH RECURSIVE`) evaluates an **anchor member** (initial query) and a **recursive member** (which references the CTE itself). On each iteration, the recursive term executes over the output of the previous step until no new rows are returned or a termination condition (`WHERE t.depth < maxDepth`) is met.

### Q3: How does `traverseGraph` prevent infinite loops on cyclic dependency graphs?
**Answer:** Each row in the CTE maintains an array of visited node IDs (`path = ARRAY[n.id::text]`). In the recursive term, the query checks `WHERE NOT (next_node.id::text = ANY(t.path))`. If a target node is already present in the path array, the branch is pruned, preventing infinite recursion.

### Q4: How is maximum depth enforced and why is a hard upper bound required?
**Answer:** Server-side validation rejects any `maxDepth` argument that is non-integer, negative, or exceeds `HARD_MAX_TRAVERSAL_DEPTH = 20`, throwing `GraphTraversalValidationError`. Inside PostgreSQL, `WHERE t.depth < maxDepth` halts recursion when `depth` reaches `maxDepth`. This protects PostgreSQL from runaway query execution.

### Q5: How does the query handle multiple paths to the same node (fan-in)?
**Answer:** The CTE uses `ROW_NUMBER() OVER (PARTITION BY node_id ORDER BY depth ASC, path::text ASC)` to deduplicate reached nodes. Filtering by `WHERE rn = 1` selects the shortest path (minimum depth) and guarantees deterministic results.

### Q6: How are Row-Level Security (RLS) and multi-tenancy preserved during recursive traversal?
**Answer:** All database operations run inside `withTenant(pool, organizationId, ...)` which sets `app.current_org_id`. Both the anchor member and recursive term filter by `analysis_run_id = $2::uuid`. Child records are protected by Postgres RLS policies joining up to `organization_id`.

### Q7: Why does Fluxora use PostgreSQL recursive CTEs instead of a dedicated graph database like Neo4j?
**Answer:** Per `docs/architecture/06-database-schema.md §6.1`, single-repository graphs (1k–50k nodes) fit comfortably in PostgreSQL. Postgres recursive CTEs provide transactional consistency between graph records and evidence records in a single database engine, eliminating distributed transaction complexity while enforcing RLS.

## Architectural Invariants Verified

1. **Deterministic Core**: Traversal results depend only on graph structure and depth parameters, never on AI or non-deterministic state.
2. **Cycle Safety**: Traversal is guaranteed to terminate on any graph structure including cycles.
3. **Hard Depth Cap**: Depth limits are enforced server-side (`maxDepth <= 20`).
4. **Parameterized SQL**: All SQL values are parameterized using `$1, $2, $3...` preventing SQL injection.
5. **Evidence Preservation**: Associated evidence records are retrieved without altering or fabricating source provenance.
