## Core Technical Questions & Strong Answers

### Q1: Explain the complete Fluxora code-intelligence pipeline.
**Answer:** The Phase 3 pipeline processes a repository snapshot through 8 sequential stages:
1. **Stack Detection (Step 18)**: Identifies languages (TypeScript, JavaScript, JSON, CSS, Markdown) and frameworks (Next.js, React, Node.js) via extension mapping, manifests, and configs.
2. **AST Symbol Extraction (Step 19)**: Traverses TypeScript Compiler API ASTs per file to extract functions, classes, interfaces, types, and variables.
3. **Module Graph Extraction (Step 20)**: Extracts static import/export edges and resolves `tsconfig.json` path aliases (`@/*`).
4. **API & Route Detection (Step 21)**: Detects Next.js App Router HTTP handlers (`GET`, `POST`, etc.) and Express router instances.
5. **Event Pattern Detection (Step 22)**: Identifies pub/sub method shapes (EventEmitter, Redis, KafkaJS, RabbitMQ).
6. **Database Reference Detection (Step 23)**: Scans for ORM/database interactions (Prisma, Drizzle, TypeORM, Sequelize).
7. **Tree-sitter Fallback Pass (Step 24)**: Runs WASM Tree-sitter parsing for non-TS/JS files (JSON, CSS, HTML, Markdown).
8. **Normalization (Step 25)**: Resolves barrel file re-export chains, dedupes symbols, assigns canonical IDs (`sym:...`, `edge:...`), and produces statistics.

### Q2: Why is static analysis performed in stages rather than in one giant pass?
**Answer:** Staging enforces separation of concerns, testability, and modularity. Each stage specializes in a specific construct (e.g., symbol AST traversal vs module graph specifier resolution vs route detection). Staging also enables language-specific optimization—such as reserving Tree-sitter fallback parsing only for files where the primary TypeScript Compiler API pass was inapplicable.

### Q3: Why isn't Tree-sitter the primary parser for TypeScript/JavaScript?
**Answer:** The official TypeScript Compiler API handles complete TS syntax fidelity, type annotations, and full AST granularity for JavaScript and TypeScript files. Tree-sitter is used as a fast, multi-language fallback parser for non-TS/JS files (JSON, CSS, HTML, Markdown) or malformed source code where the primary compiler cannot parse safely.

### Q4: Why normalize before graph construction?
**Answer:** Symbol extraction produces file-local AST declarations, and module graph extraction produces string specifier edges. Barrel re-exports (`export * from "./foo"`) create alias chains that mask canonical definitions. Normalization resolves barrel files, resolves aliases to canonical declaration IDs (`sym:...`), and dedupes symbols *before* writing to Postgres database tables (`GraphNode`, `GraphEdge`) in Phase 4.

### Q5: Why is determinism critical in automated code intelligence?
**Answer:** Code analysis outputs must be reproducible and explainable. Running the pipeline twice over the exact same snapshot must yield identical canonical IDs, ordering, edge counts, and summary statistics. Determinism prevents phantom diffs, flaky tests, and non-reproducible graph nodes.

### Q6: How do you verify that an automated code-intelligence system is correct?
**Answer:** By running the pipeline against a pinned, checksum-verified golden fixture repository (`shadcn-ui/taxonomy`), and hand-verifying representative extracted symbols, module edges, API routes, and database references directly against the actual fixture source files and line numbers.

### Q7: Why use a golden fixture repository?
**Answer:** Synthetic toy code snippets do not capture real-world repository complexity (monorepo paths, complex imports, Next.js App Router conventions, Prisma schemas, multi-language configurations). A golden fixture provides an immutable, real-world baseline with pinned commit SHA and SHA-256 checksum integrity.

### Q8: How do you handle unresolved or ambiguous relationships?
**Answer:** Fluxora records unresolved references explicitly in `normalized.unresolved` with category tags (`module`, `export`, `symbol`, `route`, `event`, `database`) and rationale, rather than swallowing exceptions or inventing dummy edges.

### Q9: Why is no graph database created in Phase 3?
**Answer:** Phase 3's goal is pure code intelligence extraction and normalization. Database schema migrations, relational persistence (`GraphNode`, `GraphEdge`, `Evidence`), and depth-bounded recursive CTE traversals belong to **Phase 4 — Graph**.

## Architectural Invariants Matrix

| Invariant | Implementation Mechanism |
| :--- | :--- |
| **No Code Execution** | Static AST and compiler analysis only; customer code is never imported or executed. |
| **No AI/LLM non-determinism** | 100% deterministic rule-based analysis. |
| **No Database Storage** | In-memory pipeline execution; persistence deferred to Phase 4. |
| **Golden Fixture Integrity** | Pinned commit SHA `298a8857...`, SHA-256 checksums, LF line-ending enforcement. |
