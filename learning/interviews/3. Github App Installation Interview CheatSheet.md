# GitHub App Installation — Interview Cheat Sheet

## 30-second answer

Fluxora login is Clerk. Repository permission is a GitHub App. Step 10 only stores the installation after proving it belongs to the same GitHub user Clerk already linked. The App ID signs a short JWT. The installation id comes from GitHub's Setup URL, is handled as a string, and is stored as a tenant-scoped `bigint` under PostgreSQL RLS. Completion is idempotent.

In the current deployment, web is on Vercel and the API is on Render. After GitHub redirects to `/github/setup`, the **browser** calls Clerk `useAuth().getToken()` and POSTs to Render. That cross-origin call is why the native `node:http` API implements CORS on `/api/v1/github/installations` only, allowlisted from `CLERK_AUTHORIZED_PARTIES`.

## Architecture explanation

Three identities, never collapsed:

| Piece | Proves | Does not prove |
| --- | --- | --- |
| Clerk session | Which Fluxora user is in the browser | That the App is installed, or repo access |
| GitHub App JWT | This process is the Fluxora App | Which human is logged in |
| Installation record from GitHub | The App is installed on `account.id` | That the caller is that person — until Fluxora compares it to Clerk |

Tenant mapping: Clerk GitHub `providerUserId` → `provisionGithubUser` → `organization_id` → `github_installations` row with RLS `organization_id = fluxora_current_org_id()`.

The private key never leaves the API. The web host only has the public slug and the API origin.

## Request lifecycle explanation

```text
Dashboard link
  → GitHub install UI (slug only)
  → GET /github/setup?installation_id&setup_action
  → Next server: Clerk auth() + validate query + pass FLUXORA_API_URL
  → Client: getToken()
  → OPTIONS (preflight) then POST /api/v1/github/installations
  → verify Clerk JWT (authorizedParties)
  → load GitHub external account
  → provision owner org if needed; require owner/admin
  → sign App JWT; GET /app/installations/{id}
  → account.type User and account.id === Clerk GitHub id
  → saveGithubInstallation (insert / no-op / refresh)
```

Interview line: "GitHub's redirect is a GET. Authorization is the Clerk Bearer token plus GitHub's installation resource, not the query string."

## GitHub App vs Clerk

- Clerk: who is logged in, and which GitHub user id is linked to that login.
- GitHub App: Fluxora's integration identity (App ID + private key).
- Installation: that App installed on one GitHub account.
- Clerk login does not install the App. The App install does not create the Clerk session. `/github/setup` binds them.

## App ID vs installation ID

- App ID is static configuration. It is the JWT `iss` claim. One App, one id.
- Installation ID is created by GitHub per install. It is dynamic. It must not be an env var or a constant.
- Slug is public and only builds `https://github.com/apps/{slug}/installations/new`.
- Private key signs JWTs. It never goes to the browser or into the JWT payload.

## Dynamic installation ids

GitHub redirects to:

```text
/github/setup?installation_id=123&setup_action=install
```

`setup_action` is `install` or `update` (or omitted). The id is taken from that request and sent as JSON string `github_installation_id`. The API then asks GitHub `GET /app/installations/{id}` and checks the id GitHub returns is the same one.

## Why string, then bigint

JavaScript numbers cannot represent every integer PostgreSQL `bigint` can store. `JSON.parse` rounds integers past `2^53 - 1`. The API rejects JSON numbers, keeps decimal strings, inserts with `::bigint`, and selects with `::text`. GitHub's JSON is pre-processed with `quoteJsonIntegers` so payload ids stay strings.

Say this if asked "why not just use number?": because a rounded id would verify or store the wrong installation, and the failure would look like success.

## GitHub App JWT

- RS256 via `node:crypto`, no GitHub SDK.
- `iat` minus 60 seconds for clock skew.
- expires 9 minutes after `iat` because GitHub allows at most 10 minutes.
- used only to read the installation in this step.
- installation access tokens are a later ingestion concern. They are not stored. The private key plus installation id is enough to mint one later.

## Verification

Accept only when GitHub says:

- `account.type === "User"`
- `account.id === clerk github provider user id`
- installation id matches the request

Reject org installs here. The account id on an org install is the org, and an App JWT does not prove the signed-in user administers that org. Binding it anyway would cross tenants.

The query parameter is not authorization. Authorization is Clerk session + GitHub's installation record + role `owner` or `admin`.

## Setup URL and Clerk browser token

1. Dashboard link opens GitHub's install page.
2. GitHub redirects the browser to the Setup URL.
3. Next.js **server** checks the Clerk session and query params. It does not mint the API Bearer token.
4. A **client** component calls `useAuth().getToken()` and POSTs to the existing `node:http` API.
5. API persists under the caller's organization.

**Why the token moved to the browser:** after the GitHub redirect, Vercel still had a Clerk session (`auth()` authenticated) but server-side `getToken()` returned `null`, so setup showed "Authentication required." Browser `getToken()` is the session JWT that `authenticateClerkToken` accepts.

The redirect is a GET. That is safe because the POST is idempotent and the installation is checked against the session's GitHub user. A forged id fails the account match.

## CORS

The completion `fetch` is Vercel origin → Render origin, with `Authorization` and JSON `Content-Type`, so the browser sends OPTIONS first.

Implementation:

- `apps/api/src/http/cors.ts`
- allowlist = `CLERK_AUTHORIZED_PARTIES` (default `http://localhost:3000`)
- methods `GET, POST, OPTIONS`
- headers `Authorization, Content-Type`
- echo the request `Origin` when it is listed; never `*`
- applied only on `/api/v1/github/installations`

OPTIONS always returns 204; if the origin is not allowed, CORS headers are omitted so the browser blocks. POST applies the same headers via `res.setHeader` before `sendJson`.

Quirk to know: OPTIONS then calls `writeHead(204, responseHeaders({}))` with an empty extra object after `applyCorsHeaders`. CORS is not passed into `responseHeaders`; it relies on Node merging `setHeader` values.

## Tenant mapping / RLS

Table `github_installations`:

- one row per organization
- installation id unique globally
- RLS: `organization_id = fluxora_current_org_id()`
- `FORCE ROW LEVEL SECURITY`
- writes inside `withTenant`

RLS hides other tenants, so it cannot by itself tell you that another org already took the installation id. The unique index does, and the API returns a generic 409.

## Idempotency

- same install again → `200` and `created: false`
- reinstall, same GitHub account, new installation id → update the row
- different GitHub account → 403
- installation id already stored for another org → 409

Interview line: "Retrying the setup redirect must not create a second row or an error."

## Least privilege

App permissions intended for Fluxora: contents read, pull requests read, metadata read. No writes. Webhooks are not part of this step.

The web process does not load the private key. The API does. Logs redact PEMs, bearer tokens, and JWTs.

## PostgreSQL lesson worth telling

`unique_violation` aborts the current transaction. You cannot catch it and keep querying unless the insert ran in a savepoint. Fluxora rolls back to `fluxora_github_installation_write` and then re-reads only the current tenant's row. That is also why the code does not `SELECT` the conflicting tenant: RLS would return nothing, which is the point.

## Security decisions (say these out loud)

- Untrusted `installation_id` in the URL; GitHub is the source of truth.
- Personal User installs only until org membership is proven.
- String ids so bigint cannot be rounded.
- CORS allowlist reused from Clerk authorized parties — one trusted-origin list.
- CORS scoped to the one browser-called route.
- App PEM on the API host, not Vercel.
- Web stopped manually reading repo-root `.env` with `fs` because Vercel/Turbopack cannot treat that like the API process.

## Trade-offs

- Env/file for the private key matches how the API already holds `CLERK_SECRET_KEY`. Secrets Manager remains the production direction from Step 5; this step does not invent a second secrets system.
- Superusers bypass RLS. Unique installation id still holds. Same local-dev caveat as the earlier tenant tables.
- User ids still cross the existing numeric provision function, and unsafe integers are rejected. Installation ids do not cross `Number`.
- Completing from the browser (vs Next server `fetch`) fixes the null `getToken()` bug and **requires** CORS. Completing from the server would avoid CORS but did not work on Vercel after the GitHub redirect.
- Reusing `CLERK_AUTHORIZED_PARTIES` for CORS avoids a second origin list that could drift from Clerk's `azp` check. Cost: a CORS origin change is also an auth config change.

## Likely interviewer questions

### Why did you choose a GitHub App instead of a user OAuth token from Clerk?

Clerk already linked the GitHub **user id**. A user OAuth token would follow the person, pick up extra scopes, and vanish if they disconnect Clerk. A GitHub App is Fluxora's integration: least-privilege repo permissions, installation tokens later, rate limits, and an installation id we can store per tenant. Step 10 does not even mint that installation token yet.

### Why is Clerk still needed if GitHub authenticates the user?

GitHub authenticates the **installer of the App**. Fluxora still needs a product login, a tenant (`organization_id`), and a stable link to `users.github_user_id`. Clerk is that identity. Without it, an `installation_id` in a URL has no Fluxora principal to authorize.

### Why is `installation_id` dynamic? Why not put it in `.env`?

GitHub generates it per install and per reinstall. An env var would be one person's id baked into every environment and would be wrong after they reinstall. The Setup URL is the delivery mechanism.

### What happens if installation is replayed?

The same Clerk user + same installation + same GitHub account hits `planGithubInstallationWrite` `unchanged`: HTTP 200, `created: false`, no second row. That is why GitHub's GET redirect is safe to hit twice.

### How do you prevent another GitHub account from claiming an installation?

The API loads the installation with the **App** JWT and requires `account.id` to equal the Clerk GitHub `providerUserId`. Mismatch → 403 `installation_account_mismatch`. A second organization trying to insert the same `github_installation_id` hits the global unique index → 409 `installation_conflict` after the savepoint, without leaking the other org. Org-type installations are rejected because that `account.id` is not the person.

### Why is CORS required?

After token acquisition moved to the browser, `fetch` runs on the Vercel origin against the Render API origin. That is cross-origin. The POST uses `Authorization` and `application/json`, so the browser preflights with OPTIONS. A native `node:http` server that ignores OPTIONS/`Access-Control-*` will look like a network/auth failure in the UI even if the POST handler is correct.

### Why shouldn't the private key be in Vercel?

Vercel hosts Next.js. The App JWT is signed in the API. The key is GitHub App identity, equivalent in sensitivity to `CLERK_SECRET_KEY`. Putting it on Vercel expands the blast radius (frontend deploys, preview envs, any client-adjacent leak) and is unnecessary: the browser never signs App JWTs.

### What would change when moving Render → AWS?

The **protocol** stays: Clerk JWT in, App JWT to GitHub, RLS write. Hosting changes:

- Run the same `node:http` process on ECS/EC2/Lambda-with-caveats instead of Render.
- `DATABASE_URL` points at RDS (or similar); migrations still apply `0008`.
- `GITHUB_APP_PRIVATE_KEY` should move from env toward Secrets Manager / KMS envelope encryption (architecture §11.2–11.3). The API already has a Step 5 secrets abstraction; Step 10 did not switch onto it yet.
- `CLERK_AUTHORIZED_PARTIES` / CORS still must list the Vercel origin (or CloudFront origin if the web host moves).
- `FLUXORA_API_URL` on Vercel becomes the new https API origin.
- No change to string ids, ownership checks, or the savepoint.

### Why string IDs in JSON?

IEEE-754 cannot hold every PostgreSQL `bigint`. A rounded installation id would look valid.

### Why personal User installs only?

An Organization installation's `account.id` is the org. The App JWT does not prove the signed-in user administers that org. Binding it would attach another tenant's repos.

### Why sign JWTs with `node:crypto` instead of Octokit?

Step 10 only needs one signed JWT and one GET. An SDK would add surface area without changing the security model.

### Why reuse `CLERK_AUTHORIZED_PARTIES` for CORS?

Those origins are already the allowed Clerk `azp` values. A second list would drift. Tests assert `*` is rejected and that the Vercel origin and localhost can both be listed.

### Why did you empty `loadWebRootEnv()`?

The web app used `node:fs` to copy selected keys from the monorepo `.env`. Vercel/Turbopack is not that Node API process; the import/load failed. Next and Vercel already inject env. Local web vars belong in `apps/web/.env.local`. The API still loads repo-root `.env`.

### How do you handle a unique violation under RLS?

Savepoint, rollback to it, re-read **this** tenant's row. No row means another tenant won the unique index → generic 409.

## Common follow-ups (short)

**Could Next.js proxy the POST to avoid CORS?** Yes, that would be server-to-server again — which is what failed when `getToken()` was null. You would need a working server token or a BFF that already has the session.

**Is the Clerk token a GitHub token?** No.

**Do you store installation access tokens?** No. Only installation id + account snapshot.

**Member/viewer?** `GithubInstallationRoleError` → 403 `insufficient_role`.

**Missing App config?** 503 `github_app_not_configured`; process still serves `/healthz`.

**Partial App config?** `createApiServer` throws with a message that does not include the PEM.

**Large body?** 413 after 4096 bytes.

**JSON number id?** 400 `invalid_installation_id`.

## Other trade-offs (kept)

- Env/file for the private key matches `CLERK_SECRET_KEY`. Secrets Manager remains the documented production direction.
- Superusers bypass RLS; unique installation id still holds.
- Clerk user ids still cross the numeric provision function.

## What not to claim

- Tests / typecheck / lint / build / migrate were not run as part of the documentation update.
- Repository ingestion is not done.
- An org-wide install is not accepted yet.
- Architecture's KMS-backed private-key storage is not implemented in Step 10; the key is env/file on the API host.
- DESIGN.md still describes a Next **server** POST; the **code** uses a browser POST plus CORS. Interview from the code.
