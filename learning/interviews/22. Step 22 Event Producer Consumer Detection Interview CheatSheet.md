# Step 22: Event Producer & Consumer Pattern Detection Interview CheatSheet

## High-Level Pitch
Step 22 implements deterministic static detection for event producer and consumer patterns across TypeScript and JavaScript source files. It transforms code intelligence from *"what files and symbols exist"* into *"what asynchronous pub/sub channels, event streams, and message queues connect different subsystems?"*. Operating strictly on AST traversal without code execution, it detects producers and consumers across Node.js EventEmitter, Redis pub/sub, KafkaJS, and RabbitMQ (amqplib).

---

## Key Architectural Concepts

### 1. The 4 Initial Ecosystems
- **Node.js EventEmitter**:
  - Producer: `emitter.emit("event")`, `this.emit("event")` in subclass.
  - Consumer: `emitter.on("event", fn)`, `emitter.once("event", fn)`, `emitter.addListener("event", fn)`.
- **Redis Pub/Sub**:
  - Producer: `client.publish("channel", ...)`.
  - Consumer: `client.subscribe("channel", fn)`, `client.pSubscribe("pattern", fn)`.
- **KafkaJS**:
  - Producer: `producer.send({ topic: "..." })`.
  - Consumer: `consumer.subscribe({ topic: "..." })`, `consumer.run({ eachMessage: ... })`, `consumer.run({ eachBatch: ... })`.
- **RabbitMQ / amqplib**:
  - Producer: `channel.publish(exchange, routingKey, ...)`, `channel.sendToQueue(queue, ...)`.
  - Consumer: `channel.consume(queue, fn)`.

### 2. Provenance Tracking & False-Positive Elimination
- **The Problem**: Methods like `.emit()`, `.publish()`, and `.consume()` appear in unrelated packages (e.g. Socket.io, blog CMS, iterator tools).
- **The Solution**: Two-pass AST scope analysis:
  1. Scope Pass: Collect imported library specifiers (`events`, `redis`, `kafkajs`, `amqplib`), variable initializers (`createClient()`, `kafka.producer()`, `conn.createChannel()`), and classes extending `EventEmitter`.
  2. Inspection Pass: Only inspect calls on confirmed receivers or within confirmed subclass methods.
  3. Rejection: Arbitrary objects invoking `.emit()` or `.publish()` without proven library origin are completely excluded.

### 3. Safe Static String Extraction vs. Dynamic Expressions
- Literal strings (`"orders.created"`) and non-interpolated template literals (`` `orders.created` ``) are extracted statically.
- Computed expressions (e.g. `client.publish(getChannelName(), data)`) are never evaluated with `eval()`. They are recorded with `eventName: null` and `status: "unresolved"`.

### 4. Deterministic Core Invariant
- Repository code is untrusted and never executed.
- Analysis output is pure in-memory data with deterministic ordering (by file path, start offset, id).
- Edge creation and graph database persistence are strictly deferred to Phase 4.

## Common Interview Questions & Answers

### Q: Why not execute the repository to discover dynamic event names?
**A:** Customer repository code is completely untrusted. Running customer code in a SaaS multi-tenant environment introduces severe remote code execution (RCE) vulnerabilities, arbitrary network calls, process hangs, and environment dependency requirements. Fluxora operates as a deterministic static analysis engine: dynamic expressions are explicitly represented as unresolved rather than guessed or executed.

### Q: Why didn't you link producers to consumers into graph edges in this step?
**A:** In Fluxora's architecture, Phase 3 is exclusively extraction (turning snapshots into typed finding sets). Phase 4 is graph persistence (`GraphNode`, `GraphEdge`, `Evidence` in PostgreSQL). Separating extraction from graph linking keeps modules small, cohesive, testable, and maintainable.

### Q: How do you differentiate between an internal application event and a distributed message queue?
**A:** Each detected event record carries an explicit `family` property (`node_event_emitter` vs `redis_pubsub` vs `kafkajs` vs `rabbitmq_amqplib`) and `methodShape`. Downstream graph construction and blast-radius analysis can differentiate process-local synchronous events from out-of-process distributed queues.
