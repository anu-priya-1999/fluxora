# Step 29 Evidence Writer & CI Evidence Lint Interview CheatSheet

## Executive Summary

Global Step 29 implements the **Evidence Writer** abstraction and the static **CI Evidence Lint** check. In Fluxora's architecture, structural conclusions (graph nodes and edges) must be accompanied by explicit, un-fabricated evidence establishing their source provenance. Step 29 makes evidence persistence a first-class architectural responsibility and enforces via CI static AST linting that no developer can add unevidenced graph-write code paths.

---

## Core Interview Questions & Model Answers

### Q1: What problem does the Evidence Writer solve?
**Concise Answer:**
The Evidence Writer elevates evidence persistence from an ad-hoc implementation detail to a first-class architectural abstraction. It standardizes evidence identity derivation (deterministic SHA-256 UUIDs), enforces coordinate/provenance validation, prevents fabrication of fake locations, and guarantees atomic database insertion alongside graph nodes and edges within a single PostgreSQL transaction.

---

### Q2: Why not write evidence directly inside every database graph repository function?
**Concise Answer:**
Inlining evidence writing inside individual node or edge repository calls leads to code duplication, inconsistent ID generation, unvalidated source locations, and potential transaction fragmentation where nodes commit but evidence fails. By isolating evidence creation into `EvidenceWriter`, we gain a single testable boundary that guarantees consistent validation, deterministic identity, and uniform transaction support.

---

### Q3: How do you guarantee idempotency for evidence records?
**Concise Answer:**
Evidence primary keys (`id`) are deterministically derived via SHA-256 from semantic properties:
`${analysisRunId}:evidence:${subjectType}:${subjectId}:${filePath}:${relationshipDescription}`
Because identical analysis runs produce identical evidence UUIDs, writing to PostgreSQL uses `ON CONFLICT (id) DO UPDATE`. Executing the graph build pipeline multiple times for the same commit snapshot never creates duplicate rows or primary key conflicts.

---

### Q4: How is source provenance preserved, and what happens if provenance is missing or unresolved?
**Concise Answer:**
`EvidenceWriter` preserves 1-based source line and column boundaries (`lineStart`, `lineEnd`, `columnStart`, `columnEnd`), file paths, symbol IDs, confidence scores, and custom metadata. When provenance is unresolved or absent (e.g. dynamic imports or missing source maps), `EvidenceWriter` stores `null` for missing coordinates rather than fabricating fake line numbers or file paths, preserving the core invariant that Fluxora never invents provenance.

---

### Q5: How do you guarantee atomic persistence between graph records and evidence?
**Concise Answer:**
Persistence occurs inside `persistGraphBuild` using `withTenant` to manage a single PostgreSQL transaction block. Nodes, edges, and evidence arrays are committed together using `ON CONFLICT` updates. If any evidence input fails validation or database constraint, the transaction issues an immediate `ROLLBACK`, ensuring the database never holds partial graph data without its corresponding evidence.

---

### Q6: How does PostgreSQL Row-Level Security (RLS) isolate evidence across tenants?
**Concise Answer:**
All evidence rows reference `analysis_run_id`. PostgreSQL policies check tenant ownership via `fluxora_analysis_run_in_current_tenant(analysis_run_id)`, which traverses to `repository_snapshots` -> `repositories` -> `fluxora_current_org_id()`. Every database query executes within `withTenant(pool, organizationId, ...)` which sets `SET LOCAL app.current_organization_id`. Cross-tenant reads or writes are rejected at the database engine level.

---

### Q7: Why use a CI static AST check instead of runtime validation alone?
**Concise Answer:**
Runtime validation can only fail if an unevidenced code path is actually executed during a test or in production. A static AST check (built with the TypeScript Compiler API) inspects the source code before deployment, guaranteeing at CI time that every function writing graph records explicitly invokes `EvidenceWriter`. This prevents architectural drift as new developers contribute to the codebase.

---

### Q8: What happens if a developer introduces a new graph-write path that bypasses Evidence Writer?
**Concise Answer:**
During pull request verification, `pnpm lint:evidence` (run as a mandatory CI step in GitHub Actions) parses the updated source files via TypeScript AST. It flags the function as an architectural violation, outputting the file name, line number, function name, and remediation instructions (`"Function X performs graph writes but does not invoke EvidenceWriter"`), blocking the PR from merging until fixed.

---

### Q9: What are the trade-offs and limitations of this design?
**Concise Answer:**
- **Trade-off:** Requiring evidence for every graph write increases database storage volume (more rows in `evidence` table). *Mitigation:* Evidence indexing on `(analysis_run_id, subject_type, subject_id)` keeps lookup fast.
- **Limitation:** The static CI lint checks syntax patterns (`EvidenceWriter` invocation) rather than semantic completeness of the evidence payload. Functional correctness is covered by the 14 focused unit/integration tests.
