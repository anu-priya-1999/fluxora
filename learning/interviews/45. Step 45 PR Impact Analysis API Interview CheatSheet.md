# Step 45: PR Impact Analysis API Interview CheatSheet

## Core Narrative & Problem Statement

**Q: Why expose PR impact analysis asynchronously via 202 Accepted instead of a synchronous 200 OK?**
- **Non-blocking Operations**: Computing blast radiuses involves repository diff parsing, symbol resolution, and multi-seed bounded graph traversal across potentially large codebases. In heavy pull requests, this can take seconds, risking HTTP connection timeouts and thread pool saturation.
- **Resilience & Idempotency**: By enqueueing a background job into PostgreSQL (`jobs` table) and returning `202 Accepted`, we decouple HTTP ingestion from heavy compute, enable automatic worker retries with backoff, and enforce idempotency through unique keys.

---

## Technical Highlights

### 1. Zero Trust for Client Identity & Strict Tenant Scoping
- **Question**: "How do you prevent a malicious client from triggering or reading impact analysis on another tenant's pull request?"
- **Answer**: "The API server never trusts `organization_id` from the client request body or query parameters. If a client attempts to pass `organization_id` in the body, the request is rejected with `400 invalid_request`. Instead, `organization_id` is derived solely from the authenticated Bearer JWT session. When resolving the pull request or reading the persisted impact analysis, queries are strictly scoped by `organization_id = user.organizationId` and protected by PostgreSQL Row-Level Security (`FORCE ROW LEVEL SECURITY`). Any cross-tenant access returns `404 Not Found`, preventing resource enumeration."

### 2. Idempotency Key Handling & Deterministic Deduplication
- **Question**: "How does the API handle repeated triggers or network retries of the same analysis request?"
- **Answer**: "The endpoint accepts an optional `Idempotency-Key` header. It derives a compound idempotency key `pull_request.impact_analysis:${pullRequestId}:${analysisRunId}:${clientKey}` and calculates a deterministic UUID `impactAnalysisId`. If a client retries the request with the same key, the job queue avoids duplicate work, and worker writes use PostgreSQL `ON CONFLICT (id) DO UPDATE` to ensure zero duplicated records or evidence rows."

### 3. Read-Only Retrieval & Separation of Responsibilities
- **Question**: "What happens when a client calls `GET /api/v1/impact-analyses/:id`?"
- **Answer**: "The GET endpoint is strictly read-only and idempotent. It queries the persisted `impact_analyses` record from PostgreSQL via `getImpactAnalysisById`, verifies tenant ownership via RLS, and formats the response using stable serialization mappers. It never runs the impact engine, parses diffs, or traverses graphs on GET."

## Cheat Sheet Summary Table

| Concern | Implementation | Architectural Invariant |
| --- | --- | --- |
| Async Orchestration | `POST .../analyze-impact` returns `202 Accepted` | Heavy compute decoupled from HTTP request loop |
| Job Coordination | `pull_request.impact_analysis` in PostgreSQL `jobs` table | Distributed, transactional, retryable worker harness |
| Tenant Isolation | Bearer JWT session + RLS (`withTenant`) | Client cannot forge `organization_id`; cross-tenant returns 404 |
| Idempotency | `Idempotency-Key` header + deterministic UUID derivation | Zero duplicate jobs or duplicate evidence records |
| Query Read Model | `GET /api/v1/impact-analyses/:id` reads persisted DB row | Fast, read-only, non-recomputing query endpoint |
| Error Shape | `{ error: { code, message, details? } }` | Universal API error contract across Fluxora |
