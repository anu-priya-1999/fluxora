# Step 67: Runtime Telemetry Data Foundation — Interview CheatSheet

## 1. Core Design Question
**How do you design a multi-tenant runtime telemetry schema that prevents cross-repository node linking and plaintext secret storage before ingestion even exists?**

- **Tenant Isolation**: `telemetry_sources` and `observations` both enforce `FORCE ROW LEVEL SECURITY` via `fluxora_repository_in_current_tenant(repository_id)` (`app.current_org_id`).
- **Cross-Repository Prevention**: `observations` carries `repository_id` (authoritatively derived from `telemetry_sources` via `BEFORE INSERT` trigger and locked via `BEFORE UPDATE` immutability trigger) and references `graph_nodes(repository_id, id)` with a composite FK `ON DELETE SET NULL (node_id)`.
- **Why `ON DELETE SET NULL (node_id)`?**: If an old `AnalysisRun`'s `GraphNode` is pruned, PostgreSQL unmaps `node_id` to `NULL` without nullifying `repository_id` or deleting historical observations.
- **Why an Opaque Encrypted Envelope (`^(enc|kms):v[0-9]+:[^\s]+$`)?**: Fluxora's `packages/infrastructure` doesn't have KMS envelope encryption yet; rejecting plaintext JSON/tokens at both the app and DB `CHECK` boundaries enforces fail-closed security without inventing custom cryptography.
- **Why `NUMERIC` + `timestamptz`?**: Exact decimal precision (avoiding IEEE-754 float rounding) and timezone-aware UTC `observed_at` preserved independently of `created_at`.
