# Step 16 — Ingestion Failure-Path Hardening Interview Cheat Sheet

## 1. 30-Second Elevator Pitch

> "Step 16 hardens Fluxora's asynchronous repository ingestion pipeline against external failure modes. We classify failures into permanent errors (revoked access, 404 repo, invalid ref, oversized archives, unsafe tarballs, snapshot conflicts) versus transient retryable errors (GitHub rate limits, 5xx outages, timeouts, object-storage blips). Permanent errors transition the repository to `needs_reauth` or `error` and immediately halt retries without calling `retryFailedJob`. Transient errors leave repository status untouched and enqueue retries using deterministic, bounded exponential backoff (`delay = min(baseDelay * 2^(attempt - 1), 300s)`). This protects worker concurrency, prevents stampeding herds against GitHub, and guarantees cleanup of temporary working directories on all execution paths."

---

## 2. Key Architecture Questions & Answers

### Q: Why distinguish between `needs_reauth` and `error`?
**A:** `needs_reauth` signals to the user and frontend that the GitHub App authorization or installation is missing or revoked (e.g. 401/403 or inaccessible repository 404). Re-running the GitHub App install/connect flow can resolve it. `error` indicates a non-retryable operational problem within the repository itself (e.g., ref does not exist, repository exceeds size limits, or tarball contains forbidden symlinks).

### Q: Why should retryable errors NOT update the repository connection status?
**A:** If GitHub has a temporary 503 outage or rate-limits the worker, the user's repository configuration is not broken. Updating the repository status to `error` or `needs_reauth` would trigger confusing alerts and false re-authentication prompts in the UI. The job simply retries in the background.

### Q: How does the exponential backoff work?
**A:** In `JobWorker.handleFailure`, when a job failure is retryable, we invoke `computeRetryDelay(baseDelaySeconds, attemptCount)`. With base 5s, the retry intervals sequence as 5s, 10s, 20s, 40s, 80s, 160s, and cap at 300s (5 minutes). The attempt count is tracked durably in PostgreSQL (`jobs.attempt_count`), ensuring deterministic delays even if workers crash or restart.

### Q: What prevents worker disk exhaustion during frequent failures?
**A:** `ingestRepository` executes inside a `try...catch...finally` block that unlinks any created temporary directory (`removeWorkDir`) whenever an exception occurs, and `createRepositoryIngestHandler` removes the directory upon successful completion in its `finally` block.
