# Step 31 Graph Query API Interview CheatSheet

## Executive Summary & Quick Answers

- **What does Step 31 do?**
  Step 31 implements `POST /api/v1/graph/query`, providing an authenticated, tenant-isolated, validated HTTP endpoint that exposes the Step 30 recursive-CTE graph traversal primitive to clients.

- **Why separate Step 30 (traversal primitive) and Step 31 (API boundary)?**
  Step 30 is an internal database domain primitive designed for reuse across multiple subsystems (the HTTP API, PR Impact Analysis Engine, Simulation Engine, Background Workers). Step 31 handles HTTP-specific concerns (authentication, JSON parsing, content negotiation, public parameter mapping, error shapes).

- **Why keep recursive CTE logic out of the HTTP layer?**
  Mixing SQL queries with HTTP routing violates separation of concerns, makes testing brittle, risks SQL injection, and prevents other internal services from reusing the traversal logic.

- **How is tenant isolation enforced?**
  The endpoint extracts the client's Bearer JWT, validates it with Clerk, derives the user's `organizationId` from database session state, and passes it to PostgreSQL's `withTenant(pool, organizationId, ...)`. Request bodies attempting to specify `organization_id` are explicitly rejected.

- **How do downstream/upstream map to internal directions?**
  Public `"downstream"` maps to internal `"outgoing"` (edges originating from the node). Public `"upstream"` maps to internal `"incoming"` (edges terminating at the node). Public `"both"` maps to `"both"`.

- **How do you prevent traversal abuse and Denial of Service?**
  1. Server-side hard cap: `max_depth` cannot exceed `20` (`HARD_MAX_TRAVERSAL_DEPTH`).
  2. Bounded recursion in PostgreSQL: `WHERE t.depth < maxDepth`.
  3. Cycle tracking: `WHERE NOT (next_node.id::text = ANY(t.path))`.
  4. Payload size limits: Maximum JSON body size is 16KB.

- **How does evidence reach the API client?**
  Evidence records associated with traversed nodes and edges are fetched from PostgreSQL and mapped into API response objects (`evidence` array) with `evidence_id` links on edges, preserving source file path, line numbers, and relationships without fabricating data.

- **Why is the endpoint strictly read-only?**
  Querying the architecture twin must never have side effects. Mutations only occur during repository ingestion (Phase 2), intelligence extraction (Phase 3), or graph building (Step 28).

## In-Depth Interview Questions & Answers

### 1. How does the endpoint handle start nodes that do not exist or belong to another tenant?
**Answer:** The repository query executes inside `withTenant(pool, organizationId, ...)`, setting PostgreSQL RLS to the authenticated tenant. The start node query searches for the node where `id = $1::uuid AND analysis_run_id = $2::uuid`. If the node does not exist or belongs to another tenant, PostgreSQL returns 0 rows. The API maps this to HTTP `404` (`start_node_not_found`). It never returns different error messages for "belongs to someone else" vs. "does not exist", preventing cross-tenant enumeration attacks.

### 2. How is `min_confidence` applied?
**Answer:** `min_confidence` filters out noisy or speculative relationships.
1. Any node whose confidence is strictly lower than `min_confidence` is excluded.
2. Any edge whose confidence is strictly lower than `min_confidence`, or whose source/target node was excluded, is pruned.
3. Evidence records referencing excluded nodes or edges are pruned.
This ensures the client always receives a topologically valid sub-graph where every edge connects two existing nodes.

### 3. What would you cache in later steps and why is caching excluded in Step 31?
**Answer:**
- In Phase 5 / scaling phases, repeated read-only graph queries for immutable analysis runs can be cached in Redis using a key formed from `${analysisRunId}:${startNodeId}:${direction}:${maxDepth}:${filters}`.
- Step 31 focuses exclusively on the deterministic correctness of the HTTP boundary, request validation, and tenant isolation. Adding premature caching would add state synchronization complexity before the baseline query contract is proven.

### 4. What are the primary scalability limitations of recursive CTE traversal?
**Answer:**
- Highly connected "super-nodes" (e.g. utility libraries imported by thousands of files) cause high fan-out during deep traversals.
- In later phases, this is mitigated by:
  1. Enforcing small default depth limits (`maxDepth = 5`) and hard caps (`20`).
  2. Composite indexing on `(analysis_run_id, source_node_id, edge_type)`.
  3. Edge-type and node-type filtering to prune unnecessary branches in SQL.
