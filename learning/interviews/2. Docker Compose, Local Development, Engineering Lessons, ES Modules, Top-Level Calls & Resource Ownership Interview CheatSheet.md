# Fluxora Step 9 — Interview Cheat Sheet

> Answer pattern:
>
> **Requirement → decision → alternative → trade-off → failure mode → verification**

---

# 1. What was Step 9?

> "Step 9 established repeatable, safe local development. I added the Compose infrastructure recipe plus deterministic seed/reset tooling before entering repository ingestion."

---

# 2. Why Docker Compose?

> "Compose gives us a reproducible local service topology. It standardizes infrastructure without forcing every developer to manually install/configure services."

---

# 3. Why don't you run Docker locally?

> "My development machine has 4 GB RAM, so Docker Desktop adds unnecessary virtualization overhead. I use native PostgreSQL and lightweight local adapters, while Compose remains the reproducible multi-service recipe."

---

# 4. Is Compose production?

No.

```text
Compose = local orchestration
Production = deployed containers + managed services
```

---

# 5. Why PostgreSQL host port 5433?

> "Native PostgreSQL already uses port 5432, so the Compose container maps to host 5433 to avoid collision."

---

# 6. Why MinIO?

> "It provides S3-compatible local object storage so storage behavior can be developed without paying for or depending on real AWS storage."

---

# 7. Why no new SQL migration?

> "Step 9 does not change schema. Migrations are for schema structure; seed/reset are for local data lifecycle."

---

# 8. Migration vs seed?

```text
migration → structure
seed      → data
```

---

# 9. Why must seed be idempotent?

> "Developers rerun bootstrap commands. I want repeated execution to converge to the same logical state rather than create duplicate organizations and users."

---

# 10. How did you verify seed idempotency?

```powershell
pnpm db:seed
pnpm db:seed
```

Both returned the same organization and user IDs.

---

# 11. Why guard reset?

> "Reset is destructive. I don't want safety to depend on a developer remembering which database is configured. The command fails closed unless the target is clearly the local fluxora_dev development database."

---

# 12. Why TRUNCATE CASCADE?

> "Organizations are the tenant root. PostgreSQL can clear dependent tenant data through foreign-key relationships. Because truncation is destructive, the target DB is validated first."

---

# 13. What is a top-level call?

A function call directly at module scope:

```ts
function main() {
  console.log("hello");
}

main(); // top-level call
```

---

# 14. Does importing a function execute it?

**No.**

This is the precise rule:

> Importing an ES module causes the module to be evaluated. That evaluates top-level executable statements. A function body runs only when that function is actually called.

Example:

```ts
// seed.ts
export function seed() {
  console.log("seed");
}

function main() {
  console.log("main");
}

main();
```

Then:

```ts
import { seed } from "./seed.ts";
```

results conceptually in:

```text
seed function → defined
main function → defined
main()         → executes
seed()         → does not execute
```

---

# 15. What bug did you encounter?

> "The seed module mixed reusable seed logic with an automatically executed CLI entrypoint. When reset imported the seed module, the module's top-level main() call executed as a side effect."

---

# 16. What error did you see?

```text
Called end on pool more than once
```

The local data reset itself succeeded. The failure was database-pool cleanup.

---

# 17. What caused the pool error?

> "The imported seed module unexpectedly ran its CLI main, so resource cleanup could happen from more than one path. The shared PostgreSQL pool was effectively closed more than once."

---

# 18. How did you fix it?

> "I separated reusable seed logic from direct CLI execution and guarded the CLI entrypoint so main() runs only when the seed file is directly invoked."

---

# 19. Why is that a good senior-level story?

Because it demonstrates:

```text
module evaluation
side-effect boundaries
resource ownership
CLI/library separation
runtime debugging
```

---

# 20. Why didn't typecheck catch it?

> "The code was type-correct. The bug was runtime behavior caused by module side effects, which static type checking does not generally prove absent."

---

# 21. Why didn't existing tests catch it?

> "The existing tests covered infrastructure behavior, but not this specific CLI import/lifecycle path. The acceptance test for reset exposed it."

Good follow-up:

> "It reinforced that unit tests, typecheck, and build are necessary but not sufficient; critical lifecycle flows need direct integration verification."

---

# 22. What did you learn?

> "Reusable modules should not unexpectedly execute CLI behavior when imported, and the owner of a shared resource should have clear responsibility for its lifecycle."

---

# 23. Why infrastructure abstractions?

> "I want local and production environments to implement the same contracts without changing domain logic."

Example:

```text
Redis:
local → in-memory
prod  → real/managed

Storage:
local → filesystem/MinIO
prod  → S3

Secrets:
local → env
prod  → managed secrets
```

---

# 24. Why not perfect production parity locally?

> "The laptop has constrained resources. I optimize local developer experience while preserving production-compatible contracts. Perfect parity is less important than a usable, deterministic and testable environment."

---

# 25. What did Step 9 prove?

> "It proved the foundation is reproducible and safe enough to support the much more complex repository-ingestion work that follows."

# 30. Strong debugging answer

If asked:

**"Tell me about a bug you found in this project."**

Say:

> "During local reset verification, I initially got a 'Called end on pool more than once' error. The data reset actually succeeded, so I traced the failure to lifecycle behavior rather than the database schema. I found that seed.ts had a top-level main() call. Reset imported the seed module to reuse its seed function, but importing the module also evaluated the top-level main call. That meant CLI behavior and pool cleanup were happening from an unexpected path. I separated reusable logic from the direct CLI entrypoint and reran the acceptance flow successfully."

This is a strong real-world debugging story because it explains:

```text
symptom → investigation → root cause → fix → verification
```
