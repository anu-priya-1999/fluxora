# Step 64 Tool-Calling Architecture Chat — Staff+ Interview CheatSheet

## 1. High-Level Pitch: What Did We Build?

"In Global Step 64 (Phase 9, Step 6), we implemented an evidence-grounded, provider-independent **Tool-Calling Architecture Chat** (`chat_query`) that lets users ask free-form natural-language questions about a connected repository's architecture, dependencies, and failure impact.

Unlike PR impact explanation (Step 62) and simulation narration (Step 63)—which narrate a single pre-computed artifact—architecture Q&A requires dynamic retrieval across the model:
1. **Authenticated Async API (`POST /api/v1/chat/query`):** Authenticates via Clerk JWT, derives `organizationId` from the session, validates repository/analysis-run ownership, creates/reuses a pending `AIAnalysis` (`subject_type = 'chat_query'`), enqueues a durable `chat.query` PostgreSQL job, and returns `202 Accepted` (supporting `Idempotency-Key`).
2. **Provider-Independent Tool-Calling Gateway:** Extended `ModelGateway` (`apps/workers/src/ai/types.ts`) with `ToolDefinition`, `ModelTextBlock`, `ModelToolUseBlock`, and `ModelToolResultBlock`. `AnthropicProviderAdapter` translates to/from Anthropic `tool_use`/`tool_result` blocks, while `MockModelProvider` supports queued `toolUses` for deterministic offline/CI tests.
3. **Strictly Three Controlled Deterministic Tools (`apps/workers/src/ai/chat/tools.ts`):** Exposes *only* `query_graph`, `get_evidence`, and `run_simulation`—never raw file reads, shell commands, or arbitrary SQL. Every tool enforces strict schema validation, unknown-tool rejection, and server-injected tenant/run scoping.
4. **Bounded Execution & Prompt-Injection Containment:** Enforces hard limits (`MAX_TOOL_ROUNDS = 5`, `MAX_TOTAL_TOOL_CALLS = 10`, `MAX_EXECUTION_TIME_MS = 45_000`, `MAX_SIMULATIONS_PER_REQUEST = 2`, `MAX_SIMULATIONS_PER_SESSION = 5`, `MAX_HISTORY_MESSAGES = 10`, `MAX_QUESTION_CHARS = 2_000`, `MAX_TOOL_RESULT_CHARS = 16_000`) and wraps escaped history/questions in `<conversation_history>` and `<user_question>` XML delimiters.
5. **Manifest-Grounded Validation & Durable Persistence:** Accumulates `allowedEvidenceIds` from successful tool calls, validates the final JSON response against `chat-query-output-v1` (max 1 corrective retry, atomic withholding on rejection), aggregates token/cost/latency metrics across all rounds, and persists to `ai_analyses` (`subject_type = 'chat_query'`).
6. **Frontend (`ArchitectureChatPanel`):** Integrated into the Architecture Explorer; submits questions, polls `GET /api/v1/ai-analyses/:id`, and displays tool activity badges, clickable `EvidenceCitationList` chips, confidence badges, caveats, and retry recovery."

## 2. Core Architecture & Design Breakdown

### 2.1 Asynchronous Request & Job Flow
1. `ArchitectureChatPanel` sends `POST /api/v1/chat/query` with `{ repository_id, analysis_run_id, question, history?, session_id? }`.
2. `handleChatQuery` (`apps/api/src/http/chat-query.ts`) verifies the Clerk Bearer JWT, resolves GitHub identity, derives `organizationId` from the authenticated user record, and validates the payload (64 KiB body cap, `question` max 2,000 chars, `history` max 10 items / 1,500 chars each, UUIDs for `repository_id`, `analysis_run_id`, optional `session_id`).
3. Verifies tenant ownership of both `repository_id` and `analysis_run_id` (returning `404` on missing or cross-tenant records).
4. Derives `chatQueryId`: deterministic UUIDv4-shaped SHA-256 hash of `(organizationId, repositoryId, analysisRunId, idempotencyKey)` when `Idempotency-Key` is present, or `randomUUID()` otherwise.
5. Creates/reuses `AIAnalysis` (`subject_type = 'chat_query'`, `subject_id = chatQueryId`, `status = 'pending'`), enqueues `chat.query` with idempotency key `chat.query:<chatQueryId>`, and returns `202 Accepted` with `{ chat_query_id, ai_analysis_id, status, job_id }`.
6. Worker `processChatQueryJob` (`apps/workers/src/ai/chat/job-handler.ts`) parses the payload via `parseChatQueryJobPayload` and invokes `orchestrateChatQuery` inside an isolated `try/catch` block.
7. Frontend polls `GET /api/v1/ai-analyses/:id` every `1500ms` up to `20` attempts (`ArchitectureChatPanel.tsx`).

### 2.2 The Three Controlled Tools (`apps/workers/src/ai/chat/tools.ts`)
| Tool | Parameters | Deterministic Backing & Guardrails | Evidence Registration |
| :--- | :--- | :--- | :--- |
| `query_graph` | `start_node` (required), `direction?`, `max_depth?`, `edge_types?` | **Read-only.** Resolves node by UUID or canonical ID within `analysisRunId`; `0 <= max_depth <= HARD_MAX_TRAVERSAL_DEPTH` (20, default 3); validates `edge_types` against `GraphEdgeTypes` (max 20); calls `traverseGraph(..., { includeEvidence: true })`. | Adds all returned traversal evidence IDs to `ctx.allowedEvidenceIds`. |
| `get_evidence` | `evidence_id` (required UUID) | **Read-only.** Calls tenant-scoped `getEvidenceById`; rejects if missing or `record.analysisRunId !== ctx.trusted.analysisRunId`. | Adds verified `record.id` to `ctx.allowedEvidenceIds`. |
| `run_simulation` | `target_node` (required), `failure_type` (`"unavailable" \| "latency"`) | **Sole bounded, non-destructive state-creating operation.** Resolves target node in `analysisRunId`; checks in-request cache `${resolvedNode.id}:${failureType}`; enforces `MAX_SIMULATIONS_PER_REQUEST` (2) and `MAX_SIMULATIONS_PER_SESSION` (5); creates synthetic `Scenario` (`source: "chat_query"`) + `Simulation` and runs `executeSimulation(..., { enqueueNarrationJob: false })`. | Adds `simulation_state` evidence IDs to `ctx.allowedEvidenceIds`. |

### 2.3 Provider Abstraction (`ModelGateway`)
- `apps/workers/src/ai/types.ts` defines provider-neutral `ToolDefinition`, `ModelTextBlock`, `ModelToolUseBlock`, `ModelToolResultBlock`, `ModelMessage.blocks`, `ModelGatewayRequest.tools`, and `ModelGatewayResponse.toolUses`.
- `AnthropicProviderAdapter` (`apps/workers/src/ai/anthropic-adapter.ts`) converts `ToolDefinition` to Anthropic tool schemas, extracts `tool_use` blocks from responses into `ModelToolUseBlock[]`, and serializes `ModelMessage.blocks` (`tool_use` / `tool_result`) for multi-turn rounds.
- `MockModelProvider` (`apps/workers/src/ai/mock-gateway.ts`) accepts queued `toolUses` so multi-round tool loops run deterministically offline and in CI.
- `ModelRoutingPolicy` (`apps/workers/src/ai/policy.ts`) routes `chat_query` to `claude-sonnet-5-5` (primary) and `claude-haiku-5-5` (fallback) with `timeoutMs: 45_000`, `maxTokens: 4096`, and `maxPrimaryRetries: 2`.

### 2.4 Security, Trust Boundaries & Prompt-Injection Containment
- **Trusted Server Context Only:** `organizationId`, `repositoryId`, and `analysisRunId` come exclusively from `TrustedChatContext` (verified session + DB ownership), never from model arguments or client body `organization_id`.
- **Strict Tool Admission:** `executeControlledChatTool` rejects unknown tools (`unknown_tool`), non-object inputs (`invalid_arguments`), and any extra keys (`rejectKeysOutside` / `additionalProperties: false`).
- **XML & Unicode Containment:** `escapeUntrustedChatPayload` (`request-builder.ts`) escapes `&`, `<`, `>` to `\u0026`, `\u003c`, `\u003e` in both `history` and `question` before embedding inside `<conversation_history>` and `<user_question>` delimiters.
- **No Raw Code / Shell / SQL or Destructive Mutation:** The model cannot read arbitrary files, execute repository code, run SQL, or modify source code, repositories, existing graph records, infrastructure, or existing simulations — preserving ADR-006 and ADR-009. `query_graph` and `get_evidence` are strictly read-only; `run_simulation` is the sole bounded, non-destructive state-creating operation (creating synthetic `Scenario` and `Simulation` records through the deterministic simulation engine, not unrestricted database mutation or autonomous remediation).
- **Isolated Tool Failure Boundaries:** Unexpected exceptions in `executeControlledChatTool` are caught and returned as `tool_execution_error` tool results (`isError: true`), and `processChatQueryJob` wraps `orchestrateChatQuery` in an isolated `try/catch` so AI failures never crash unrelated workers or leak raw invalid output (`outputText: null`, `outputStructured: null` on `rejected`/`failed`).
- **Error & Secret Sanitization:** `sanitizeErrorMessage` redacts `sk-...` API keys and `Bearer ...` tokens before logging or persisting `errorMessage`.

### 2.5 Persistence, Idempotency & Execution Limits
- **Persistence:** `ai_analyses` (`subject_type = 'chat_query'`, `subject_id = chatQueryId`) with `UNIQUE (organization_id, subject_type, subject_id)`. Records `outputText`, `outputStructured`, `inputEvidenceIds` (the accumulated `allowedEvidenceIds`), `tokenCount`, `costUsd`, `latencyMs`, and `metadata` (`schemaVersion`, `repositoryId`, `analysisRunId`, `sessionId?`, `gatewayCalls`, `validationAttempts`, `usedFallback`, `provider`, `toolActivity`, `totalToolCalls`).
- **Atomic Withholding:** On `rejected` or `failed`, `outputText` and `outputStructured` are `null`; raw unvalidated model text is never persisted.
- **Idempotency:**
  1. HTTP layer: `Idempotency-Key` header $\to$ deterministic `chatQueryId` $\to$ reuses existing `AIAnalysis` and `chatQueryIdempotencyKey(chatQueryId)` job key.
  2. Orchestrator layer: `getAIAnalysisBySubject` short-circuits immediately on `completed` (and on `rejected`/`failed` unless `forceRetry: true`).
  3. Tool layer: `run_simulation` caches `${resolvedNode.id}:${failureType}` in `ctx.simulationCache` within the request so repeated identical calls do not double-count against simulation limits or re-run the engine.
- **Execution Limits (`CHAT_EXECUTION_LIMITS`):**
  - `MAX_TOOL_ROUNDS = 5` (on `round === maxToolRounds`, `tools` is omitted to force a final JSON answer; if the model still attempts a tool call, orchestration fails cleanly).
  - `MAX_TOTAL_TOOL_CALLS = 10` (excess calls in a round return `tool_call_limit_exceeded` tool errors instructing the model to finalize).
  - `MAX_SIMULATIONS_PER_REQUEST = 2`, `MAX_SIMULATIONS_PER_SESSION = 5`.
  - `MAX_EXECUTION_TIME_MS = 45_000` (enforced via `AbortController` + loop wall-clock check).
  - `MAX_HISTORY_MESSAGES = 10`, `MAX_HISTORY_MESSAGE_CHARS = 1_500`, `MAX_QUESTION_CHARS = 2_000`, `MAX_TOOL_RESULT_CHARS = 16_000`.

## 3. Tradeoffs & Known Limitations

1. **Async `202 Accepted` + Polling vs. SSE/WebSocket Streaming:** Polling (`1500ms` interval, max `20` attempts) adds slight UI latency compared to token streaming, but preserves API/worker package isolation, durable job retries, and `ai_analyses` auditability without holding open HTTP connections in `apps/api`.
2. **Manifest Membership vs. Semantic Entailment:** `validateChatQueryOutput` verifies that every cited `evidence_id` was actually returned by a tool during *this* query (`allowedEvidenceIds`), proving citation provenance—not that the evidence semantically entails the natural-language claim (acknowledged in ADR-017 and `request-builder.ts`; semantic evaluation is addressed in Step 65).
3. **In-Request Session Simulation Counter:** `simulationCountInSession` is initialized per orchestration run (`{ count: 0 }`) in `orchestrator.ts`; cross-request session-level simulation counting across separate HTTP calls is a known boundary unless backed by a shared store or DB query on `scenarios.parameters->>'sessionId'`.
4. **No Distributed Lock on `AIAnalysis`:** Simultaneous worker deliveries before completion can both invoke `ModelGateway`, though DB `UNIQUE (organization_id, subject_type, subject_id)` and conditional upserts prevent duplicate rows or overwriting `completed` records.

## 4. Likely Senior-Engineering Interview Questions & Answers

### Q1: Why restrict the Architecture Chat to three controlled tools instead of giving the LLM a codebase search or file-reading tool?
**Answer:**
"Because Fluxora's core architectural invariant (ADR-001, ADR-006, ADR-009) is that the deterministic graph and simulation engines are the sole source of architectural truth. Giving an LLM arbitrary file-read, grep, or SQL tools would let it bypass the normalized graph, infer unverified relationships from raw untrusted repository code, introduce prompt-injection surfaces, and make citation grounding impossible to verify. Restricting the model to `query_graph`, `get_evidence`, and `run_simulation` guarantees every fact comes from tenant-scoped, evidence-backed deterministic engines."

### Q2: How do you prevent the model from hallucinating evidence IDs in a multi-turn tool-calling conversation?
**Answer:**
"We build the `allowedEvidenceIds` manifest dynamically during the query. Every successful `query_graph`, `get_evidence`, and `run_simulation` call registers the exact `evidence_id`s it returned into `toolCtx.allowedEvidenceIds`. When the model produces its final JSON answer, `validateChatQueryWithRetry` validates it against `chat-query-output-v1` (which reuses Step 61's strict 4-field schema validator). Any claim citing an ID not in `allowedEvidenceIds`, omitting citations, or duplicating IDs triggers whole-response rejection, at most one corrective retry, and atomic withholding (`output_text: null`, `output_structured: null`) if still invalid."

### Q3: How did you keep the chat orchestrator decoupled from the Anthropic SDK?
**Answer:**
"We extended the `ModelGateway` contract in `apps/workers/src/ai/types.ts` with provider-neutral `ToolDefinition`, `ModelTextBlock`, `ModelToolUseBlock`, and `ModelToolResultBlock` types. The chat orchestrator only ever constructs and consumes these neutral types. `AnthropicProviderAdapter` handles translating them to/from Anthropic's `tool_use` and `tool_result` blocks, while `MockModelProvider` supports queued `toolUses` for deterministic offline testing. Swapping or adding another provider requires zero changes to `apps/workers/src/ai/chat/`."

### Q4: What happens if a model gets stuck in an infinite tool-calling loop or tries to trigger expensive simulations repeatedly?
**Answer:**
"We enforce defense-in-depth execution ceilings in `CHAT_EXECUTION_LIMITS` and `orchestrator.ts`:
1. `MAX_TOOL_ROUNDS = 5`: On the final round (`round === maxToolRounds`), the orchestrator omits `tools` from the gateway request to force a final JSON answer; if the model still emits tool calls, orchestration fails cleanly.
2. `MAX_TOTAL_TOOL_CALLS = 10`: Any tool call beyond 10 returns a `tool_call_limit_exceeded` error block telling the model to finalize with gathered evidence.
3. `MAX_SIMULATIONS_PER_REQUEST = 2` and `MAX_SIMULATIONS_PER_SESSION = 5`, plus an in-request `(resolvedNode.id, failureType)` cache so identical simulation requests are idempotent and free.
4. `MAX_EXECUTION_TIME_MS = 45_000` enforced via an `AbortController` signal and per-round elapsed time checks."

### Q5: How do you protect against prompt injection from repository data or prior chat history?
**Answer:**
"First, `query_graph` and `get_evidence` return structured metadata and evidence descriptions—never raw source files or arbitrary `GraphNode.metadata` blobs. Second, `request-builder.ts` (`escapeUntrustedChatPayload`) Unicode-escapes `&`, `<`, and `>` to `\u0026`, `\u003c`, and `\u003e` in both bounded `history` (max 10 turns, 1,500 chars each) and `question` (max 2,000 chars), then wraps them in `<conversation_history>` and `<user_question>` XML delimiters. The system prompt explicitly classifies all delimited content and tool-returned repository strings as untrusted data that must never override system instructions."

### Q6: Why does `run_simulation` pass `{ enqueueNarrationJob: false }` when invoked from chat?
**Answer:**
"Because the chat orchestrator itself is already generating the user-facing explanation for that simulation within the `chat_query` response. Enqueueing a separate background `simulation.narration` job (Step 63) for every exploratory chat simulation would waste LLM tokens and database writes on an unviewed narration."

### Q7: How is multi-tenant isolation enforced end-to-end in `chat_query`?
**Answer:**
"At every boundary:
1. **HTTP API (`POST /api/v1/chat/query`):** `organizationId` is derived strictly from the authenticated Clerk session and provisioned `User`, never from the request body, and both `repository_id` and `analysis_run_id` are verified against that `organizationId`.
2. **Tool Execution (`TrustedChatContext`):** `organizationId`, `repositoryId`, and `analysisRunId` are injected from server context. `resolveNodeInRun` and `get_evidence` explicitly verify `record.analysisRunId === ctx.trusted.analysisRunId`, preventing even same-tenant cross-run leakage.
3. **Database:** All repository calls (`getRepositoryById`, `getAnalysisRunById`, `traverseGraph`, `getEvidenceById`, `executeSimulation`, `saveAIAnalysis`) run under tenant-scoped queries and PostgreSQL RLS."
