# Step 12 — Repository Ingestion Worker Interview Cheat Sheet

Senior answers. Prefer mechanisms Fluxora actually has: PostgreSQL jobs, leases, RLS, GitHub App installations, untrusted repo bytes.

## Worker architecture

**Q: Why is ingestion a worker, not an API handler?**  
A: Clone/fetch is slow, retryable, and resource-heavy. The API authenticates and enqueues. The worker leases a job, talks to GitHub, and writes status. HTTP request lifetime must not own GitHub I/O.

**Q: What is the handler registry?**  
A: A map of job `type` → function. `JobWorker` claims any due job and dispatches. Unknown types fail. `repository.ingest` sits beside `test.echo`; no new queue product.

## Retries

**Q: How do retries work?**  
A: `failJob` stores the error and sets `failed` or `dead_letter` if `attempt_count >= max_attempts`. `JobWorker` then calls `retryFailedJob` (delay, `pending` again) **only if the error is retryable**.

**Q: What must not retry?**  
A: Auth/revocation (`needs_reauth`), invalid ref, oversized repo, path traversal. Retrying those burns attempts and can look like GitHub flapping.

## Leasing

**Q: How does a worker own a job?**  
A: `fluxora_claim_next_job` sets `running`, `locked_by`, `lease_expires_at`, increments attempts. Complete/fail require matching worker id and unexpired lease. Crash → lease expires → reclaim. That is fencing, not a distributed lock service.

## Idempotency

**Q: At-least-once means the handler can run twice. Why is that safe here?**  
A: No snapshot insert in Step 12. Status updates are idempotent. Temp dirs are per attempt. Future snapshot insert (Step 13) must use Step 11’s unique `(repository_id, commit_sha)` so a second upload does not duplicate truth.

**Q: Where is the idempotency key?**  
A: On `jobs`, unique with `organization_id`. Key = `repository.ingest:{repositoryId}:{commitSha}`. Do not add a parallel store.

## GitHub App tokens

**Q: Why not store a GitHub PAT?**  
A: Installation tokens expire in ~1 hour, are scoped to the installation, and can be revoked by uninstall. A stored PAT is long-lived stolen credential. Mint per job from App JWT + installation id.

**Q: Why not use the Clerk session token?**  
A: Clerk authenticates the Fluxora user. GitHub API needs an installation token. Mixing them couples user sessions to background work that outlives the browser.

## Rate limiting

**Q: 403 can mean “no access” or “slow down”. How do you tell?**  
A: Rate limit: `429`, remaining=0, or `Retry-After`. Those are retryable, no `needs_reauth`. Other 401/403: permanent + `needs_reauth`.

## Tenant isolation

**Q: Jobs have `organization_id`. Why still load the repository with that id?**  
A: Defense in depth (`11-security-architecture.md`). RLS is necessary; the worker also refuses to fetch GitHub if `getRepositoryById(job.organizationId, payload.repositoryId)` is null. A crafted payload cannot ingest another tenant’s repo.

## Untrusted repository content

**Q: Why is a README dangerous?**  
A: Later AI context. Even in Step 12, treat bytes as hostile: zip bombs, `../` members, symlinks to `/etc`, huge files. Never execute hooks or `npm test` from the tree.

## Archive attacks

**Q: Zip bomb?**  
A: Stream gunzip+tar; cap compressed and uncompressed bytes and file count; time budget; fail `error` instead of OOM.

**Q: Path traversal in tar?**  
A: Strip GitHub root prefix, reject `..` and absolute names, `path.resolve` must stay under the work dir, reject link types.

## Cleanup

**Q: Temp dir leak?**  
A: `try/finally` on failure inside ingest and on success in the handler. Delete only under `fluxora-ingest-` in `os.tmpdir()`.

## Large repositories

**Q: What happens if the repo is too big?**  
A: Permanent `repository_too_large` with `fileCount`/`sizeBytes`/limits on the error (for later truncated analysis). Do not keep buffering. Do not mark `active`.

## API vs worker

**Q: Draw the boundary.**  
A: API: Clerk, RBAC, enqueue. Worker: GitHub App credentials, fetch, extract, job completion. Analysis workers later read snapshots from object storage and must not call GitHub (`11-security-architecture.md` service identities).
