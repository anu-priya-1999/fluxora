# 42. Step 42 PullRequest and Diff Storage Interview CheatSheet

## Core Concepts & Quick Answers

### Q1: What is the purpose of Step 42 and why is it decoupled from Step 41 and Step 43?
**Answer:**
Step 42 implements the durable persistence layer for pull requests, changed files, and git diffs.
- **Decoupled from Step 41**: Step 41 is the HTTP webhook reception boundary. It must respond to GitHub within milliseconds to avoid delivery timeouts. Background processing is offloaded to a queue.
- **Decoupled from Step 43**: Step 43 is the Impact Analysis Engine. Separating storage from analysis ensures that pull request state is durably recorded, queryable, and reproducible before embarking on AST symbol parsing and graph traversal.

### Q2: How is the database schema designed for pull requests and changed files?
**Answer:**
We introduce two normalized tables in `packages/db`:
1. `pull_requests`: Stores tenant `organization_id`, foreign key `repository_id`, `github_pr_id`, `number`, `title`, `base_ref`/`base_sha`, `head_ref`/`head_sha`, `status`, and author metadata. It enforces `UNIQUE (repository_id, number)` so that a PR is uniquely identified per repository.
2. `pull_request_files`: Stores `pull_request_id`, relative file `path`, `previous_path` (for renames), `status` (`added`, `modified`, `removed`, `renamed`), `additions`, `deletions`, `changes`, `patch` unified diff text, and `patch_truncated`. It enforces `UNIQUE (pull_request_id, path)`.

### Q3: How is multi-tenant Row-Level Security (RLS) enforced on `pull_request_files` without storing `organization_id`?
**Answer:**
Storing redundant tenant IDs on child tables increases denormalization risks. Instead, `pull_request_files` inherits tenant isolation from `pull_requests` via a `SECURITY DEFINER` helper function `fluxora_pull_request_in_current_tenant(pull_request_id)`.
The function checks that the referenced `pull_request_id` belongs to `fluxora_current_org_id()`. All queries on `pull_request_files` evaluate this policy, guaranteeing that a tenant can never view, insert, or modify another tenant's files.

### Q4: How are `pull_request.synchronize` events handled?
**Answer:**
When new commits are pushed to a PR, GitHub issues a `synchronize` event with a new `head_sha`.
In Step 42, we execute an atomic transaction (`savePullRequestWithFiles`):
1. `upsertPullRequest`: Updates `head_sha`, `base_sha`, `title`, `status`, and timestamps on the existing PR record using `ON CONFLICT (repository_id, number) DO UPDATE`.
2. `replacePullRequestFiles`: Deletes all prior `pull_request_files` for that PR and inserts the current snapshot's changed files.
This ensures the stored diff is 100% consistent with the latest revision and avoids orphaned files from previous commits.

### Q5: Why is it an architectural anti-pattern to perform GitHub API calls inside a database transaction?
**Answer:**
Database transactions hold locks on rows/tables and consume database pool connections. If slow external HTTP calls (such as GitHub API requests with network latency or rate limiting) are placed inside a database transaction, database connections remain open and idle for hundreds of milliseconds or seconds. This quickly exhausts the database connection pool and degrades application throughput.
Best practice: Perform all network I/O and payload preprocessing *before* opening the database transaction, then commit changes in a tight, millisecond-level transaction.

### Q6: How do you handle massive pull requests (e.g. 5,000 files or 50MB diffs)?
**Answer:**
Unbounded inputs invite memory exhaustion and database degradation. Fluxora applies strict defensive thresholds via `PullRequestLimits`:
- `maxFilesPerPr` (default 1,000 files): Limits the number of changed files processed per PR.
- `maxPatchBytesPerFile` (default 512 KB): Individual file patches exceeding this size are truncated with `patch_truncated = true`.
- `maxTotalPatchBytesPerPr` (default 10 MB): Caps total cumulative patch bytes stored per PR.

### Q7: How is idempotency preserved when processing webhook jobs?
**Answer:**
1. **Delivery Level**: The `jobs` table uses `ON CONFLICT (organization_id, idempotency_key)` where the key is `pull_request.webhook:${deliveryId}`.
2. **Database Level**: `pull_requests` uses `ON CONFLICT (repository_id, number) DO UPDATE`.
3. **File Level**: `replacePullRequestFiles` completely replaces the file set inside a transaction.
Processing the exact same webhook delivery multiple times yields the identical, deterministic database state without duplicates or errors.

### Q8: How does repository lookup enforce tenant security?
**Answer:**
The worker looks up the repository by `(organization_id, github_repo_id)`.
The `organization_id` comes strictly from the verified GitHub App installation mapping (established server-side in Step 41). If the repository is not connected to that specific tenant, the processor immediately rejects the job with `tenant_mismatch` (`retryable: false`). It never guesses or looks across other tenants.

### Q9: How are GitHub App installation tokens secured?
**Answer:**
1. Short-lived installation access tokens are minted on-demand using GitHub App private keys.
2. Tokens are kept in memory and passed directly to the GitHub client.
3. Tokens are **never** persisted to the database, logged in stdout/stderr, or attached to OpenTelemetry trace spans.

### Q10: What are the strict scope boundaries of Step 42?
**Answer:**
Step 42 strictly owns:
- `PullRequest` and `PullRequestFile` storage models and migrations;
- Changed-file and diff/patch persistence;
- Worker processing of `pull_request.webhook` jobs into storage.

Step 42 does **NOT**:
- Run the Impact Analysis Engine or BFS/DFS symbol traversal (Step 43);
- Calculate blast radius or affected dependencies (Step 43);
- Persist `ImpactAnalysis` records or evidence (Step 44);
- Expose impact analysis HTTP REST endpoints (Step 45);
- Build frontend change overlays (Step 46);
- Execute golden-fixture PR validations (Step 47).
