# 20. Step 20 Import Export Graph Interview CheatSheet

## Core Architectural Concepts

### 1. What is Step 20's objective and how does it relate to Step 19 and Phase 4?
**Answer:**
- **Step 19** answers: *"What symbols exist inside each individual file?"* (file-local AST extraction).
- **Step 20** answers: *"How are repository modules connected through imports and exports?"* (inter-module dependency topology).
- **Phase 4** takes these in-memory edges, normalizations, and symbols and persists them into queryable PostgreSQL `GraphNode`, `GraphEdge`, and `Evidence` tables.
Step 20 is the pure static-analysis module-resolution layer that computes raw dependency topology without database writes.

---

### 2. How are TypeScript path aliases resolved deterministically in memory?
**Answer:**
Using the TypeScript Compiler API (`ts.readConfigFile`, `ts.parseJsonConfigFileContent`, and `ts.resolveModuleName`) paired with a custom in-memory `ts.ModuleResolutionHost`:
- The custom host delegates `fileExists` and `readFile` directly to the snapshot file map (`SnapshotFileMap`).
- Directory presence is pre-indexed for fast lookups.
- `ts.resolveModuleName` reads `baseUrl` and `paths` mappings from `tsconfig.json` and deterministically resolves aliases (e.g. `@/*` -> `src/*`) to the virtual snapshot paths.

---

### 3. Why are customer repositories never executed during module resolution?
**Answer:**
Customer repository contents are untrusted. Running repository code (`require`, `import()`, `eval`, or executing build tools like `tsc` or `npm`) introduces severe security risks: arbitrary code execution, filesystem and environment secret exfiltration, denial of service, and non-deterministic behavior. Step 20 parses code strictly as inert text through ASTs and resolves modules using pure in-memory path math.

---

### 4. Why must barrel files (re-exports) NOT be collapsed in Step 20?
**Answer:**
In Step 20, our goal is to capture the genuine structural dependencies of the repository. If `app.ts` imports `index.ts`, and `index.ts` re-exports `payment.ts`, there are two real edges:
1. `app.ts -> index.ts` (`import`)
2. `index.ts -> payment.ts` (`re_export`)
Collapsing `index.ts` away prematurely loses the knowledge of the barrel file's existence and creates fake direct dependencies. Normalization and barrel-file collapsing is explicitly deferred to **Step 25**.

---

### 5. How does Step 20 distinguish between internal, external, and unresolved imports?
**Answer:**
- **Internal**: The specifier resolves to an existing file in the repository snapshot.
- **External**: The specifier is non-relative and does not match any configured `tsconfig.json` path alias (e.g., `react`, `zod`).
- **Unresolved**: The specifier is either relative (`./missing`) or matches an internal path alias pattern (`@/components/nonexistent`), but the target file is missing from the snapshot.
- **Unsupported Dynamic**: Dynamic imports (`import(fn())`) or requires (`require(varName)`) where the module specifier cannot be statically determined at parse time.

---

### 6. How is determinism guaranteed across operating systems?
**Answer:**
- All file paths and module specifiers are normalized to POSIX forward slashes (`/`).
- Edge IDs, reference IDs, and output arrays (`filesAnalyzed`, `references`, `internalEdges`, `externalReferences`, `unresolvedReferences`) are sorted deterministically using lexicographical comparisons (`localeCompare`).
- Line endings and path separators do not affect character offsets or source locations.
