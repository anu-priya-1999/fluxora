# Step 15 — Repository Indexed Event & WebSocket Push Interview Cheat Sheet

## 30-second answer

> "Step 15 bridges the asynchronous worker ingestion pipeline with the frontend UI using a deterministic, durable event outbox and real-time push. Once a snapshot is persisted and the repository is activated, the worker writes a tenant-scoped, idempotent `repository.indexed` event into the PostgreSQL `events` table under RLS. A database trigger publishes the event via `pg_notify('fluxora_events')`. The API server listens on this channel, routes the event through an in-memory `WebSocketHub` strictly partitioned by organization ID, and pushes it over an authenticated `/api/v1/ws` connection (verified with Clerk session tokens). The Next.js frontend updates its dashboard in real time without polling, while preserving strict tenant isolation."

---

## 1. Why do we store events in PostgreSQL before pushing them over WebSockets?

**Answer:** Storing events in a durable `events` table (the Transactional Outbox pattern) ensures that events are not lost if the API server or WebSocket connections drop. It provides an auditable history, idempotency enforcement at the database level (`uq_events_org_idempotency`), and guarantees that an event was committed along with state transitions.

---

## 2. Why PostgreSQL LISTEN/NOTIFY instead of Redis Pub/Sub or Kafka?

**Answer:** Following Fluxora's scope discipline and architectural guidelines, PostgreSQL is already our single source of truth and state store. `LISTEN`/`NOTIFY` is built directly into Postgres and requires zero additional operational infrastructure (no Kafka, Redis, or RabbitMQ clusters) for our current phase. It operates with sub-millisecond latency within the database connection.

---

## 3. How is WebSocket authentication handled?

**Answer:** Browsers cannot send custom `Authorization: Bearer <token>` headers during a native WebSocket handshake (`new WebSocket(url)`). Therefore, the API endpoint `/api/v1/ws` supports extracting the token from:
1. `Authorization` HTTP header (for non-browser clients or test runners)
2. `?token=<jwt>` or `?authorization=Bearer%20<jwt>` query parameters (for standard browser connections)
3. `Sec-WebSocket-Protocol: bearer.<jwt>` subprotocol

Before upgrading the HTTP connection to a WebSocket connection (`wss.handleUpgrade`), the server validates the token against Clerk, extracts `userId` and `organizationId`, and terminates unauthenticated or unauthorized requests with HTTP 401 or 403.

---

## 4. How is tenant isolation enforced in WebSocket event broadcasting?

**Answer:**
1. The WebSocket connection requires an authenticated Clerk session with a valid `org_id`.
2. The `WebSocketHub` stores connections in a hash map keyed by `organizationId`: `Map<string, Set<ClientConnection>>`.
3. When an event arrives from PostgreSQL, its `organization_id` is inspected.
4. The hub looks up only the connections registered under that specific `organizationId` and transmits the message exclusively to them. Clients belonging to other organizations never receive the event.

---

## 5. How is event idempotency achieved?

**Answer:** Each event type defines a deterministic idempotency key format. For `repository.indexed`, it is `repository.indexed:<repositoryId>:<commitSha>`. The `events` table enforces a unique constraint `UNIQUE (organization_id, idempotency_key)`. If a worker retries the job or emits the event twice for the same snapshot and commit, the database detects the conflict and prevents duplicate event insertion.

---

## 6. What payload does `repository.indexed` contain?

**Answer:**
```json
{
  "repositoryId": "<uuid>",
  "snapshotId": "<uuid>",
  "commitSha": "<40-char-sha>",
  "ref": "refs/heads/main"
}
```
All fields adhere to strict validation rules: UUID format for IDs, 40-character hex string for Git commit SHAs, and snake_case compatibility (`repository_id`, `snapshot_id`, `commit_sha`).

---

## 7. What does the frontend do with `repository.indexed`?

**Answer:** The frontend dashboard connects to `/api/v1/ws` using the Clerk token from `useAuth().getToken()`. When a `repository.indexed` event is received, `handleRepositoryIndexedMessage` validates and parses the payload and prepends the indexed repository info to the live activity feed, letting the user know the repository has been ingested and activated without requiring a page reload or continuous HTTP polling.
