# Step 39 WebSocket Live Updates — Technical Interview CheatSheet

A high-yield reference guide for system design, frontend architecture, and full-stack engineering interviews covering real-time systems, WebSockets, and state synchronization.

---

## 1. Core Architecture & Data Flow

### Q: Walk me through the real-time event pipeline in Fluxora from repository update to browser render.
**Answer:**
1. **Worker Persistence**: The ingestion worker finishes an analysis run and writes graph nodes and edges to PostgreSQL within a database transaction.
2. **Transactional Outbox & Notification**: In the same transaction, a `graph.updated` event envelope is written to the `events` table and emitted via `pg_notify('fluxora_events', payload)`.
3. **API Event Listener**: `PostgresEventListener` (running in Fastify API) maintains a persistent `LISTEN fluxora_events` connection.
4. **WebSocket Hub Isolation**: Upon receiving the notification, the API passes it to `WebSocketHub`, which retrieves the set of active sockets matching the envelope's `organization_id` and broadcasts the message only to them.
5. **Browser Invalidation**: The explorer's WebSocket client validates the envelope and checks whether `payload.repository_id` and `payload.analysis_run_id` match the currently viewed context.
6. **Authoritative Query**: If relevant, the explorer triggers a fresh `POST /api/v1/graph/query` passing the user's active Step 37 filters.
7. **Smooth Presentation Update**: The response updates React state, recomputes Step 38 Level-of-Detail (LOD), and maintains node selection without resetting zoom.

## 2. Invalidation Channel vs. Mutation Streaming

### Q: Why not stream graph diffs over the WebSocket and mutate the graph in browser memory?
**Answer:**
1. **Single Source of Truth**: The PostgreSQL recursive CTE is the definitive authority on graph reachability, depth bounds, and confidence scoring. Replicating traversal logic in the browser introduces duplicate code and divergent behavior.
2. **Filter Independence**: The user can have complex filters active (e.g., hiding symbols, filtering edge types, min confidence). Streaming raw entity diffs requires the client to re-evaluate all filter constraints across topological dependencies.
3. **State Drift Resilience**: WebSocket connections drop and reconnect. If a client misses mutation event #4 out of 10, the in-memory graph is corrupted. In an invalidation model, the event is just a cache bust signal—the subsequent query returns the exact current state.
4. **Lightweight Messages**: WebSocket frames remain small (just identifiers and summary metadata) rather than transmitting megabytes of serialized graph data.

## 3. WebSocket Authentication & Security

### Q: How do you authenticate a WebSocket connection in the browser without exposing secrets or leaking tokens in URLs?
**Answer:**
- Standard browser `WebSocket` APIs cannot set custom HTTP request headers (like `Authorization: Bearer <token>`).
- Passing tokens in URL query parameters (`wss://api/ws?token=...`) is an anti-pattern because URLs are stored in browser history, proxy access logs, and referrer headers.
- **Solution (Sec-WebSocket-Protocol)**: Pass the token as a subprotocol string: `new WebSocket(url, ["bearer." + sessionToken])`.
- The browser automatically sends this via the `Sec-WebSocket-Protocol` header.
- The server extracts the token from the header, validates the JWT, identifies the user and tenant, and accepts the upgrade.
- The client never passes an `organization_id`; tenancy is strictly verified server-side.

## 4. Reconnection & Resilience

### Q: How do you prevent a "reconnect storm" (thundering herd) when the WebSocket server restarts?
**Answer:**
- Use **bounded exponential backoff**:
  - Initial delay: 1000ms.
  - Multiplier: $delay = baseDelay \times 2^{attempts}$.
  - Cap: Maximum delay capped at 10,000ms.
  - Max attempts: Stop retrying after 5 attempts to prevent runaway background timers.
- **Immediate reset**: Reset `reconnectAttempts = 0` on successful socket `open`.
- **Strict cleanup**: When the component unmounts, cancel any pending `setTimeout` timer before tearing down the active socket.

## 5. Race Conditions & Stale Responses

### Q: How do you handle out-of-order responses when multiple live updates trigger refetches in quick succession?
**Answer:**
- Use **request sequence tracking** combined with **effect-level cancellation**:
  - Maintain a sequence/generation counter (`requestSeqRef`).
  - When starting a query, increment the counter: `const currentSeq = ++requestSeqRef.current;`.
  - When the fetch promise resolves, check: `if (currentSeq !== requestSeqRef.current) return;`.
  - If a newer request has already started, discard the stale response.
  - Additionally, use `AbortController` or cancellation flags (`isCancelled`) during component unmount.

## 6. Interaction with UI State (Selection & LOD)

### Q: What happens to the user's selected node and zoom level when a live graph update arrives?
**Answer:**
- **Viewport & Zoom**: Maintained seamlessly. React Flow's viewport position is preserved, and Step 38 LOD automatically re-evaluates which nodes are visible at the current zoom tier over the fresh dataset.
- **Selected Node**:
  - If the selected node ID still exists in the newly fetched graph, `selectedNodeId` is preserved.
  - If the selected node was deleted or no longer satisfies the updated graph filters, `selectedNodeId` is safely reset to `null`.
  - `NodeInspectorPanel` and `EvidenceTrail` gracefully transition to their empty state without throwing runtime errors.

## 7. Scalability & System Tradeoffs

| Approach | Pros | Cons | Fluxora Choice |
| :--- | :--- | :--- | :--- |
| **Short Polling** (e.g. `setInterval(fetch, 2000)`) | Simple to implement, works anywhere | High server/database load, delayed updates | ❌ Rejected |
| **Full Graph Streaming over WS** | Lowest query latency | Memory drift, complex client logic, large frames | ❌ Rejected |
| **WS Invalidation + HTTP Query** | Single source of truth, minimal WS traffic, filter-compatible | Incurs an HTTP round-trip after the signal | ✅ **Adopted** |

### Q: When would this pattern struggle at massive scale, and how would you optimize it?
**Answer:**
- If a repository receives 50 updates per second (e.g. continuous streaming commits), triggering an HTTP graph query on every update would overwhelm the server.
- **Optimization**: Debounce invalidations on the client (e.g., coalesce updates within a 500ms sliding window) or publish batch invalidations on the server.
