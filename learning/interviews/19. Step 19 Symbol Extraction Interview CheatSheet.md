# 19. Step 19 Symbol Extraction Interview CheatSheet

## Core Architectural Concepts

### 1. What is Step 19's objective and how does it fit into Fluxora?
**Answer:**
Step 19 implements deterministic per-file symbol extraction (`05-component-responsibilities.md §5.3`). Given an ingested repository snapshot, it identifies code entities (functions, classes, methods, interfaces, type aliases, enums, variables, constants) within each supported TypeScript/JavaScript source file. It builds the vocabulary of code entities that subsequent steps (Step 20 import/export graphs and Phase 4 graph persistence) connect together.

---

### 2. Why use the TypeScript Compiler API directly instead of ts-morph or tree-sitter for Step 19?
**Answer:**
- **Zero footprint overhead:** `typescript` is already a core devDependency in the monorepo. Using `ts.createSourceFile` requires no heavy external wrappers or native bindings.
- **Full TypeScript syntactic coverage:** Understands modern TS 5.x features, JSX/TSX syntax, decorators, and modern ES module exports natively.
- **Fault-tolerant parsing:** `ts.createSourceFile` produces partial syntax trees and structured diagnostic arrays without throwing unhandled exceptions.
- *Tree-sitter* is deferred to Step 24 as a fallback for non-TS-aware languages.

---

### 3. Why must repository code never be executed during symbol extraction?
**Answer:**
Customer repositories are completely untrusted. Executing repository code (`eval`, `import()`, or running build scripts) introduces critical security vulnerabilities: arbitrary code execution, disk/network tampering, environment secret leakage, and Denial of Service (infinite loops). Fluxora strictly analyzes code as inert text via AST parsing.

---

### 4. Why is Step 19 strictly decoupled from Step 20?
**Answer:**
- **Step 19 (Per-file symbol extraction)** is embarrassing parallel: each file can be parsed completely in isolation without knowledge of any other file in the repository.
- **Step 20 (Import/export graph extraction)** requires multi-file coordination: resolving module specifiers, evaluating `tsconfig.json` path mappings, and tracing cross-file dependencies.
Decoupling them ensures single-responsibility design, clean cacheability, simpler unit testing, and predictable performance.

---

### 5. How are source locations represented, and why is offset included alongside line/column?
**Answer:**
Each symbol captures a `SourceLocation` containing `start` and `end` `SourcePosition`s with:
- `line` (1-based)
- `column` (1-based)
- `offset` (0-based character index)
Line and column provide human-readable references for UI displays and diffs. The byte/character offset provides unambiguous, lightning-fast string slicing and evidence generation without requiring newline re-scanning.

---

### 6. How are nested symbols (e.g. class methods) represented?
**Answer:**
Class methods are not emitted as disconnected top-level symbols. Instead, they reference their enclosing class via `parentSymbolId` and `parentName`. Their unique identifier incorporates their parent's name (e.g., `src/service.ts#method:PaymentService.charge:120`), ensuring deterministic parentage and preventing naming collisions with other methods or functions.
