# Step 61: Structured Output Validator Interview Cheat Sheet

## 1. High-Level Concept & Elevator Pitch

### The 30-Second Elevator Pitch
> *"In Fluxora Step 61, we built the admission-control boundary for AI explanations. Because Fluxora is a deterministic software digital twin, an LLM must never invent relationships or cite fabricated evidence. Our validator strictly parses raw model output as JSON, verifies compliance against a 4-field schema, and cross-checks every cited evidence ID against an allowlist manifest generated by deterministic static analysis. If any claim cites an ungrounded ID, the entire response is rejected. We provide bounded corrective feedback for exactly one retry before failing closed to a deterministic non-AI template."*

### Layman Analogy: The Customs Manifest Checkpoint
- **Context Assembler (Step 60)**: Prepares the official customs manifest listing every approved item (`allowedEvidenceIds`).
- **LLM Generator (Step 59/62)**: The cargo carrier arriving at the border with a shipment of claims.
- **Output Validator (Step 61)**: The customs border officer. Every container must have an official manifest number. If a single unlisted container is found, the shipment is turned back for one inspection retry. If it fails again, the shipment is turned away and standard domestic emergency supplies (deterministic fallback) are dispatched instead.

## 2. Staff-Level Architecture Q&A

### Q1: Why not use a library like Zod or TypeBox for validation?
**Answer**:
- **Zero Drift**: In many teams, developers maintain a Zod schema in one file, a JSON Schema for model tool-use in another, and manual grounding checks in a third. In Step 61, our pure TypeScript validator unifies JSON parsing, schema checking, and manifest grounding in a single cohesive pass.
- **Zero Overhead**: Adding Zod to worker bundles introduces transitive dependencies and bundle size. A small, zero-dependency validator is lightweight, fast, 100% deterministic, and has zero external security attack surface.
- **Custom Grounding Mechanics**: Standard validation libraries validate shapes and primitive types, but cannot natively enforce allowlist manifest membership across nested arrays or duplicate citation checks within claims without complex custom refinements.

---

### Q2: Why reject the entire response instead of stripping ungrounded claims? (ADR-014)
**Answer**:
- **Semantic Mutilation**: Claims in an explanation are rarely independent. A model's `summary` or subsequent claims often refer to findings introduced in earlier claims. If an ungrounded claim is silently deleted, the narrative becomes logically incoherent or misleading.
- **Explicit Failure Visibility**: Silent stripping masks hallucinations from callers and evaluation harnesses. If the model hallucinated 20% of its citations, downstream orchestration and evaluation suites need an explicit failure result rather than partially corrupted data.
- **Fail-Closed Safety**: In mission-critical infrastructure software, showing a clean deterministic template (Step 66) is far safer than showing an AI explanation with missing pieces.

---

### Q3: Why does manifest membership NOT guarantee that the explanation is true?
**Answer**:
This is the core insight of the **Three-Level Grounding Guarantee**:
- **Level 1 (Step 60 Context)**: Guarantees candidate evidence is structurally linked to verified impact findings.
- **Level 2 (Step 61 Validator)**: Guarantees citation provenance—the model only cited IDs we gave it, not fabricated IDs.
- **Level 3 (Semantic Support)**: Requires proving that the English sentence actually matches what the code evidence says. A model could cite a valid evidence ID describing a modified route in `PaymentService` to support a false claim like *"The entire database was dropped."* Manifest validation passes because the ID is allowed, but the claim is semantically false.
- *Staff Takeaway*: Never promise that schema validation eliminates hallucinations. It enforces citation provenance, while semantic support requires downstream evaluation or human review.

---

### Q4: How do you prevent prompt-injection attacks when feeding validation errors back to the model during retry?
**Answer**:
1. **Never Echo Raw Output**: The corrective prompt never repeats the raw text of the prior response, preventing reflection or jailbreak re-triggering.
2. **Bounded Error Payloads**: Error lists in corrective prompts are capped at 10 items (`MAX_CORRECTIVE_FEEDBACK_ISSUES = 10`), preventing prompt bloat and token overhead, while the caller result retains up to 20 issues (`MAX_VALIDATION_ISSUES = 20`) for downstream callers and diagnostics.
3. **Machine-Readable Codes**: Errors are formatted as structured directives (`- [UNKNOWN_EVIDENCE_ID] at 'claims[0].evidence_ids[0]'`), instructing the model purely on structural compliance.

---

### Q5: How do you handle provider outages during the validation retry?
**Answer**:
- **Exception Transparency**: We do not catch `ModelGatewayError` or network exceptions inside `validateImpactExplanationWithRetry`. If the retry callback throws an Anthropic 429, 500, or timeout error, it bubbles up immediately to the caller.
- This ensures the orchestrator can distinguish between:
  - *Provider Downtime*: Retry or fall back based on network resilience policies.
  - *Model Incompetence*: Exhausted retries on invalid structured output $\to$ trigger Step 66 deterministic fallback.

## 3. Comparison Matrix: Permissive vs. Strict AI Output Handling

| Aspect | Permissive Approach (Common in Prototypes) | Strict Fluxora Approach (Step 61) |
|---|---|---|
| **JSON Parsing** | Regex extraction (`/\{.*\}/s`) | Strict `JSON.parse` across full trimmed string |
| **Markdown Fences** | Auto-stripped (`replace(/```json/g, '')`) | Rejected with `MARKDOWN_CODE_FENCE_DETECTED` |
| **Unknown Keys** | Silently dropped | Rejected with `UNRECOGNIZED_PROPERTY` |
| **Ungrounded Citations** | Silently stripped or ignored | Whole response rejected (`UNKNOWN_EVIDENCE_ID`) |
| **Retry Policy** | Unbounded loops or zero retries | Exactly 1 retry (max 2 total attempts) |
| **Error Feedback** | Full stack trace or raw prompt echo | Bounded error codes and property paths |
| **Fallback** | Display broken/partial text to user | Fail closed to deterministic template (Step 66) |

## 4. Production Runbook & Traps to Avoid

1. **Trap: Mixing Up Prompt Version and Output Schema Version**:
   - Prompt Version (`impact-explain-v1`): Governs the instructions sent to the model.
   - Output Schema Version (`impact-explanation-output-v1`): Governs the JSON shape expected in return. They must be versioned independently so prompt tweaks don't break downstream parsers.
2. **Trap: Permissive String Trimming in Schema**:
   - Checking `typeof str === "string"` without checking `str.trim().length === 0` allows empty strings like `"   "` to pass as valid claims or summaries.
3. **Trap: Forgetting Duplicate Citations within a Single Claim**:
   - Models often hallucinate repeats like `evidence_ids: ["ev-1", "ev-1"]`. The validator must enforce uniqueness per claim while allowing different claims to cite the same ID.
