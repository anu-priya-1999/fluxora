# Step 11 Interview Cheat Sheet — Repository, Snapshot, Commit

Use with `docs/architecture/06-database-schema.md`, `11-security-architecture.md`, and `packages/db/migrations/0011_repositories_snapshots_commits.sql`.

---

## Repository vs snapshot vs commit

**Repository** is Fluxora's tenant-owned *connection* to a GitHub repo: name, default branch, `connection_status`, `last_indexed_at`. It is mutable (reconnect, reauth, rename).

**Commit** is git *object metadata*: SHA, author, message, `committed_at`, `parent_shas`. It does not include file bytes.

**RepositorySnapshot** is an *immutable packaged tree* for one commit: `commit_sha`, `ref`, `storage_uri`, size stats. Later analysis attaches to the snapshot, not to a moving GitHub HEAD.

Sound bite: *repo = connection, commit = history fact, snapshot = frozen artifact we actually analyze.*

---

## Why snapshots are immutable

Evidence and graph nodes will cite `snapshot_id`. Overwriting storage metadata or replacing files under the same id makes provenance a lie and opens TOCTOU (fetch A, analyze as if still A, GitHub now B).

Enforcement: unique `(repository_id, commit_sha)`, no UPDATE RLS policy under FORCE RLS, application rejects mismatched replay.

Re-index of a new SHA creates a **new** snapshot. Same SHA is idempotent.

---

## Why not store repository contents in PostgreSQL

Trees are large, binary, rarely joined row-by-row, and would bloat WAL/backups. Architecture: S3-compatible object storage for snapshots; Postgres for relational metadata, graph, evidence, tenancy.

`storage_uri` is the pointer. Step 11 stores the pointer contract; Step 12 writes the object.

---

## Why not put `organization_id` on every child table

§6.5: children inherit tenancy through the parent chain. Duplicating org id risks divergence from `repository.organization_id`. RLS joins/EXISTS up to `repositories`. Denormalize later if EXPLAIN shows the EXISTS is hot.

---

## How parent-chain RLS works

Session: `app.current_org_id`.

`repositories`: `organization_id = fluxora_current_org_id()`.

`repository_snapshots` / `commits`: `fluxora_repository_in_current_tenant(repository_id)` → `EXISTS (SELECT 1 FROM repositories r WHERE r.id = … AND r.organization_id = fluxora_current_org_id())`.

The EXISTS runs as invoker, so nested RLS on `repositories` applies. A stolen child UUID from another org does not pass SELECT. INSERT `WITH CHECK` uses the same function so you cannot attach a snapshot to another tenant's repo.

---

## How FK constraints help (and what they don't)

FKs prevent orphans and dangling `repository_id`s. `ON DELETE CASCADE` cleans children when a repo/org is removed.

FKs **do not** enforce tenancy: PostgreSQL FK checks bypass RLS. Isolation is policies + `withTenant` in the app.

---

## Uniqueness for GitHub repo IDs

GitHub's `github_repo_id` is globally unique **on GitHub**.

In Fluxora it must be unique **per organization**: `UNIQUE (organization_id, github_repo_id)`.

- Global unique would block two tenants from connecting the same public repo.
- Contrast: `github_installation_id` **is** globally unique because one App installation is a single resource that must not be claimed by two Fluxora orgs.

TypeScript keeps the id as a decimal **string**; SQL uses `bigint`. Same reason as installation ids (JSON number rounding).

---

## Indexes and why

- `(organization_id, github_repo_id)` unique — connect/lookup
- `(organization_id)`, `(organization_id, connection_status)`, `(organization_id, created_at DESC)` — tenant lists and status filters
- `(repository_id, commit_sha)` unique — ingest idempotency
- `(repository_id, created_at DESC)` on snapshots — latest snapshot
- `(repository_id, sha)` unique on commits — history lookup
- `(repository_id, committed_at DESC)` — timeline

---

## Re-indexing and history

Repository row stays. Each new HEAD SHA → new commit row (if unseen) + new snapshot. Old snapshots remain (history / time-travel later). `last_indexed_at` updates on the repository only.

Do not UPDATE the previous snapshot.

---

## Concurrent writes

`withTenant` wraps BEGIN / set_config / COMMIT.

Unique violations abort the PostgreSQL transaction unless caught with a **savepoint** (same lesson as GitHub installations). Replay: if payload matches, return existing row; if not, conflict/immutable error.

Two workers inserting the same SHA: one wins insert, the other hits 23505, savepoint rollback, select existing.

---

## Disconnect / reconnect

`connection_status` moves to `needs_reauth` or `error` without deleting snapshots/commits. Reconnect sets `active` (future GitHub App / token steps). Historical snapshots remain the evidence base.

Deleting the repository row cascades children. Prefer status changes over delete unless the tenant intends to purge.

---

## Preparing ingestion workers

Worker will run under the org's tenant session, insert commit + snapshot, set `storage_uri`, flip status. Schema already forbids snapshot mutation and cross-tenant child inserts. Worker must not query GitHub from analysis processes (later security split); this step only lays the tables.

---

## Larger scale

- Denormalize `organization_id` onto snapshots/commits if EXISTS shows up in p95.
- Partition snapshots by time or `repository_id`.
- Object storage lifecycle: drop old blobs, keep graph/evidence.
- Shard by `organization_id` (ADR-008) — child tables follow parent repos in the same shard.

---

## Source of truth vs derived

| Source of truth (this step) | Derived / later |
|---|---|
| Repository connection fields | Graph nodes/edges from analysis |
| Commit SHA/author/message/parents | Impact reports |
| Snapshot identity + storage_uri + counts | AI explanations |
| GitHub remains SoT for git until snapshotted | After snapshot, **the snapshot** is SoT for analysis (do not re-fetch mid-job) |

PostgreSQL is SoT for metadata. Object storage will be SoT for bytes. GitHub is SoT for live git until freeze.

---

## Likely follow-ups interviewers want

- Why FORCE RLS? Table owner (API role) would otherwise bypass policies.
- Why no snapshot UPDATE policy instead of a trigger? Default-deny under FORCE RLS is enough for the app role; cheaper than a trigger.
- Why SHA-1 40 hex? GitHub commits are still SHA-1; reject abbreviations so ids are canonical.
- Why `size_bytes` as text in TypeScript? Postgres `bigint` can exceed `Number.MAX_SAFE_INTEGER`.
