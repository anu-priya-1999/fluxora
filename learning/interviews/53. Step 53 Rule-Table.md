# Step 53 — Initial Simulation Rule Table Interview CheatSheet

## Q1: What is the role of the Simulation Rule Table in Fluxora's architecture?
**Answer**:
The Rule Table is a deterministic, versioned, pure domain function that evaluates whether a graph edge and adjacent node states cause a failure or degradation to propagate. It takes inputs such as edge type, current source/target states, sync/async status, fallback and circuit-breaker presence, and failure type (`unavailable` | `latency`), and returns a deterministic decision (`matched`, `resultingState`, `ruleId`, `capped`, `assumptions`, `confidence`). It is completely independent of PostgreSQL, graph traversal algorithms, HTTP APIs, and UI layers.

---

## Q2: Why is the Rule Table kept separate from the Simulation Engine?
**Answer**:
Separation of concerns. The Rule Table defines the **policy** of failure propagation ("What happens when node A calls degraded node B over a synchronous edge without fallback?"), while the Simulation Engine (Step 54) defines the **mechanism** of propagation (breadth-first traversal, monotonic state convergence, snapshot loading, and result persistence). Keeping them separate makes the rules testable in pure unit isolation without database mocks or graph traversal complexity.

---

## Q3: Why are fallback handlers and asynchronous calls modeled as non-matches rather than separate propagation rules?
**Answer**:
In Fluxora's simulation architecture, all nodes are initialized to `HEALTHY` (except the scenario target). State transitions only occur when an explicit failure propagation rule matches.
- A fallback handler mitigates callee failure; it prevents degradation from propagating to the caller.
- An asynchronous call decouples caller execution from callee response times.
Modeling them as `CALLS + fallback → HEALTHY` would create synthetic state transitions where none occurred. Modeling them as explicit non-matches (`matched: false`) accurately reflects that the failure stopped propagating and the caller remains in its existing state.

---

## Q4: How does `WRITES+failure` propagate, and why is it restricted to dependent reads?
**Answer**:
Per `04-system-architecture-diagrams.md §4.7`, `WRITES + failure → dependent reads → AT_RISK`. When a database or storage system experiences write failures or an outage, components that read or query that database (`QUERIES_DB`) become `AT_RISK` due to stale, uncommitted, or inconsistent data. Evaluating the rule across a write edge (`WRITES`) is a non-match because write failures affect downstream readers of the corrupted/missing data.

---

## Q5: How does Fluxora handle unknown edge metadata? Why tri-state?
**Answer**:
Static analysis cannot always guarantee whether a pattern like a circuit breaker or fallback exists. Using a binary boolean (`true | false`) would force static analysis to assume `false` when it simply didn't know, creating false certainty.
Fluxora uses tri-state metadata: `true | false | "unknown"`. When metadata is `"unknown"`:
1. The rule table applies a conservative default (behaves as though protection is absent).
2. It surfaces an explicit assumption in the simulation output (e.g., `"No circuit breaker detected on OrderService->PaymentService call"`).
3. It calibrates the confidence score (e.g., 0.90 instead of 1.0) to reflect the unverified assumption.

---

## Q6: How does the Rule Table model latency degradation in Step 53?
**Answer**:
Qualitatively and deterministically. The scenario failure type `latency` flows through the same deterministic dependency paths as `unavailable`, but triggers latency-specific assumptions (e.g., synchronous dependency latency causing caller timeouts, or event broker queue latency putting consumer SLAs at risk). It deliberately avoids synthetic quantitative metrics (milliseconds, percentiles, queueing theory), which belong to future runtime telemetry phases.
