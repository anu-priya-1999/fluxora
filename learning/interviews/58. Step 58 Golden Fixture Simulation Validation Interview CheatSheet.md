## 1. High-Level Concept & Architectural Motivation

### Q: Why do we validate our simulation engine against a "Golden Fixture" rather than relying purely on synthetic unit tests?
**Answer:**
Synthetic tests construct artificial graphs in memory, which inevitably reflect the test author's assumptions: clean tree topologies, unambiguous metadata, and uniform node granularities. Real software systems, however, exhibit dense dependency fan-outs, barrel-file re-exports, circular module references, and incomplete static metadata.

Fluxora maintains pinned, immutable open-source repositories (such as `shadcn-ui/taxonomy` at commit `298a8857c7128a0d121e7f699dfd729f23b3966d`) with recorded SHA-256 manifests. Validating against this fixture proves:
1. The real static analysis pipeline parses and normalizes authentic repository source files.
2. The deterministic graph projection generates realistic topologies (490 nodes, 888 edges).
3. The simulation engine scales and converges deterministically over hundreds of real nodes.
4. Negative controls (unrelated modules) remain unaffected in a dense graph environment.

## 2. Invariant & Semantic Boundaries: `IMPORTS` vs. `CALLS`

### Q: Why is it an architectural violation to treat `IMPORTS` edges as `CALLS` in the simulation engine?
**Answer:**
Treating `IMPORTS` as `CALLS` is the single most dangerous false-positive trap in static dependency analysis:
- An import is a **static compilation/packaging dependency**; a call is a **runtime operational interaction**.
- In TypeScript/Next.js systems, modules frequently import files to consume interfaces/types, utility constants, or dormant helper functions.
- If importing `lib/subscription.ts` implied that a failure in `lib/subscription.ts` degrades the importer, nearly every page, layout, and API route in the application would be marked as degraded or failed.
- This produces an explosive, false-positive blast-radius cascade that destroys engineering trust.

In Fluxora's Step 53 rule table, rules specifically trigger on semantic, operational edges: `CALLS`, `QUERIES_DB`, `WRITES`, and `CONSUMES_EVENT`. In Step 58, **Test B (IMPORTS Negative Control)** explicitly proves that running failure simulation on a pure projected graph with `IMPORTS` results in zero caller degradation.

## 3. Fixture-Backed Test Provenance (ADR-012)

### Q: If the Taxonomy graph extractor doesn't currently produce `CALLS` edges, how did you validate call failure propagation without fabricating production data?
**Answer:**
We resolved this via **ADR-012 (Separation of Fixture-Backed Simulation Edges from Production Graph Projections)**:
1. **Source Inspection & Ground Truth**: We inspected the pinned fixture code and verified an authentic, awaited call site:
   `app/api/users/stripe/route.ts:20` awaiting `getUserSubscriptionPlan(session.user.id)` from `lib/subscription.ts`.
2. **Explicit Manifest Contract**: We documented this relationship in `fixtures/golden/simulation-manifest.json` with exact coordinates, snippet, caller/callee canonical IDs, and `isTestOnly: true`.
3. **In-Memory Snapshot Injection**: For simulation validation, we construct a `SimulationGraphSnapshot` combining the untouched production projection (490 nodes, 888 edges) with the single verified `SimulationEdge` (`test-edge:...`).
4. **Strict Isolation**: The test edge is never persisted in PostgreSQL, never returned by graph queries, and never attributed to the production graph builder. This allows us to validate the simulation engine's propagation, causal trail, and confidence calculations against real entities without faking extraction capabilities.

## 4. Simulation Engine Mechanics & Causal Evidence

### Q: Walk me through the execution of the subscription helper failure scenario. What state transitions occur, and why?
**Answer:**
1. **Target Failure Seeding**:
   - Scenario targets `mod:lib/subscription.ts` with failure type `unavailable`.
   - Seed node transitions: `healthy → failed` (state severity 3).
   - Seed step: `edgeId: null`, rule `target_failure`, confidence `1.0`.
   - Worklist queue initialized with `[mod:lib/subscription.ts]`.
2. **First Worklist Iteration**:
   - Engine pops `mod:lib/subscription.ts`.
   - Incident edge evaluated: `mod:app/api/users/stripe/route.ts` `--CALLS-->` `mod:lib/subscription.ts`.
   - Edge metadata: `{ sync: true, hasFallback: "unknown", hasCircuitBreaker: "unknown" }`.
   - Rule evaluated: `CALLS+sync+no_fallback`.
   - Target is impaired (`failed`), call is synchronous, and no fallback/circuit-breaker is confirmed present.
   - Decision: Caller transitions `healthy → degraded` (state severity 2).
   - Confidence: `0.9` (penalized because fallback/circuit-breaker presence is `"unknown"`).
   - Assumptions generated:
     - `"No circuit breaker detected on app/api/users/stripe/route.ts->lib/subscription.ts call"`
     - `"No fallback handler detected on app/api/users/stripe/route.ts->lib/subscription.ts call"`
   - Monotonicity check passes (`degraded > healthy`). Caller is pushed to work queue.
3. **Second Worklist Iteration**:
   - Engine pops caller. Caller's incident edges are evaluated, but no connected dependencies are impaired.
   - Queue empties. Engine terminates and converges in 2 iterations.
4. **Negative Controls**:
   - Unrelated nodes (e.g. `mod:components/site-footer.tsx`) remain `healthy` and are omitted from the affected results list.

## 5. Causal Trail & Evidence Integrity

### Q: How does Fluxora ensure that simulation results are explainable and verifiable rather than "black-box" outputs?
**Answer:**
Every affected node in `SimulationEngineResult.results` contains a structured `propagationPath: readonly SimulationCausalStep[]`:
- **Step 0**: Seed step on `mod:lib/subscription.ts` with `edgeId: null`, `ruleId: target_failure`, `resultingState: failed`.
- **Step 1**: Causal step on `mod:app/api/users/stripe/route.ts` with:
  - `edgeId`: Exact ID of the traversed edge (`test-edge:...`).
  - `ruleId`: `CALLS+sync+no_fallback`.
  - `ruleVersion`: `"1.0.0"`.
  - `previousState`: `"healthy"`.
  - `resultingState`: `"degraded"`.
  - `confidence`: `0.9`.
  - `assumptions`: Full list of domain assumptions.

Automated assertions verify that every step points to a real edge in the snapshot, the edge connects the actual caller and callee, and the causal path begins with the authentic seed transition.

## 6. Determinism & Performance

### Q: How do you prove that the simulation engine is deterministic across runs?
**Answer:**
In `golden-simulation.test.ts`, **Test D** runs the identical scenario 3 times against the snapshot:
- We sort/index affected nodes by canonical ID.
- We assert that `run1`, `run2`, and `run3` produce identical resulting states, applied rules, confidence scores, assumption arrays, causal paths, and iteration counts.
- There are no timestamps or random UUIDs in the causal logic; all IDs and transitions are strictly deterministic functions of input entities.
