# 43. Step 43 Impact Analysis Engine Interview CheatSheet

## Core Concepts & Quick Answers

### Q1: What is the purpose of Step 43 and how does it fit into Fluxora's architecture?
**Answer:**
Step 43 builds the **deterministic Impact Analysis Engine**. It takes a pull request's changed files and diffs (persisted in Step 42) along with the current repository graph snapshot, resolves modified lines to AST symbols, and performs bounded downstream graph traversal to compute the pull request's architectural blast radius.
It serves as the deterministic core that classifies affected APIs, events, and services before persistence (Step 44), API exposure (Step 45), or UI visualization (Step 46).

---

### Q2: How does the engine map a file diff to specific AST symbols?
**Answer:**
1. **Diff Hunk Parsing**: The engine parses unified diff hunk headers (`@@ -old,count +new,count @@`) using `parsePatchModifiedLines` to extract exact modified line numbers.
2. **AST Range Intersection**: For each symbol node located in the modified file, it compares the modified lines with the symbol's `[lineStart, lineEnd]` range (from metadata or evidence).
3. **Graceful Fallback**: If a diff lacks hunks (e.g. an added file or entire file rewrite), all symbols in that file are included as seeds.
4. **Unresolved Cataloging**: Non-code files (e.g. documentation or build scripts) with no graph symbols are explicitly cataloged in `unresolvedFiles` with a clear reason rather than silently ignored.

---

### Q3: Why is BFS preferred over DFS for blast-radius traversal?
**Answer:**
1. **Shortest Distance Guarantee**: Breadth-First Search (BFS) visits nodes layer by layer. When multiple paths reach the same downstream node, BFS encounters it via its shortest hop distance first.
2. **Confidence Maximization**: Because confidence decays per hop ($0.9^d$), the shallowest path yields the highest confidence score.
3. **Deterministic Stratification**: BFS cleanly partitions discoveries into direct impacts (`depth = 1`) and downstream impacts (`depth >= 2`).

---

### Q4: How are graph cycles prevented from causing infinite loops?
**Answer:**
Software dependency graphs frequently contain cycles (e.g. circular imports, mutual service dependencies).
The engine maintains a `visited` set of node IDs. Before traversing an edge, the engine checks if the target node has already been visited. If so, the edge is skipped, ensuring the algorithm always terminates in finite time.

---

### Q5: How does the engine handle multi-seed deduplication when multiple changed symbols reach the same downstream node?
**Answer:**
If Symbol A and Symbol B both lead to Node X (e.g. Symbol A at 2 hops, Symbol B at 4 hops):
- The engine deduplicates Node X, keeping only the **shallowest path** (depth = 2).
- Node X receives the higher confidence score ($0.9^2 = 0.810$ instead of $0.9^4 = 0.656$).
- The finding records both seeds in `seedNodeIds: ['symbol_a', 'symbol_b']` for complete provenance.

---

### Q6: How does confidence decay work across graph hops?
**Answer:**
Confidence represents how directly an upstream change affects a downstream component.
$$\text{Confidence}(d) = \text{InitialConfidence} \times (0.9)^d$$
- Seed nodes have confidence 1.0 (depth 0).
- Direct callers at depth 1 have confidence 0.9.
- Downstream nodes at depth 2 have confidence 0.81, and so on.
- Confidence is strictly monotonic non-increasing with depth.

---

### Q7: How is traversal truncation detected and reported?
**Answer:**
The engine enforces a default maximum depth of 5 hops (`DEFAULT_IMPACT_MAX_DEPTH`) and a hard system ceiling of 20 hops (`HARD_MAX_IMPACT_DEPTH`).
If a node is reached at `depth === maxDepth`, and that node has outgoing downstream edges, the engine:
1. Sets `truncated: true` on that individual `ImpactFinding`.
2. Sets `truncated: true` on the top-level `ImpactAnalysisResult`.
This explicitly signals to users, CI checks, and UI components that the blast radius extends beyond the search horizon.

---

### Q8: How is multi-tenant isolation enforced during graph queries?
**Answer:**
All database queries execute through `withTenant(pool, organizationId, ...)`:
- Sets `SET LOCAL app.current_organization_id = $organizationId` in PostgreSQL.
- Enforces `FORCE ROW LEVEL SECURITY` across `repositories`, `repository_snapshots`, `graph_nodes`, `graph_edges`, and `pull_requests`.
- Enforces tenant integrity: if a pull request ID does not belong to the requested organization, the engine throws `PullRequestNotFoundError`.

---

### Q9: How is absolute determinism guaranteed across multiple runs?
**Answer:**
1. Traversal logic does not depend on database retrieval order.
2. Traversal orders seeds and edges using stable identifiers (`nodeId`).
3. Results are explicitly sorted:
   - Findings: `depth ASC`, `confidence DESC`, `nodeId ASC`.
   - Seed nodes: `nodeId ASC`.
   - Affected APIs/Events/Services: `nodeId ASC`.
   - Unresolved files: `path ASC`.
Running analysis over the same snapshot and PR diff always produces the exact same byte-for-byte JSON output.

---

### Q10: Why are persistence, REST endpoints, and UI overlays excluded from Step 43?
**Answer:**
Following strict single-responsibility step discipline:
- **Step 43**: Pure in-memory calculation, diff-to-symbol resolution, graph traversal, and taxonomy classification.
- **Step 44**: `impact_analyses` database table, migrations, RLS policies, and `EvidenceWriter` provenance linking.
- **Step 45**: Fastify REST endpoints (`/api/v1/pull-requests/:id/impact`).
- **Step 46**: Frontend Next.js GraphCanvas change-mode overlay.
Decoupling calculation from persistence allows instantaneous unit testing and avoids premature database schema commitments before algorithmic verification is complete.

---

### Q11: What are the limitations and potential false-negative risks of static impact analysis?
**Answer:**
1. **Dynamic Dispatch / Reflection**: Runtime dynamic method calls or `eval()` cannot be detected by static AST analysis.
2. **String-Based Event Names**: If an event producer emits a message using a dynamic string, static analysis might fail to link it to the consumer unless explicit edge metadata exists.
3. **Non-Code Diffs**: Changes to build scripts, Dockerfiles, or documentation files cannot be resolved to AST symbols and are classified in `unresolvedFiles`.
4. **Diff Truncation**: Extremely large PRs with truncated patches fallback to whole-file symbol matching, which might overestimate initial seeds.
