# Step 24 — Tree-sitter Fallback Interview CheatSheet

## Q1: Why does Fluxora need a Tree-sitter Fallback Pass if it already has TypeScript Compiler API parsing?
**Answer**:
The TypeScript Compiler API is authoritative for TS and JS source files, but repositories contain other critical assets—such as package manifests (`package.json`), design tokens (`globals.css`), templates (`index.html`), and documentation (`README.md`). Furthermore, if a TS/JS file has severe syntax errors that crash the primary compiler AST generation, Fluxora uses Tree-sitter to perform fault-tolerant error recovery parsing without failing the ingestion worker.

## Q2: Why not use Tree-sitter for all language parsing in Fluxora?
**Answer**:
Tree-sitter provides concrete syntax trees (CSTs) suited for syntax highlighting and broad parsing, but it lacks full semantic resolution, type checker symbols, module resolution rules, and tsconfig path alias resolution provided by the TypeScript Compiler API. Therefore, Fluxora preserves a strict primary-versus-fallback hierarchy: Compiler API for primary deep semantic intelligence, Tree-sitter for non-code assets and syntax fallbacks.

## Q3: How is deterministic parsing guaranteed during fallback?
**Answer**:
1. Grammars are loaded as version-pinned WebAssembly binaries (`web-tree-sitter`).
2. Node position ranges use 1-based line/col and 0-based character offsets.
3. Diagnostic messages and generic structural units are deterministically sorted by offset and name.
4. Identifiers follow a predictable template: `${relativePath}#tree-sitter`.

## Q4: What security boundaries apply to Tree-sitter in Fluxora?
**Answer**:
Tree-sitter parsing is strictly static and isolated inside WebAssembly sandboxes. It never executes target repository code, imports target dependencies, or connects to external network/database services.
