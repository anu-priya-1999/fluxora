# 35. Step 35 Architecture Explorer Interview CheatSheet

## Core Conceptual Questions

### Q1: What is the Architecture Explorer route and what is its role in Fluxora?
**Answer**:
The Architecture Explorer route (`/repositories/[repoId]/explorer`) is the primary UI viewport for exploring a repository's deterministic software digital twin. In Step 35, it serves as the route-level orchestration layer: it verifies user authentication via Clerk, resolves the relevant analysis run and entry node context, performs an authenticated HTTP request to `POST /api/v1/graph/query`, transforms the response into React Flow elements, and mounts the Step 34 presentational `GraphCanvas`.

---

### Q2: Why is the route separate from GraphCanvas?
**Answer**:
`GraphCanvas` is purely presentational: it takes input nodes and edges and renders them in React Flow with zooming, panning, and styling. It has zero knowledge of URL parameters, Clerk authentication, or network protocols.
The Explorer route handles Next.js App Router routing, server-side auth guards, API client communication, and route-level error/empty states. This separation prevents UI components from coupling to transport details and allows `GraphCanvas` to be reused across different views (such as simulation diffs or pull request impact analysis).

---

### Q3: Why doesn't `apps/web` import `@fluxora/db` directly?
**Answer**:
Architectural boundary separation: The frontend web application is a client of the Fluxora backend API, not an owner of the database layer. Having the frontend directly query PostgreSQL violates the three-tier architecture, exposes DB schemas and secrets to the web boundary, breaks Next.js bundler isolation (due to native dependencies and migration scripts in `@fluxora/db`), and circumvents the centralized API middleware, rate limiting, and OpenTelemetry instrumentation established in `apps/api`.

---

### Q4: How is tenancy preserved in graph queries from the browser?
**Answer**:
The browser never passes an `organization_id` or `organizationId` parameter. Instead, it sends the user's Clerk JWT session token in the `Authorization: Bearer <token>` header. The backend API (`apps/api`) verifies the token against Clerk, provisions/maps the user identity, extracts the authoritative `organization_id`, and opens a PostgreSQL transaction scoped to that tenant via `withTenant(...)` and Row-Level Security (RLS).

---

### Q5: How are loading, not-ready, and error states handled in the Explorer?
**Answer**:
- **Loading State**: A dedicated loading indicator is displayed while the graph query is executing asynchronously.
- **Not Ready / Empty State**: If a repository has no completed analysis run or no start node provided, the route renders an accessible, informative message explaining that graph analysis is not ready yet, rather than fabricating a blank or artificial graph.
- **Error State**: Network failures, 401/403 authorization failures, or 404 not-found errors render a clear error UI without leaking tokens, internal stack traces, or sensitive server internals.
