# Step 63 AI Simulation Narration — Staff+ Interview CheatSheet

## 1. High-Level Pitch: What Did We Build?

"In Global Step 63, we implemented production-quality, evidence-grounded AI narration for Fluxora's deterministic failure simulation engine.

We extended the Phase 9 AI pipeline to support complex multi-hop failure scenarios:
1. **Deterministic Execution:** The simulation engine injects target failures, evaluates cascade rules across the dependency graph, and commits `simulation_results` and `simulation_state` evidence to PostgreSQL.
2. **Deterministic Context Assembly:** A pure, tenant-scoped assembler bounds results by character budgets, prioritizes results deterministically by `confidence DESC → severity DESC` (`failed` > `degraded` > `at_risk` > `healthy`, with unknown states defaulting to `0`) `→ hopDistance ASC → nodeId ASC` (keeping `capped` as a separate boolean flag rather than a severity state), and derives an exact `allowedEvidenceIds` manifest.
3. **Model Gateway & Safe Prompting:** Dispatches via the provider-independent gateway using `simulation-narrate-v1`, enforcing strict simulation-vs-production reality distinctions and Unicode XML containment.
4. **Strict Structured Output Validation:** Uses schema `simulation-narration-output-v1` with zero tolerance for unknown properties, ungrounded claims, or fabricated citations, supported by at most 1 corrective retry.
5. **Durable Persistence:** Saves to polymorphic `ai_analyses` table (`subject_type = 'simulation'`) with atomic withholding of rejected raw model output.
6. **Authenticated API:** Extends `GET /api/v1/simulations/:id` with `ai_analysis_id` and `ai_analysis_status`.
7. **Frontend Experience:** Renders `AISimulationNarrationPanel` in `SimulationStudio` with an amber simulated scenario notice, model confidence badges, clickable evidence citation chips, and bounded discovery polling."

## 2. Key Architecture Questions & Answers

### Q1: How does simulation narration differ from impact explanation (Step 62)?
**Answer:**
"While both share the Model Gateway and evidence grounding principles, simulation narration has distinct domain requirements:
1. **Simulation vs. Reality Semantics:** Simulation models hypothetical synthetic failures (e.g., Redis outage). The prompt and UI must explicitly prevent confusing synthetic simulations with active production incidents.
2. **Multi-Hop Propagation Traversal:** While PR impact evaluates static blast radius from modified code, simulation evaluates dynamic rule-table cascades across multiple hop distances with circuit-breaker capping. The context assembler prioritizes results deterministically using `confidence DESC → severity DESC → hopDistance ASC → nodeId ASC`—so higher-confidence outcomes take priority even over lower-confidence outcomes with greater severity, severity resolves equal-confidence ties, shorter hop distances resolve equal-confidence/equal-severity ties, and `nodeId` provides the final deterministic tie-breaker before applying the context budget.
3. **Dedicated Schema:** The structured output uses `simulation-narration-output-v1` capturing summary, confidence, caveats, and claims linked to `simulation_state` evidence records."

### Q2: What ensures that AI provider downtime cannot break deterministic simulation execution?
**Answer:**
"A strict **failure isolation boundary**:
1. Deterministic simulation execution (`executeSimulation`) runs and completes in its own transaction, persisting simulation state and evidence records to PostgreSQL first.
2. AI narration is executed downstream in an isolated `try/catch` block.
3. If the Model Gateway fails, times out, or the output fails grounding validation, the error is caught and logged, the `ai_analyses` record is marked `failed` or `rejected`, and the simulation run remains 100% completed and valid.
4. Client requests to `POST /scenarios/:id/run` or `GET /simulations/:id` always return the completed simulation results regardless of AI status."

### Q3: How do you prevent hallucinated causal claims in AI narration?
**Answer:**
"We implement a defense-in-depth approach:
1. **System Prompt Guardrails:** The model is strictly instructed: 'Explain only the deterministic simulation results supplied in context. Do not invent affected services or dependency paths. Cite only permitted evidence IDs.'
2. **Deterministic Evidence Manifest (`allowedEvidenceIds`):** The context assembler extracts evidence IDs directly from verified, retained database records.
3. **Strict AST & JSON Validation:** `validateSimulationNarrationOutput` checks every claim's citations against `allowedEvidenceIds`. If any citation is fabricated, duplicate, or belongs to a truncated record, the entire response is rejected.
4. **Atomic Rejection & Withholding:** On persistent validation rejection, `output_text` and `output_structured` remain `null` in the database. The user interface displays a clear notice that narration was withheld, preventing raw ungrounded hallucination from ever reaching users."

### Q4: How does the frontend handle the discovery race when simulation narration is generated asynchronously?
**Answer:**
"When a simulation completes, the frontend immediately retrieves the simulation response. If the worker is still assembling context or querying the Model Gateway, `ai_analysis_id` may initially be null.
We solve this with a **bounded discovery poller**:
1. When `simulationStatus === 'completed'` and `aiAnalysisId` is null, the panel initiates polling against `GET /api/v1/simulations/:id`.
2. It polls at a 2-second interval for up to `MAX_AI_DISCOVERY_ATTEMPTS = 5` (10 seconds total).
3. If discovered, it updates state and transitions immediately to loading the AI analysis.
4. If the budget elapses without discovery, it halts cleanly and displays an unavailable card with a 'Check again' button for user-triggered retries.
5. All timers are cleaned up immediately on unmount, preventing memory leaks or background network requests."

### Q5: How is multi-tenant isolation preserved across the simulation narration stack?
**Answer:**
"Tenant isolation is enforced across three distinct layers:
1. **Repository Layer:** Every query filters by `organizationId = $1` and uses tenant transaction helpers (`withTenant`).
2. **Evidence Association Verification:** `loadSimulationNarrationContext` verifies that the simulation run, scenario, and evidence rows belong to the authenticated organization. Any cross-tenant or mismatched records are rejected immediately.
3. **PostgreSQL Row-Level Security (RLS):** Both `evidence` and `ai_analyses` have `ENABLE & FORCE ROW LEVEL SECURITY` with tenant policies checking `organization_id = NULLIF(current_setting('app.current_org_id', true), '')::UUID`."
