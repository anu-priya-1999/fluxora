# Step 62 Impact Explanation Integration — Staff+ Interview CheatSheet

## 1. High-Level Pitch: What Did We Build?

"In Global Step 62, we completed the production integration of Fluxora's end-to-end AI impact-explanation pipeline. We connected our deterministic graph blast-radius engine to our LLM layer through a resilient pipeline:
1. Deterministic impact computation and evidence persistence in PostgreSQL.
2. Tenant-scoped context assembly and allowed evidence-ID manifest generation (Step 60).
3. Provider-independent Model Gateway with transient retries and secondary model fallback (Step 59).
4. Strict structured-output and evidence-grounding validation with a single bounded corrective retry (Step 61).
5. Durable, tenant-isolated persistence in `ai_analyses` (Migration 0028, RLS).
6. Authenticated REST API (`GET /api/v1/ai-analyses/:id`).
7. `AIExplanationPanel` in the Next.js Architecture Explorer with interactive evidence citations and model confidence indicators.

Crucially, we implemented an isolated failure boundary ensuring that AI provider outages, rate limits, or validation rejections never compromise or invalidate our deterministic blast-radius findings."

## 2. Key Architecture Questions & Answers

### Q1: Why not run LLM generation inside the same transaction as deterministic impact analysis?
**Answer:**
"Running third-party LLM calls inside an active database transaction is an anti-pattern:
1. **Connection Exhaustion:** LLM calls take 500ms to 20 seconds. Holding open a PostgreSQL connection throughout the network call quickly exhausts the pool.
2. **Blast-Radius Coupling:** If the LLM call times out or encounters a 429 rate limit, the entire transaction rolls back, destroying the deterministic impact findings that took CPU cycles to compute.
3. **Core Invariant Violation:** Our core thesis is that the deterministic engine is authoritative. By executing AI narration downstream in an isolated try/catch block, deterministic findings are committed and durable before the LLM is even called."

### Q2: How did you design the database persistence model for AI analyses?
**Answer:**
"We created a dedicated `ai_analyses` table (Migration 0028) rather than tacking columns onto `impact_analyses`.
1. **Polymorphic Subject:** `subject_type` and `subject_id` allow this table to serve PR impact analyses (Step 62), failure simulations (Step 63), and chat queries (Step 64).
2. **Tenant Isolation:** Enforced via `ENABLE & FORCE ROW LEVEL SECURITY` with `organization_id = NULLIF(current_setting('app.current_org_id', true), '')::UUID`.
3. **Idempotency:** A unique constraint `(organization_id, subject_type, subject_id)` ensures that repeated job deliveries update the record in-place rather than creating duplicate rows.
4. **Separation of Lifecycle from Validation:** `status` tracks operational lifecycle (`pending`, `completed`, `rejected`, `failed`), while `validation_status` tracks schema and grounding validation (`passed`, `rejected`).
5. **Withholding Invalid Outputs:** On rejection or failure, `output_text` and `output_structured` remain `null`, persisting only sanitized diagnostics."

### Q3: How do you handle failure isolation in the worker?
**Answer:**
"In `apps/workers/src/pull-request/impact-handler.ts`, we compute and persist the deterministic impact analysis first. Then we invoke `explainImpact` inside a dedicated `try/catch` block.
If the AI orchestrator throws or returns a failure/rejection:
- The error is logged and recorded in `ai_analyses`.
- The worker does NOT throw or fail the job.
- The deterministic impact analysis job completes with status `completed`.
- We avoid unnecessary exponential queue retries that would repeatedly re-execute expensive graph traversals."

### Q4: How does the frontend handle the asynchronous nature of AI generation?
**Answer:**
"The UI handles this gracefully across distinct states:
1. When impact analysis is running, the panel shows `Waiting for deterministic impact analysis to complete...`
2. When the impact analysis completes, the API returns `ai_analysis_id` and `ai_analysis_status: 'pending'`. The UI enters an active polling state with a gentle spinner.
3. When `completed`, it displays the summary, grounded claims, clickable citation chips (`EvidenceCitationList`), and the model confidence badge.
4. If validation was `rejected`, it displays an informative amber banner explaining that narration was withheld due to ungrounded claims, assuring the user that the deterministic graph findings below are fully valid.
5. If the provider failed, it shows a neutral card noting AI unavailability."

### Q5: How do you track token usage and costs?
**Answer:**
"Our Model Gateway computes microdollar token costs based on model-specific pricing registries (e.g. Claude 3.5 Sonnet at $2.00/MTok input, $10.00/MTok output).
In the orchestrator, we aggregate input tokens, output tokens, costs, and latencies across **both** the initial attempt and any corrective retry attempt. We do not count only the final response, ensuring accurate accounting for customer billing and cost observability."

## 3. Key Trade-offs & Decisions

| Decision | Alternative Considered | Rationale |
| --- | --- | --- |
| Dedicated `ai_analyses` table | Columns in `impact_analyses` | Reusable across simulations/chat, decouples schema lifecycles, cleaner RLS |
| Worker failure isolation | Fail job on AI error | Preserves deterministic findings; prevents expensive traversal retry loops |
| Strict whole-response rejection | Strip invalid claims | Preserves narrative coherence; prevents silent prompt degradation/hallucinations |
| Decoupled API endpoints | Inline AI object in impact API | Keeps payload light; allows independent caching and lazy loading |
