# Fluxora Step 8 — Interview Cheat Sheet

## 60-second answer

> "Fluxora is a pnpm monorepo. I implemented CI with GitHub Actions for pull requests and pushes to main. The workflow installs the frozen lockfile and runs lint, TypeScript type checking, tests, and the production build. For delivery, the Next.js frontend runs on Vercel and the Node API runs separately on Render. The API uses Node's native TypeScript strip-types runtime, so it has no artificial build script; the Render build instead installs dependencies, runs database migrations, and typechecks the API. The API reads the platform-provided PORT, binds to 0.0.0.0, and exposes an unauthenticated /healthz endpoint that runs SELECT 1 against PostgreSQL. Production secrets are injected through the hosting environment. I manually verified the hosted authentication flow and the hosted API health endpoint. The first Render deployment failed because CLERK_SECRET_KEY was missing, which demonstrated why CI correctness and runtime configuration correctness are separate concerns."

## Ten likely interviewer questions

### 1. Why GitHub Actions?

Because the source already lives in GitHub, and workflow configuration can be version controlled next to the code.

### 2. Why frozen lockfile?

To make CI install the committed dependency graph instead of silently changing dependency resolution.

### 3. Why separate Vercel and Render?

Frontend and backend have different responsibilities and deployment/scaling characteristics.

### 4. Why no API build script?

The API directly executes erasable TypeScript through Node's strip-types runtime.

### 5. Why `0.0.0.0`?

The hosted platform must be able to reach the server through its network interface.

### 6. Why `PORT`?

The hosting platform controls the externally allocated port.

### 7. Why hosted PostgreSQL?

`localhost:5432` on the developer machine is not reachable as a production database endpoint.

### 8. Why `/healthz`?

The platform needs an unauthenticated readiness signal; checking the database catches dependency failures.

### 9. Why runtime env vars?

Secrets should be injected at runtime and kept out of source control.

### 10. Is this complete production CI/CD?

No. It is the working foundation. Staging promotion, automated E2E gates, worker deployment, smoke-test automation, and rollback hardening come later.
