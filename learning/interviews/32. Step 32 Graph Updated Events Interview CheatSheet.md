# Step 32 Graph Updated Events Interview CheatSheet

## Executive Summary & Quick Answers

- **What does Step 32 do?**
  Step 32 implements deterministic graph diff computation and transactional `graph.updated` event emission. When graph state changes between analysis runs, it calculates exact differences (added, removed, changed nodes and edges) and emits a strongly typed event to the outbox for real-time WebSocket broadcast.

- **Why compute the diff in memory instead of relying on database triggers?**
  In-memory diffing via `computeGraphDiff(previous, current)` is 100% pure, unit-testable, and deterministic. It compares canonical node IDs and composite edge keys with normalized JSON metadata without relying on non-deterministic SQL row ordering or trigger side-effects.

- **How is the transactional outbox pattern used?**
  Graph nodes, edges, evidence, and the `graph.updated` outbox event are inserted in the exact same `withTenant` PostgreSQL transaction (`persistGraphBuild`). If any graph write fails, the entire transaction rolls back—preventing phantom event emission. Upon commit, PostgreSQL's `fluxora_notify_event()` trigger sends a `NOTIFY fluxora_events` payload.

- **How are WebSocket subscribers notified?**
  `apps/api/src/ws/server.ts` uses `createEventListener` to `LISTEN` to `fluxora_events`. When a notification arrives, it parses the event envelope and pushes the message to active WebSocket connections whose authenticated `organizationId` matches the event's `organizationId`.

- **How is idempotency preserved?**
  The event payload and database row use a deterministic idempotency key format: `graph:updated:<analysisRunId>:<previousAnalysisRunId|initial>`. Re-running the builder on the same analysis run reuses this key, ensuring the operation is idempotent.

- **How is tenant isolation maintained?**
  State resolution queries set `app.current_organization_id` inside `withTenant` and include defensive SQL clauses (`AND fluxora_analysis_run_in_current_tenant(analysis_run_id)`). Comparing or publishing graph state across tenants is impossible.

- **Why is there no direct coupling between graph persistence and React Flow?**
  Domain and worker layers know only about graph models and events. React Flow and visual layout belong strictly to the frontend presentation layer (Phase 5). This keeps the deterministic core decoupled from UI concerns.

## In-Depth Interview Questions & Answers

### 1. How does `computeGraphDiff` detect that a node or edge has "changed"?
**Answer:**
- **Nodes**: A node with identical canonical `id` in both versions is considered changed if any of `nodeType`, `name`, `path`, `confidence`, or `metadata` differ.
- **Edges**: An edge with matching composite key `(sourceNodeId, targetNodeId, edgeType)` is considered changed if `confidence`, `provenance`, `canonicalId`, or `metadata` differ.
- **Canonical Serialization**: To prevent false positives caused by arbitrary JSON key ordering, metadata objects are serialized recursively using `canonicalStringify`, guaranteeing deterministic byte-for-byte comparisons.

### 2. What happens if a graph transaction fails halfway through?
**Answer:**
Because all graph mutations (nodes, edges, evidence) and the outbox event insertion (`createEventClient.insert`) occur within the same `withTenant` database transaction, any unhandled error triggers an immediate `ROLLBACK`. The event row is never committed, and PostgreSQL never fires the `fluxora_notify_event()` trigger. Downstream consumers will never observe an event for a failed graph mutation.

### 3. How does Step 32 prevent cross-tenant graph leakage?
**Answer:**
1. All queries executed to resolve the current or previous graph state (`getGraphStateForAnalysisRunTx`) run within `withTenant(pool, organizationId, ...)`, activating PostgreSQL Row-Level Security.
2. In addition to RLS, queries include explicit defensive SQL filters `AND fluxora_analysis_run_in_current_tenant(analysis_run_id)`.
3. The WebSocket dispatcher only broadcasts the event envelope to client connections that have successfully authenticated under the matching `organizationId`.

### 4. What is the scope boundary of Step 32 vs. Step 33 and Phase 5?
**Answer:**
- **Step 32**: Pure in-memory graph diff calculation, outbox event persistence, and WebSocket push.
- **Step 33**: End-to-end golden repository graph pipeline verification.
- **Phase 5**: Interactive web UI canvas, React Flow rendering, graph visualization layouts, and user interactions.
