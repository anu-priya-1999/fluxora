# Step 49: Clickable Evidence Citation UI Interview CheatSheet

## Core Narrative & Architectural Philosophy

**Q: What is the core problem that Step 49 solves in Fluxora?**
- **The "Unclickable Conclusion" Anti-Pattern**: In many software analysis platforms, impact or architecture claims are shown as static text (e.g. "PaymentService is affected by PR #42"). When an engineer asks "Where in the code did you see this?", they have to manually search their codebase or guess the file and lines.
- **Fluxora's Traceability Thesis**: In Fluxora, every graph edge and blast-radius finding has verified, append-only provenance stored in PostgreSQL via `EvidenceWriter` (Step 48). Step 49 turns this evidence into a real, clickable `EvidenceCitation` experience in the UI:
  1. A conclusion surfaces an inline citation chip or expanded card.
  2. Clicking the citation navigates to the exact lines in GitHub (`#L10–L25`) via a validated permalink.
  3. If metadata is missing or unverified, the UI honestly explains why navigation is unavailable rather than fabricating URLs or line numbers.

## Technical Highlights & Staff-Level Q&A

### 1. Permalinks vs. Mutable Branch URLs
- **Q**: "Why do you prefer commit SHAs over branch names when constructing GitHub permalinks?"
- **Answer**:
  - Branch refs like `main` or `feature-branch` are mutable: the code at line 42 today might be completely different tomorrow after another commit is merged.
  - An evidence citation is an assertion about the code *at the time of analysis*.
  - By pinning permalinks to immutable commit SHAs (`/blob/{commitSha}/{filePath}#L{start}-L{end}`), the link remains a stable, permanent proof of the analysis run forever. We only fall back to branch refs when an immutable SHA is strictly unavailable.

### 2. Path Traversal & Security in Evidence Links
- **Q**: "Since evidence comes from ingested repositories, could a malicious repository craft paths like `../../etc/passwd` or `javascript:...` to trigger XSS or malicious navigation?"
- **Answer**:
  - Yes, repository contents are untrusted input.
  - In `buildSourcePermalink` (`evidence-citation-data.ts`), we enforce strict validation:
    1. Paths starting with `/`, `\\`, or containing `..` are immediately rejected with `"Invalid or unsafe file path"`.
    2. URI schemes (`javascript:`, `data:`, `file:`) and illegal characters (`<`, `>`, `"`, `|`, `?`, `*`, `(`, `)`) are rejected.
    3. External anchor tags use `rel="noopener noreferrer"` and `target="_blank"`.
    4. When validation fails, the UI safely renders an unclickable citation with an explanation tooltip, guaranteeing zero browser injection vulnerabilities.

### 3. Non-Fabrication Invariant in Frontend UX
- **Q**: "What if the backend returns an impact finding where line numbers are not available (e.g. whole-file dependency or multi-hop finding)?"
- **Answer**:
  - We strictly obey the **Non-Fabrication Invariant**:
    - We NEVER render fake line numbers like `L0` or `L1`.
    - `formatLineRange` returns `null` unless positive integers exist (`line_start > 0`).
    - The citation displays the file path without a line badge.
    - If direct permalinks cannot be securely generated, the component displays an accessible `"Source link unavailable"` badge with an honest explanation tooltip (`title="..."`).
    - The valid finding is still shown; we communicate "evidence available, source link unavailable" instead of hiding valid findings or fabricating fake links.

### 4. React 19 Prop Discipline: `gitRef` vs `ref`
- **Q**: "Why did you name the git reference prop `gitRef` instead of `ref` in your React components?"
- **Answer**:
  - In React 19, `ref` is a reserved component keyword. Modern ESLint rules (`react-hooks/refs`) analyze any component property named `ref` as a React `RefObject` and prohibit reading or passing it during render.
  - Naming the domain prop `gitRef` cleanly avoids this compiler/linter collision while maintaining domain clarity (distinguishing Git refs from React DOM element refs).

### 5. Multi-Tenant API Design for Evidence Readback
- **Q**: "Did you need to add a new API endpoint for Step 49?"
- **Answer**:
  - No separate endpoint was needed. Adding a dedicated endpoint would have introduced extra network round-trips for every finding.
  - Instead, we extended the existing `GET /api/v1/impact-analyses/:id` route to include associated evidence records (`impactAnalysis.evidence`) formatted as `GraphQueryResponseEvidence[]`.
  - The API joins evidence records via `@fluxora/db`'s `listImpactFindingEvidence` scoped strictly to `tenantContext.organizationId`, preserving PostgreSQL RLS tenant isolation.
