# Staff Engineering Interview Guide: Step 55 — Simulation HTTP APIs

This interview guide focuses on API system design, distributed security, multi-tenant boundary enforcement, and RESTful contract modeling for deterministic simulation engines.

---

### Q1: Why does `POST /scenarios/:id/run` execute synchronously and return `200 OK` instead of returning `202 Accepted` with a background job queue?

**Answer:**
Architectural truthfulness is paramount in system design:
1. **Computational Reality**: In-memory deterministic graph simulation (Step 54) completes within single-digit milliseconds even on graphs with thousands of nodes and edges, because it is bounded by $O(K \cdot (|V| + |E|))$ and avoids external I/O during propagation.
2. **Avoiding Speculative Architecture**: Returning `202 Accepted` with a `job_id` or polling status endpoint when no asynchronous background worker or message queue is provisioned creates fake architectural promises. It forces clients to write polling loops, increases Redis/queue overhead, and complicates state synchronization unnecessarily.
3. **Simplicity and Atomicity**: Synchronous execution allows the simulation propagation, result persistence, and `simulation_state` evidence writing to occur atomically inside a single tenant-scoped PostgreSQL transaction (`withTenant`). The client receives the complete results, causal paths, and convergence metrics immediately.
4. **Extensibility**: If future simulations incorporate heavy cross-monorepo static analysis or large-scale monte carlo parameter sweeps exceeding the HTTP gateway timeout budget (e.g. >15 seconds), the endpoint can cleanly transition to asynchronous worker delegation without altering the scenario domain model.

### Q2: Why do cross-tenant lookups on scenarios, simulations, and results return `404 Not Found` rather than `403 Forbidden`?

**Answer:**
Returning `403 Forbidden` leaks resource existence:
- If `GET /simulations/uuid-1` returns `403 Forbidden` when requested by Tenant B, an attacker knows that `uuid-1` exists in the system and belongs to another tenant. This enables resource enumeration, timing attacks, and identifier harvesting.
- Returning `404 Not Found` treats foreign resources as non-existent within the caller's tenant boundary:
  ```sql
  SELECT s.id FROM simulations s
  JOIN scenarios sc ON sc.id = s.scenario_id
  WHERE s.id = $1::uuid AND sc.organization_id = $2::uuid;
  ```
- If the row does not match the join on the authenticated caller's `organization_id`, the query returns zero rows, and the API uniformly responds with:
  ```json
  { "error": { "code": "not_found", "message": "Simulation not found." } }
  ```
This guarantees zero information leakage across tenant boundaries.

### Q3: Why does `POST /scenarios` reject `organization_id` in the request body with a `400` error instead of silently ignoring it or validating permissions?

**Answer:**
Strict fail-fast validation prevents spoofing and security confusion:
1. **Never Trust Caller Assertions**: Authorization must be strictly derived from verified identity (Clerk JWT $\to$ verified GitHub account $\to$ database-resolved organization membership).
2. **Preventing Ambiguity and Bugs**: If the API accepted `organization_id` in the JSON payload, developers might assume they can act on behalf of another organization, or multi-tenant frontends might accidentally pass stale organization IDs from cached local storage.
3. **Fail-Fast Security Invariant**: By throwing `SimulationRequestValidationError("Tenant organization cannot be specified in the request body.", "invalid_request", 400)`, any client sending tenant overrides is caught immediately in testing rather than proceeding with mismatched expectations.

### Q4: Why must the scenario target node be validated against the specific `analysis_run_id` snapshot rather than just the repository?

**Answer:**
Software architectures change over time. Repositories have many snapshots:
1. **Graph Drift**: Node identifiers (`graph_nodes.id`) belong to a specific `analysis_run_id` representing an exact commit SHA and AST snapshot. A microservice or module that existed in commit $C_1$ might have been renamed or deleted in commit $C_2$.
2. **Snapshot Contamination**: If a scenario allowed a target node from analysis run $A_1$ to run against a graph snapshot from analysis run $A_2$, the simulation engine would either fail to seed the target node or propagate failures across non-existent edges.
3. **Enforced Boundary**: The endpoint verifies:
   ```sql
   SELECT gn.id
   FROM graph_nodes gn
   JOIN analysis_runs ar ON ar.id = gn.analysis_run_id
   JOIN repository_snapshots rs ON rs.id = ar.snapshot_id
   JOIN repositories r ON r.id = rs.repository_id
   WHERE gn.id = $1::uuid AND ar.id = $2::uuid AND r.organization_id = $3::uuid;
   ```
This guarantees that scenario definitions are mathematically coupled to an immutable architectural snapshot.

### Q5: How do the simulation endpoints preserve causal provenance without losing fidelity or degrading performance?

**Answer:**
The API serializes complete, structured causal paths rather than lossy summaries:
1. **Structured Steps**: Each node's `propagation_path` is serialized as an array of `SimulationCausalStep` objects:
   ```typescript
   export interface SimulationCausalStep {
     nodeId: string;
     edgeId?: string | null;
     ruleId: string;
     ruleVersion: string;
     previousState: SimulationResultState;
     resultingState: SimulationResultState;
     assumptions: readonly string[];
     confidence: number;
     capped?: boolean;
   }
   ```
2. **Deterministic Ordering**: `GET /simulations/:id/results` orders rows deterministically by `created_at ASC, id ASC`.
3. **Evidence Invariant**: Each persisted simulation result is linked to `simulation_state` evidence via `EvidenceWriter`, enabling the frontend to highlight both the causal propagation chain on the graph canvas and link directly to the underlying code symbols and files.

### Q6: How does the API handle qualitative latency vs numerical `latency_ms` parameters?

**Answer:**
This reflects the separation between domain parameterization and deterministic rule semantics:
1. **Parameter Extensibility**: The API accepts generic scenario parameters (e.g. `parameters: { "latency_ms": 500 }`) and persists them as JSONB in PostgreSQL.
2. **Qualitative Simulation Core**: The Step 54 simulation engine operates strictly on discrete qualitative states:
   - `failure_type === "latency"` seeds the target node state as `"degraded"` (whereas `"unavailable"` seeds `"failed"`).
   - Downstream propagation evaluates qualitative rules (e.g., synchronous dependency calls degrade the caller; datastore latency raises read timeout assumptions).
3. **Invariance**: The simulation core avoids ungrounded numerical math (such as fake millisecond queueing calculations) while preserving the client's experiment parameters for future historical comparison or Phase 10 telemetry validation.

### Q7: How does the system handle idempotency between HTTP requests and result persistence?

**Answer:**
There is a critical architectural distinction between request-level idempotency and result persistence idempotency:
1. **Request-Level Execution**: Each accepted HTTP call to `POST /scenarios/:id/run` intentionally initializes and runs a distinct `Simulation` execution record (`simulations.id`). This preserves full historical observability across repeated what-if trials on a scenario over time, without artificial deduplication.
2. **Result Persistence Idempotency**: Within any given simulation run, persistence is strictly idempotent at the database layer. Table `simulation_results` defines a unique constraint:
   ```sql
   CONSTRAINT uq_simulation_results_node UNIQUE (simulation_id, node_id)
   ```
   Step 54's `executeSimulation` inserts results via an atomic upsert:
   ```sql
   INSERT INTO simulation_results (...)
   VALUES (...)
   ON CONFLICT (simulation_id, node_id) DO UPDATE
     SET resulting_state = EXCLUDED.resulting_state,
         propagation_path = EXCLUDED.propagation_path,
         rule_applied = EXCLUDED.rule_applied,
         assumptions = EXCLUDED.assumptions,
         confidence = EXCLUDED.confidence;
   ```
3. **Clean Lifecycle**: A simulation record transitions `pending -> running -> completed` within the transaction. If execution fails, it transitions to `failed` without leaving orphan result rows. Retrying persistence for a simulation updates in-place without corrupting evidence trails.

### Q8: What error envelope and status code strategy does the API use, and why?

**Answer:**
Fluxora adopts a standardized, machine-readable error envelope:
```json
{
  "error": {
    "code": "invalid_request",
    "message": "Human readable explanation.",
    "details": { ... }
  }
}
```
Specific status codes reflect precise architectural boundary violations:
- `400 invalid_request`: Missing required payload fields, invalid UUID format, or forbidden tenant override.
- `400 unsupported_failure_type`: Unsupported failure types (`capacity`, `removal`) outside the MVP boundary.
- `401 invalid_session`: Missing or expired Bearer JWT.
- `403 github_account_required`: Authenticated identity lacking connected GitHub account.
- `404 not_found`: Missing or cross-tenant resource (scenario, simulation, or results).
- `405 method_not_allowed`: Registered path accessed with wrong HTTP verb (e.g. `PUT /scenarios`).
- `413 payload_too_large`: Body exceeds the 16KB safeguard.
- `415 unsupported_media_type`: Non-JSON `Content-Type`.
- `422 simulation_convergence_failure`: Convergence guard tripped in cyclic graphs.
- `500 simulation_execution_failed` / `internal_error`: Unexpected database or execution failures, with internal diagnostics logged server-side and redacted from client output.
