# Step 51: Analysis Coverage View Interview CheatSheet

## Core Narrative & Architectural Philosophy

**Q: What is the goal of Step 51 in the Fluxora architecture?**
- **The Core Problem**: In static analysis and AI-assisted code tools, systems typically pretend they have analyzed 100% of the codebase, or they fail silently on dynamic code, complex exports, or unparsed files. Engineers are left wondering: *"Can I trust this dependency graph? Did it miss anything?"*
- **The Fluxora Solution (Step 51)**: We surface an honest, deterministic **Analysis Coverage View** answering: *"How much of the analyzed surface has verified evidence, and where are the gaps?"*
  - It clearly distinguishes analyzed, evidence-backed, missing-evidence, and unsupported/unresolved files.
  - It makes gaps immediately actionable by allowing engineers to inspect uncovered relationships directly on the interactive graph canvas.

## Technical Highlights & Staff-Level Q&A

### 1. How is Coverage Mathematically Defined in Fluxora?
- **Q**: "What are your exact numerator and denominator for coverage?"
- **Answer**:
  $$\text{Coverage} = \frac{\text{Evidence-Backed Conclusions}}{\text{Analyzed Conclusions in Scope}}$$
  - **Graph Edge Surface**:
    - **Denominator**: Total graph edges in the active analysis slice (`edges.length`).
    - **Numerator**: Edges with verified evidence (`typeof edge.evidence_id === "string" && edge.evidence_id.length > 0`).
  - **PR Impact Surface**:
    - **Denominator**: Total impact findings in the PR blast radius (`direct + downstream + apis + events + services`).
    - **Numerator**: Findings with verified evidence (`finding.evidence_ids.length > 0 || finding.evidence_id != null`).
  - **Why not combine them into one number?** Combining graph edge counts (thousands of AST imports) with impact finding counts (dozens of blast-radius nodes) creates an uninterpretable, mathematically flawed metric. Fluxora keeps them strictly partitioned.

### 2. Why Not Calculate Repository-Wide Coverage from the Raw Database?
- **Q**: "Why didn't you have the frontend query Postgres for all evidence records across the entire repository to show a global 100% coverage gauge?"
- **Answer**:
  - **Security & Tenancy**: The browser client must never directly query PostgreSQL or bypass API auth boundaries.
  - **Performance & Bounded Traversal**: Loading millions of evidence records into client memory causes OOM crashes and browser freezing on large monorepos.
  - **Honest Scoping**: The Architecture Explorer displays a bounded-depth graph slice (`analysisRunId`). Presenting a global percentage that doesn't correspond to the visible graph would be misleading. The coverage metric reflects the exact analysis scope loaded.

### 3. How Does Step 51 Distinguish Confidence from Coverage?
- **Q**: "If an edge has 95% confidence, isn't it basically covered?"
- **Answer**:
  - **Absolutely not**. In Fluxora, **Confidence** and **Coverage** are orthogonal:
    - **Confidence** measures *statistical or heuristic strength* ($0.0 \dots 1.0$).
    - **Coverage** measures *verified code provenance* (does an `EvidenceRecord` exist linking this conclusion to a file path and line number?).
  - An AI hypothesis edge could have 95% confidence from a prompt, but if there is no code evidence row in Postgres, it is **uncovered**.
  - Conversely, an edge with 40% confidence (e.g. a 4-hop traversal) is **covered** if it has an audit trail of AST citations. We never use confidence as a substitute for evidence.

### 4. How Does Step 51 Handle Edge Cases (Empty, Error, Stale)?
- **Q**: "What does your UI do if a graph query returns 0 edges, or fails to load?"
- **Answer**:
  - We handle 10 distinct states cleanly:
    1. **Zero edges in scope**: Displays `N/A` with text `"0 analyzed graph edges in scope"`, rather than an erroneous `"0%"` alert.
    2. **Failed fetch / Error**: Displays a clear error banner and preserves previous graph data if refreshing.
    3. **Background refresh (Stale)**: Displays an active `"Refreshing..."` badge while keeping existing metrics visible.
    4. **100% coverage**: Displays a positive emerald badge and clean `"All analyzed conclusions have verified evidence"` confirmation.
    5. **Partial / Zero coverage**: Displays exact percentages, missing counts, and lists uncovered items.

### 5. Multi-Channel Accessibility Compliance (WCAG 2.1 AA)
- **Q**: "How do you ensure coverage is accessible without relying solely on green/red colors?"
- **Answer**:
  - Every visual indicator provides text labels and numeric counts (`Covered: 842 | Missing: 31 | Total: 873`, `96.5%`).
  - Progress bars implement standard ARIA roles (`role="progressbar"`, `aria-valuenow`, `aria-valuemin="0"`, `aria-valuemax="100"`).
  - Uncovered items are labeled with explicit `"Missing Evidence"` badges, not just red borders.
