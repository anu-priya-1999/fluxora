# Step 46: Change Mode Overlay Interview CheatSheet

## Core Narrative & Problem Statement

Global Step 46 delivers the frontend visualization layer for Pull Request Change-Impact Analysis within the Fluxora Architecture Explorer. Rather than viewing impacted files as an isolated diff or static table, developers and reviewers can see the deterministic ripple effect of code changes overlaid directly on top of the system's live dependency architecture.

---

## 12 Key Technical Questions & Answers

### 1. Why overlay the existing graph instead of creating a second graph?
- **Cognitive Continuity & Spatial Memory**: Software engineers navigate architectures using spatial orientation—knowing where authentication relates to the gateway, data pipelines, and database models. Generating a separate "impact-only" graph breaks spatial continuity and forces the user to mentally reconcile two disconnected topologies.
- **Structural Context**: Blast radius is only meaningful relative to unaffected neighbors. Seeing that a utility function impact halts before reaching customer-facing API routes provides immediate safety context that an isolated subgraph obscures.
- **Single Source of Truth**: The graph topology is dictated exclusively by `/graph/query`. An overlay guarantees that impact visualization cannot drift from the canonical architecture.

### 2. Why not recompute impact on the client?
- **Deterministic Core Invariant**: Traversal, symbol resolution, and cycle handling require the full AST metadata and PostgreSQL graph edge database. Recomputing impact in the browser would require transmitting the entire repository and dependency database to the client.
- **Performance & Scalability**: Traversing large dependency graphs with thousands of nodes in JavaScript can block the UI main thread.
- **Auditability & Provenance**: The server's persisted `impact_analyses` record links every finding to durable `Evidence` rows via `EvidenceWriter`. A client calculation would lack verifiable provenance.

### 3. How do you map persisted findings to graph nodes?
- **Stable Canonical Node IDs**: We map findings strictly by `finding.node_id === node.id`.
- **Zero Fuzzy Matching**: We never match nodes by display labels, file paths, array positions, or React keys.
- **Normalized Sets for $O(1)$ Lookups**: During response normalization, node IDs are placed into `Set<string>` collections (`directNodeIds`, `downstreamNodeIds`, `affectedApiNodeIds`, `affectedEventNodeIds`) and `Map<string, number>` tables for hop distances and confidence scores.

### 4. How do you represent direct vs. downstream impact?
- **Direct Impacts (depth = 0)**:
  - Solid crimson border (`#dc2626`), glowing 3px accent ring, and a prominent red `Direct Change` badge.
  - Represents the root cause—files and symbols directly modified in the PR diff.
- **Downstream Impacts (depth >= 1)**:
  - Chromatic amber hierarchy where border saturation softens with distance (`#d97706` for hop 1, `#f59e0b` for hop 2, `#fbbf24` for hop 3+).
  - Explicit badge displaying propagation distance: `Downstream (hop N)`.
- **Unaffected Nodes**:
  - Visually de-emphasized with reduced opacity (`0.45`) and subtle desaturation (`grayscale(30%)`), allowing the blast radius to pop while preserving full interactivity.

### 5. How does hop distance affect confidence?
- **Geometric Confidence Decay**: As impact propagates transitively across graph edges, confidence decays geometrically ($C = 1.0 \times 0.9^{\text{hop}}$).
- **Visualizing Uncertainty**: When confidence drops below 70% ($< 0.70$), the node border transitions from solid to dashed (`2px dashed <color>`) and displays a `(low)` indicator. This ensures reviewers are explicitly informed when transitive impact carries lower certainty.

### 6. How does Change Mode interact with GraphFilters?
- **Independent Filtering**: Active filters (filtering by node type, edge type, confidence threshold, or depth) remain 100% operational.
- **State Preservation**: Filtering a node out of the visible canvas does NOT remove it from `NormalizedChangeModeState`. If the user resets filters, the node re-appears with its change-mode styling intact.
- **Slice Indicators**: The UI surfaces an indicator badge showing how many impacted nodes are currently visible in the active slice versus total impacted nodes.

### 7. How does it interact with Level-of-Detail (LOD)?
- **Tier Consistency**: LOD clustering (System tier vs. Module tier vs. Detail tier based on viewport zoom) continues to work smoothly.
- **No Global Disabling**: Change Mode never disables LOD globally, which would cause browser rendering crashes on 10,000+ node graphs.
- **Zoom Invariance**: Visual styling, badges, and inspector data survive all zoom transitions and rerenders.

### 8. What happens if an impacted node is not loaded in the current graph slice?
- **Zero Node Fabrication**: The frontend never synthesizes fake nodes or fabricates synthetic clusters.
- **Metric Tracking**: `computeImpactSliceMetrics` compares `state.directNodeIds` and `state.downstreamNodeIds` against `graphNodes.map(n => n.id)` to compute visible vs. hidden counts.
- **User Awareness**: The LOD badge explicitly warns `• X/Y impacted visible`, informing the user that more impacted nodes exist beyond the loaded query slice.

### 9. How do you avoid rerendering the whole graph unnecessarily?
- **Single-Pass Normalization**: The raw API payload is normalized once into flat Sets and Maps when fetched, not on every animation frame or render cycle.
- **Targeted Property Injection**: Only nodes with changed impact properties update their `FluxoraNodeData`; React Flow's memoized node wrappers prevent re-drawing unaffected canvas paths.
- **Separation of Controls**: The `ChangeModeBar` lives outside the React Flow canvas hierarchy, allowing user input and drawer toggles without invalidating canvas layout.

### 10. How does evidence remain trustworthy?
- **Immutable Server Provenance**: Every finding returned by `GET /api/v1/impact-analyses/:id` contains verified `evidence_ids` generated during Step 44 persistence.
- **Audit Trail in Inspector**: Selecting an impacted node exposes its exact evidence IDs in the `NodeInspectorPanel`, linking the visual node to static AST coordinates and diff hunks.
- **No Client Mutation**: The frontend treats evidence IDs as strictly read-only arrays.

### 11. Why is the API result authoritative?
- **Single Source of Truth**: The impact analysis was computed by the Step 43 deterministic engine and persisted in PostgreSQL under strict multi-tenant isolation.
- **No Speculative Client Updates**: Even if the user edits code locally, the visualization reflects the durable server-persisted state until a new analysis is triggered and saved.
- **Multi-Tenant Security**: Bearer JWT authentication and PostgreSQL RLS guarantee that users only ever view impact analyses belonging to their own organization.

### 12. How would you extend this later for a full impact report?
- **Dedicated Report Route**: Create `/repositories/:id/pull-requests/:prId/impact` reusing `NormalizedChangeModeState` and `normalizeImpactAnalysisResponse`.
- **Side-by-Side Diff & Graph View**: Embed the GraphCanvas alongside a Monaco code diff editor, highlighting changed symbol declarations in the editor when clicking a direct node.
- **Historical Analysis Diffing**: Allow comparing two impact analyses for the same PR across different commits to visualize blast-radius reduction.

## Cheat Sheet Summary Table

| Concern | Implementation Choice | Architectural Invariant |
| --- | --- | --- |
| **Visual Architecture** | Interactive overlay over `/graph/query` | Single unified architecture mental model |
| **Data Source** | `GET /api/v1/impact-analyses/:id` | Read-only, server-authoritative, zero client traversal |
| **Node Mapping** | Exact canonical UUID matching (`finding.node_id === node.id`) | Zero fuzzy or heuristic node identification |
| **Direct Impact** | Crimson border (`#dc2626`), ring, `Direct Change` badge | Primary visual emphasis on root cause diff |
| **Downstream Impact** | Chromatic amber fade (`#d97706` $\to$ `#fbbf24`), hop badge | Clear transitive risk gradient |
| **Low Confidence** | Dashed border, explicit `(low)` tag ($< 0.70$) | Uncertainty is explicitly communicated |
| **LOD & Filters** | Full coexistence; slice metric counter | Zero LOD disabling; preserved state |
| **Selection Priority** | Selection styles (`#2563eb`) strictly override overlay styles | Interactive exploration continuity |
| **Security Boundary** | Bearer JWT + PostgreSQL RLS (`withTenant`) | Tenant isolation enforced; cross-tenant returns 404 |
