# Step 18 — Language and Framework Detection Interview Cheat Sheet

## 1. 30-Second Elevator Pitch

> "Step 18 implements Fluxora's deterministic Language and Framework Detector. Given an immutable repository snapshot, it statically analyzes file trees and configuration manifests (`package.json`, `tsconfig.json`, `next.config.mjs`, lockfiles) to identify all languages present (TypeScript, JavaScript, JSON, CSS, HTML, Markdown) and frameworks/tooling (Next.js, React, Node.js ecosystem). It strictly obeys Fluxora's core invariant: all classifications and evidence provenance are deterministic and explainable without using an LLM or executing untrusted repository code."

---

## 2. Key Architecture Questions & Answers

### Q: Why is language and framework detection deterministic instead of using an LLM?
**A:** In Fluxora, the code intelligence core is deterministic, while LLMs operate solely at the probabilistic AI edge to explain verified facts (`AGENTS.md` and `docs/architecture/03-architecture-principles.md`). Using an LLM for stack detection would introduce non-determinism, hallucinations, token costs, and latency into the ingestion pipeline. Static file extensions and package manifests provide 100% reproducible ground truth.

### Q: How are generated files, caches, and dependency directories handled?
**A:** The detector enforces an exclusion filter (`DEFAULT_IGNORED_DIRECTORIES`) ignoring `node_modules`, `.git`, `.next`, `build`, `dist`, `out`, `.turbo`, `.cache`, and `coverage`. Files inside these directories are excluded from language counting, framework inference, and recognized file summaries.

### Q: How does framework detection avoid false positives?
**A:** The detector never infers a framework merely from a file name or path (such as `docs/next-guide.md` or `src/react-helpers.ts`). Instead, it requires concrete manifest or configuration evidence:
- Package manifest dependencies (`package.json` `dependencies` / `devDependencies`)
- Canonical configuration files (`next.config.mjs`, `next.config.js`)
- Structural patterns matched in combination with package manifests (e.g., App Router directory structure).

### Q: How is evidence recorded for detection decisions?
**A:** The result contains structured `RepositoryDetectorEvidence` entries grouping reasons by target and category:
- `target`: e.g. `Next.js`
- `category`: `"framework"`
- `reasons`: `["config: next.config.mjs", "directory: app router structure", "package.json: dependency 'next'"]`
This gives downstream stages and UI explanations clear provenance.

### Q: What were the detection results against the Step 17 golden fixture?
**A:** The detector correctly classified `shadcn-ui/taxonomy`:
- Primary language: `TypeScript`
- Languages: `["CSS", "HTML", "JSON", "JavaScript", "Markdown", "TypeScript"]`
- Primary framework: `Next.js`
- Frameworks: `["Next.js", "Node.js", "React"]`
- Evidence captured Next.js dependencies, `next.config.mjs`, and App Router directory layouts.

### Q: What does Step 18 deliberately NOT implement?
**A:** Step 18 strictly handles stack classification and evidence gathering. It does NOT implement AST parsing, ts-morph / TypeScript Compiler API symbol extraction (Step 19), import/export dependency extraction (Step 20), route detection (Step 21), or database graph persistence (Phase 4).
