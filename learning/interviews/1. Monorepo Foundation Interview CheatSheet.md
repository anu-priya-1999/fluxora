# Fluxora Step 1 — Monorepo Foundation Interview CheatSheet

## 1. What this step established

Fluxora starts as a pnpm workspace monorepo with explicit application/package boundaries, strict TypeScript, shared packages, and a root-level typecheck gate. The goal is to make the repository structure scale before product-specific code intelligence is added.

## 2. 30-second interview answer

> “I chose a pnpm workspace monorepo so the web app, API, workers, shared types, and database package can evolve together while still having explicit package boundaries. Shared contracts live in packages instead of being duplicated. The root scripts provide consistent typecheck, lint, test, and build entry points. TypeScript stays strict so architectural mistakes appear during development rather than at runtime.”

## 3. Core questions

### Q1. Why a monorepo for Fluxora?

A monorepo keeps related deployables and shared packages versioned together. Fluxora has web, API, worker, shared types, and database concerns, so changes across boundaries can be reviewed and tested in one repository.

### Q2. Why pnpm workspaces?

pnpm provides workspace linking, efficient dependency storage, and explicit workspace package relationships. It also makes local packages behave like real packages rather than ad-hoc relative imports.

### Q3. What should be shared versus duplicated?

Stable contracts and reusable infrastructure can be shared; feature-specific business logic should remain close to the package that owns it. Sharing everything creates coupling.

### Q4. Why strict TypeScript?

Strict mode catches nullability, implicit-any, unsafe assumptions, and contract drift early. In a multi-package system, that is especially valuable because a type change can reveal downstream breakage immediately.

### Q5. How do package boundaries help architecture?

A package boundary turns an architectural dependency into something visible and reviewable. It becomes possible to ask whether `apps/web` is allowed to import worker internals or whether a shared type belongs in `packages/shared-types`.

### Q6. Why not keep everything inside the web app?

That would make background processing and backend responsibilities harder to isolate and deploy. Fluxora has long-running ingestion work that should not execute inside a browser request lifecycle.

### Q7. What is the difference between an application package and a library package?

An application is deployable and owns runtime behavior; a library/package is intended to be consumed by other packages. Fluxora separates these so shared contracts and infrastructure do not become accidental application entry points.

### Q8. What is the biggest monorepo failure mode?

Turning the monorepo into a giant shared-code bucket. Once every package depends on every other package, boundaries disappear and changes become risky.

### Q9. How would you enforce dependency direction?

Use workspace conventions plus linting/build rules and, where needed, package-specific import restrictions. The rule should be explicit: for example, UI code consumes shared contracts but should not depend on worker implementation details.

### Q10. Why is a root typecheck useful?

It tests the repository as a system rather than only testing one package. A shared type change that breaks another workspace package is therefore visible before merge.

## 4. Senior-level questions

### Q11. How would you scale the monorepo to dozens of packages?

Introduce strict ownership, dependency graphs, package-level CI, caching, affected-package builds, clear public APIs, and rules against circular dependencies. The monorepo should optimize feedback time rather than simply grow indefinitely.

### Q12. When would you choose polyrepos instead?

If teams are highly independent, release cadences differ substantially, or repository-scale tooling becomes the bottleneck, separate repositories can reduce coordination. The decision should follow organizational and deployment boundaries, not ideology.

### Q13. How do you avoid circular package dependencies?

Keep shared primitives at lower layers, define one-way dependency direction, and move truly shared contracts down rather than importing upward. A dependency graph should have a clear architectural shape.

### Q14. What happens when a shared package changes incompatibly?

The workspace should fail at typecheck/build/test boundaries for consumers. For independently deployed systems, semantic versioning or explicit contract versioning may also be needed.

### Q15. How would you speed up CI in a large monorepo?

Cache the package manager and build outputs, run only affected tests/builds when safe, parallelize independent jobs, and keep repository-wide gates for critical cross-package checks.

## 5. Scenario questions

### Scenario: the web app imports worker internals

Explain that this is an architectural smell. Move the required contract into a shared package or expose the capability through an API boundary.

### Scenario: two packages define the same `Repository` type

Prefer one canonical shared contract when the semantics are the same. Keep separate types only when their ownership or lifecycle is intentionally different.

### Scenario: one package needs a tiny helper from another package

Ask whether that helper belongs in a shared lower-level package. Do not create a dependency merely because a few lines can be reused.

## 6. Common traps

- “Monorepo means everything is shared.” — False.
- “pnpm solves architecture automatically.” — False; it only provides useful workspace primitives.
- “Strict TypeScript guarantees runtime correctness.” — False; it reduces a class of errors but does not replace tests or validation.

## 7. Strong closing statement

> “Step 1 was intentionally boring infrastructure. The important result is that later Fluxora steps can add authentication, queues, workers, ingestion, and storage without collapsing all concerns into one package.”
