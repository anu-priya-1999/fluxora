# Step 13 — Repository Snapshot Storage Interview Cheat Sheet

## 30-second answer

> "Step 13 turns the temporary repository tree produced by the ingestion worker into a durable immutable artifact. Fluxora deterministically packages the tree as `snapshot.tar.gz`, calculates SHA-256 over the final archive bytes, uploads the archive through the existing object-storage abstraction, and persists tenant-scoped RepositorySnapshot metadata in PostgreSQL. PostgreSQL stores metadata while object storage stores the repository bytes. The implementation also cleans up partial archives and deletes uploaded objects if DB persistence fails."

---

## 1. Why do you need Step 13 after Step 12?

**Answer:** Step 12 gives Fluxora a temporary extracted repository. That filesystem is not durable. Step 13 freezes the repository tree into a durable artifact so later analysis can use the same exact input.

---

## 2. What exactly is stored?

**Answer:** One deterministic compressed archive:

```text
snapshot.tar.gz
```

It contains the repository files. We are not currently creating a separate object for every source file.

---

## 3. Why not keep the temporary directory?

**Answer:** Worker filesystems are ephemeral. A worker can restart, a retry can execute elsewhere, and a temp directory cannot be the durable artifact.

---

## 4. What does "deterministic archive" mean?

**Answer:** The same repository tree should produce the same archive bytes. Stable file ordering, portable metadata, normalized timestamps, and deterministic gzip-header handling remove accidental machine-specific differences.

---

## 5. Why SHA-256?

**Answer:** It is the fingerprint of the final archive bytes. It gives us an integrity/reproducibility identifier for the exact snapshot artifact.

---

## 6. What exactly does the checksum cover?

**Answer:** The final `snapshot.tar.gz` bytes that are persisted, not an individual source file and not only the uncompressed tree.

---

## 7. Why object storage?

**Answer:** Repository snapshots are large binary artifacts. Object storage is designed for that workload, while PostgreSQL is better for relational metadata and tenant-aware querying.

---

## 8. What goes into PostgreSQL?

**Answer:**

```text
snapshot id
repository id
commit SHA
ref
storage URI
sha256
file count
size
createdAt
```

The database points to the object; it does not contain the entire archive.

---

## 9. Why is the snapshot immutable?

**Answer:** Later evidence and analysis results must point to a stable input. Mutating the source artifact would undermine reproducibility and provenance.

---

## 10. How is the object key tenant-scoped?

**Answer:**

```text
{organizationId}/{repositoryId}/{snapshotId}/snapshot.tar.gz
```

This aligns storage paths with the tenant boundary.

---

## 11. What happens if object upload succeeds but PostgreSQL insert fails?

**Answer:** The implementation deletes the uploaded object. Otherwise we'd leave an orphaned durable artifact without corresponding metadata.

---

## 12. What happens if packaging fails halfway through?

**Answer:** The partial archive is removed.

---

## 13. What size limits apply?

**Answer:** Step 13 preserves the ingestion limits: file count, total repository bytes, compressed archive bytes, and timeout. A repository exceeding the compressed snapshot limit is a permanent size failure and the partial archive is removed.

---

## 14. How does Step 13 preserve idempotency?

**Answer:** It reuses the Step 11 snapshot identity boundary `(repository_id, commit_sha)` and does not introduce another retry or queue system.

---

## 15. What happens on re-ingestion?

**Answer:** Re-running successful ingestion does not replace the existing immutable snapshot object. A redundant object created during a replay path is cleaned up rather than replacing the original.

---

## 16. Why not write one object per file?

**Answer:** One archive is simpler for the MVP: fewer object operations, fewer partial-failure cases, and one deterministic checksum for the complete source tree.

---

## 17. Why not store the archive in PostgreSQL?

**Answer:** Large binary blobs would increase database storage, WAL and backup pressure. PostgreSQL remains the relational system of record while object storage holds snapshot bytes.

---

## 18. How does tenant isolation work end to end?

**Answer:**

```text
Clerk / Fluxora authorization
        ↓
organization_id
        ↓
PostgreSQL RLS
        +
tenant-scoped storage key
        +
tenant-aware worker job
```

Security is defense in depth, not a single application `WHERE` clause.

---

## 19. Does Step 13 introduce a new queue?

**Answer:** No. It reuses the existing PostgreSQL-backed job queue and JobWorker.

---

## 20. Does Step 13 parse code?

**Answer:** No. It only creates a durable source artifact. AST/symbol/dependency analysis comes later.

---

## 21. Does Step 13 execute repository code?

**Answer:** No. Repository contents remain untrusted data. Packaging only reads and archives files.

---

## 22. What engineering problem did you hit?

**Answer:** Node 24's strip-only TypeScript runtime exposed two runtime issues during verification:

- TypeScript parameter-property syntax in a runtime-tested class;
- passing `undefined` as a `pipeline()` argument.

The final implementation uses explicit fields and conditional pipeline options.

---

## 23. Why is this a distributed-systems problem?

**Answer:** One logical operation crosses PostgreSQL and object storage. They do not share one database transaction, so partial failure is possible. Explicit cleanup minimizes orphaned-object state.

---

## 24. How would you harden this at larger scale?

**Answer:** Possible future improvements include content-addressed objects, staged snapshot states, orphan-object garbage collection, multipart uploads, storage/DB reconciliation, and object lifecycle policies. Those are future hardening, not required for this MVP step.

---

## 25. What is the most important design decision?

> "We freeze the exact repository state before analysis. The deterministic snapshot becomes the stable input to all later code intelligence."

---

## 26. Explain Repository vs Commit vs Snapshot.

```text
Repository = tenant-owned GitHub connection
Commit     = Git revision metadata
Snapshot   = frozen source tree artifact
```

---

## 27. Why keep both `commitSha` and `sha256`?

**Answer:**

- `commitSha` identifies the Git revision.
- `sha256` identifies the exact packaged bytes.

They answer different questions.

---

## 28. How do you verify that the checksum is meaningful?

**Answer:** The checksum is computed from the exact archive file that gets uploaded. The focused tests also recompute SHA-256 from the resulting archive and compare it with the packaging result.

---

## 29. What proves Step 13 is actually done?

**Answer:**

```text
worker tests       24 passed / 0 failed
typecheck          passed
lint               passed
full workspace test suite passed
```

The focused snapshot tests verify deterministic checksum/file contents and compressed-size cleanup.

---

## 30. One-minute final answer

> "Step 13 is the snapshot persistence boundary. Step 12 leaves us with a temporary extracted repository; Step 13 walks that tree deterministically, packages it as `snapshot.tar.gz`, computes SHA-256 over the final bytes, stores it through the existing object-storage abstraction, and writes an immutable RepositorySnapshot row in PostgreSQL. The object key is tenant-scoped. If object upload succeeds but the database insert fails, the object is deleted, and partial archives are also removed. The existing job queue, retry model, and snapshot idempotency rules are preserved. After this step, later analysis workers have a durable, reproducible input artifact."
