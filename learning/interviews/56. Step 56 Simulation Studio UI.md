# Staff Engineering Interview Guide: Step 56 — Simulation Studio UI

This interview guide focuses on frontend architecture, state synchronization, causal graph visualization, fail-fast UX design, API contract alignment, and security invariants for deterministic simulation platforms.

---

### Q1: Why is the Simulation Studio architected as a separate route (`/simulations`) rather than an overlay modal inside the Architecture Explorer?

**Answer:**
A dedicated route provides distinct architectural and operational advantages:
1. **Separation of Concerns**: The Architecture Explorer is an inspection tool for exploring existing static code structure, module dependencies, and pull-request change-impact slices. The Simulation Studio is an active failure experiment workbench (creating scenarios, selecting failure modes, executing propagation runs, analyzing multi-hop causal chains, and comparing outcomes).
2. **Deep-Linking & Shareability**: Having a dedicated route with query parameter synchronization (`/simulations?repository_id=...&analysis_run_id=...&target_node_id=...&scenario_id=...`) enables engineers to bookmark, share, and audit specific simulated failure scenarios directly in pull request reviews or post-mortem incident documentation.
3. **Decoupled Performance**: Rendering a full React Flow visual canvas with interactive nodes and edges introduces significant WebGL/DOM rendering overhead. Keeping the Simulation Studio layout focused on a dual-column workbench (configuration controls on the left, filterable results table and causal path timeline on the right) ensures instant, accessible rendering and fast tabular sorting without dragging canvas state into form management.

### Q2: Why is "Create Scenario" separated from "Run Simulation" in the UI rather than combined into a single "Simulate" button?

**Answer:**
Separating creation from execution reflects the underlying domain model:
1. **Domain Boundary (Scenario vs Simulation)**:
   - A `Scenario` is a persisted specification: "What failure is being hypothesized?" (target node, failure type, parameters).
   - A `Simulation` is an execution of that scenario against a specific analysis graph snapshot: "What happened when we ran this scenario on snapshot $S$ at timestamp $T$?"
2. **Reusability Across Analysis Runs**: One scenario can be evaluated repeatedly against different commits or branches (e.g. running "Payment Gateway Unavailable" against `main` vs against a feature branch that adds a circuit breaker to verify whether the architectural fix stops cascading failure).
3. **Auditability & Reproducibility**: Creating a scenario produces a stable UUID (`scenario_id`). If execution fails due to a network interruption or convergence timeout, the scenario specification is not lost. The user can retry execution or inspect previous simulation runs linked to that scenario.

### Q3: What is the authoritative request/response contract with Step 55, and why was `seed_failures` rejected?

**Answer:**
1. **Contract Schema Alignment**: In Step 55's API (`parseCreateScenarioBody`), the scenario creation request requires:
   - `name`: non-empty string.
   - `target_node_id`: valid UUID string.
   - `failure_type`: `"unavailable"` | `"latency"`.
   - `repository_id` and/or `analysis_run_id`: valid UUID string (at least one is required).
   - `parameters`: optional JSON object.
2. **Rejection of `seed_failures`**: An early assumption considered passing an array of `seed_failures: [{ node_id, failure_type }]`. The actual Step 55 API parser validates `target_node_id` and `failure_type` at the root of the JSON body. Sending `seed_failures` causes validation failure (`target_node_id is required`).
3. **Tenant Invariant**: The client never sends `organization_id` or `organizationId` in request bodies. The API strictly extracts tenant identity from the verified Clerk session token and rejects client-supplied tenant fields with `400 invalid_request`.

### Q4: How does the UI distinguish canonical result states from scenario failure types?

**Answer:**
1. **Canonical Result States**: In Step 53–55, node states in simulation results are strictly:
   - `healthy`: operating normally.
   - `at_risk`: potentially degraded or dependent on degraded/unstable dependencies.
   - `degraded`: reduced performance, delayed responses, or qualitative latency impact.
   - `failed`: completely unresponsive or failed component.
2. **Failure Types Are Inputs, Not States**: `"unavailable"` and `"latency"` are scenario hypothesis inputs (failure types). An `"unavailable"` failure type seeds the target node into a `failed` state, whereas a `"latency"` failure type seeds the target node into a `degraded` state.
3. **No Fabricated States**: Labels like `"delayed"` are completely unsupported. Sorting severity follows the canonical order: `failed (4) > degraded (3) > at_risk (2) > healthy (1)`.

### Q5: How are response fields mapped, and how does the UI avoid assuming unreturned metadata?

**Answer:**
1. **Result Count**: `GET /simulations/:id/results` returns `{ simulation_id, results, total }`. The field is `total`, not `total_affected`.
2. **Causal Steps**: Each result contains `propagation_path` (an array of `SimulationCausalStep | string`). There is no `causal_steps` field.
3. **Rule Table Version**: Endpoints do not return a top-level `rule_table_version` on `SimulationResponse`. Instead, the UI derives the version from `step.ruleVersion` inside the first populated causal step. If absent, it gracefully displays `"1.0.0 (rule table default)"` rather than inventing an endpoint response.
4. **Convergence Metadata**: Only `POST /scenarios/:id/run` returns `converged` and `iterations`. When inspecting an existing run via `GET /simulations/:id`, convergence metadata is not included in the response. The UI handles `converged: undefined` by displaying `"Not reported by server"` rather than claiming convergence passed.

### Q6: How does the UI handle repository and analysis run selection given that the backend exposes no list endpoints?

**Answer:**
1. **Architecture Discovery**: Fluxora's Step 55 API (implemented with Node's native `node:http` server, not Fastify) does not expose a `GET /api/v1/repositories` or `GET /api/v1/analysis-runs` endpoint.
2. **Context Resolution**: The application resolves repository and run contexts through route parameters (`/repositories/[repoId]/explorer`) or query parameters (`/simulations?repository_id=...&analysis_run_id=...`). The Explorer view includes a direct "Simulation Studio" action button that links directly to the studio pre-seeded with the active repository and analysis run.
3. **Snapshot Scoping**: Once an `analysis_run_id` is supplied, graph nodes are loaded exclusively via `POST /api/v1/graph/query`. The target node selector is strictly populated from this snapshot. If the user changes repository or run ID, all dependent state (nodes, target selection, scenario, simulation, results) is immediately invalidated to prevent cross-snapshot contamination.

### Q7: Why must the UI explicitly state that "Simulation confidence is not a real-world failure probability"?

**Answer:**
Preventing the "false sense of mathematical certainty" is a core tenet of honest engineering:
1. **Deterministic Rule Confidence vs Statistical Probability**: In Fluxora's deterministic rule engine (Step 53–54), a confidence score of `0.90` on a causal step simply indicates that conservative assumptions were made (e.g. unverified fallback metadata on a call edge reduced confidence from `1.0` to `0.9`). It does **not** mean there is a 90% chance of downtime in production.
2. **Avoiding Hallucinated SLAs**: Claiming that a simulation provides "99.9% uptime prediction" or "estimated 42 minutes of downtime" without live runtime telemetry, traffic volume, and queue depth modeling would be dishonest.
3. **Honest Caveats in UI**: The Simulation Studio explicitly displays a caveat badge and details section clarifying that confidence reflects static code metadata completeness and rule assumptions, not probabilistic odds.

### Q8: How does the Causal Path Inspector render the failure seed differently from downstream propagation steps?

**Answer:**
By inspecting the edge identity and rule identifier:
1. **Failure Seed Step**:
   - `ruleId === "target_failure"`
   - `edgeId === null` or `undefined`
   - UI displays: `"Step 1: Target Failure Seed"`, `Edge ID: "None (Seed target failure)"`, and `Transition: healthy → failed` (or `healthy → degraded`).
2. **Downstream Propagation Steps**:
   - `ruleId === "CALLS_SYNC_NO_FALLBACK"`, `"CALLS_CIRCUIT_BREAKER"`, etc.
   - `edgeId === "<uuid>"`
   - UI displays: `"Step N: Propagation Decision"`, `Edge ID: "<uuid>"`, and `Transition: previousState → resultingState`.
3. **Capped Propagation**:
   - If a step has `capped === true` (e.g. circuit breaker tripped), the inspector displays a prominent badge: `"Propagation Capped (Circuit Breaker)"`, explaining why downstream cascading failure stopped at that node.
