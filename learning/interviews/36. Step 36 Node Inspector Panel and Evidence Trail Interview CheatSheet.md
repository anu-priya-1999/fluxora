# 36. Step 36 Node Inspector Panel and Evidence Trail Interview CheatSheet

## Senior-Level Architectural & Technical Q&A

### Q1: What is the primary purpose of Step 36 in the Fluxora architecture?
**Answer**:
Step 36 surfaces deterministic, verifiable provenance to the frontend user. In Fluxora, the visual software graph is grounded in exact source code evidence recorded by `EvidenceWriter`. Step 36 implements `NodeInspectorPanel` and `EvidenceTrail` so that when an engineer clicks any node in the Architecture Explorer, they immediately see its architectural properties (node type, name, depth, confidence, canonical ID) and its verified AST coordinates (file path, line start/end, column start/end, relationship description).

---

### Q2: Why is evidence fetched in the initial `GraphQueryResponse` rather than lazily when a node is clicked?
**Answer**:
1. **Zero Secondary Latency**: Clicking a node is an instantaneous, synchronous operation without loading spinners or layout shifts.
2. **Deterministic Response Coherence**: Because the evidence comes from the exact same analysis run snapshot queried in the bounded CTE traversal, there is zero risk of snapshot mismatch or race conditions between the node structure and its provenance.
3. **Bounded Payloads**: In Step 30/31, `GraphQueryResponse` is bounded by `max_depth` and traversal rules, keeping the evidence collection compact and deterministic.

---

### Q3: How is evidence association strictly enforced in EvidenceTrail?
**Answer**:
Evidence records in `GraphQueryResponse.evidence` may include evidence for nodes, edges, or other domain entities. `EvidenceTrail` explicitly filters using:
```ts
evidence.subject_type === "graph_node" && evidence.subject_id === selectedNode.id
```
Any evidence with `subject_type === "graph_edge"`, evidence for another subject type, or evidence matching a different `subject_id` is completely excluded.

---

### Q4: Why must evidence ordering be deterministic, and how is it achieved?
**Answer**:
Deterministic ordering guarantees that two renders on different browsers or devices produce identical DOM output. We sort using an immutable multi-key comparator:
1. `file_path` (lexicographically)
2. `line_start` (ascending numerical; `-1` if absent)
3. `line_end` (ascending numerical; `-1` if absent)
4. `id` (lexicographically as a stable tie-breaker)
This avoids relying on unpredictable database retrieval orders, nondeterministic arrays, or arbitrary client timestamps.

---

### Q5: How is selection state managed without introducing an external state library?
**Answer**:
We adhere to the principle of least-privilege state management: `selectedNodeId` is owned exclusively at the minimal common parent component (`ArchitectureExplorerClient`) via standard React `useState`. `GraphCanvas` receives the ID to visually highlight the selected node, and `NodeInspectorPanel` receives the derived node object and evidence. Adding external libraries (such as Zustand, Redux, or Jotai) for local UI selection would introduce unnecessary bundle overhead and global mutable state without architectural justification.

---

### Q6: How does the inspector protect against oversized metadata or malicious repository strings?
**Answer**:
- `safeFormatMetadataValue` serializes complex objects and enforces a strict length cap (200 characters), truncating overflowing data with `...`.
- All paths, names, and symbol identifiers are rendered as pure text nodes (never `dangerouslySetInnerHTML`), preventing XSS or script injection from untrusted repository contents.

---

### Q7: What does Step 36 explicitly NOT do, and what comes next in Step 37?
**Answer**:
Step 36 does **not** implement graph filtering by node/edge type, clustering, live WebSocket cache invalidation, or change-impact simulation.
Step 37 will introduce `GraphFilters` to allow filtering the visible nodes and edges on the canvas by category, confidence threshold, and edge types.
