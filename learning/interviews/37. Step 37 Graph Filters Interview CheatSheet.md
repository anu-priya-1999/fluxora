# Step 37 — Graph Filters Interview CheatSheet

### Q1: Why should graph filtering be evaluated on the backend rather than simply hiding nodes in the browser?
**Answer:**
Evaluating filters on the backend preserves graph traversal correctness. When traversing a software graph with maximum depth $k$, filtering edge types or node types during the backend CTE determines *which paths can be traversed*. If the frontend only traverses an unfiltered graph and hides nodes post-hoc, it risks severing traversal paths or exceeding depth bounds without reaching valid reachable nodes beyond the hidden elements. Furthermore, server-side evaluation minimizes network payload sizes and prevents DOM/canvas bloat on large software codebases.

### Q2: How does Step 37 ensure that user rapid filter adjustments do not cause race conditions with network responses?
**Answer:**
In `ArchitectureExplorerClient`, the graph query effect registers a cleanup function setting `isCancelled = true`. When a user rapidly toggles filters, the previous effect's cleanup executes immediately. When the slow or out-of-order network response arrives from the initial request, `if (isCancelled) return;` prevents it from overwriting the newer state with stale graph data.

---

### Q3: What happens to the selected node and the `NodeInspectorPanel` when the user applies a filter?
**Answer:**
The selection is reconciled deterministically. After receiving the new `GraphQueryResponse`, the client verifies whether `selectedNodeId` is present in `result.data.nodes`:
- If the node is still present, `selectedNodeId` remains unchanged, and the inspector continues displaying the node and its filtered evidence trail.
- If the node was filtered out, `selectedNodeId` is set to `null`, gracefully returning `NodeInspectorPanel` to its default empty state without runtime errors.

---

### Q4: Why is `organization_id` deliberately omitted from the frontend's `GraphQueryRequest`?
**Answer:**
Tenancy security is an invariant in Fluxora. The frontend is untrusted and must never dictate the tenant boundary. The Fastify API server inspects the authenticated Clerk session JWT, resolves the tenant organization, and runs all graph queries inside PostgreSQL using `withTenant(organizationId, ...)`. Exposing an `organization_id` property in client requests would introduce tenant impersonation vulnerabilities.

---

### Q5: How is filter state structured, and why wasn't a global state library like Zustand introduced?
**Answer:**
Filter state is represented as a focused immutable interface:
```typescript
export interface GraphFilterState {
  readonly nodeTypes: readonly GraphNodeType[];
  readonly edgeTypes: readonly GraphEdgeType[];
  readonly minConfidence: number;
  readonly maxDepth: number;
}
```
Because this state is only consumed by `GraphFilters` and its parent `ArchitectureExplorerClient`, React's standard `useState` provides optimal locality, avoids unnecessary re-renders across the rest of the application, and keeps the frontend bundle lean without adding external runtime dependencies.
