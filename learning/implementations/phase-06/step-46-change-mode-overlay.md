# Step 46 — Change-Mode Overlay in Architecture Explorer

## Objective & Role in Roadmap

Global Step 46 implements the frontend Change-Mode overlay within the flagship Architecture Explorer in `apps/web`. It allows software engineers and reviewers to inspect the deterministic blast radius of a pull request visually superimposed on top of the system's canonical dependency graph.

This fulfills **Global Step 46** of **Phase 6: PR Impact Analysis** as defined by:
- `docs/architecture/17-implementation-roadmap.md` (Phase 6, Step 6: frontend change-mode overlay)

## Detailed Specifications

### 1. What Change Mode Is
Change Mode is an interactive visualization mode of the Architecture Explorer. When enabled, it overlays the blast radius computed for a pull request onto the existing codebase architecture graph. Instead of reading a static text list of files, developers can see which services, modules, APIs, and events are changed directly or impacted downstream.

### 2. Why It Is an Overlay Instead of a Second Graph
Fluxora's core product thesis is that the system architecture is the single unified mental model of truth. Rendering a second separate "impact graph" would sever the relationship between changed code and the rest of the application, forcing reviewers to mentally reconcile two graphs. An overlay preserves the topology, spatial memory, clusters, and connectivity of the codebase while emphasizing the blast radius.

### 3. How Persisted ImpactAnalysis Data Reaches the Frontend
The client never runs graph traversal or diff computations locally. When the user enables Change Mode and provides or selects an Impact Analysis ID, the frontend issues:
```http
GET /api/v1/impact-analyses/:id
Authorization: Bearer <session_jwt>
```
The server validates multi-tenant permissions via PostgreSQL Row-Level Security (RLS) and returns the durable, evidence-backed `ImpactAnalysisResponse` generated by Step 44 persistence and the Step 43 deterministic engine.

### 4. Representation of Direct vs. Downstream Impact
- **Direct Impacts (depth = 0)**:
  - Strongest visual emphasis: solid red border (`#dc2626`), glowing ring (`0 0 0 3px rgba(220, 38, 38, 0.25)`), and prominent `Direct Change` badge.
- **Downstream Impacts (depth >= 1)**:
  - Chromatic hierarchy: Amber borders that fade as hop distance increases (`#d97706` for hop 1, `#f59e0b` for hop 2, `#fbbf24` for hop 3+).
  - Explicit badge displaying hop distance: `Downstream (hop N)`.
- **Unaffected Nodes**:
  - Visually de-emphasized with reduced opacity (`0.45`) and subtle grayscale (`30%`) so the blast radius stands out immediately.
  - Unaffected nodes remain fully clickable, selectable, and interactive; they are never removed from the underlying graph.

### 5. How Hop Distance and Confidence Affect Display
- **Hop Distance**: Each traversal step monotonically increases hop distance. The UI colors nodes with a warmer, more saturated amber for direct downstream neighbors (hop 1) and lighter shades for distant downstream nodes.
- **Confidence Decay**: Statically computed geometric decay ($1.0 \times 0.9^d$) is preserved.
- **Low-Confidence Visual Differentiation**: Findings with confidence below 70% are rendered with a dashed border (`2px dashed <color>`) and marked with an explicit `(low)` tag in the inspector and node renderer, ensuring uncertainty is never obscured.

### 6. Identification of Affected APIs and Events
API routes and async events represent critical cross-boundary contracts. Nodes in `affected_apis` and `affected_events` are normalized into dedicated ID sets and receive distinct badges:
- `API`: Emerald badge (`#d1fae5` / `#047857`) for impacted HTTP endpoints and RPC routes.
- `Event`: Purple badge (`#ede9fe` / `#6d28d9`) for impacted event producers, consumers, and message schemas.

### 7. Evidence ID Preservation
Every finding links to durable evidence records stored by Step 44 via `EvidenceWriter`. The frontend normalization deduplicates and sorts all evidence IDs lexicographically. When an impacted node is selected, `NodeInspectorPanel` renders clickable finding evidence tags linked to AST and repository provenance.

### 8. Unresolved Files and Truncated State
- **Unresolved Files**: Non-code files (e.g. `README.md`, binary assets, config files without AST nodes) cannot be mapped to graph nodes. Rather than pretending they do not exist, the UI surfaces an expandable warning banner detailing each unparsed file path and reason.
- **Truncated Analysis**: If traversal reached the configured `maxDepth` ceiling with remaining outgoing edges, `truncated: true` is preserved and prominently displayed in `ChangeModeBar` along with `truncation_reason`.

### 9. Filter and Level-of-Detail (LOD) Interaction
- Existing `GraphFilters` (node types, edge types, min confidence, max depth) remain 100% operational.
- Existing zoom-driven `computeLodGraph` (system, module, detail tiers) remains active.
- Impact findings for nodes currently hidden by filters or LOD are preserved in state, never deleted.
- The canvas LOD badge surfaces an active slice indicator (e.g., `• 3/5 impacted visible`), informing the user that additional impacted nodes exist outside the current viewport or filter configuration.

### 10. Selection Priority and NodeInspectorPanel Integration
- Selection state (`isSelected`) takes absolute priority over Change-Mode styling. If an engineer clicks a direct red node, the selection border (`#2563eb`) and focus ring take precedence.
- `NodeInspectorPanel` embeds a dedicated "PR Impact Analysis" card showing:
  - Role (`Direct Change` vs. `Downstream (hop N)` vs. `Unaffected`)
  - Exact hop distance and impact confidence percentage
  - Affected API / Event tags
  - Exact impact finding evidence IDs

### 11. Why the Browser Does Not Recompute Impact
Computing change impact requires AST parsing, dependency graph traversal, cycle-checking, and tenant database validation. Client-side recomputation would require sending entire codebases to the browser, producing non-deterministic results, and creating security vulnerabilities. The server's persisted result is the single source of truth.

### 12. Security & Sandbox Safeguards
The browser never connects to GitHub or the database directly. All requests go through `GET /api/v1/impact-analyses/:id` with Bearer JWT session authentication. Cross-tenant impact analyses return `404 Not Found` via PostgreSQL RLS policies.

### 13. Performance Considerations
- **Normalized Sets/Maps**: Findings are normalized once into `Set<string>` and `Map<string, number>`. Graph rendering achieves $O(1)$ lookups per node rather than $O(N \times M)$ scan loops.
- **React Flow Render Stability**: State memoization prevents canvas layout resets or edge recalculations during pan/zoom.

### 14. Accessibility & Clarity
- Semantic badges accompany chromatic changes so color-blind users can distinguish direct vs. downstream impact.
- Standard ARIA labels and roles (`role="status"`, `aria-label="Change Mode Controls"`) are provided.

### 15. Empty, Loading, and Error States
- **OFF**: Change mode inactive; default explorer behaviour.
- **LOADING**: Non-blocking spinner in `ChangeModeBar` while impact data is fetched.
- **PENDING / RUNNING**: Surfaces "Analysis in progress (running)..." with automatic polling every 4 seconds.
- **EMPTY**: Displays "Analysis completed with 0 affected nodes."
- **ERROR**: Renders error alert with "Retry" action while keeping the underlying base architecture graph fully interactive.

### 16. Testing Strategy
A comprehensive Vitest test suite (`apps/web/src/components/graph/change-mode.test.ts`) covers requirements A through W:
- Normalization correctness, direct/downstream classification, duplicate node resolution (multi-seed shallowest path), hop and confidence preservation, evidence deduplication, truncated state preservation, filter/LOD interaction, selection priority, error recovery, and component markup tests.
